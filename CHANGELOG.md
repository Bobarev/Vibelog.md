### Добавлено

- **VL-141: бот-команда `/analyze` и CLI `vibelog agent analyze` — штатный разбор сессии агента по session-ref** — команда `/analyze vb:agent-XXX` (префикс `vb:` необязателен; суффиксы `:qwen`/`:vb` как у `/prompt`) запускает headless-фазу analyze без задачи (runKey `analyze-<sessionId>`), taskId/фаза/cwd берутся из `meta.json` сессии (VL-114) и подставляются в промпт; при taskId дописывается компактный блок задачи для вердикта. Новый шаблон `templates/qwen-commands/phase-analyze.md` даёт агенту детерминированный протокол: (1) статистика jsonl одним node-скриптом — длительность (ms-epoch ID сессии + mtime), прогоны по «Продолжи», wall-убийства, «Пустой ответ модели», NaN-индексы, профиль tool-вызовов по именам, топ-10 больших tool-выводов, чтения/правки по файлам; (2) вердикт «объём задачи vs тупик/расточительство»; (3) рекомендации с предварительным `backlog_search` — ссылки на уже открытые задачи, новых не создавать; финал — одно слово «Готово». `startAnalyze` валидирует session-ref (`agent-\d+`; qwen-UUID отклоняется — jsonl-транскрипты только у vibelog-agent), запуск идёт из главного cwd (jsonl хранится там же, VL-107-fix), фаза analyze закрыта в `startPhase` отдельным гардом и получает `--allowed-mcp-server-names vibelog` в phaseFlags. CLI-паритет: `vibelog agent analyze <session-ref>` (`src/cli/commands/agent.ts`) — тот же `startAnalyze` с ожиданием onExit и печатью результата; гард в `src/agent/cli.ts` запрещает phase-режим `analyze`. Реестр бота: 18 → 19 команд. Тесты: `parseAnalyzeCommand` (7), реестр (длина 19 + help-строка), `startAnalyze` (спавн/guard/нет сессии/битый ref/гард startPhase), `runAgent` (позитив со стаб-бином + негативы), шаблон analyze.
- **VL-138: новый MCP-инструмент `backlog_finish_phase` — завершение фазы одним вызовом** — статус + отчётный комментарий + modifiedFiles + батч-отметки AC/DoD (`{id, status?, comment?, modifiedFiles?, acChecks?, dodChecks?}`; все поля опциональны кроме `id`) вместо цепочки `backlog_add_comment` → `backlog_update_status` → `backlog_update_task(modifiedFiles)` → `manage_ac/dod check` (~10 ходов → 1–2 вызова; экономия по профилю code −4..−6 ходов, spec/close −2..−3). Частичное применение: невалидное поле (статус вне конфига, битый индекс) пропускается с понятным сообщением в сводке, вызов не падает; все валидные обновления собираются и применяются одной записью `updateTaskFile` (файл атомарен, «полу-состояния» не бывает). Сводка вида «Статус: Review; отчёт добавлен; отмечено AC: 2, DoD: 1; файлов: 3» (+ `Ошибки: …`). Шаблоны `phase-1/2/3/close/close-worktree` используют его вместо цепочки (списки AC/DoD — по-прежнему через `manage_ac/dod` action list, отметки — в `acChecks`/`dodChecks`). Счётчик MCP-инструментов 21 → 22 (doctor, тесты, README, doc-8). Тесты: 7 кейсов в `server.test.mjs` + required-контракт в `mcp-client.test.mjs`.
- **VL-139: скрипт `pnpm test:fast` — запуск тестов без сборки** — `vitest run` без предварительного `tsc` для итераций разработки (`pnpm test` собирает build, как и раньше; выгода небольшая — `tsc` быстрый, ~1.5 с). Упомянут в README и AGENTS.md.

- `task edit`: batch AC/DoD — `--check-ac 1,3`, `--uncheck-dod 1,2`; MCP `manage_ac`/`manage_dod` принимают массив индексов (как `acceptanceCriteriaCheck` оригинала), `remove` — по убыванию без сдвига.
- `task list`: `--limit N`, `--skip N` — после фильтрации и сортировки.
