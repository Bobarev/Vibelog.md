# AGENTS.md — Vibelog.md

Этот проект — **Vibelog.md**, markdown-нативный таск-менеджер для git-репозиториев, максимально совместимый с Backlog.md. Реализуется на TypeScript (исходники `.ts` → `tsc` → `dist/` ESM) + pnpm, без нативных зависимостей.

## Зачем этот проект существует

Оригинальный **Backlog.md** невозможно запустить на macOS 10.15 Catalina (использует нативный Bun-рантайм). Также на Catalina не работают Claude Code, Opencode и другие популярные AI-агенты — работает **только Qwen Code**. Поэтому нужен инструмент, который:

1. Работает на Catalina + Node.js 20+.
2. Полностью совместим по формату данных с Backlog.md (чтобы при апгрейде на новую macOS можно было просто переключиться на оригинал).
3. Интегрируется с Qwen Code через CLI и MCP.

Совместимость нужна **только с Qwen Code** — остальные агенты могут использовать оригинал Backlog.md.

## Язык

**Всё на русском языке:**
- Комментарии в коде — обязательно, подробные, объясняющие «почему», а не «что».
- Краткие JSDoc-комментарии к экспортируемым функциям; типы — в сигнатурах TS (не дублировать в @param/@type).
- Сообщения об ошибках — на русском.
- Тексты CLI-вывода — на русском.
- Документация, README, планы — на русском.
- Коммиты — на русском (`feat: добавить парсер YAML`).

Английский — только там, где это технически неизбежно (имена полей frontmatter для совместимости с Backlog.md, имена MCP-инструментов, ключи JSON-RPC).

## Право на корректировку планов

Если Implementation Plan в задаче содержит неточности, упущения или недостаточный функционал — **вноси правки прямо в него, не спрашивая разрешения**. Коммить изменения плана отдельно (`docs(plan): ...`). Касается любого аспекта совместимости, форматов и реализации.

## Важные правила

- **TypeScript-исходники** (`.ts`, strict) → `pnpm build` (`tsc`) → `dist/` (ES modules). TypeScript и `@types/node` — только devDependencies. Никаких нативных зависимостей, node-gyp, SQLite, Bun.
- **pnpm** — менеджер пакетов, версия **10.7.1** (`packageManager: "pnpm@10.7.1"`).
- **Сборка обязательна**: `bin/vibelog.mjs` импортирует `dist/` — после `pnpm install` и любых изменений src выполняйте `pnpm build`. `pnpm test` = build + `vitest run` (Vitest, конфиг — `vitest.config.mts`: include `src/**/*.test.mjs`, параллелизм по файлам включён (`fileParallelism: true`, VL-140), `isolate: false` — workers переиспользуются между файлами (VL-139)). `pnpm test:fast` = `vitest run` без сборки — для быстрых итераций, когда `dist/` уже собран (build остаётся в `pnpm test`). Тесты — `*.test.mjs` (импортируют `dist/`).
- **Перед npm publish**: гонять `node scripts/npm-smoke.mjs` (VL-32) — проверка установки из tarball (CLI/init/browser/шаблоны).
- **Релизные задачи — publish и пуш без согласия**: если задача релизная, публикация пакета (npm publish, токен без 2FA) и пуш на gitverse разрешены в процессе выполнения задачи без дополнительного согласия пользователя (решение Pavel, 2026-10-04).
- **Совместимость с Backlog.md** — строгая ТОЛЬКО в хранении данных: структура папок backlog/, формат md/yaml файлов, frontmatter задач. Внутренние API (core-функции, CLI-команды, веб-интерфейс) развиваются свободно — например, addComment в core допустим, хотя в оригинале его нет.
- **Node.js 20+**, macOS 10.15 Catalina (проверять, что нет нативных модулей).
- **Не использовать Claude Code / Codex / Opencode** — они не работают на Catalina. Целевой агент — Qwen Code.

## Запрет на внешние рантаймы

Проект на чистом Node.js. **Не использовать python, ruby, perl, awk, jq и другие внешние рантаймы** — ни в коде, ни в скриптах, ни в тестах, ни в командах проверки, ни в документации.

Все проверки, парсинг, валидация — только на Node.js (`node -e`, `node --input-type=module -e`, или отдельные скрипты в `scripts/`).

Причина: пользователь работает на macOS 10.15 Catalina, где внешние рантаймы либо отсутствуют, либо нестабильны.

## Работа через Vibelog

Проект реализован; исторические планы бутстрэпа (`PLAN-*.md`) перенесены в `backlog/completed/` — их последовательное чтение не требуется. Новая работа идёт через Vibelog: задачи живут в `backlog/tasks/` (создаются через MCP или CLI); план крупного эпика пишется в Implementation Plan задачи.

Примеры:

```bash
# Создать задачу
vibelog task create "Добавить фичу X" -d "Описание" --ac "Критерий 1" --priority High

# Список задач
vibelog task list --ready

# Завершить задачу
vibelog task complete <id>
```

## Проверка в браузере (chrome-devtools MCP)

В проекте подключён MCP-сервер **chrome-devtools** (см. `.qwen/settings.json`): npx chrome-devtools-mcp с Яндекс-браузером (не headless, изолированная сессия).

**Экономия контекста (VL-178):** `mcp__chrome-devtools__take_screenshot` — **не использовать** (один кадр — десятки КБ в каждом ходе; инцидент VL-178: два вывода по 624 КБ → отказ провайдера «high risk»). Полный `take_snapshot` без `filePath` — тоже избегать.

**Используй вместо скриншотов:**
- `evaluate_script` — в контекст уходит только нужный кусок данных из DOM (проверка текста, состояния, значений).
- `take_snapshot` с параметром `filePath` — снапшот пишется на диск, в контекст — только подтверждение записи; полный разбор делай через чтение файла (grep/read_file с диапазоном).
- `list_console_messages` / `list_network_requests` — как раньше (обычно компактны).
- После запуска `vibelog browser` — открой страницу через `mcp__chrome-devtools__new_page`, проверь консоль и сеть перечисленными инструментами.
- Drag-and-drop kanban: `evaluate_script` или `drag` для симуляции перетаскивания; после — убедиться, что PATCH /api/tasks/:id ушёл и файл задачи обновлён.
- Это НЕ заменяет автотесты — только ручная/визуальная верификация веб-слоя.

## Команды Vibelog

В этом проекте доступны команды Qwen Code:

- `/vibelog:spec <описание>` — уточнить фичу и определить масштаб (Фаза 1)
- `/vibelog:plan <ID>` — составить план для задачи (Фаза 2)
- `/vibelog:code <ID>` — реализовать план (Фаза 3)

Workflow: spec → plan → code. Интерактивные команды ждут подтверждения пользователя на каждой фазе; автоматические фазы (web-оркестратор, vibelog-agent) выполняются без подтверждения. Дополнительно есть фазы close (закрытие задачи) и comment (запрос из комментария).
