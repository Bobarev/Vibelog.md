# Vibelog.md

[![npm version](https://img.shields.io/npm/v/vibelog.md.svg)](https://www.npmjs.com/package/vibelog.md)
[![license](https://img.shields.io/badge/license-Unlicense-blue)](http://unlicense.org)
[![Node.js 20+](https://img.shields.io/badge/node-%E2%89%A5%2020-brightgreen)](https://nodejs.org)

Markdown-нативный таск-менеджер для git-репозиториев, совместимый с [Backlog.md](https://github.com/MrLesk/Backlog.md) и работающий на чистом Node.js 20+.

Репозиторий: [https://gitverse.ru/bobarev/Vibelog.md](https://gitverse.ru/bobarev/Vibelog.md)

## Зачем

Оригинальный Backlog.md написан на Bun и не работает на macOS 10.15 Catalina. Vibelog.md — совместимая замена на Node.js:

- **Node.js 20+**, никаких нативных зависимостей
- **Формат данных идентичен** Backlog.md — при апгрейде macOS можно переключиться на оригинал
- **Работает с Qwen Code** через CLI и MCP
- **Минимум зависимостей** — runtime-зависимости только grammy (Telegram-бот) и undici; HTML→markdown для кэша references конвертирует собственный код (`src/core/html-to-markdown.ts`, VL-232)

## Prerequisites

- [Node.js](https://nodejs.org) 20 или новее

## Installation

```bash
npm install -g vibelog.md
```

В пакете уже собраны CLI (`dist/`) и веб-интерфейс (`web/dist`) — ничего компилировать не нужно. Одноразовый запуск без установки: `npx vibelog.md`.

Доступны два имени CLI: `vibelog` и алиас `vb` — один и тот же бинарь, поведение идентично. Запуск без аргументов показывает справку; `vibelog agent` открывает TUI-чат с LLM-агентом (см. [Агент Vibelog](backlog/docs/doc-10-Агент-Vibelog-vibelog-agent.md)).

## Usage

```bash
# Инициализация backlog-а в текущем git-репозитории
vibelog init "Мой проект"

# Создание задачи
vibelog task create "Добавить авторизацию" -d "Реализовать JWT" --ac "Токен создаётся"

# Доска задач в терминале
vibelog board

# Веб-интерфейс (kanban с drag-and-drop)
vibelog browser

# ...с доступом из локальной сети (по умолчанию слушает только 127.0.0.1)
vibelog browser --host 0.0.0.0
```

Остальные команды, флаги и диагностика — в [CLI-справочнике](backlog/docs/doc-7-CLI-справочник-Vibelogmd.md).

### Лимиты агента (vibelog-agent)

Лимиты tool-calling loop фаз (подробнее — [Агент Vibelog](backlog/docs/doc-10-Агент-Vibelog-vibelog-agent.md)):

- `--max-tool-calls <N>` — лимит tool-calls одного рана (дефолт 100);
  сбрасывается при каждом resume.
- `--tool-calls-per-session <N>` — **опциональный** кумулятивный лимит
  tool-calls сессии (VL-223): при resume счётчик восстанавливается из
  jsonl-истории прошлых ранов, превышение прерывает фазу до выполнения
  вызова. Без флага действует только per-run лимит (поведение прежнее).
- `--max-wall-time <сек>` — жёсткий потолок времени фазы (дефолт 900).
- `--idle-timeout <сек>` — **idle-watchdog** (VL-274, doc-19 §8): фаза
  прерывается, если столько секунд не было активности — ни новых токенов
  стрима, ни завершённых tool-вызовов. Дефолт 600, `0` — выключено
  (в отличие от остальных числовых лимитов `0` здесь не «сброс»: сброс к
  дефолту — удаление ключа `idle_timeout_seconds`; в боте — `/set idle-timeout`).

**idle vs wall-time.** Зависшая фаза рвётся быстро (по простою), а
длинная-но-живая — не рвётся никогда, пока обновляется активность; wall-time
остаётся жёстким потолком безопасности и срабатывает последним. На время
выполнения инструмента idle-таймер снимается: долгий легитимный `pnpm test`
(десятки минут без вывода) — не зависание, его ограничивают собственные
таймауты инструмента и wall-time. Настройка читается на каждый запуск фазы;
без неё агент берёт дефолт 600 с (поведение фаз не меняется).

**Guard повторов (VL-229).** Агент склонен зацикливаться на одних и тех же
файлах и grep-паттернах — контекст раздувается, растёт доля «Продолжи».
Чтобы это ловить, loop считает обращения по ключу `<инструмент>|<path|pattern>`
и при превышении порога отдаёт модели предупреждение прямо в контекст
(одним user-сообщением после tool-результатов хода):

- 3-е обращение к тому же `grep_search`/`glob` с тем же `pattern`;
- 5-е чтение того же файла (`read_file`, любой `offset`/`limit`);
- `edit`/`write_file` только считаются — повторная правка легитимна.

Пороги настраиваются программно (`LoopLimits.repeatSearchLimit` /
`repeatReadLimit`), guard отключается `repeatGuardDisabled`; CLI-флагов нет.
Текст предупреждения: «Ты уже обращался к … N раз — используй ранее
полученный результат…»; максимум 15 предупреждений за ран.

**Метрика повторов.** Не зависит от guard'а и считается по всему транскрипту
сессии: `repeat_stats` в `.vibelog/agent-sessions/<id>.meta.json` —
`tool_calls_total`, `repeat_calls`, `repeat_share` (доля повторных от ВСЕХ
tool-вызовов сессии) и `top` (до 10 ключей с числом обращений). Те же цифры
уходят в stderr-диагностику фазы (`повторов=…, топ-повторов=…`) и
автоматически подставляются в отчёт `/analyze` (`vibelog agent analyze
<session-ref>`) — топ перечитываемых файлов и повторяющихся запросов виден
без ручного пересчёта.

**Сводка сессии (VL-261).** Разбор сессии начинается с готовых фактов, а не
с ручного чтения JSONL:

```bash
vibelog session summary agent-1793328615846          # сводка по id
vibelog session summary --task VL-235               # последняя сессия задачи
vibelog session summary agent-1793328615846 --json  # стабильная схема для /analyze
vibelog agent-session summary agent-1793328615846   # алиас
```

Выводит число строк и ранов; по каждому рану — фазу (из billing → маркера
промпта фазы → меты), строки-границы маркеров в jsonl, тайминги, LLM-запросы,
`input/output/cache/reasoning`, `max payload_bytes`, инструменты и правки;
агрегаты по всей сессии — `tool → count`, топ-5 скелетов `run_shell_command`
(`git status --porcelain` и `git status -s` попадают в один ключ), топ-5
путей чтения и правок (`edit` и `write_file` раздельно), метрика повторов.
`--json` отдаёт `{schemaVersion, kind: "session-summary", runs, totals}` —
поле `schemaVersion` меняется при несовместимой правке схемы.

**Обзор транскрипта (VL-258).** Когда нужно понять структуру сессии, а не
агрегаты, читать JSONL построчно бессмысленно: в транскрипте бывают строки по
20+ КБ (промпт фазы с блоком задачи), и в лимит tool-вывода 8 КБ влезает 1–2
строки. Обзор печатает по строке — индекс, роль, размер в байтах, число и
имена `tool_calls`, маркер рана/фазы и первые 80 символов:

```bash
vibelog session outline agent-1793328615846           # вся сессия одним выводом
vibelog session outline --task VL-235 --limit 40      # окно строк
vibelog session outline agent-1793328615846 --json    # kind: "session-outline"
```

Шапка называет число строк, ранов и самую большую строку (индикатор
дублирования промпта), секция «Раны» — фазу и строку её маркера
(`2 → стр. 107 (code)`), дальше идёт таблица строк. Целевые строки после
обзора читаются обычным `read_file "<файл>:N-M"`. Агенту тот же обзор доступен
локальным инструментом `agent_session_outline`.

**Resume без дублирования промпта (VL-258).** Блок «Задача (подставлена
автоматически):» при `--resume` сравнивается по хэшу с блоками прошлых ранов.
Не изменился — в историю (и в jsonl) уходит строка-ссылка «без изменений с
рана N (строка M, хэш abc12345)» вместо полного текста описания/плана; изменился
(например, Plan записал план) — промпт остаётся полным.

## Веб-чат (#/chat)

Чат с LLM прямо в веб-интерфейсе (`vibelog browser` → пункт «Чат» в
сайдбаре или `#/chat`): обсуждение проекта, вопросы по задачам и создание
задач через tool-calling (VL-204, на базе assistant-ui).

- **Env**: обычно лежат в `.env` проекта —
  `VIBELOG_LLM_BASE_URL` / `VIBELOG_LLM_API_KEY` / `VIBELOG_LLM_MODEL`.
  Основной путь (VL-209) — секции `providers`/`models` в
  `.vibelog/settings.json` (см. «Модели и провайдеры»): модель выбирается
  в `#/settings` или пикером модели в нижней строке композера чата (VL-265), без правки `.env`.
  Без секций models действует fallback на env; без них обоих чат ответит
  событием error.
- **Инструменты модели** (VL-219): чат получает **все** MCP-инструменты
  Vibelog (задачи, вехи, документы, references, lessons, конфиги) плюс
  локальные `read_file`/`write_file`/`search_files`. Схемы не дублируются —
  `chatToolDefs()` берёт их из реестра MCP, поэтому новые инструменты
  подключаются автоматически.
  - **Правило read/write — по природе операции, не по списку имён**
    (`isWriteOperation` в `src/web/tool-policy.ts`): read-операции
    (`list`/`view`/`search`/`get`/`ready`/`read`, локальные `read_file`,
    `grep_search`, `glob`, `search_files`) выполняются сразу; write-операции
    (`create`/`update`/`add`/`remove`/`manage`/`link`/`sync`/…, локальные
    `write_file`, `edit`) — **только с подтверждением**: ассистент
    показывает карточку «Выполнить операцию?» с кнопками
    «Разрешить»/«Отклонить» (human-in-the-loop). Неизвестное имя инструмента
    трактуется как write (fail-safe: подтверждение лучше молчаливой записи).
  - **Отбор полей `fields`** (VL-162/VL-236/VL-260) у `backlog_view_task`,
    `backlog_list_tasks` и `backlog_search` — одна общая логика: канонический
    ключ `Task` → camelCase/snake_case-алиас (`modifiedFiles` ↔
    `modified_files`) → смысловой алиас (`notes` → `implementationNotes`,
    `plan` → `implementationPlan`, `ac` → `acceptanceCriteria`, `dod` →
    `definitionOfDone`, `summary` → `finalSummary`). Неизвестное имя **не
    валит вызов**: валидные поля возвращаются, а в ответ добавляется ключ
    `_warning` со списком проигнорированных имён, ближайшими допустимыми
    (fuzzy по расстоянию) и полным перечнем ключей. Допустимые ключи
    перечислены в описании схемы каждого инструмента.
  - **`read_file`** (`path`, опционально `offset`/`limit`) — чтение любого
    файла проекта без подтверждения. `path` допускает суффикс диапазона строк
    (VL-252): `файл:171-340` — строки 171–340 (1-based, включительно),
    `файл:171` — с 171-й до конца, алиас `файл#L171-L340`; диапазон в `path`
    приоритетнее `offset`/`limit`. Смысл — следующий диапазон едет в
    **обязательном** аргументе: маркер обрезки печатает готовый к копированию
    `path="файл:172-342"`, потому что необязательный `offset` модель
    заполняет не всегда (инцидент VL-252: ~25 одинаковых вызовов `{path}`).
    Если `path` — каталог (VL-233),
    возвращается отсортированный листинг: каталоги с суффиксом `/`, лимит
    200 записей с пометкой об усечении, служебные `node_modules`/`.git`/`dist`
    показываются, но не разворачиваются; `path: "."` — листинг корня проекта.
    Если файла нет (VL-257), ответ содержит листинг ближайшего существующего
    каталога, секцию «Возможно, вы имели в виду» с похожими путями (сравнение
    по имени без учёта регистра и расширения, не более 5 кандидатов) и, для
    путей вида `<ID>.md`, подсказку читать задачу через `backlog_view_task <id>`.
    Та же подсказка (`formatMissingPathHint`) выдаётся `search_files` и
    `grep_search` при отсутствующем `path`; путь вне проекта по-прежнему даёт
    прежний отказ без листинга.
    Строки длиннее лимита вывода (VL-250): `offset`/`limit` применяются
    **до** обрезки, бюджет 8 КБ расходуется на выбранный диапазон, слишком
    длинная строка усекается с пометкой и подсказкой следующего `offset` —
    так читаются `.vibelog/agent-sessions/*.jsonl` (одна запись = одна
    длинная строка).
  - **Карта проекта `project_map`** (VL-235) — read-only: модули каталога
    `src/` (путь + первая строка шапки модуля + экспорты) одним вызовом,
    без серии `read_file`. Аргументы: `query` (подстрока по пути/описанию/
    экспортам — включает полные описания и все экспорты, это ответ на вопрос
    «где реализован X»), `exports` (по умолчанию да), `dir` (по умолчанию
    `src`), `limit` (по умолчанию 150). Ответ укладывается в бюджет 8 КБ
    ступенчатым сжатием (без экспортов → короткие описания → только имена
    модулей) с явным маркером; усечение по лимиту помечается отдельно.
    Та же генерация доступна в CLI: `vibelog map [query]`.
  - **`write_file`** (`path`, `content`) — создание/перезапись файла внутри
    проекта; без Allow запись не выполняется (после Deny диалог
    продолжается без изменений). Задачи, lessons, references и documents
    правь MCP-инструментами, не через `write_file`.
  - **`search_files`** (VL-234) — поиск по исходникам без подтверждения:
    `pattern` (literal по умолчанию, `regex: true` — регулярка), `glob`,
    `path`, `context` (0-5 строк вокруг совпадения), `limit` (дефолт 100),
    `caseSensitive`. Выдача сгруппирована по файлу (`N:` — совпадение,
    `N-` — контекст); `node_modules`/`.git`/`dist`, бинарники и файлы
    >1 МБ пропускаются. Основной инструмент для вопросов «где используется
    X» / «где определён Y» — вместо серии `read_file` с offset/limit.
  - **Статус Spec** (VL-219): задачи, созданные через чат
    (`backlog_create_task`), попадают сразу в статус **Spec** — ассистент
    выполняет фазу spec: в `description` попадает контекст/цель/входные
    данные из диалога, `acceptanceCriteria` заполняются на том же шаге,
    если данные есть. Явно указанный пользователем статус приоритетнее.
  - **`backlog_update_task`** — редактирование существующих задач с
    подтверждением (в т.ч. новое поле `acceptanceCriteria`, полная замена
    чеклиста); несуществующий id → понятная ошибка «Задача … не найдена».
  - **Пределы проекта**: `../` и абсолютные пути наружу отклоняются для
    обоих файловых инструментов (`resolveInProject`).
  - **Технически недоступны в чате** (`CHAT_DISALLOWED_TOOLS`):
    `backlog_finish_phase`, `reference_sync`, `milestone_remove` —
    destructive-операции, которые выполняет рабочий процесс Vibelog,
    а не чат.
- **Системная инструкция** — `templates/prompts/chat-system.md`
  (переопределение проектом: `.vibelog/prompts/chat-system.md`); описывает
  все инструменты, правило read/write, границы проекта и запрет фаз/релиза.
  Динамический контекст (результаты глобального поиска) добавляется поверх
  шаблона на каждом ходе.
- **Режим ответа** (VL-238) — блок из трёх правил в той же системной
  инструкции: ответ по имеющимся данным раньше исследования (с названием
  недостающего факта), тайм-бокс ~8–10 вызовов инструментов на вопрос
  с явной пометкой «не проверено: …», и короткое «Продолжи»/«Давай ответ»/«Ну?»
  как требование выдать результат, а не разрешение копать глубже.
  Тот же блок подключается к TUI-чату агента (`vibelog agent`) отдельным
  шаблоном `templates/agent-prompt-chat.md` (переопределение проектом:
  `.vibelog/prompts/agent-prompt-chat.md`) — opt-in `buildSystemPrompt(cwd,
  { chat: true })`, поэтому headless-фазы его не получают. Проектное
  переопределение `chat-system.md` полностью заменяет встроенный шаблон
  (вместе с блоком правил).
- **История**: `<проект>/.vibelog/chat-sessions/<threadId>.jsonl`
  (по строке на сообщение; каталог в `.gitignore`).
- **Треды и навигация** (VL-207): активный тред закреплён в hash-роуте —
  `#/chat/<threadId>` (localStorage не используется). При входе на `#/chat`
  подгружается последний тред с сервера, история не теряется при уходе
  на другие страницы; список тредов — в сайдбаре **справа** (слева занят
  сайдбаром приложения), там же кнопка «Новый» и переключение тредов.
  Сайдбар тредов сворачивается кнопкой `PanelLeft` в своей шапке
  (`w-64 ↔ w-12`, содержимое скрыто через `inert`/`opacity`), выбор
  сохраняется в localStorage `vibelog-layout-prefs`
  (поле `chat_threads_collapsed`, VL-263) и переживает переходы
  между страницами.
- **Раскладка клавиш композера** (VL-263): Enter — отправить,
  Shift+Enter — перенос строки, Ctrl/Cmd+Enter — тоже перенос строки
  (в `@assistant-ui/react` такого режима нет — сочетание перехватывается
  своим `onKeyDown` в `web/src/components/chat/thread.tsx`, перенос
  вставляется в позицию каретки через `aui.composer.setText`).
- **Каркас страницы** (VL-263): хедер приложения и оба сайдбара статичны,
  скроллится только контентная область под шапкой (на `#/chat` — лента
  сообщений `ThreadPrimitive.Viewport`, композер закреплён внизу;
  в сайдбаре тредов — только список `nav`). Каркас — `SidebarProvider`
  с `h-svh overflow-hidden` и `SidebarInset` с `h-full min-h-0`
  в `web/src/App.tsx`; сам `ui/sidebar.tsx` не менялся.
- **API тредов**: `GET /api/chat/threads` — список тредов (id, title,
  updatedAt, messageCount) без тел сообщений; `GET /api/chat/threads/:id` —
  история треда для восстановления (дополнительно отдаёт `allowList` —
  инструменты, разрешённые в треде навсегда).
- **Внешний вид сообщений и tool-вызовов (VL-264)** — один-в-один по
  референсу ref-22 (assistant-ui): layout сообщений из
  `apps/docs/components/pages/examples/perplexity.tsx`, рендер тулзов из
  `packages/ui/src/components/react/assistant-ui/elements/`. Ответ ассистента
  — **без пузыря**: аватар-кружок `size-8` с border, текст прямо в ленте
  шириной `--thread-max-width` (40rem). Сообщение пользователя — пузырь
  `rounded-3xl rounded-tr-md` с border (не `bg-primary`), `max-w-[85%]`,
  выровнен вправо. Action bar (Copy/Edit, Reload) — кнопки-призраки
  `size-8 rounded-full`, появляются на hover/focus-within сообщения.
  - **Read-инструменты** (`read_file`, `search_files`, `backlog_view_task`,
    `backlog_search`, `project_map` и т.п.) — свёрнутая строка: chevron,
    label/activeLabel (во время выполнения — shimmer), mono-чип с ключевым
    аргументом (`query`/`path`/`id`), галочка по завершении; раскрытие
    показывает блоки `Request` и `Result`. При ошибке строка авто-раскрыта.
  - **Write-инструменты** — карточка-approval (иконка, title/subtitle,
    description, блок details label/value, кнопки **Deny / Always allow /
    Allow once**); после решения — status-строка (Approved running /
    Finished / Denied) с фокусом на результат для скринридера.
  - **Always allow** (VL-264): разрешение хранится **per-thread** в
    `<проект>/.vibelog/chat-sessions/<threadId>.allow.json`; последующие
    вызовы того же инструмента в этом треде идут без паузы (событие
    `tool_start` с `auto: true`), карточка показывает пометку «Разрешено
    всегда · отозвать». API: `GET /api/chat/threads/:id/allow` →
    `{tools}`, `POST …/allow` (`{tool}`), `DELETE …/allow?tool=<name>`
    (отзыв возвращает паузу; невалидный id/tool → 400). Решение с «always»
    пишется в `approvals.jsonl` (`decided` + `always: true`).
  - **Группировка** подряд идущих tool-вызовов — один аккордеон
    «N вызовов инструментов» (`MessagePrimitive.GroupedParts` +
    `groupPartByType`); write-вызовы в группу не прячутся — карточка
    подтверждения остаётся активной.
  - **Раскрытие панелей (VL-271)** — общий механизм `CollapseContent` в
    `web/src/components/chat/surfaces.tsx` (класс `.collapse-panel` в
    `web/src/index.css`) на grid-rows трюке (`grid-template-rows: 1fr ↔ 0fr`,
    где `1fr` в auto-высоте = max-content) с `forceMount`: высота панели всегда
    по контенту и вложенность любой глубины работает без измерения. Раньше
    высота фиксировалась Radix-переменной `--radix-collapsible-content-height`
    (значение на момент открытия), поэтому длинный `Result` и раскрытый внутри
    группы `ToolCall` срезались `overflow-hidden` — «разворачивались в
    невидимую область». Анимация — CSS keyframes `vl-collapse-down/up`
    (transition по `grid-template-rows` на React-пути не стартует, а Radix
    `Presence` ждёт `animationend`); при раскрытии панель докручивается в
    viewport (`scrollIntoView`), скрытый контент закрытой панели помечается
    `inert` + `aria-hidden`, чтобы не ловить Tab.
  - **Ошибки и обрыв**: ошибка стрима/инструмента — единая inline-плашка
    `error-state` (не текст посреди ответа); прерванный/незавершённый run —
    плашка `stopped-run` с причиной и кнопками «Продолжить»/«Скрыть».
    Ошибки стрима в jsonl не сохраняются (после перезагрузки треда
    восстанавливается только оборванный tool-call — показывается как
    «Прервано»).
- **Повторы и лимит tool-вызовов (VL-255)**: дословный повтор вызова в
  одном ходе не исполняется. Ключ вызова — имя инструмента + стабильная
  сериализация аргументов (ключи объектов отсортированы рекурсивно, порядок
  ключей в JSON модели не важен). Повтор получает tool-результат
  `{ok:false, duplicate:true, message}` с указанием использовать ранее
  полученный результат; события `tool_start`/`tool_end` при этом сохраняются
  (парность для UI), в историю тоже пишется tool-сообщение.
  - **Легитимный повтор разрешён**: для каждого ресурса (`read_file`/
    `write_file`/`edit` → путь, поиск → pattern) ведётся epoch; write-вызов
    его инкрементит, поэтому чтение файла после записи к нему — новый вызов,
    а дословный повтор самой записи — блокируется.
  - **Лимит вызовов на один ответ модели** — `chat_max_tool_calls` в
    `.vibelog/settings.json` (дефолт **16**, допустимо 1–200; отсутствие
    ключа, строка, дробное, 0, отрицательное или битый settings.json →
    дефолт). Считается на **ответ** модели, а не на весь POST: внутри
    одного запроса до 8 итераций LLM, поэтому пакетное чтение не ломается.
    Сверхлимитные вызовы получают `{ok:false, limit:true, message}` с
    указанием завершить ход и продолжить следующим.
  - **Диагностика**: по завершении хода (включая пути ошибок) пишется
    `<проект>/.vibelog/chat-sessions/<threadId>.repeat.json` —
    `{ts, turn, repeat_stats, executed, deduped, limit_hits}`, где
    `repeat_stats` в формате агент-петли (VL-229: `tool_calls_total`/
    `repeat_calls`/`repeat_share`/`top`), поэтому диагностика общая с
    `vibelog-agent`. Расширение `.json` (не `.jsonl`) — иначе файл попал бы
    в список тредов. Сбой записи диагностики диалог не рвёт.
  - **Отличие от `repeat-tracker` (VL-229)**: там грубый ключ
    (`read_file|<path>` без offset/limit) даёт модели *предупреждение* после
    N повторов; здесь — точный ключ, который *блокирует исполнение*
    дословного дубля. Механизмы дополняют друг друга; стейт guard'а живёт в
    памяти одного POST (межзапросного дедупа в resume нет — после хода
    модель уже видит прежние результаты в истории).
- **Протокол**: `POST /api/chat` — SSE (`text/event-stream`), события
  `text`/`tool_start`/`tool_end`/`approval`/`truncated`/`done`/`error`.
- **Лимиты хода и авто-продолжение (VL-269)**: лимиты чата живут в секции
  `chat` файла `.vibelog/settings.json` и читаются **на каждый ход** —
  правка применяется к следующему сообщению без перезапуска веб-сервера.
  Без секции работают прежние дефолты (поведение не меняется):

  | Ключ | Дефолт | Диапазон | Что ограничивает |
  |------|--------|----------|------------------|
  | `chat.max_iterations` | 8 | 1–200 | итераций LLM-цикла на ход (один ответ модели + его tool-вызовы = одна итерация) |
  | `chat.max_wall_time` | 120 (с) | 1–86400 | общий бюджет времени одного хода |
  | `chat.max_auto_continue` | 3 | 1–20 | авто-продолжений подряд на клиенте |
  | `chat.call_timeout` | 90 (с) | 1–3600 | ожидание одного вызова модели **без единого токена** |

  - **Per-call таймаут отделён от бюджета хода**: `call_timeout` — это окно
    неактивности одного запроса к модели, оно перевзводится на каждом
    токене стрима, поэтому медленный, но живой ответ не обрывается. Раньше
    единственные 120 с резали весь ход вместе с пятью быстрыми tool-вызовами.
  - **`truncated` вместо `error`**: при исчерпании итераций или бюджета
    сервер отдаёт `{type:'truncated', reason:'iterations'|'wall_time', step,
    limits, saved:true}` — история `<threadId>.jsonl` к этому моменту уже
    дописана (append после каждого сообщения), висящие write-вызовы закрыты
    `not_confirmed` (payload остаётся валидным для провайдера).
  - **Авто-продолжение**: клиент на `truncated` сам повторяет
    `POST /api/chat {continue: true}` — без нового user-сообщения и без
    пустой строки в треде, и показывает в треде строку «Продолжаю — шаг N,
    <причина> исчерпан». После `max_auto_continue` подряд в треде остаётся
    плашка с причиной и кнопкой **«Продолжить»** (каждое нажатие — один ход),
    так что ручное «Продолжи» становится аварийным выходом, а не ритмом
    работы. Кнопка остановки (Cancel) прерывает авто-продолжение и новый ход
    не запускает.
  - **Мусор в конфиге не роняет чат**: невалидное значение (0, отрицательное,
    дробное, строка, сверх потолка) откатывается к дефолту, причина уходит
    предупреждением в лог сервера (`[vibelog-chat] некорректные лимиты…`).
  - Правка — страница `#/settings`, карточка «Лимиты веб-чата» (пусто или 0 =
    сброс ключа к дефолту); `GET/PUT /api/settings` отдают и принимают секцию
    `chat` с той же валидацией (`env`-секреты по-прежнему не отдаются).
- **Подтверждения при нескольких write в одном ходе (VL-256)**: гейты
  последовательные — на каждый write-вызов приходит свой Allow/Deny, после
  решения по вызову N сервер показывает гейт для N+1 (отказ по одному не
  отменяет остальные, read-only вызовы между ними выполняются сразу).
  Запросы и решения пишутся в `<проект>/.vibelog/chat-sessions/<threadId>.approvals.jsonl`
  (`requested`/`decided`/`not_confirmed` + номер хода): пара «запрос без
  решения» = потерянное подтверждение, видно в диагностике. Если пользователь
  присылает новое сообщение вместо решения, висящие вызовы закрываются
  `{denied: true, reason: 'not_confirmed'}` — это не отказ, повтор безопасен.
- Замечание для `pnpm dev` в `web/`: dev-прокси `/api` → :3030 пропускает
  SSE стримом; при подозрении на буферизацию проверяй через `vibelog browser`.

- **Пикеры у инпута (VL-265)**: в нижней строке композера слева —
  пикер роли ассистента, справа (рядом с кнопкой Send) — пикер модели.
  Оба — дропдауны в стиле ref-22 (perplexity): название, галочка у выбранного
  пункта, описание во второй строке. Выбор модели — разовое переопределение
  для чата (`body.model`, default в `#/settings` не меняется); выбор роли —
  `body.persona` (module-state, при перезагрузке страницы снова «Помощник»).
  Пикеры независимы: роль НЕ задаёт модель.

### Роли ассистента (`chat_personas`, VL-265)

Роль — это дополнительный блок системного промпта и пара настроек
поведения. Общая часть промпта (правило read/write, список инструментов,
границы проекта) живёт в `templates/prompts/chat-system.md` и в файлах
ролей НЕ дублируется: итоговый промпт = общая часть + блок
`## Текущая роль: <label>` + контекст поиска по сообщению.

Встроенные роли (работают без настройки): `helper` «Помощник» (быстро,
задачи в `Spec`), `architect` «Архитектор» (глубокое исследование кода,
задачи сразу в `Planned`), `supervisor` «Супервизор» (ведёт ночной прогон: тик-цикл наблюдения,
лечение зацикливаний, авто-баг; задачи в `Spec`; свой лимит хода —
`supervisor.limits`, см. §«Супервизор: тик, лечение и планировщик»). Тексты —
`templates/prompts/personas/<id>.md`; для супервизора промпт лежит в
`templates/prompts/personas/supervisor.md` и переопределяется
`<проект>/.vibelog/prompts/personas/supervisor.md` (общая схема поиска
шаблона — как у остальных ролей).

Проект добавляет свои роли и переопределяет встроенные секцией
`chat_personas` в `.vibelog/settings.json` (ключ — id роли):

```json
{
  "chat_personas": {
    "researcher": {
      "label": "Ресёрчер",
      "description": "Ищет информацию и предлагает задачи",
      "prompt": "researcher",
      "default_status": "Spec"
    },
    "auditor": {
      "label": "Аудитор",
      "description": "Находит несоответствия, создаёт задачи на фикс",
      "prompt": "auditor",
      "allow_tools": ["backlog_search", "read_file", "search_files"],
      "default_status": "Spec"
    }
  }
}
```

- `prompt` — имя файла шаблона без `.md`: сначала
  `<проект>/.vibelog/prompts/personas/<prompt>.md`, затем встроенный
  `templates/prompts/personas/<prompt>.md`. Если нет ни одного — ход
  падает fail-closed с понятной ошибкой (роль объявлена, текста нет).
- `default_status` — статус создаваемой из чата задачи (должен быть в
  `statuses` из `backlog/config.yml`); явно переданный в вызове статус
  приоритетнее.
- `allow_tools` — **шов на будущее**: массив известных имён инструментов
  читается и валидируется, но фильтрация инструментов по роли пока НЕ
  применяется (отдельная задача).
- Битые записи (не объект, нет `label`/`prompt`, неизвестный инструмент или
  статус) не роняют чат: роли работают, а `GET /api/personas` отдаёт список
  `errors`. Список ролей для пикера — `GET /api/personas`
  (`id`/`label`/`description`, без текстов промптов).

## Супервизор: запуск фаз из чата и grant на прогон (VL-268)

Чат умеет управлять фазами: четыре MCP-инструмента доступны любой роли
(не только будущему «Супервизору»).

| Инструмент | Назначение |
|---|---|
| `backlog_trigger_phase` | Запустить фазу задачи: `id`, `phase?`, `comment?`, `sameSession?`. Без `phase` — первая допустимая по workflow из текущего статуса |
| `backlog_phase_status` | Состояние запуска: `running`, `phase`, `pid`, `exitCode`, `logTail`, `result`, `repeat_stats`, `last_run.is_error` |
| `backlog_auto_queue` | Автоочередь (то же, что `/auto` в боте): `action` = `add` (с тем же дедупом) / `start` / `stop` / `status` |
| `backlog_supervisor` | Прогон: `action` = `plan` (сухой прогон: состав, порядок, волны, обоснование) / `start` / `stop` / `status` |

**Ошибки запуска формулируются отдельно** (без is_error-мусора): задача не
найдена; фаза не разрешена из текущего статуса (с перечнем разрешённых); фаза
уже идёт; превышен лимит параллельных фаз; задача вне grant-а прогона.

### Grant — доверие на прогон

Пользователь подтверждает прогон ОДИН раз в карточке чата (состав задач,
чекбоксы инструментов, срок), после чего модель работает без пауз
Allow/Deny — но только внутри трёх границ:

- **задачи** — `taskIds`. Задача вне набора не запускается: модель получает
  отказ с предложением расширить прогон (расширение = новая карточка);
- **инструменты** — `allowedTools`. Инструмент вне списка идёт обычным путём
  Allow/Deny;
- **срок** — `expiresAt`. Истёкший grant не даёт стартовать новые фазы,
  текущая доводится.

Файл: `.vibelog/supervisor/grants/<runId>.json`

```json
{
  "runId": "run-2026-10-31T22-00-00",
  "taskIds": ["VL-263", "VL-264"],
  "allowedTools": ["backlog_trigger_phase", "backlog_phase_status",
                    "backlog_auto_queue", "backlog_supervisor", "backlog_create_task"],
  "grantedAt": "2026-10-31T21:58:00.000Z",
  "expiresAt": "2026-11-01T05:58:00.000Z"
}
```

- `expiresAt` = `grantedAt + expiresInHours` (по умолчанию 8 ч) либо явный
  `expiresAt`; мусор отклоняется с понятной ошибкой.
- **`write_file`, `edit` и shell-команды не входят в grant никогда** —
  список развязываемых инструментов задан константой в коде
  (`GRANTABLE_TOOLS`), пользовательский ввод фильтруется, файловые write
  всегда требуют подтверждения.
- Проверка идёт **перед каждым вызовом** (в трёх точках approval-гейта), а не
  один раз на ход: отзыв действует немедленно.
- Отзыв — при `stop` и автоматически, когда все задачи прогона в терминальном
  статусе: в файле появляется `revokedAt`, `findActiveGrant` его не видит, а
  следующие вызовы снова требуют подтверждений. Файл не удаляется — история
  прогона остаётся читаемой.
- Состояние прогона: `.vibelog/supervisor/runs/<runId>.json` (состав, волны,
  запущенные задачи, `stoppedAt`/`finishedAt`).
- Настройки — секция `supervisor` в `.vibelog/settings.json`:
  `max_parallel_phases` (1–8, дефолт 3), `default_ttl_hours` (дефолт 8),
  `tick_seconds` (дефолт 60), `heal_attempts` (дефолт 2),
  `allow_self_tuning` (дефолт `false`), `parallel_mode`
  (`conservative`/`aggressive`), `limits.chat_max_iterations` (30) и
  `limits.chat_max_wall_time` (600 с) — лимиты хода для роли `supervisor`.
  Битая секция не отключает дефолты — ошибка попадает в список при чтении.

## Супервизор: тик, лечение и планировщик (VL-270)

При активном grant в процессе `vibelog browser` работает **тик** (период
`tick_seconds`, дефолт 60 с): он собирает состояние фаз, пишет heartbeat и
принимает решения. Таймер заводится только при действующем grant'е, не держит
процесс (`unref`) и глушится `VIBELOG_SUPERVISOR_TICK=off`.

Точка подъёма таймера (VL-272): он стартует и при запуске `vibelog browser`,
если grant уже лежит на диске, и **в момент выдачи grant'а** (`backlog_supervisor
start`) — сервер обычно работает раньше, чем пользователь подтверждает состав,
и без второй точки прогон оставался без планирования следующих волн, лечения и
авто-багов до перезапуска процесса. Повторный вызов идемпотентен (второй
интервал не создаётся). Гасится таймер на stop прогона, при авто-отзыве grant'а
(все задачи терминальны) и при истечении срока — тик видит `skipped=no-grant` и
останавливает интервал сам, а также на `server.close`.

Один тик: собрать состояние → записать `state.json`/`heartbeat.md` → **wake
gate** (изменилось ли что-то?) → вызвать модель (если изменилось) → применить
решение. Состояния в памяти нет: рестарт `vibelog browser` не ломает прогон —
живость фазы определяется по `pid` + `phaseRunId` (`process.kill(pid, 0)`),
поэтому зависшая после рестарта фаза распознаётся как упавшая и попадает в
лечение, а не считается вечно идущей.

Файлы состояния (`.vibelog/supervisor/`):

| Файл | Что внутри |
|---|---|
| `state.json` | машинное состояние прогона: задачи, фазы, попытки, healAttempts, группы, последнее решение. Запись атомарна (temp + rename) |
| `heartbeat.md` | человекочитаемый срез: таблица задач, прошлое решение, обоснование групп, предупреждения правил. Он же инжектится в промпт тика |
| `settings.json` | правила лечения `heal_rules` + `default_action` (этот файл модель может править при `allow_self_tuning`) |
| `tuning.log` | история самонастроек: время, что было, что стало, причина |
| `runs/<runId>.json` | запись прогона (состав, волны, запущенные задачи) |

**Правила лечения (уровень 1)** — декларативные, применяются кодом до вызова
модели, первое совпавшее правило выигрывает. Действия: `retry`,
`comment_and_retry`, `retry_once_then_bug`, `bug`, `stop`. Пример:

```json
{
  "heal_rules": [
    { "id": "repeat-loop", "when": { "repeat_share_min": 0.25, "repeat_calls_min": 8 },
      "action": "comment_and_retry",
      "comment_template": "Ты повторно обращался к тем же путям: {top_repeats}. Следующий шаг — правка, а не чтение." },
    { "id": "payload-limit", "when": { "fail_reason_contains": ["payload"] }, "action": "retry" },
    { "id": "no-progress", "when": { "status_unchanged": true }, "action": "retry_once_then_bug" }
  ],
  "default_action": "bug"
}
```

Подстановки шаблона: `{top_repeats}`, `{fail_reason}`, `{task_id}`, `{attempt}`.
Директива уходит фазе `comment` перед рестартом. Битое правило выпадает с
предупреждением (в heartbeat и в отчёт тика), валидные продолжают работать;
файла нет — действуют дефолтные правила. **Уровень 2** — содержательный разбор
моделью (упавшие тесты, ошибочный план) по `logTail`, `repeat_stats` и
`fail_reason`; фаза `analyze` для лечения не используется (она read-only).
При исчерпании `heal_attempts` создаётся баг-задача в статусе **Spec** с метками
`auto-bug` и именем фазы: в описании — причина, фрагмент лога, ID сессии,
цепочка сработавших правил и ссылка на исходную задачу.

**Режимы параллельности** (`parallel_mode`): `conservative` (по умолчанию) —
каждую группу модель обязана обосновать по компонентным меткам/подсистемам,
обоснование пишется в `heartbeat.md`; не обосновала — задачи идут
последовательно. `aggressive` — параллель до лимита без обоснования.
`dependencies`/`blocks` — жёсткий запрет параллели в любом режиме. Лимит
`max_parallel_phases` считается по числу **одновременно работающих фаз**, а не
по числу задач (у задач разные workflow и разное число шагов до close).
`modified_files` в решении не участвует: поле заполняет только фаза `code`,
а worktree создаётся раньше (`plan`/`do`), поэтому признак бесполезен.

**Worktree задачи поднимается и при создании сразу в Planned (VL-278).** Раньше
worktree `vb/<id>` создавался ТОЛЬКО оркестратором при запуске фазы `plan`/`do`
(`src/web/orchestrator.ts`), поэтому задача, созданная из чата сразу в статусе
Planned (spec выполнен ролью Архитектор в том же вызове), оставалась без ветки:
фаза `plan` для неё больше не запускалась, `code` шёл в главном рабочем дереве,
а close брал обычный шаблон без merge-шага — design «одна задача = одна ветка =
изолированный worktree» тихо отключался, и условия работы зависели от того, каким
путём пришла задача (фаза vs чат). Теперь условие «нужен ли worktree» вынесено в
ОДИН хелпер `shouldEnsureWorktree` (`src/core/worktree.ts`) и применяется в двух
триггерах: `{kind:'phase'}` (запуск plan/do — как раньше) и `{kind:'create', status}`
(создание задачи, статус которой совпадает с `produces_status` перехода фазы plan
в workflow ЭТОЙ задачи — кастомные workflow из `backlog/config.yml`/`.vibelog/settings.json`
уважаются, «Planned» не хардкодится; в simple-workflow такого перехода нет, там
worktree поднимет запуск `do`). Порядок проверок: branch-mode выключен → worktree
не нужен; `type=epic` → не нужен; worktree уже существует → переиспользуется;
иначе — по триггеру. Создание идёт через тот же `ensureTaskWorktree`, что и
штатный `plan`, поэтому повторяет все его шаги, включая `linkWorktreeDeps`
(симлинки `node_modules` и `backlog/references/data` из главного репо); сборка
`buildTaskWorktree` при создании НЕ выполняется — как и при обычном запуске plan
(сборка происходит при перезапуске бота из ветки). Ошибка git не роняет создание
задачи (fail-open, паттерн ensure/build в боте): задача создаётся, в ответ
`backlog_create_task` уходит `applied.worktree` с абсолютным путём worktree либо
предупреждение «задача создана, worktree не поднят: …», диагностика — в stderr
(`[vibelog-worktree] …`). Подключена MCP-поверхность (`backlog_create_task`);
CLI `vibelog task create` и `POST /api/tasks` создают задачу без git-действий —
то же условие подключается к ним одним вызовом `ensureWorktreeOnCreate`.

**Незакрытые зависимости блокируют запуск (VL-275).** Задача, у которой есть
зависимость не в терминальном статусе, в тике не запускается и НЕ лечится: тик
проверяет её через `isReady` (та же точка правды, что у планировщика прогона и
автоочереди) и держит в состоянии `pending` с заполненным `blockedBy`
(канонические ID блокеров). Причина не «нет прогресса», а внешняя — перезапуск
фазы её не устранит, поэтому попытки лечения на такой задаче не расходуются
(инцидент VL-239: 7 прогонов `code` при незакрытой VL-209, которой в прогоне не
было, сожгли `heal_attempts` и породили авто-баг). В `heartbeat.md` появляется
секция «Заблокированы зависимостями» (`- VL-N — ждёт VL-X (нет в прогоне)`), а
`blockedBy` входит в ключ снимка состояния — поэтому снятие блокировки будит
wake gate и задача запускается в ближайшем тике. Перезапуск заблокированной
задачи дополнительно отсекается в `applyHealAction` (защита от решения модели
«retry»), а задача с уже идущей фазой не трогается.

**Самонастройка**: при `allow_self_tuning: true` модель может править
`heal_rules` и `comment_template` в `.vibelog/supervisor/settings.json`;
изменения пишутся в `tuning.log`. Защищённые поля — `max_parallel_phases`,
`heal_attempts`, `allow_self_tuning`, `parallel_mode` — модель не трогает ни
при каких настройках: это страховка, которую нельзя разрешить себе самому.

Важное: супервизор **не назначает фазы** — следующую фазу всегда определяет
workflow (`getWorkflowForTask → getAvailablePhases → isPhaseAllowed`),
`backlog_finish_phase` роли недоступен, статусы в обход фаз не меняются.

Ограничение: `activeRuns`/`lastRuns` оркестратора живут в памяти процесса
(доска после рестарта не возобновляет поллинг сама), но состояние прогона
восстановимо — тик читает `state.json` и живость по pid.

**Залипший лок фазы (VL-276).** `close` процесса Node означает не смерть
процесса, а закрытие его stdio: если stdout-пайп удерживает живой потомок
(MCP-сервер агента, node/npx-обёртка), событие `close` может не прийти никогда,
хотя процесс давно вышел. Раньше это оставляло запись в `activeRuns` навсегда —
задача получала «Запуск уже выполняется» и не двигалась с места (инцидент
VL-248). Теперь: (1) по событию `exit` заводится таймер `RUN_CLOSE_GRACE_MS`
(2 с) — не дождались `close`, ран завершается по `exit` (данные рана
сохраняются: буферы досыпаются, результат парсится, `onExit` вызывается один
раз); (2) перед проверкой лока в гардах `spawnQwenRun`/close-очереди, а также
в `getRun`/`countActiveRuns` выполняется reap: записи с завершившимся процессом
(`exitCode`/`signalCode`) или мёртвым pid снимаются через штатный `finalize`;
(3) залипший флаг `closeActive` (close-ран умер, не вызвав `onExit`) сбрасывается
и очередь close разгребается. Мёртвый ран больше не выглядит как `running: true`
и не занимает слот `max_parallel_phases`.

**Неудачная доставка директивы лечения (VL-276).** Если `startTaskPhase` для
лечебного действия вернул ошибку (типичный случай — лок оркестратора,
«Запуск уже выполняется»), попытка **расходует** `heal_attempts`, задача остаётся
`failed`, а причина классифицируется: «фаза занята локом оркестратора
(транспорт): …» либо «директива не доставлена: …». Раньше бюджет не тратился,
и один и тот же безуспешный шаг повторялся до конца прогона без прогресса;
теперь по исчерпании бюджета заводится авто-баг с различимой причиной.

## Учёт токенов (billing)

Сколько LLM-токенов потрачено на задачу и по фазам — три уровня хранения
(деньги НЕ хранятся: тариф меняется, стоимость считается на лету):

1. **Мета сессии** `.vibelog/agent-sessions/<sessionId>.meta.json` —
   `usage {input, output, cache, total, requests}`, `startedAt/finishedAt/durationMs`,
   `model`, `agent` (vb/qwen) — самодостаточно для сверки с провайдером.
   Поля модели (VL-239): `model_id`, `model_provider`, `model_name`, `api_mode`
   фиксируют модель **сессии** (пишутся при её создании и больше не меняются),
   а `model` — фактическая модель последнего рана (её же пишет billing).
   На них опирается resume: продолжение сессии идёт на модели сессии
   (см. «Модели и провайдеры»).
2. **Frontmatter задачи** `token_usage` — агрегат по всем сессиям:
   totals + `duration_ms` + `by_phase: {spec/plan/…: {input, output, cache, requests}}`.
   Показывается в карточке (web-таб «Токены», `/task` в боте, `task view` в CLI).
3. **`.vibelog/billing/<taskId>.json`** — append-only журнал сессий
   (источник правды: одна запись на ран).

**Поля записи billing (VL-243).** `phase` — фаза **этого рана**: у resume-рана
(например `code` в сессии `plan` при `code_same_session`) в записи стоит `code`,
а исходная фаза сессии уходит в необязательное поле `sessionPhase` (раньше такая
запись маркировалась `plan`, и `code`-раны «терялись» при сверке журнала).
`fallback: true` — запись дописана оркестратором «по факту»: CLI-пост-ран свою
запись не оставил (ран убит сигналом/упал до учёта). Маркер `billing_recorded`
в мете сессии гарантирует, что ран учитывается ровно один раз.

**Фаза Close учитывается как любая другая (VL-243).** Раньше close был исключён
из задачного env оркестратора, и его ран не попадал ни в мету, ни в billing. Теперь
исключение close касается только git worktree (VL-112: закрытие с merge ветки и
`docs(task)`-коммитом допустимо лишь в главном репо) — учёт работает всегда.
Проверка: в `.vibelog/billing/<ID>.json` появляется запись `phase: "close"`, в мете
сессии — `taskId` и `phase: "close"`.

**Close в branch-mode не стартует при незавершённом merge (VL-246).** Перед стартом
close-фазы в режиме веток оркестратор проверяет git-состояние главного репозитория
(`getMergeState`: `MERGE_HEAD` + `git diff --name-only --diff-filter=U`). Если слияние
уже идёт (например, от параллельной Close — инцидент VL-212/VL-219, lesson-82), фаза
**отклоняется** с сообщением «Close не может начать слияние: в главном репозитории
идёт незавершённый merge (MERGE_HEAD <sha7>), конфликты: …», процесс агента не
запускается, **статус задачи не меняется** — вместо падения на `git merge --no-ff`
с «you have unmerged files». В не-git проекте проверка fail-open (close не ломается).
Второй close другой задачи по-прежнему встаёт в очередь (VL-146), и сообщение теперь
называет её владельца: «стартует после завершения текущего close (VL-M)» (поле
`queuedBehind` в ответе оркестратора).

**История ранов и время старта рана (VL-259).** `startedAt` записи billing —
фактическое начало **этого рана** (оркестратор передаёт его в env
`VIBELOG_RUN_STARTED_AT`, прямое CLI-использование — старт процесса), а не время
создания сессии; поле `startedAtKind: "run"` это фиксирует. У старых записей
поля нет и `startedAt` ненадёжен (у всех resume-ранов сессии он одинаковый) —
начало рана восстанавливается как `finishedAt − durationMs`. Мета сессии хранит
историю ранов: `runs: [{sessionId, phase, sessionPhase, startedAt, finishedAt,
durationMs, usage, agent, billing}]` (до 50 записей) и `lastRunPhase` — по ним
видно, сколько было ранов, в какой фазе шёл каждый и сколько стоил. Поле
`phase` меты остаётся фазой **создания** сессии: по нему ищется план-сессия
(`code_same_session`, VL-147), поэтому resume-ран его не перезаписывает.
Разбивка `by_phase` в frontmatter задачи агрегируется по фазе **рана** (служебная
фаза `prompt` туда не попадает).

Записывают все три писателя с дельта-идемпотентностью (отметка
`usage_recorded` в мете): `backlog_finish_phase` (поле `tokenUsage`,
fallback — мета сессии → её jsonl; объект из одних нулей трактуется как
отсутствующий параметр — VL-251), CLI-пост-ран и finish-блок
оркестратора (основной путь для qwen-ранов). Requests/usage в JSONL
сессии дописывает loop в каждое assistant-сообщение.

**Файл задачи коммитится после записи `token_usage` (VL-277).** Раньше шаг 6
шаблона close коммитил `backlog/tasks/<ID>*.md` изнутри агента, а `token_usage`
дописывался **позже** — пост-раном уже завершившегося процесса (в момент коммита
расход рана ещё неизвестен), поэтому после каждого close задача оставалась
грязной ровно один раз. Теперь коммит файла задачи перенесён в пост-ран: порядок
детерминированный — сначала usage записан в frontmatter, затем файл закоммичен
(хелпер `src/agent/task-commit.ts`), и `git status --porcelain -- backlog/tasks/<ID>*.md`
после close пуст. Если HEAD — уже `docs(task)`-коммит **этой** задачи и он не
запушен, используется `git commit --amend --no-edit` (комментарий и смена статуса
из `finish_phase` попадают в тот же коммит), иначе создаётся отдельный
`docs(task): <ID> — token_usage (<phase>)`. Гейт по фазе — только `close`
(spec/plan/code/comment по-прежнему ничего не коммитят); коммитится исключительно
явный путь файла задачи в главном репозитории (`git add -A` не используется,
`backlog/references/data/` не трогается); любая git-ошибка глушится в stderr и
не меняет exit-код и статус уже завершившейся фазы.

**Контракт `backlog_finish_phase` (VL-251, уточнён VL-253).** `comment` (отчёт
о фазе) объявлен в `properties` и в `required` схемы инструмента — tool-calling
обязан его сгенерировать (требование, живущее только в `description` или в
тексте ошибки, модель выполнить не может: инцидент VL-250/VL-252 — луп на
10+ вызовах без `comment`). Если `comment` всё же не передан, сервер **не
падает**: он собирает авто-отчёт (статус, счётчики AC/DoD, `modified_files`,
фрагмент `implementationPlan`/`finalSummary`, маркер «Отчёт собран сервером
автоматически (VL-253)») и завершает фазу. Повторный вызов со статусом,
равным текущему, по-прежнему ошибка (`already_finished`): в тексте — дата,
автор и начало существующего отчёта плюс следующий шаг. Явный `tokenUsage`
игнорируется, если предыдущий ран сессии упал (`last_run.is_error` в мете) —
иначе числа из сводки упавшей фазы попадали бы в frontmatter как «успешный»
usage. Loop detection: повторная блокировка той же сигнатуры немедленно
прерывает фазу, плюс жёсткий кап 5 заблокированных вызовов за ран.

**Смена статуса разрешена только фазе workflow (VL-245).** Статус, валидный по
`config.statuses`, всё равно не запишется, если фаза вызывающего не даёт перехода
«текущий статус + фаза → запрошенный статус» (`phaseStatusTransitionError` в
`src/core/workflow.ts`). Фаза резолвится только из доверенных источников:
`VIBELOG_RUN_PHASE` → `VIBELOG_PHASE_NAME` (кроме служебного `prompt`) →
`meta.lastRunPhase` → `meta.phase`; поле `phase` самого вызова для этого
**не используется** (оно про учёт usage, VL-259 — иначе агент выписывал бы себе
разрешение). Служебные фазы (`comment`/`prompt`/`analyze`/`resume`) статус не
меняют вовсе: именно фаза `comment` выставила Done у VL-219 (инцидент VL-231).
Во время рана задача временно в `In Progress` (VL-196), поэтому базой проверки
служит статус **до** фазы из транзиент-кэша (`getPhaseTransientStatus`), а не
текущий. Фаза не резолвится (ручной вызов MCP из стороннего клиента) → fail-open:
работают прежние правила по `config.statuses`. Нарушение — не `isError`, а
понятная ошибка в сводке (паттерн частичного применения: отчёт/AC/DoD
применяются, статус — нет). Ручные переводы статуса идут мимо MCP (CLI
`vibelog task edit --status`, веб `PATCH /api/tasks/:id` с `canMoveTo`), поэтому
флага-исключения в схеме инструмента нет.

**Аварийное завершение фазы: `aborted: true` (VL-244).** Аварийные ветки
шаблонов фаз (`templates/phases/phase-close*.md` — конфликт merge, упавшая
сборка/тесты) заканчивались обычным текстом агента: процесс выходил с кодом 0,
и `produces_status` применялся, хотя фаза не была выполнена (инцидент VL-219 —
Done выставлен при незавершённом merge и необновлённой документации). Теперь
у `backlog_finish_phase` есть булев флаг `aborted`: tool пишет его в
transient-кэш (`.vibelog/phase-in-progress.json`, межпроцессный носитель —
MCP-сервер и оркестратор это разные процессы, `markPhaseAborted`), а
`finalizePhaseStatus` при наличии флага игнорирует `exitCode 0` и уходит в
fail-ветку: статус возвращается к статусу до фазы (`prevStatus`) и в задачу
пишется машинный комментарий-причина. Флаг ставится только явно — fallback по
финальному тексту/`logTail` («не завершена», «прервана») остаётся диагностикой
и критерием НЕ является. Передача `status` вместе с `aborted` оставляет
приоритет за явным действием агента (поведение VL-196). Флаг без записи в
кэше (служебная фаза) — no-op с пометкой в сводке `aborted: фаза вне
транзиента`, без ошибки.

**Терминальный статус при непройденных DoD (VL-248).** Закрывать задачу в
терминальный статус (Done/Rejected) при невыполненных пунктах DoD нельзя без
явного согласия: инциденты VL-212/VL-219 — задача уходила в Done с отмеченным
DoD «Тесты проходят» при красном полном прогоне. Терминальность считается по
workflow задачи (`isTerminalStatus`), без хардкода имён статусов. Если `status`
запрошен терминальным и в эффективном списке DoD (с учётом `dodChecks` этого же
вызова) остаются неотмеченные пункты, `backlog_finish_phase` бросает ошибку
(`isError: true`) **до любых записей**: файл задачи, комментарий и usage не
трогаются, статус гарантированно не меняется. В тексте ошибки — номера
невыполненных пунктов и два пути: непустой `dodOverride` с причиной (если задача
честно закрывается с остатком) либо `aborted: true` без `status` (если работа не
завершена). При переданном `dodOverride` статус ставится, причина уходит строкой
`DoD override: …` в комментарий-отчёт фазы, а в сводке появляется предупреждение
`терминальный статус при непройденных DoD: #2 (override: <причина>)`.
Предупреждение выводится для любого итогового терминального статуса с
непройденными DoD — в том числе когда `status` не передан, а задача уже закрыта
(жёсткое требование override при этом не применяется: комментарий к закрытой
задаче не блокируется). `dodOverride` не объявлен в `required` схемы —
обязательность условная, её несёт ошибка с именем поля.

**`requests` — это LLM-запросы (ходы модели), НЕ tool-calls (VL-221):**
лимит `--max-tool-calls` считает tool-calls текущего рана (счётчик
сбрасывается при resume) — разные независимые счётчики; в диагностике
фазы они выводятся рядом (`запросов=N`, `tool-calls=M/лимит`).

Стоимость — только в аналитике: `calculateCost(usage, pricing)`, тарифы —
`pricing` активной модели в секции `models.available`
`.vibelog/settings.json` (VL-209, см. `getActiveModelPricing`); для конфигов
до VL-209 поддерживается legacy-секция `pricing` (модель → тариф):

```json
{
  "pricing": {
    "mimo-v2.6-pro": { "input_per_1m": 1.2, "output_per_1m": 6, "cache_per_1m": 0.3 }
  }
}
```

`reasoning_tokens` хранится отдельно (из `completion_tokens_details`, ref-19) —
для аналитики, не вычитается из output. Запросы LLM несут заголовок
`X-Session-Id` (ref-18) — группировка сессии на дашборде RouterAI.

## Модели и провайдеры (VL-209)

Реестр LLM-моделей и провайдеров — секции `providers`/`models` в
`.vibelog/settings.json`. Переключение модели — CLI, ботом или вебом,
без правки `.env`. Без секции `models` всё работает как раньше
(env `VIBELOG_LLM_*`, полный fallback).

```json
{
  "providers": {
    "routerai": { "base_url": "https://routerai.ru/api/v1", "api_key_env": "ROUTERAI_API_KEY" },
    "cloudru": { "base_url": "https://foundation-models.api.cloud.ru/v1", "api_key_env": "CLOUDRU_API_KEY" }
  },
  "models": {
    "default": "routerai/xiaomi/mimo-v2.6-pro",
    "available": {
      "routerai/xiaomi/mimo-v2.6-pro": {
        "label": "MiMo v2.6 Pro",
        "provider": "routerai",
        "model": "xiaomi/mimo-v2.6-pro",
        "api_mode": "chat",
        "pricing": { "input_per_1m": 1.2, "output_per_1m": 6, "cache_per_1m": 0.3 }
      }
    }
  }
}
```

- **id модели** — строка `provider/model`; **provider** — ссылка на
  `providers[<id>]`; **model** — wire-имя у провайдера;
- **api_mode** — `chat` | `responses` (VL-205); флаг `--api-mode` остаётся
  приоритетным разовым переопределением;
- **api_key_env** — имя переменной с ключом (не сам ключ): читается из
  env → `.env` → env-секции settings.json (приоритет VL-143). `api_key`
  напрямую — fallback для не-секретных случаев, не рекомендуется;
- **pricing** — тарифы для billing (секция выше);
- валидация при старте фазы: `model.provider` обязан существовать в
  `providers`, `api_key_env` — быть заданным; иначе понятная ошибка в
  stderr (→ logTail). В stderr фазы пишется лог
  `Модель: <label> (<id>), api_mode: <chat|responses>`.

Способы переключения:

```bash
vibelog model list       # список с маркером * у активной
vibelog model use <id>   # переключить models.default
vibelog model current    # активная модель
vibelog provider list    # base_url + статус ключа (значения не выводятся)
```

Бот: `/model` — список, `/set model <id>` — переключение.
Веб: `#/settings` — селект активной модели; в чате (`#/chat`) — переключатель
в сайдбаре тредов (переопределение для чата, default не меняется).

### Модель фиксируется на сессии (VL-239)

Смена `models.default` больше не подменяет модель «на середине» задачи: сессия
запоминает модель, с которой начата, и resume-ран идёт на ней.

- **Запись**: при создании задачной сессии CLI пишет в мету `model_id`,
  `model_provider`, `model_name`, `api_mode` — до первого LLM-запроса.
- **Идентичность модели** — пара `provider` + wire-имя `model` (стабильна при
  переименовании id); id из `available` — подпись. Резолв при resume сначала
  пробует `model_id`, затем ищет по паре provider+model (модель переименовали —
  нашли), и только потом уходит на активную.
- **Приоритет резолва**: `--model <id>` → `--model-follow-settings`
  (взять активную из settings) → модель сессии → активная модель → env
  (`VIBELOG_LLM_MODEL`, для конфигов без секции `models`).
- **Флаги** (разовое переопределение):
  `vibelog agent --model <id> …` — продолжить на указанной модели;
  `vibelog agent --model-follow-settings …` — осознанно перейти на активную.
  Вместе несовместимы (exit 1).
- **`api_mode`** берётся из меты сессии приоритетнее конфига; флаг `--api-mode`
  остаётся выше всех.
- **Лог старта фазы** печатает фактическую модель и источник:
  `Модель: <label> (<id>), api_mode: chat — из сессии` (`— из настроек`,
  `— из env`, `явный --model`).
- **Расхождение** меты и активной модели даёт предупреждение в stderr
  (→ `logTail` оркестратора) с обеими моделями, применённой и подсказкой
  по флагам переопределения.
- **Fail-open**: мета без model-полей (старые сессии), удалённая модель или
  провайдер, отсутствующий ключ — фаза не падает: применяется активная/env-модель
  с предупреждением.
- **Ограничение**: мета пишется только для задачных сессий (фаза + задача).
  Сессии `/prompt` и TUI-чат (`vibelog agent` без фазы) меты не создают, поэтому
  продолжаются на активной модели, как раньше.
- **Billing не менялся**: запись журнала хранит `model` фактической модели рана,
  тариф считается по факту; разные тарифы у ранов одной задачи — ожидаемо.

## /auto — автоочередь фаз

Telegram-бот умеет последовательно прогонять фазы задач из очереди
`.vibelog/auto-queue.json` (`/auto add <VL-N>…`, `/auto start|stop|status`;
подробности — в [руководстве пользователя](backlog/docs/doc-6-Руководство-пользователя-Vibelogmd.md)).

Статусы элемента очереди: `pending`, `running`, `done`, `failed`,
**`failed_permanent`** — провал с исчерпанными ретраями (`attempts >
max_retries`). Такой элемент терминален:

- ретраев больше не будет, а причина провала лежит в `fail_reason` и видна
  в `/auto status` (`VL-9 — failed_permanent, причина: …`);
- в stderr бота пишется строка
  `[auto VL-228] VL-9 → failed_permanent: фаза code, попыток 2 из 1, причина: …; сессия: <sessionId>`
  — по ссылке на сессию видно, где искать контекст агента;
- следующий цикл очереди его не трогает и не выбирает (`pending`-задачей он
  не считается), `/auto add` **не реанимирует** такой элемент автоматически.
  Ручная реанимация — удалить запись из `.vibelog/auto-queue.json` и добавить
  задачу заново (`/auto add VL-N`) — новый элемент создаётся с `attempts: 0`.

Застрявшие элементы старых очередей (`failed` при `attempts > max_retries`)
мигрируются в `failed_permanent` автоматически при ближайшем `sweep`
(перед выбором следующей задачи), с заполнением причины.
