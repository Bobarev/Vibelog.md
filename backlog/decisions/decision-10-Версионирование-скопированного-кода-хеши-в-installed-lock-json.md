## Context

При модели «код компонента копируется в проект» (decision-7) встаёт вопрос обновлений. У shadcn встроенного версионирования нет: CLI не записывает установленную версию, автоматического обновления не существует, люди выкручиваются через `npx shadcn diff`, ручной `git merge-file` или сторонние инструменты, которые пишут версию и хеш файла в свой конфиг.

Для Vibelog.md сложность усиливается принципом zero human code: файл компонента регулярно правит агент, и система должна отличать «это наш исходник» от «это локальная правка».

## Decision

1. Lock-файл установки — `.vibelog/installed.lock.json` (имя обосновано в decision-9): фиксирует точное состояние установленного, а не «опись пакета».
2. При каждой установке `vb install` пишет в него для каждого компонента и каждого файла: `version` (версия компонента на момент установки), `hash` (`sha256:` содержимого записанного файла), `sourceVersion` (версия в реестре), `installedAt`.
3. В lock-файл пишется `schemaVersion`, чтобы `vb update` мог читать файлы старых схем без ломающих изменений.
4. Версии — простые (`1.0.0`, `1.0.1`), без `^` и `~`. Никакой семантики транзитивных зависимостей: компонент — это код, а не библиотека.
5. `vb update` (следующий этап) работает детерминированно:
   - хеш файла в проекте **совпадает** с хешем в lock-файле → файл не менялся → безопасная перезапись новой версией;
   - хеш **не совпадает** → файл правился человеком или агентом → не перезаписывать: показать diff и спросить (в `--yes`-режиме — пропустить).
6. Хеш может обновлять агент после собственной правки файла — тогда система знает, что это осознанная локальная модификация, а не расхождение.
7. Lock-файл хранится в git вместе с проектом. Запись — атомарная: сначала файлы компонента во временном каталоге, затем lock-файл; частичный сбой откатывается целиком.
8. Lock-файл — коллектор данных с первого дня: версии и хеши пишутся уже сейчас, даже пока `vb update` не реализован.

## Consequences

- Детерминированное управление версиями без npm-семантики: отслеживается не «пакет версии X», а «этот файл, скопированный из версии X, с тех пор не менялся».
- Локальные правки агента никогда не затираются молча — главный риск zero human code закрыт.
- Цена: обновление не автоматическое, требуется явный вызов `vb update` и решение по конфликтным файлам.
- Цена: lock-файл надо держать в git, иначе история правок теряется между машинами.
- Ограничение: хеш ловит факт изменения, но не его смысл — содержательный мерж остаётся за агентом/человеком.

## Alternatives

- **npm-семантика версий (`^`/`~`)** — не применима: нет пакета, нет транзитивных зависимостей, диапазоны создают иллюзию автоматического обновления.
- **Только `npx shadcn diff` без lock-файла** — не знает, что именно было установлено, поэтому diff сравнивает с последней версией реестра, а не с установленной; ручной мерж каждый раз.
- **Без версионирования (перезапись при каждом install)** — просто, но гарантированно уничтожает правки агента.
- **Отдельный git-репозиторий/сабмодуль для скопированного кода** — лишняя механика для набора небольших файлов.
- **Имя `manifest.json`** — смешивается с `registry.json` реестра и с описями пакетов; `installed.lock.json` точнее.
