## Context

Инфраструктура Vibelog.md требует трёх разных сценариев: создать новый проект с нуля, подключить Vibelog.md к уже существующему проекту, доставить в проект код компонента. Рассматривалось: одна команда с флагами (`vb new --init --install button`), две команды (init внутри install), три отдельные команды.

Отдельный вопрос — где хранить служебные файлы. В shadcn это `components.json` в корне проекта; в Vibelog.md уже есть каталог `.vibelog/` (его создаёт `vb init`).

## Decision

1. **Три команды, три обязанности:**
   - `vb create myapp --template vibelog.md/templates/svelte-minimal` — «создать проект»: клонирует шаблон, ставит зависимости, выполняет `postCreate` (включая `vb init`), опционально ставит компоненты из `vibelog.components`.
   - `vb init` — «интегрировать Vibelog.md в существующий проект»: создаёт `.vibelog/` с `config.json` и `installed.lock.json`, прописывает псевдонимы путей, запись реестра `vibelog.md` (owner `Vibelog-md`, ветка `main`), путь к lock-файлу, базовые CSS-переменные темы. **`vb init` не знает про стек проекта:** он работает с любым репозиторием, включая не-Svelte, и ничего не проверяет про Tailwind или другие пакеты.
   - `vb install vibelog.md/ui/button` — «доставить код компонента»: скачивает JSON, доставляет зависимости, раскладывает файлы, пишет хеши в lock-файл.
2. `vb init` **не является** частью `vb install`. `vb install` предполагает существующий `.vibelog/` и при его отсутствии подсказывает выполнить `vb init` (а не создаёт каталог молча).
3. **Все служебные файлы — внутри `.vibelog/`:** `config.json` (настройки проекта) и `installed.lock.json` (точное состояние установленного: версии и хеши). Корень проекта остаётся чистым: там только файлы самого проекта (`package.json`, `svelte.config.js` и т.п.). `vb install` не создаёт файлов в корне.
4. Имя lock-файла — `installed.lock.json`, а не `manifest.json`: «manifest» — это опись содержимого пакета (как `registry.json` реестра), а здесь фиксируется состояние установки. `installed` отвечает на «что», `lock` — на «версии и хеши».
5. Файлы компонентов кладутся по путям, вычисленным из псевдонимов в `config.json` (см. decision-7).
6. Команды `vb` вызываются без слова `package`: `install` уже подразумевает установку.
7. `vb` — тот же бинарь, что `vibelog` (алиас); команды добавляются в существующий CLI, отдельного пакета не появляется.
8. **Проверка зависимостей — только по декларации в JSON реестра.** Элемент реестра объявляет `dependencies` (npm-пакеты) и `registryDependencies` (элементы реестра); `vb install` сверяет их с проектом и предлагает доустановить отсутствующие. CLI не содержит списка «известных» пакетов: Tailwind, `clsx`, `bits-ui` — такие же записи в `dependencies`, как и любые другие. Компонент без внешних зависимостей (хук, утилита) объявляет пустой список.

## Consequences

- Каждая команда предсказуема и объяснима одной фразой — критично и для агента, и для новых пользователей.
- `vb init` остаётся универсальным: он не ломается и не предупреждает зря в проектах без Tailwind (сам Vibelog.md, бэкенды, любые репозитории).
- Новая зависимость у компонента не требует релиза CLI — меняется только JSON в реестре.
- `vb install` не делает «магии» с инициализацией: неожиданного появления `.vibelog/` или правок корня не происходит.
- Чистый корень упрощает diff и снижает риск конфликта с файлами проекта.
- Имя `installed.lock.json` не путается с `registry.json` реестра и с `package-lock.json` проекта.
- Цена: два шага вместо одного для нового проекта — снимается тем, что `vb create` сам вызывает `vb init` через `postCreate`.
- Цена: `vb install` не инициализирует, поэтому сценарий «поставил компонент в неинициализированный проект» завершается понятной ошибкой (код 2), а не автопочинкой.
- Цена: корректность проверки зависимостей целиком зависит от качества JSON реестра — нужна валидация схемы при сборке `public/r/*.json`.

## Alternatives

- **Одна команда с флагами** — меньше запоминать, но смешивает три разных предусловия и делает поведение непредсказуемым для агента.
- **`init` внутри `install`** — короче для пользователя, но install становится частичной инициализацией с побочными эффектами, которых пользователь не просил.
- **`components.json` в корне (как в shadcn)** — привычно знатокам shadcn, но засоряет корень и расходится с существующим `.vibelog/`.
- **`manifest.json` для lock-файла** — семантика не та и путается с `registry.json`; `installed.json` не намекает на хеши и неизменность.
- **Захардкоженная проверка конкретных пакетов в CLI** — превращает общий установщик в набор частных случаев и требует релиза CLI при каждой новой зависимости.
- **Отдельный пакет/бинарь для `vb`** — дублирование инфраструктуры и лишняя публикация; `vb` уже алиас `vibelog`.
