## Context

Для Vibelog.md нужны тестовые проекты, которые одновременно работают в реальной эксплуатации. Первый кейс — UI Kit для мессенджера MAX Mini App на Svelte. Ключевые принципы продукта: zero human code (код пишет агент, человек ставит задачи и проверяет результат) и AI-first (решения оцениваются по тому, насколько агенту дёшево и предсказуемо с этим работать).

Состояние на момент решения: React-версия Vibelog.md (React + shadcn) уже существует и работает, но тормозит на мобильных. Обучающих данных по Svelte у LLM меньше (загрузки npm ~в 30 раз ниже, чем у React). Для стилей рассматривались Tailwind CSS и UnoCSS.

## Decision

1. **Фронтенд: Svelte 5 с Runes + SvelteKit.** React-проект не удаляется и служит эталоном дизайна для параллельной сборки.
2. **Стили: Tailwind CSS.** UnoCSS не используется, смешение двух систем классов запрещено.
3. Недостаток обучающих данных по Svelte компенсируется строгими правилами для агента: файл правил (`CLAUDE.md` / `.cursorrules`) в каждом шаблоне с явным указанием «только Svelte 5 Runes» (запрет `export let`, `$:`, `on:click`, `<slot>`, `createEventDispatcher`, `svelte:component`) и «стилизация только Tailwind, без кастомного CSS».
4. В шаблоны включается опция `ai-tools` из `sv create`: MCP-сервер, skills и sub-agents, чтобы агент опирался на актуальные практики Svelte, а не на устаревший синтаксис Svelte 4.
5. **Единственный механизм проверки внешних зависимостей — объявленный список в JSON реестра.** Каждый элемент реестра (корневой пакет `vibelog.md/ui`, компонент, хук, утилита) декларирует свои зависимости полями `dependencies` (npm-пакеты) и `registryDependencies` (элементы реестра). `vb install` читает эти поля и проверяет/предлагает доустановить отсутствующее. Захардкоженных проверок конкретных пакетов в CLI нет — Tailwind, `clsx`, `tailwind-merge`, `bits-ui` для CLI неотличимы от любого другого пакета из `dependencies`. Компонент без зависимостей (например, хук) объявляет `dependencies: []`, и проверять нечего.
6. **`vb init` не проверяет стек проекта вообще:** он универсален и работает с любым репозиторием, включая не-Svelte.

Обоснование по Svelte: до 40% меньше строк кода на ту же функциональность → меньше токенов на генерацию и проверку; эксперименты показывают, что с явным указанием «только Svelte 5 Runes» агент выдаёт код не хуже, а иногда идиоматичнее React-версии.

Обоснование по Tailwind: стандарт де-факто для LLM (v0, Cursor, Claude Artifacts выдают Tailwind), классы известны модели наизусть, не нужно объяснять конфигурацию — экономия токенов; UnoCSS требует настройки правил и пресетов и создаёт риск галлюцинаций. Экосистема Svelte-компонентов (shadcn-svelte, Sivir UI) построена на Tailwind — упрощается адаптация чужого кода.

## Consequences

- Меньше объёма кода и дешевле генерация; выше риск устаревшего синтаксиса Svelte 4 — закрывается файлом правил и ai-tools.
- Поддержка двух фронтендов (React как эталон + Svelte как целевой) — параллельная двойная работа по UI.
- Если «тормоза» React-версии вызваны конкретным тяжёлым компонентом, а не фреймворком, выигрыш от Svelte будет меньше ожидаемого — проверяется первым же прототипом.
- Zero dependency трактуется как **zero runtime dependency**: зависимости, объявленные в реестре, ставятся обычным пакетным менеджером и фиксируются в `.vibelog/installed.lock.json`; сам CLI `vb` от них не зависит.
- Добавление нового требования (новая версия Tailwind, новый рантайм-пакет) не требует правки CLI — только JSON реестра.

## Alternatives

- **Остаться на React + shadcn** — не требует переписывания, но сохраняет мобильные тормоза и не решает задачу тестового проекта под Svelte.
- **React как целевой стек, Svelte только как эксперимент** — не даёт проверить кейс MAX Mini App на Svelte и не проверяет агента на менее знакомом стеке.
- **UnoCSS** — меньше токенов конфигурации, но меньше обучающих данных, риск смешения синтаксиса и слабая совместимость с готовыми Svelte-компонентами.
- **Захардкоженная в CLI проверка Tailwind** — частность, протащенная в общий инструмент: ломается на компонентах без стилей (хуки, утилиты) и требует релиза CLI при каждой новой зависимости.
- **Проверка зависимостей в `vb init`** — неверное место: `vb init` работает с любым репозиторием и не знает, что в него будут ставить.
