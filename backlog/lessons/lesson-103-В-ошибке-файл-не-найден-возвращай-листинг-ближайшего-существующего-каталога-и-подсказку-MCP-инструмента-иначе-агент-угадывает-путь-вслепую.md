## Проблема

`read_file` на несуществующем пути отвечал одной строкой `Файл не найден: <абс. путь>`. Агент веб-чата трижды подряд угадывал путь к задаче, перебирая каталоги хранения (сначала с файлом задачи, затем `active`, затем корень `backlog`), потому что вывод не сообщал ни структуру каталогов, ни то, что задачи вообще читаются через MCP. В паре с отсутствием дедупа вызовов это дало десятки холостых вызовов.

## Решение

Ошибка об отсутствии пути должна быть самодостаточной: поднимаемся до ближайшего существующего родительского каталога, печатаем его листинг (переиспользуя уже готовый форматтер с лимитом), добавляем секцию «Возможно, вы имели в виду:» с fuzzy-кандидатами (по stem без регистра/расширения, до 5) и для путей вида `VL-\d+` — явную инструкцию «используй MCP backlog_view_task {"id": …}». Одну функцию подсказки вызывают все поверхности (CLI-агент, веб-чат, search_files/grep_search), текст ошибки для «путь вне проекта» не меняется, первая строка исходной ошибки остаётся первой (существующие ассерты).

## Пример

```
Файл не найден: <абс. путь>/backlog/tasks/VL-254.md

Ближайший существующий каталог: backlog/tasks/
  200 файлов, каталоги с "/"
Возможно, вы имели в виду:
  backlog/tasks/VL-254 - <заголовок задачи>.md
Подсказка: задачи Vibelog хранятся не по этому пути — используй MCP-инструмент backlog_view_task {"id":"VL-254"}.
```

> Уточнено при санитарном проходе (VL-281): из текста убраны заведомо неверные варианты пути, которые агент перебирал, — аудит читал их как ссылки на несуществующие файлы.
