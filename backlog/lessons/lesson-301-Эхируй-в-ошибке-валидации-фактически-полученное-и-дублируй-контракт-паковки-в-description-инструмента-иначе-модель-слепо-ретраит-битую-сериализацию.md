## Проблема
В тредах веб-чата агенты получали на ask_user ошибку «поле question обязателен», хотя слали непустой аргумент: options приходило строкой (двойное кодирование — внутри строки лежал question, поле question могло отсутствовать вовсе), либо модель упаковывала два вопроса в один вызов и сериализация склеивалась в битый JSON, который parseToolArguments возвращал как {__raw}. Текст ошибки противоречил тому, что реально отправлено, и не называл ни фактический тип, ни полученное значение — модель слепо повторяла ту же битую сериализацию 10–11 раз подряд и в итоге уходила спрашивать текстом. Контракт «один вопрос = один вызов» жил только в комментарии кода, а формат options — только в описании свойства схемы, которое модель игнорирует при паковке аргументов.

## Решение
parseAskUserArgs различает три кейса, и в каждом называет фактически полученное через хелпер describeReceived: (б) аргументы не разобраны ('__raw' in raw) — эхо сырья первыми ~200 символами плюс ожидаемый формат; (в′) options — строка — эхо строки и «массив объектов, а не JSON-строка», проверка ДО проверки question (строка содержит question, поле может отсутствовать); (а) question пуст — фактический тип/значение. Контракт паковки продублирован там, где модель его читает: в description makeAskUserTool («один вызов — ровно один вопрос, серия — очередью вызовов», «options — массив [{id,label}], а не JSON-строка») и в системном промпте чата.

## Пример
Модель послала {"question_":"Какой язык выбрать?","options":"[{\"id\":\"a\",\"label\":\"TS\"}]"} — options уехал строкой, поле question отсутствовало; старый текст «поле question обязательно» противоречил отправленному и вызов повторялся 10–11 раз подряд. Новый текст: «options пришло строкой: …первые 200 символов…; options — массив объектов, а не JSON-строка; один вызов = один вопрос» — модель корректируется со второго шага.
