## Проблема

Санитарный проход по корпусу lessons (153 файла) провалился на лимите tool-calls: исследование «какой урок ещё верен» съело 100 вызовов, и фаза не дошла до правок. Причина — попытка прочитать/проверить десятки уроков по одному и повторные `grep` по корпусу с одними и теми же паттернами; при этом изменение n файлов через MCP — по одному вызову на урок.

## Решение

Планируй такой проход как конвейер с фиксированным бюджетом вызовов, а не как чтение корпуса:

1. **Один механический скан** — `lesson audit --write` (read-only + AUDIT.md) вместо ручного чтения: он сразу даёт полный список кандидатов (дубли, битые пути, висячие ссылки) с similarity/path-деталями.
2. **Проверяй урок только по своему кандидатскому признаку**: битый путь — `pathExists`-сканом или одним `ls`; дубль — сравнение тел двух уроков (`lesson_view` ×2), не всего блока.
3. **Своди дубли цепочкой вызовов `lesson_supersede` + один `lesson_update` на впитывание фактов** — не переписывай оба урока по отдельности.
4. **Разбивай на раны по темам** (tags): 150 уроков на один ран не влезают ни в контекст, ни в лимит вызовов.

## Пример

VL-281: 100 вызовов ушли на скан и анализ; провал фазы. Второй ран сделал тот же объём (пары дублей, два `outdated`, техдолг-задача, гайд) за счёт того, что начал с audit + списка кандидатов и правил только их.
