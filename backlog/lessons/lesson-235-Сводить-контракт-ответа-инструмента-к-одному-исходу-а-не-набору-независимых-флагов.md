## Проблема

За две недели закрыто 14 задач одного класса: агентская фаза падала кодом 1, потому что модель дословно повторяла write-вызов. Корни — три: (1) четыре независимых детектора повторов с разными порогами и словарями директив (loop.ts, repeat-tracker.ts, web/tool-dedup.ts, капы оркестратора); (2) классификация инструмента по токенам имени (`manage` → write) — отсюда ложное «уже применено» на `backlog_manage_dod {action:'list'}` (VL-351); (3) ответ инструмента = набор независимых флагов `ok/noop/denied/read/missing/hint/retryWith`, которые комбинируются свободно — «применили часть, но ответ выглядит как отказ» (VL-355), «создали сущность, но ответ выглядит как ошибка» (VL-356).

## Решение

Протокол с ОДНИМ исходом. `outcome: 'applied'|'partial'|'noop'|'rejected'|'read'|'unknown'` объявляется инструментом; совместимые флаги (`ok`, `noop`, `denied`, `read`) — вычисляемые геттеры при сериализации, старые тексты `message` не меняются. Вид операции (`read|write|mixed`) объявлен таблицей рядом с реестром, а не выводится из имени; `mixed` разрешается по аргументам (`action:'list'` → read). Пороги и директивы повторов — один объект `REPEAT_LIMITS` в `repeat-tracker.ts`, остальные слои читают его. Исчерпание капа повторов вызывает `fail()` только при недостигнутой цели: успешная правка файла/коммит/отчёт делают завершение штатным.

## Пример

`lesson_create {title:'x'}` без тела возвращает `{outcome:'partial', ok:true, missing:[{field:'content'}], hint:'…'}` — урок СОЗДАН, модель получает следующий шаг, петли нет. Инвариант закреплён тестом, обходящим `listTools()`: новый write-инструмент с жёстким отказом на отсутствие необязательного по смыслу поля валит сборку.
