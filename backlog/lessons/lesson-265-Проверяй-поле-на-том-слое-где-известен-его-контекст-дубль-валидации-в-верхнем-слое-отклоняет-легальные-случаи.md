## Проблема
Одно правило валидации было продублировано в двух слоях, и верхний слой рубил легальный случай: в валидации формы `target` безусловно отклонялся при наличии `..`, хотя легальность перехода вверх зависит от типа алиаса, который на этом слое ещё неизвестен. Дефект не поймали тесты — покрытия на легальный `..` не было.

## Решение
Проверяй поле только на том слое, где есть контекст для решения: форма (типы, непустота, абсолютность) не знает про семантику путей, а единственное место проверки переходов вверх — вычислитель путей, где известен алиас и есть финальная проверка «внутри корня проекта». При переносе правила между слоями сразу добавляй тесты на легальный и нелегальный случаи — именно их отсутствие дало дефект.

## Пример
VL-383: `validateRegistryItem` (registry-fetch) отклонял `target`, содержащий `..`, а `resolveAliasPath` (components-config) корректно считал `../utils.ts` → `src/lib/utils.ts`, потому что база — `dirname(aliases.utils)`. Из-за дубля `vb install vibelog.md/ui/base` не мог установить корневой элемент. Решение: из формы убрана проверка `..`, в `resolveAliasPath` правило разделено по типу алиаса (файл — ровно один уровень вверх и имя файла; каталог — запрещено), финальная проверка «внутри корня проекта» осталась одна.
