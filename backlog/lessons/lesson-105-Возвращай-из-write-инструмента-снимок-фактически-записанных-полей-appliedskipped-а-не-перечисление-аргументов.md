## Проблема

Write-инструмент MCP отвечал текстом («Задача X обновлена: title, type»), состав применённого вычислялся из **переданных** аргументов, а не из фактически записанных полей. При отказе подтверждения агент не мог отличить «применилось всё» от «применилось частично» и не знал, какие поля записались (инцидент VL-254).

## Решение

1. Ответ write-инструмента — JSON-снимок `{ok, message, applied, skipped}`, где `applied` берётся из объекта ПОСЛЕ записи (значения читаются из файла/модели), а `skipped` перечисляет переданные ключи вне известного набора полей — раньше они молча игнорировались и это был главный источник «частичности» без единого отказа.
2. Подстроки прежних формулировок («создана», «обновлена») сохраняются в поле `message` — тогда переход на JSON не ломает существующие substring-проверки в тестах и промптах.
3. Отказ кодируется машиночитаемо: `{ok:false, denied:true, reason:'denied'|'not_confirmed', applied:{}, skipped}` — явный отказ пользователя и «подтверждение не получено» требуют разных действий агента (повтор безопасен только во втором случае).
4. Идемпотентность — отдельный модуль с файлом-кэшем по ключу `<tool>:<idempotencyKey>` (TTL + кап, fail-open при битом JSON): повтор write-вызова не дублирует эффект.

## Пример

```ts
const task = updateTaskFile(cwd, id, updates);          // единственная запись
const applied = {};                                      // значения — из task, не из updates
for (const key of Object.keys(updates)) applied[key] = task[key];
return ackOk(`Задача ${task.id} обновлена: ${keys}`, applied, unknownFields(args, KNOWN));
```

Атомарность в ядре уже была (один `writeFileSync`), защищать надо было **контракт ответа** — переписывать слой хранения не потребовалось.
