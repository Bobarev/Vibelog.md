## Description
<!-- SECTION:DESCRIPTION:BEGIN -->
Шестая задача реализации doc-25 (v1.3, §4.3 шаги 5–6). Расширяет ядро `vb install` (VL-337) двумя механизмами: проверкой npm-зависимостей и разрешением `registryDependencies`.

**Зависимость:** VL-337 (ядро `install` — план, конфликты, атомарная запись, lock). Задача расширяет `src/core/install.ts`, не переписывая его.

**Что добавляется:**

1. **`dependencies`** — элемент реестра объявляет npm-пакеты (`["clsx", "tailwind-merge"]`). Команда сверяет их с `package.json` проекта и предлагает доустановить отсутствующие. Пакетный менеджер определяется по lock-файлу проекта.

2. **`registryDependencies`** — элемент ссылается на другие элементы (`["vibelog.md/ui/base"]`). Отсутствующие в `installed.lock.json` устанавливаются **до** самого элемента, на **один уровень** вглубь (их собственные зависимости не разрешаются — явное ограничение v1, doc-25 §1.2).

**Почему один уровень.** Полное рекурсивное разрешение требует обхода графа с обнаружением циклов и топологической сортировкой. Для первой версии (4 компонента, все зависят от `base`) это избыточно. Ограничение задокументировано в doc-25 §1.2 и должно выводиться предупреждением, если у зависимости есть свои `registryDependencies`.

**Правило владения файлами.** `base` содержит `utils.ts`, на который ссылаются все компоненты. Если два элемента объявят один файл, lock не должен получить двух владельцев: совпадающий хеш — переиспользование, расхождение — конфликт.

**Границы.** Задача не реализует `vb create` (задача 7) и не делает рекурсивное разрешение зависимостей. Не устанавливает пакеты без подтверждения пользователя.

**Связанные решения:** doc-25 §3.3 (`dependencies`, `registryDependencies`), §4.3 шаги 5–6, §1.2 (один уровень), §3.2 (владение файлами); decision-9 п.8 (проверка только по декларации в JSON реестра, CLI не содержит списка известных пакетов).

## Implementation Plan
<!-- SECTION:PLAN:BEGIN -->
**Файлы.** `src/core/install-deps.ts` (новый: сверка npm-зависимостей, определение пакетного менеджера), `src/core/install-registry-deps.ts` (новый: разрешение `registryDependencies`), правки `src/core/install.ts` (встраивание в поток), `src/cli/commands/install.ts` (флаги и вывод), тесты `src/core/install-deps.test.mjs`, `src/core/install-registry-deps.test.mjs`.

**Шаг 1. Определение пакетного менеджера.**

1. `detectPackageManager(cwd): 'pnpm' | 'npm' | 'bun' | 'yarn'` — по наличию lock-файла в корне: `pnpm-lock.yaml` → pnpm, `package-lock.json` → npm, `bun.lockb`/`bun.lock` → bun, `yarn.lock` → yarn; несколько — приоритет pnpm → bun → yarn → npm; ни одного → npm.
2. `installCommand(pm, packages): string[]` — `pnpm add <pkgs>`, `npm install <pkgs>`, `bun add <pkgs>`, `yarn add <pkgs>`. Возвращать массив аргументов (не строку) — запуск через `spawnSync` без shell, как в `core/git.ts`.

**Шаг 2. Сверка `dependencies`.**

3. `readProjectDeps(cwd): Set<string>` — объединение ключей `dependencies` и `devDependencies` из `package.json`. Нет `package.json` → пустое множество (не ошибка: `vb init` не требует стека, decision-9).
4. `missingDeps(item, projectDeps): string[]` — `item.dependencies` минус `projectDeps`. Сохранять порядок объявления из элемента (детерминированный вывод).
5. `--dry-run` → в план добавляется секция «зависимости: отсутствуют N, команда `<pm> add ...`», ничего не выполняется.

**Шаг 3. Установка зависимостей.**

6. Интерактив: `p.confirm` «Установить отсутствующие пакеты (N)?» с `initialValue: true`; при отказе — предупреждение, установка файлов продолжается.
7. `--yes` без `--force`-подобного флага: **не устанавливать**, вывести предупреждение со списком и готовой командой. Причина: `--yes` означает «без вопросов», а не «делай что хочешь с package.json» — молчаливая правка зависимостей проекта недопустима.
8. Запуск: `spawnSync(pm, args, { cwd, stdio: 'inherit' })`; ненулевой код → предупреждение (не ошибка установки файлов), в итог пишется «зависимости не установлены, компонент может не работать».
9. После успешной установки — перечитать `package.json` и записать в lock только **подтверждённо установленные** пакеты (doc-25 §3.2: `dependencies` — «объявленные элементом и подтверждённо установленные»).

**Шаг 4. Разрешение `registryDependencies`.**

10. `parseRegistryRef(ref): { alias, repo, name }` — три сегмента, иначе ошибка с указанием элемента-источника.
11. `resolveRegistryDeps(cwd, config, lock, item, depth = 0): InstallPlan[]` — для каждой ссылки:
    - если `lock.components[name]` существует → пропустить, при расхождении `version` с реестром вывести предупреждение (не переустанавливать);
    - иначе — скачать элемент (VL-335), построить план (VL-337), добавить в очередь;
    - **`depth >= 1` → не разрешать дальше**: если у зависимости есть свои `registryDependencies`, вывести предупреждение «зависимости второго уровня не разрешаются (v1)».
12. Цикл: множество посещённых имён в пределах вызова; повторное имя → предупреждение «циклическая ссылка A → B → A, второй уровень не разрешается», без рекурсии.
13. Порядок применения: сначала все планы зависимостей (в порядке объявления), затем план самого элемента. `base` окажется на месте до компонента.

**Шаг 5. Владение файлами.**

14. `checkFileOwnership(lock, item, plan): Conflict[]` — для каждого файла плана: если путь уже присутствует в `lock.components[<другой элемент>].files`:
    - хеши совпадают → `reuse` (файл не перезаписывается, запись остаётся у первого владельца, в lock родителя файл **не** дублируется);
    - хеши различаются → `conflict` с указанием обоих владельцев; разрешается по правилам VL-337 (`--force` / вопрос / пропуск).
15. В lock файл принадлежит ровно одному элементу: при `reuse` запись родителя не создаётся, но в итоговом выводе указывается «файл переиспользован из `<элемент>`».

**Шаг 6. Атомарность цепочки.**

16. Все планы (зависимости + элемент) применяются в одной транзакции: temp-каталог один, перемещения — после подготовки всех файлов всех планов, lock пишется один раз в конце.
17. Сбой при установке зависимости → ни один файл не перемещён, lock не изменён (тест: зависимость с недоступным целевым путём).

**Шаг 7. Вывод.**

18. Итоговый блок: установленные зависимости (пакеты), установленные элементы (в порядке применения), переиспользованные файлы, пропущенные с причиной, предупреждения о втором уровне и циклах.
19. Новый флаг не нужен: поведение управляется существующими `--yes`, `--force`, `--dry-run`.

**Шаг 8. Тесты.**

20. `detectPackageManager`: каждый lock-файл, несколько сразу (приоритет), ни одного.
21. `missingDeps`: все отсутствуют, часть есть, `package.json` без `dependencies`, `package.json` отсутствует.
22. `--yes` + отсутствующие зависимости → предупреждение, файлы установлены, `package.json` не изменён.
23. Интерактивное подтверждение → вызвана команда пакетного менеджера (мок `spawnSync`), lock содержит пакеты.
24. `registryDependencies`: отсутствующая зависимость устанавливается первой; уже установленная не переустанавливается; цикл A→B→A не зацикливается; второй уровень не разрешается с предупреждением.
25. Владение: два элемента с одинаковым файлом и совпадающим хешем → один владелец в lock; с разными хешами → конфликт.
26. Атомарность цепочки: сбой на зависимости → родительский элемент не установлен, lock не изменён.

**Риски.**
- `--yes` не устанавливает зависимости — это может удивить: пользователь ждёт «всё автоматически». Обоснование в описании (молчаливая правка `package.json` недопустима), но поведение нужно явно писать в итоговом блоке.
- `spawnSync` с `stdio: 'inherit'` в тестах неудобен — инъектировать функцию запуска (параметр `runner`), чтобы мокать без подмены `child_process`.
- Определение пакетного менеджера по lock-файлу ошибается, если lock есть, а менеджер не установлен — команда упадёт; ловить `ENOENT` и предлагать `npm` как fallback с предупреждением.
- Один temp-каталог на всю цепочку усложняет откат: при сбое нужно восстановить файлы всех планов, а не одного. Тест на атомарность должен покрывать именно цепочку.
- `registryDependencies` на элемент из другого репозитория (`vibelog.md/templates/x`) — в v1 запрещено; валидировать alias и выдавать понятную ошибку, а не пытаться скачать.

**Проверка.** `pnpm typecheck && pnpm test`; вручную — установка элемента с `registryDependencies` в чистом проекте (проверить порядок: `base` первым), повторный запуск (ничего не переустанавливается), `--yes` с отсутствующими зависимостями (предупреждение, файлы на месте).
