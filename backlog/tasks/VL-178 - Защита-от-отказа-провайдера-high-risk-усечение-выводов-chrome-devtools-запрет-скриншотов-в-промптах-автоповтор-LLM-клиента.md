## Проблема

В сессии agent-1792913208465 (VL-172) выпала ошибка провайдера LLM: **«The request was rejected because it was considered high risk»** (1 раз, запись #171). Непосредственно перед отказом в запрос ушли **два вывода `chrome_devtools__take_snapshot` по ~624 КБ каждый** (~1.25 МБ полезной нагрузки). Работа продолжилась только вручную через «Продолжить» (50% user-сообщений сессии — resume-прогоны).

Скриншоты (`take_screenshot`) как решение НЕ использовать — они тоже едят очень много токенов.

## Что сделать (все пункты разбора)

1. **Проверить обрезку выводов chrome-devtools MCP (связь: VL-110).** Убедиться, что трейт-кат/лимит длины tool-выводов реально применяется к `chrome_devtools__take_snapshot` — в транскрипте лежат два снапшота по 624 КБ целиком. Если лимит не покрывает MCP-инструменты — расширить (например, глобальный cap в LLM-клиенте или промпт-трейткат).
2. **Проверить компакшн на таких выводах (связь: VL-122).** Подтвердить, что гигантские снапшоты не выживают в истории сообщений между ходами после компакшн-логики.
3. **Обновить промпты фаз / AGENTS.md: вместо скриншотов и полных снапшотов — точечные инструменты.** Запретить `take_screenshot` в практике агента (дорого по токенам); рекомендовать:
   - `evaluate_script` — в контекст только нужный кусок данных из DOM;
   - `take_snapshot` с параметром `filePath` (снапшот на диск, в контекст — только подтверждение);
   - `take_screenshot` — не использовать вовсе.
4. **Автоповтор при отказе «high risk» в LLM-клиенте (связь: VL-83).** При ошибке «The request was rejected because it was considered high risk» (и аналогичных отказах провайдера) — автоматический повтор запроса с усечённой полезной нагрузки (выкинуть самые длинные tool-выводы/историю) вместо ручного «Продолжить». Обработать в логике resume-хендлеров оркестратора.
