## Контекст

Фаза Close VL-227 (`vb:agent-1793312743226`) длилась ~30 минут при лимите `max_wall_time: 2400` с. Содержательная работа — один `git merge --no-ff` и запись в CHANGELOG. Остальное — **три полных прогона тестов**:

1. `pnpm build && pnpm test` после merge → 29 падений;
2. `mv settings.json` + `vitest run --no-file-parallelism` (полный, последовательный) → 12 падений;
3. `pnpm test` без settings.json → зелёный.

Плюс диагностика между ними. Фаза Code той же задачи уже прогнала полный `pnpm test` (зелёный, 86 файлов) — и это дало ложное ощущение, что проверку можно не повторять.

## Важная поправка к первой формулировке задачи

Изначальный тезис «Close не дублирует полный прогон, гоняет только затронутое» **опасен** — так делать нельзя:

1. **Code проверял worktree, Close проверяет master после merge.** Ветка была зелёной до ветвления, master за это время получил чужие коммиты. Merge-интерференция ловится только прогоном на master.
2. **Мэппинг «модуль → тест» неполон**: есть интеграционные наборы на чужие модули (`src/cli/*.test.mjs` тестируют `core/`) и инвариант-тесты, читающие файлы репозитория (`src/web/phase-prompt.test.mjs` следит за `templates/` и `AGENTS.md`, инварианты VL-105/222/227).
3. **Параллельные worktree**: master после merge содержит код соседних задач — взаимовлияние ловится только полным прогоном (инцидент vl-233 + vl-227).

Дорого в VL-227 был не сам полный прогон, а **три** прогона поверх двух известных флаков (VL-240, VL-241).

## Скорректированная цель

Не «убрать полный прогон», а **не дублировать и не повторять** его: один обязательный полный прогон на master, дешёвый фильтр перед ним, жёсткий порядок при падениях.

## Предлагаемое правило для `templates/phases/phase-close.md`

После merge в главном репо:

1. **`pnpm build`** — обязательно.
2. **Точечный прогон как ранний фильтр**: тесты, затронутые `git diff --name-only <pre-merge>..HEAD` (модуль → соседний `*.test.mjs`; нет соответствия → весь каталог). Цель — быстро отсечь «слитый код нерабочий». Это НЕ замена шагу 3.
3. **Полный `pnpm test`** — обязателен (merge-интерференция, интеграционные и инвариант-тесты, соседние worktree).
4. **Запрет повторных полных прогонов**: упал → сначала классификация падений (сравнение с родительским коммитом — lesson-79; проверка параллельного `vitest` в других worktree — lesson-89), затем **максимум один** повторный прогон с зафиксированной в отчёте причиной.
5. **Единственное исключение из полного прогона**: diff merge не затрагивает `src/`, `templates/`, `package.json`, `tsconfig.json`, `vitest.config.mts` — чисто docs/backlog-правки. Пропуск фиксируется в отчётном комментарии с причиной.
