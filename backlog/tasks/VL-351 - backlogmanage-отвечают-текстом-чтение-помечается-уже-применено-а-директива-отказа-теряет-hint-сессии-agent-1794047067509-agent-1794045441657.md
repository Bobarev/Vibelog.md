## Description
<!-- SECTION:DESCRIPTION:BEGIN -->
## Контекст

Два инцидента одного класса: агентский цикл делает **ложное утверждение о состоянии** и модель крутится на повторах.

### Инцидент 1 — `agent-1794047067509` (Close VL-349)

```
backlog_finish_phase {acChecks:[9], dodChecks:[1,2,3], status:"Done"}  → успех
backlog_manage_dod {action:"list", id:"VL-349"}                        → «Вызов backlog_manage_dod уже применён ранее — повтор НЕ выполнен»
```

`backlog_manage_dod {action:"list"}` — чистое чтение, но получило директиву «уже применён». Причина: `isWriteOperation` (`src/core/tool-classify.ts`) классифицирует по имени, токен `manage` есть в `WRITE_MARKERS` → инструмент считается write; ответ `manageChecklist` — плоский текст (`1. ✓ Тесты проходят…`), не JSON; страховка VL-306 (`src/agent/loop.ts:1532`) считает не-JSON ответ write-инструмента «применённым» → сигнатура попадает в `appliedSignatures`.

### Инцидент 2 — `agent-1794045441657` (Close VL-346, третий ран после «Повторить»)

Фикс VL-349 работает: `lesson_update` без `content` при теле-скелете отдаёт `ackError` с `missing` и `hint`. Но модель повторила вызов 6 раз и упала по `MAX_ERROR_REPEATS_PER_RUN`. Директива loop detection пришла искалеченной:

```
Loop detection: lesson_update — предыдущий вызов отклонён: Тело урока lesson-232 не заполнено (пустое или дефолтный скелет)…# Решение\n\n…\n\n## Пример\n\n…"}.. Повтор даст тот же отказ — исправь аргументы.
```

`clipErrorText` (`src/agent/loop.ts`) сохраняет голову и **хвост 35 символов**; хвост длинного `error` — обрывок JSON-примера, а готовая инструкция («Передай непустой markdown») оказалась в середине и вырезана. `parsedErrorText` берёт `parsed.error`, **игнорируя `parsed.hint`** — короткое actionable-поле, добавленное VL-319 именно для этого.

## Корень (общий)

Write-инструменты, отвечающие плоским текстом, ломают классификацию исхода вызова: цикл не может отличить «применено» от «прочитано» и от «отказано». Страховка VL-306 — заплатка под это; она же превращает чтение в «применённую запись».

## Цель

Убрать корень: все write-инструменты отвечают JSON-ack, а страховка «не-JSON = применено» перестаёт быть нужной. Плюс директива отказа должна нести `hint`, а не обрезанный `error`.

## Связанные задачи

VL-306 (страховка appliedSignatures), VL-310 (noop-детекция), VL-318 (ackError не применён), VL-323 (директива с текстом ошибки), VL-349 (ackError на теле-скелете — работает, но директива калечит текст).

## Шаг 1. `manageChecklist` — JSON-ack во всех ветках

`src/mcp/tools.ts:1546`. Сейчас каждая ветка возвращает плоский текст. Заменить:

- `list` → `ackOk('Чеклист: N пунктов', { items: list.map((it, i) => ({ index: i + 1, checked: it.checked, text: it.text })) })`. Пустой чеклист — тоже `ackOk` с `items: []` и `message: 'Чеклист пуст.'` (сохранить привычную подстроку — на неё могут опираться тесты).
- `add` → `ackOk('Добавлен критерий #N: …', { added: [...], total: list.length })`; batch-ветка — `ackOk('Добавлено критериев: N (…)', { added: [...], total })`.
- `check`/`uncheck` → `ackOk('Отмечены критерии #…', { checked: indexes, action })`; batch — с `checked: indexes`.
- `remove` → `ackOk('Удалены критерии #…', { removed: indexes, total: list.length })`.
- `default` (неизвестное действие) — оставить `throw new Error(...)`: это ошибка вызова, цикл превратит её в текст «Ошибка выполнения инструмента …», который страховка VL-306 и так не считает применённым (`/^\s*Ошибка/`).

Сохранить прежние тексты в `message` — на них завязаны `server.test.mjs` и `lesson-tools`-подобные проверки (регрессия VL-120: scalar-формат ответа `check`).

## Шаг 2. `src/agent/loop.ts` — страховка VL-306 больше не «применяет» не-JSON

`:1532`. Сейчас:

```ts
if (!applied && !noop && !failed && spec && isMcpWriteTool(call.name) && !/^\s*Ошибка/.test(output)) {
  applied = true;
}
```

После шага 1 все write-инструменты отвечают JSON, поэтому страховка становится вредной: она превращает любой не-JSON ответ (внешний MCP, будущий текстовый инструмент) в «применено». Удалить блок целиком вместе с `isMcpWriteTool` и кэшем `mcpWriteToolsCache` (если других потребителей нет — проверить `search_files`).

Проверить, что не ломается кейс VL-306 (регресс-тест в `loop.test.mjs`: «плоский текст → applied») — он переписывается на новый контракт: плоский текст → **не** applied, повтор исполняется.

## Шаг 3. `parsedErrorText` — приоритет `hint`

`:440`. Сейчас берёт первое непустое из `[parsed.error, parsed.message]`. Добавить `hint` **первым**:

```ts
for (const value of [parsed.hint, parsed.error, parsed.message]) { … }
```

`hint` — короткая готовая инструкция («Добавь в вызов `content`…»), ровно то, что нужно модели в директиве. `error` остаётся фолбэком.

## Шаг 4. `clipErrorText` — не резать по хвосту, если есть `hint`

`:465`. Сейчас сохраняет голову + хвост 35 символов. Хвост нужен был для `ackError`, где подсказка стоит в конце `error` (VL-323). После шага 3 подсказка приходит отдельным полем, поэтому:

- если текст пришёл из `hint` — не резать вовсе (он короткий по построению), только сжать пробелы;
- если из `error`/`message` — оставить текущую логику (голова + хвост), она покрывает старые случаи.

Реализация: `parsedErrorText` возвращает `{ text, fromHint }`, `clipErrorText(text, fromHint)`.

## Риски

- **Удаление страховки VL-306** — осознанный регресс: если какой-то write-инструмент остался текстовым, его повтор больше не опознается как «применён» и уйдёт в обычный loop detection. Именно поэтому шаг 1 идёт первым, а шаг 5 закрепляет инвариант тестом.
- **Тексты `message`** — на них завязаны существующие тесты; менять формулировки нельзя, только оборачивать в `ackOk`.
- **`action:list` остаётся write по классификатору** — это не чинится в рамках задачи (классификатор смотрит только имя). После шага 1 последствие исчезает: `ackOk` на чтении не даёт ложной директивы, потому что повтор `list` — это `applied`, а не «уже применён». Если понадобится точная семантика — отдельная задача на передачу args в `isWriteOperation`.
