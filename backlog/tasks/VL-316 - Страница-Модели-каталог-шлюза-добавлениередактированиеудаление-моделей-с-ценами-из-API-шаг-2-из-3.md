## Description
<!-- SECTION:DESCRIPTION:BEGIN -->
## Контекст

Фича 3, шаг 2 из 3. Шаг 1 — VL-315 (`gateway`/`vendor` в ModelConfig вместо `@`-хвоста, Planned). Шаг 3 — сверка цен и fallback (зависит от этой).

Сейчас добавление модели — это ручное редактирование `settings.json`: нужно самому сходить на сайт RouterAI, посмотреть, какие вендоры обслуживают модель, переписать от руки цены в `pricing` и вписать `@provider=X` в имя модели. Из веб-интерфейса доступно только переключение `models.default` (`GET/PUT /api/models` в `src/web/api.ts:297-340`), добавления и редактирования нет вовсе.

При этом данные доступны программно и **без аутентификации** (ref-18): `GET /v1/models` — список моделей с ценами, возможностями и размерами контекста; `GET /v1/models/{author}/{model}/endpoints` — провайдеры (вендоры) конкретной модели с их ценами.

## Цель

Отдельная страница «Модели» в веб-интерфейсе: добавление модели мастером (шлюз → поиск модели → вендор с ценой → сохранение), редактирование, удаление. Цены и `context_window` подтягиваются из API — на сайт RouterAI бегать не нужно.

Заодно закрывает открытый вопрос VL-313: `context_window` перестаёт быть ручным полем, если модель добавлена через каталог.

## Решения (согласованы)

- **Отдельная страница** «Модели» (`#/models`), не секция существующей `#/settings`: там много состояния (каталог, поиск, цены по вендорам).
- **Пока один вендор** на запись модели (в RouterAI разные вендоры = разные записи `available`, потому что цены разные).
- **Ленивая миграция** (VL-315): старый формат остаётся читаемым, структурная запись появляется при первом сохранении из UI.
- Каталог — **per-шлюз адаптер**, не хардкод RouterAI: интерфейс `listModels`/`listVendors`, реализация RouterAI; второй шлюз добавляется без переписывания UI.

## План

1. `src/core/provider-catalog.ts` (new): интерфейс каталога + RouterAI-реализация (`/v1/models`, `/v1/models/{author}/{model}/endpoints`), нормализация цен в `ModelPricing` с учётом `pricing_units`, извлечение `context_window`, кэш `.vibelog/cache/provider-catalog.json` с TTL, терпимая деградация при недоступности API.
2. `src/web/api.ts`: `GET /api/catalog/models` (поиск по каталогу, фильтр по шлюзу), `POST /api/catalog/resolve` (готовая запись модели: pricing + context_window + api_mode). Валидация входа, таймауты, ошибки в понятном тексте.
3. Запись моделей: `POST /api/models` (добавить), `PUT /api/models/:id` (изменить), `DELETE /api/models/:id` (удалить) — read-modify-write `.vibelog/settings.json` через `loadSettings`/`saveSettings`, структурный формат (`gateway`, чистый `model`, `vendor`), нормализация старой записи при сохранении, защита `models.default` и моделей из мет активных сессий/тредов.
4. `web/src/components/settings/` (или новый `web/src/components/models/`): страница «Модели» — таблица моделей (label, gateway, vendor, pricing, context_window, default), мастер добавления, форма редактирования, удаление с подтверждением. shadcn-компоненты уже есть (`Card`, `Input`, `Select`, `Switch`, `Button`, `Skeleton`).
5. Роут `#/models` + пункт в сайдбаре (`web/src/App.tsx`, `use-hash-route.ts`, layout).
6. `web/src/components/settings/api.ts`: `ModelsData` получает `gateway` и `vendor`; пикер чата (`pickers.tsx`) показывает вендора второй строкой (данные уже приходят из VL-315).
7. Тесты: каталог (парсинг, нормализация цен, кэш/TTL, offline), API каталога, валидация записи, защита удаления, ленивая нормализация.
8. Документация: `docs/user-guide.md` (страница «Модели»), README, CHANGELOG.

## Риски

- **R1. Нормализация `pricing_units`.** Ошибка «за токен vs за 1M» даёт ×1e6 в рублях — тест на это обязателен первым.
- **R2. Каталог недоступен.** `/v1/models` без аутентификации ≠ гарантия доступности (сеть/прокси/лимиты). Деградация: кэш → ручной ввод цен в форме (поля остаются редактируемыми). Работа чата и фаз от каталога не зависит.
- **R3. Удаление модели.** Модель может быть зафиксирована в мете активных сессий агента (VL-239) или в треде чата — удаление сломает resume. Нужна проверка перед удалением, а не после.
- **R4. Дублирование валидации.** `/api/models` (PUT default) уже валидирует id; новые эндпоинты должны переиспользовать `validateModelsConfig`/`loadModels`, а не заводить второй набор правил.

## Открытые вопросы

- Хранить ли в settings URL каталога отдельно от `base_url` шлюза (у RouterAI каталог на том же хосте) или выводить из `base_url` — сейчас выводим из `base_url`, кастомный путь только если понадобится.
- Показывать ли в списке моделей «цену из каталога vs цену в settings» уже здесь (зачаток VL-317) или строго в VL-317.

## Решения по открытым вопросам (Pavel, 2026-11-02)

- **URL каталога выводим из `base_url` шлюза** — отдельного поля в settings не заводим. У RouterAI каталог на том же хосте (`https://routerai.ru/api/v1` → `/v1/models`, `/v1/models/{author}/{model}/endpoints`). Если появится шлюз с каталогом на другом пути/хосте — тогда добавим опциональное `catalog_url` в GatewayConfig, но не раньше: поле «на будущее» сейчас было бы непроверяемым.
- **Показывать «цена в settings vs цена из каталога» на странице «Модели» — ДА.** Выносим в эту задачу (раньше планировалось отложить в VL-317): колонка состояния по каждой модели (совпадает / выросла / снизилась) с кнопкой «Обновить тариф из каталога». Это дешёво (каталог уже загружается страницей) и сразу даёт видимую ценность — VL-317 добавит к этому автоматику перед ходом/фазой, а не сам факт отображения.
  - Следствие для AC: добавляется пункт про индикатор состояния цены и кнопку обновления тарифа; в VL-317 остаются только `GET /api/pricing/drift`, режимы `on_drift` и проверка перед ходом/фазой (без дублирования UI).
