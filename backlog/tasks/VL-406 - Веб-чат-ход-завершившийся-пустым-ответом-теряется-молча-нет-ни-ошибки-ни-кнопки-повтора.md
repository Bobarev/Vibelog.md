## Description
<!-- SECTION:DESCRIPTION:BEGIN -->
Симптом (со слов пользователя, 2026-11-10): в веб-чате после отправки сообщения кнопка снова становится «Отправить», индикатор исчезает, и дальше ничего не происходит — даже после перезагрузки страницы. При этом в сессии какой-то контекст сохранён.

Разбор по коду:

1. **Индикатор и опрос живут только на статусе `running`.** `RunInProgressIndicator` (`web/src/components/chat/thread.tsx:708`) возвращает `null` при `run.status === "done"`; эффект опроса (`thread.tsx:914`) запускается только при `load.run?.status === "running"` и прекращается, как только статус сменился. Значит любое завершение, кроме `running`, гасит и индикатор, и опрос.

2. **Пустой ответ модели неотличим от «ничего не было».** Если прогон завершился `done`, но assistant-сообщение в jsonl не записалось (модель вернула пустой content, или все части были отброшены), то: индикатор скрыт (статус не `running`), перезагрузка истории ничего не добавляет (в jsonl нет нового сообщения), плашки ошибки нет (статус `done`, а не `error`). Пользователь видит ровно то, что описал: «ничего не происходит даже после перезагрузки».

3. **Зависший `running` не лечится.** Если продюсер умер, не записав финальный статус в `turn.json`, статус остаётся `running` навсегда: индикатор «Ассистент отвечает…» висит, опрос крутится каждые 2 с вхолостую, выйти из состояния нельзя. `resetOrphanedChatRuns` чинит это только при рестарте сервера (VL-332), а не в живом процессе.

4. **Композер не знает серверного состояния.** Кнопка «Отправить» активна, потому что клиент определяет стриминг по своему рантайму, а не по `turn.json`. Отсюда ощущение «я могу отправить ещё раз», хотя ход на сервере мог ещё идти или уже умер.

Что нужно: сервер должен явно называть исход хода (включая «пустой ответ»), а клиент — показывать этот исход плашкой с кнопкой повтора вместо молчаливого исчезновения.

Связанные: VL-332 (реестр прогонов, `turn.json`, SSE-переподключение), VL-269 (плашка лимита и `aui.message.reload()` — образец кнопки повтора), VL-334 (карточка дрейфа цены — образец «кнопка действительно продолжает ход»), VL-314 (слэш-команды и отказ в стриминге).

## Шаги

1. **Сервер: явный исход «пустой ответ».** `src/web/chat-runs.ts`:
   - В тип статуса добавить `'empty'`.
   - В продюсере (`src/web/chat.ts`, точка `finishChatRun`) перед записью `done` проверить: появилось ли в этом ходе хотя бы одно assistant-сообщение с непустым content. Не появилось — писать `status: 'empty'` с `error: 'модель вернула пустой ответ'`.
   - `finishChatRun` принимает признак `hadAssistantContent: boolean` (или продюсер сам считает по числу записанных сообщений — выбрать по фактическому коду).

2. **Сервер: сторож зависшего `running`.** `src/web/chat-runs.ts`:
   - В записи прогона хранить `lastEventAt` (обновляется на каждом событии).
   - Новый экспорт `reapStaleChatRuns(maxIdleMs = 120_000)`: прогон в статусе `running`, у которого `lastEventAt` старше порога и `promise` уже не живой, переводится в `interrupted` с `error: 'ход не отвечает'`. Вызывать из того же места, где сейчас `resetOrphanedChatRuns` (старт сервера) **и** из обработчика `GET /api/chat/threads/:id` (ленивая проверка при чтении — так живой процесс тоже лечится, без отдельного таймера).
   - Порог — константа с комментарием, почему 120 с (LLM-таймаут провайдера обычно меньше).

3. **Клиент: индикатор активной работы — три горизонтальные точки.** `web/src/components/chat/thread.tsx`:
   - Новый компонент `TypingDots` (или расширение `RunInProgressIndicator`): три точки в ряд, пульсирующие по очереди (CSS-анимация `@keyframes` со сдвигом `animation-delay` 0 / 0.15 / 0.3 с; `opacity` или `translateY` — выбрать по вкусу, но без «прыжков» вёрстки).
   - Показывается при `run.status === 'running'` **и** пока клиентский рантайм в состоянии стриминга — то есть непрерывно на весь ход, включая паузы между tool-вызовами. Сейчас между вызовами в ленте пусто, и это главная причина ощущения «пропал».
   - `prefers-reduced-motion: reduce` → точки статичны (без анимации), текст-подпись остаётся.
   - Заменяет текущий `ShimmerLabel` «Ассистент отвечает…»: текст можно оставить рядом мелким шрифтом, но визуальный индикатор — точки.
   - Позиция в ленте фиксирована: при смене статуса на `empty`/`error`/`interrupted`/`cancelled` на этом же месте рендерится плашка исхода (шаг 4) — без скачка.

4. **Клиент: плашка исхода вместо молчания.** `web/src/components/chat/thread.tsx`:
   - Для `empty` — «Модель вернула пустой ответ» + кнопка «Повторить»; для `error`/`interrupted` — существующий текст + кнопка «Повторить»; для `cancelled` — «Ход остановлен» + «Повторить».
   - Кнопка «Повторить» — `aui.message.reload()` (тот же путь, что у плашки лимита VL-269), НЕ повторная отправка текста: иначе в jsonl появится дубль user-сообщения.
   - Плашка видна и после F5: статус берётся из `run` в `GET /api/chat/threads/:id`.

5. **Клиент: композер отражает серверное состояние.** `web/src/components/chat/thread.tsx`:
   - Пока `load.run?.status === 'running'` — кнопка отправки заменяется на «Стоп» (вызов `POST /api/chat/threads/:id/cancel`); набор текста разрешён, отправка — нет.
   - После `empty`/`error`/`interrupted` — кнопка «Отправить» активна, плашка с «Повторить» остаётся выше.

6. **Опрос и перезагрузка истории.** Эффект `thread.tsx:914` снимается при статусе ≠ `running` — оставить, но перезагрузку истории выполнять и при переходе в `empty`, иначе плашка появится только после F5.

## Как проверить

- `pnpm build && pnpm test` + `cd web && npm run build && npm run lint`.
- Индикатор: отправить сообщение, которое вызовет несколько tool-вызовов подряд → точки видны непрерывно, не мигают между вызовами.
- `prefers-reduced-motion`: включить в ОС/DevTools → точки статичны, текст читается.
- Пустой ответ: подменить ответ провайдера на пустой content (тест-фикстура) → `turn.json` получает `status: 'empty'`, клиент показывает плашку с «Повторить» на месте индикатора.
- Зависание: создать `turn.json` со `status: 'running'` и старым `lastEventAt` → `GET /api/chat/threads/:id` переводит в `interrupted`, клиент показывает «ход не отвечает» + «Повторить».
- Кнопка «Повторить»: нажать → ход перезапускается, в jsonl НЕ появляется второе user-сообщение (сверить число строк до/после).
- Композер: во время `running` кнопка «Стоп», нажатие отменяет ход (`turn.json` → `cancelled`).
- F5 после `empty` → плашка на месте.

## Риски

- **Дубль user-сообщения при повторе.** Если «Повторить» реализовать как повторную отправку текста, в jsonl появится два одинаковых user-сообщения. Обязательно `aui.message.reload()`.
- **Ложное «пустой ответ».** Модель может вернуть только tool_calls без текста — это нормальный ход. Проверять «нет assistant-сообщения с непустым content И нет незавершённых tool_calls».
- **Мигание индикатора.** Если привязывать точки к событиям стрима, они будут пропадать между вызовами инструментов — ровно та проблема, которую задача лечит. Привязка — к статусу хода, не к потоку токенов.
- **Порог 120 с.** Слишком маленький — оборвёт легитимно долгий ход; слишком большой — дольше висит индикатор. При обкатке скорректировать.
- **`empty` как новый статус.** Потребители `turn.json` (`chat-limits.ts`, `commandRefusal`) должны знать про новое значение: `empty` — не стриминг, команды разрешены.
- **Анимация и доступность.** Три пульсирующие точки без `prefers-reduced-motion` — нарушение доступности; проверять в DevTools (Rendering → Emulate CSS media feature).
