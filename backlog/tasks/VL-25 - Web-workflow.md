### User story
Хочу работать над задачами в веб интерфейсе примерно как в JIRA.
1. Я создаю задачу и она попадает в Backlog (сейчас его нет - сразу ToDo)
2. Если я на канбан доске перемещаю её Backlog -> ToDo, то автоматически вызывается аналог /vibelog:spec после выполнения qwen оставляет комментарий с отчётом
3. Далее, если у меня есть какие-то правки или комментарии по этой задаче или новым задачам после выполненного spec, то я их пишу в комментарии к этой задаче (а не в чате qwen) и жду доработки (опять п.2). А если всё хорошо, то нажимаю кнопку Одобрить (или как вариант в другой столбик переношу) что соотвественно вызывает аналог /vibelog:plan
4. После выполнения /vibelog:plan задача попадает в столбик Planned, тут тоже дальнейшая работа с задачей идёт через комментарии. Если я одобряю план, то переношу задачу в In Progress, что вызывает аналог /vibelog:code
5. После выполнения /vibelog:code задача попадает в столбик Review и так же через комменты продолжение работы или если всё готово, то в Done

### Разбор текущего workflow

**Что уже готово в Vibelog.md:**
*   **Комментарии к задачам**: В Backlog.md комментарии — это структурированная секция в файле задачи с телом, временем и автором . Vibelog.md уже поддерживает их через `backlog_add_comment`.
*   **MCP-инструменты**: У тебя есть `backlog_update_status` (для смены статуса), `backlog_manage_ac`, `backlog_update_task` и другие, которые могут выполнять все действия фаз.
*   **Веб-интерфейс**: У Vibelog.md есть Kanban-доска с drag-and-drop, которая обновляет markdown-файлы.

**Чего не хватает:**
*   **Триггер на смену статуса**: Сейчас перемещение карточки просто меняет поле `status`. Нужно, чтобы это **событие** запускало внешний процесс (Qwen Code с нужным промптом).
*   **Колонки под фазы**: Статусов `To Do / In Progress / Review / Done` недостаточно. Нужны `Backlog / Spec / Planned / In Progress / Review / Done`.
*   **Петля обратной связи**: Qwen должен уметь не только менять статус, но и **оставлять отчёт в комментариях**, чтобы ты видел результат прямо в карточке, а не в чате.

### 🛠️ Как это реализовать (архитектурно)

Тебе нужно добавить в Vibelog.md слой **«оркестратора событий»**. Это не просто таск-менеджер, это **event-driven runner**.

1.  **Расширить статусы**: Добавь в `backlog.config.yml` новые статусы: `Backlog`, `Spec`, `Planned`. Твой код уже читает статусы из конфига, так что колонки в вебе появятся автоматически.
2.  **Создать эндпоинт/хук в веб-сервере**: Когда `PATCH /api/tasks/:id` меняет статус на `Spec`, сервер должен **не просто обновить файл, а запустить `child_process.spawn`** с командой `qwen` и промптом.
3.  **Передавать контекст в Qwen**: Промпт для Qwen должен содержать:
    *   `vibelog task view VL-N --json` (чтобы агент видел задачу).
    *   `vibelog task comments VL-N` (чтобы агент видел твои правки из комментариев).
    *   Инструкцию: «Выполни Фазу 1 (spec), затем запиши отчёт через `backlog_add_comment` и смени статус на `Planned`».
4.  **Слушать Qwen**: После завершения процесса Qwen, сервер Vibelog.md может **автоматически подхватить изменения** (файл задачи обновится) и отрендерить новый комментарий на доске.

### 📋 Предлагаемая Story для Vibelog.md

Вот как я бы сформулировал задачу, чтобы она была готова к реализации (с учётом того, что у тебя уже есть комментарии и MCP):

**Название:** Интеграция с Qwen Code через смену статусов (Kanban-driven workflow)

**Описание:**
Хочу, чтобы перемещение карточки на Kanban-доске автоматически запускало соответствующую фазу работы Qwen Code (`spec`, `plan`, `code`), а результат фазы фиксировался в комментариях к задаче.

**Критерии приёмки:**
1.  **Новые статусы**: В конфиг добавлены статусы `Backlog`, `Spec`, `Planned`. Доска отображает их как отдельные колонки.
2.  **Триггер Spec**: При перемещении задачи из `Backlog` в `Spec` веб-сервер запускает `qwen` с промптом для Фазы 1. После завершения Qwen оставляет комментарий с отчётом, а задача автоматически переходит в `Planned`.
3.  **Триггер Plan**: При перемещении из `Spec`/`Planned` в `In Progress` (или нажатии кнопки «Одобрить») запускается Фаза 2. Отчёт — в комментариях, статус меняется на `In Progress`.
4.  **Триггер Code**: При перемещении из `Review` (или нажатии «Код одобрен») запускается Фаза 3. Отчёт — в комментариях, статус меняется на `Done`.
5.  **Обратная связь**: Если я пишу комментарий к задаче в статусе `Spec` или `Planned`, система должна перезапустить соответствующую фазу (или уведомить Qwen о правках через MCP).
6.  **Отчётность**: Все отчёты Qwen видны в веб-интерфейсе как комментарии к задаче.

**Технические заметки:**
*   Использовать `child_process.spawn` в `src/web/server.mjs` для запуска Qwen.
*   Промпты хранить в `templates/qwen-commands/` и подставлять ID задачи.
*   После завершения Qwen — парсить обновлённый markdown-файл, чтобы отобразить комментарий на доске.


### Как это встроить в Vibelog.md

Стек: Vite + React + shadcn/ui
**Один бинарник `vibelog` остаётся.** `vibelog browser` будет **отдавать статику React-приложения** (собранного в `dist/`), а `vibelog mcp start` останется как есть. Никаких изменений в CLI/MCP.

**Структура**

```
Vibelog.md/
├── bin/vibelog.mjs              # CLI остаётся
├── src/                          # Node.js код остаётся
├── web/                          # НОВАЯ папка — React-приложение
│   ├── package.json              # отдельный package.json для web
│   ├── vite.config.ts
│   ├── src/
│   │   ├── components/
│   │   │   ├── ui/               # shadcn/ui компоненты
│   │   │   ├── kanban/           # Kanban-доска
│   │   │   └── task/             # Формы задач
│   │   ├── lib/
│   │   └── App.tsx
│   └── index.html
```

**Как `vibelog browser` работает**

1. `pnpm build` в `web/` → `web/dist/` (статические файлы).
2. `vibelog browser` → Node.js сервер:
   - `GET /` → отдаёт `web/dist/index.html`.
   - `GET /assets/*` → отдаёт `web/dist/assets/*`.
   - `GET /api/*` → **тот же API**, что и сейчас (Node.js `http`).
   - `POST /api/tasks/:id/trigger` → **новый эндпоинт** для запуска Qwen.

**Как это не ломает совместимость**

- **CLI** остаётся на чистом Node.js.
- **MCP** остаётся на чистом Node.js.
- **Формат задач** не меняется.
- **Веб-интерфейс** — это **отдельный слой**, который можно выкинуть и вернуть vanilla HTML, если что-то сломается.

### Шаблон дашборда и доски Канбан

1. **Источник:** `next-shadcn-admin-dashboard` (Next.js 16). Это **не просто компонент**, а целое приложение. В нём есть всё: роутинг, авторизация, десятки дашбордов, и где-то среди них — **Kanban Board**.
2.  **Цель:** Твой новый **чистый Vite-проект**, который сейчас лежит где-то отдельно и содержит одну кнопку.
3.  **Инструмент:** Qwen Code, который должен «вытащить» Kanban из Next.js и вставить его в Vite.

### Главная сложность и как её обойти

Проблема в том, что Kanban в шаблоне **«зашит» в архитектуру Next.js**. Он использует:
*   **Server Components / `'use client'`**: Части компонента могут быть серверными, части — клиентскими. В Vite всё клиентское.
*   **Роутинг Next.js**: Kanban — это страница, привязанная к файловой системе Next.js (`app/(main)/dashboard/kanban/page.tsx`). В Vite это будет просто компонент.
*   **Данные**: В шаблоне данные для Kanban, скорее всего, приходят из **Server Actions** или **API Routes** Next.js. В VibeLog.md данные будут приходить из **твоего Node.js API** (`fetch('/api/tasks')`).

**Но твоя задача упрощается тем, что у тебя уже есть Vite-проект.** Тебе не нужно «переписывать всё под Vite». Тебе нужно **скопировать код Kanban-компонента в твой Vite-проект** и **заменить слой данных**.
