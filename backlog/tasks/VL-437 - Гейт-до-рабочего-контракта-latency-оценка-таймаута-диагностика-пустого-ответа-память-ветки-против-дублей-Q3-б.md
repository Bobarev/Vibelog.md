## Description

Контекст: VL-436 (фаза code) внедрил гейт react|read_only, <no_answer>, срезку [DECISION] по doc-34. Живой прогон 2026-11-19 10:32–10:45 (логи .vibelog/tmp/trace-md.log / trace-ui.log) подтвердил: <no_answer> работает (приветствие → тишина у обоих), [DECISION] срезан (карточка с маркером, группа без), depth живой («Цепочка слишком длинная» на depth=3 + проигнор чужого ботом), служебное не в группу. Следствие: UI повторил свой ответ (вход на ответ чужого бота без контекста ветки → ран без памяти → дубль).

ЭТО НЕ ЗАПЛАТКИ — доведение до контракта двух ЗАПЛАНИРОВАННЫХ пунктов:
1. doc-34 §3.2/§8.1 оценил latency короткого вызова модели как 2–3 с — оценка НЕВЕРНА (факт: короткий вызов mimo через Xiaomi-роутер 3–5 с, ран с 12–14k системника 6–7 с). Инвариант спекы «гейт не задерживает вход» = «быстрее рана», он выполняется и при большем таймауте. Пересмотр оценки, а не подкрутка.
2. doc-32 §8, Q3-б (отложен в VL-433) — «память ветки из N сообщений»: обещанный контекст ветки. Он же закрывает наблюдение пользователя («ui повторил свой ответ — контекст не включает предыдущие сообщения»): в промпт кладётся наш последний ответ, модель видит дубль и не повторяет. Это ровно тот пункт, что был отложен осознанно, а не новая заплатка.

ЭТАПЫ:
1. Гейт до рабочего контракта (gate.ts):
   1.1 Таймаут: GATE_TIMEOUT_MS 2500 → дефолт, выровненный по факту (кандидат 8000 мс — всё равно быстрее рана 10+ с), при необходимости — настройка; обновить doc-34 (§3.2 и §8.1) с зачёркиванием «2–3 с» как неверной оценки;
   1.2 Пустой ответ: в trace логировать сырой ответ гейта (что реально вернул streamChat: текст/длина/начало payload); парсер — нормализация (регистр/пробелы) + маркеры ищутся в реальном тексте; пустой → fail-open с причиной «пустой ответ» в error (сейчас маскируется под «непонятный»); диагностировать причину пустоты (responses/reasoning vs промпт-формат) и устранить;
   1.3 Живой AC: на прогоне есть успешные вердикты (хотя бы read_only на ответ чужого бота — без него дубли не уйдут никогда).
2. Память ветки (Q3-б): process-память «последние N реплик ветки с нашим участием» (паттерн/санитка как у interbotReplyMap, лимит ~20 записей); buildIncomingPrompt — секция «Последние реплики ветки» (паттерн уже есть для «предыдущий вопрос/ответ» — расширение, не нововведение); антидубль: модель видит свой прошлый ответ.
3. Тесты: юнит (парсер/таймаут/память/секция промпта), стаб гейта в handlers-тестах сохранить, pnpm test; живой прогон под --trace (антидубль + минимум один успешный read_only).

## Этап 1 — гейт до рабочего контракта (src/bot/gate.ts)

1. **Таймаут по факту (AC1).** `GATE_TIMEOUT_MS` 2500 → **8000** (`gate.ts:31`) + JSDoc-шапка (`gate.ts:15-17`) и комментарий константы (`gate.ts:30`): «2–3 с» — НЕВЕРНАЯ оценка doc-34 §3.2/§8.1 (факт живого прогона 2026-11-19: короткий вызов mimo через Xiaomi-роутер 3–5 с, ран с 12–14k системника 6–7 с); инвариант спеки = «гейт быстрее рана» — выполняется и при 8000 мс. `opts.timeoutMs` остаётся переопределяемым (тесты, `gate.ts:95`). Отдельную настройку НЕ вводим (отложено вместе с decision-моделями, doc-34 §8.1) — AC допускает «константа/настройка».
2. **Диагностика сырого ответа (AC2).** В `GateResult` добавить опциональные поля `raw?: string` (первые ~120 символов `res.text` до парсинга) и `usage?` (`output_tokens`/`reasoning_tokens` из `res.usage`); в `runGate` заполнять их ДО разбора. В `handlers.ts` после `trace('гейт:', …)` (~:1054-1057) добавить строку `trace('гейт сырой:', …)` с raw/длиной/usage — в режиме `--trace` видно, что реально вернул `streamChat`.
3. **Парсер (AC2).** `parseGateVerdict` (`gate.ts:74-79`): нормализация `toLowerCase().trim()` + схлопывание пробелов/переносов (`replace(/\s+/g, ' ')`), маркеры `read_only`/`react` ищутся в нормализованном тексте через `includes` (порядок: сначала `read_only` — он не пересекается с `react`). Существующие формы («READ_ONLY\n», «react.», « react ») обязаны остаться валидными.
4. **Пустой ответ ≠ «непонятный» (AC2).** В `runGate` перед `parseGateVerdict` (`gate.ts:119-124`): `(res.text ?? '').trim() === ''` → `{verdict:'react', error:'пустой ответ гейта (длина 0, usage: …)'}` — отдельная ясная причина, а не «непонятный ответ гейта: ».
5. **Причина пустоты и её устранение (AC2).** Гипотеза: `maxTokens: 16` (`gate.ts:115`) на reasoning-модели mimo-v2.6-flash — reasoning съедает бюджет, `content` пуст (reasoning-итемы в chat/responses парсерах пропускаются: `llm.ts:781`, `llm.ts:777-785`). Фикс-кандидат: 16 → 64 (эскалация до 256, если raw покажет пустоту и при 64). Проверка: диагностический одиночный вызов `streamChat` с gate-промптом через dist (apiMode `loadApiMode(cwd)`, дефолтная модель проекта) со старым и новым лимитом + сырой ответ в trace живого прогона.
6. **Живой AC (AC4):** ≥1 успешный `read_only` на прогоне под `--trace` (см. этап 5).

## Этап 2 — память ветки Q3-б (interbot.ts + handlers.ts)

1. **Чистая структура в interbot.ts** (паттерн `rememberReplyPair`, `interbot.ts:225-236`): экспорт `pushBranchEntry(list, entry, limit = 20)` — push + FIFO-санитка (удаление самого старого при `size > limit`); тип `BranchEntry = { author: string; text: string }`.
2. **Process-память в handlers.ts** рядом с `interbotReplyMap`/`interbotThreadMemory` (~:749-767): `interbotBranchFeed: BranchEntry[] = []` (на chat_id-ветку — один канал на интербот-процесс, см. предположение 4). Точки записи:
   - **вход**: в read_only-ветке гейта (~:1058-1064) — сразу; в react-ветке — **ПОСЛЕ** построения промпта (~:1081), чтобы текущий вопрос не дублировался в секции истории;
   - **наш ответ**: публикация в onExit `.then((ids) => …)` (~:1156-1162) и `ibot:ok` (~:2364-2373): `{author: 'мы', text: published}` (запись после `stripDecisionMarker`, как `rememberThreadPair`).
3. **Секция промпта (AC3).** `buildIncomingPrompt` (`interbot.ts:378-407`): opts += `history?: readonly BranchEntry[]`; перед `parts.push('', 'Вопрос:', question)` — секция «Последние реплики ветки (уже сказанное НЕ повторяй — ответь иначе либо `<no_answer>`):», строки `author: text.slice(0, 400)`, берутся последние 10 записей вызывающим (`interbotBranchFeed.slice(-10)`). Без `history` форма промпта не меняется (регресс-тест VL-433/436 обязан пройти). Паттерн секции — расширение существующей «Предыдущий вопрос и ответ в этой ветке» (`interbot.ts:396-403`), не нововведение.
4. **Антидубль (AC4):** модель в ране видит свой прошлый ответ в секции истории и не повторяет его; секция дополняет (не заменяет) `context` из reply-цитаты.

- Таймаут 8000 мс: при зависшем гейте следующие update бота обрабатываются с задержкой до 8 с (long-polling по одному) — принимается: инвариант «быстрее рана 10+ с» сохранён, fail-open не потерял путь в ран.
