## Description
<!-- SECTION:DESCRIPTION:BEGIN -->
## Контекст

Дефект найден при проверке плана VL-371 (пересмотр тестов) — при попытке заменить проверку `/Статус не изменён/` на разбор строки отчёта.

### Что происходит

`writeAutoReportIfMissing` (`src/agent/auto-report.ts`) собирает отчёт с **целевым** статусом, а при блокировке гейтом терминальности дописывает причину с **фактическим** статусом:

```ts
let report = buildAutoReport(task, {
  status: nextStatus ?? task.status,   // ← ЦЕЛЕВОЙ статус, например 'Done'
  ...
});
...
if (terminalAtRisk) {
  effectiveStatus = prevStatus;
  report += `\n${gate.reason ?? ''}`;   // ← «…Задача оставлена в «Review»»
}
```

`buildAutoReport` (`src/mcp/auto-report.ts:47`) печатает вторую строку как `Статус: ${ctx.status}`.

### Результат — противоречие внутри одного комментария

```
Фаза: авто-отчёт (comment не передан моделью)
Статус: Done
AC отмечено: 0 из 1
DoD отмечено: 1 из 2
DoD не отмечены (1): 2. Документация обновлена
Файлы: не менялись
Фрагмент плана/резюме: …
Отчёт собран сервером автоматически (VL-253): модель не передала comment.
Статус не изменён: терминальный «Done» при неотмеченных пунктах (DoD: #2) возможен только через backlog_finish_phase с dodOverride или aborted (VL-248/VL-309). Задача оставлена в «Review».
```

Строка 2 говорит «Статус: Done», последняя строка — «Задача оставлена в «Review»». Фактический статус задачи — `Review` (это проверяется тестом `auto-report.test.mjs:159`).

### Почему это важно

Это ровно тот класс дефекта, с которым ведётся борьба в VL-369: **ответ инструмента врёт о состоянии**. Модель (и человек, читающий ленту активности) видит в структурированной строке `Статус: Done` и может решить, что задача закрыта, хотя она осталась в `Review`. Текст причины лежит ниже и слабыми моделями не взвешивается — та же механика, что в lesson-92 (noop-ответ с `ok:true` в первой строке).

Дополнительно: дефект **не покрыт ни одним тестом**. Существующий тест `auto-report.test.mjs:159-161` проверяет только наличие подстрок `/Статус не изменён/`, `/DoD: #2/`, `/backlog_finish_phase с dodOverride или aborted/` — то есть фиксирует наличие причины, но не замечает, что строка статуса ей противоречит.

## Цель

Строка `Статус:` в авто-отчёте должна показывать **фактический** статус задачи после рана, а не целевой. Если статус не изменился из-за гейта — это должно быть видно из самой строки, а не только из дописанного текста причины.

## Варианты решения

**Вариант А (предпочтительный).** Передавать в `buildAutoReport` фактический статус (`effectiveStatus`), а целевой — отдельным полем, если он отличается:

```
Статус: Review (целевой был Done — переход заблокирован гейтом терминальности)
```

Требует: вычислить `effectiveStatus` **до** вызова `buildAutoReport` (сейчас гейт считается после), либо пересобрать строку статуса после. Второе проще: `buildAutoReport` получает `status` и опциональный `blockedTarget`, строка собирается с учётом обоих.

**Вариант Б.** Оставить `Статус:` целевым, но переименовать поле в `Целевой статус:` и добавить `Фактический статус:`. Минус: два поля вместо одного, читателю сложнее.

**Вариант В.** Убрать строку `Статус:` из отчёта вовсе, оставив только текст причины. Минус: теряется полезная информация в нормальном (незаблокированном) случае.

Рекомендуется **А**.

## Риски

1. **Формат отчёта читают другие потребители.** `src/mcp/server.test.mjs` проверяет `report.includes('Статус: In Progress')`; веб/бот-лента показывает текст комментария как есть. 2. **`reportFields` берёт первое значение по ключу.** Значение статуса становится длиннее, но по-прежнему без `:` до суффикса — для `/^([^:]+):\s*(.*)$/` безопасно. Снятие: проверка в тесте (AC4).
3. **Дублирование информации в отчёте остаётся.** После правки в заблокированном случае фактический статус, целевой и причина присутствуют трижды. Это осознанно: причина несёт номера пунктов и указание на `dodOverride`/`aborted`. Снятие: не устраняем, фиксируем как решение.
4. **Вторая копия правила (lesson-250).** Гейт не дублируется — используется существующий `terminalStatusGate` (`src/core/workflow.ts:361`); меняется только порядок вызова и передача результата в текст.
5. **MCP-путь: `blockedTarget` вычисляется по `updates.status === undefined`.** Если переход отклонён, `updates.status` не выставлен — пометка появится. Если `args.status` не передан вовсе, `blockedTarget` тоже `undefined` — пометки нет, что верно (запроса на смену не было).
