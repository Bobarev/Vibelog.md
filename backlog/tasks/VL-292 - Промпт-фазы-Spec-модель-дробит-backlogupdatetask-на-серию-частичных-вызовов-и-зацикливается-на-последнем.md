## Description
<!-- SECTION:DESCRIPTION:BEGIN -->
Симптом: при выполнении фазы Spec агент вместо ОДНОГО вызова backlog_update_task с полным набором полей делает серию частичных вызовов (type → priority+type → labels+type → type → type…) и после третьего-четвёртого повторного вызова с идентичными аргументами срабатывает loop detection (VL-253), фаза падает с кодом 1.

Воспроизведение (VL-291, сессия .vibelog/agent-sessions/agent-1793569374979.jsonl, строки 3-18): 7 LLM-запросов, из них 6 — backlog_update_task; вызовы №1-3 применили type/priority/labels, затем модель трижды подряд повторила {"id":"VL-291","type":"enhancement"} без изменений; второе срабатывание блокировки = немедленный fail по VL-253. Итог: acceptanceCriteria не заполнены, отчёт-комментарий не оставлен, статус остался To Do — фаза формально выполнена лишь частично, хотя 200k токенов израсходовано.

Причина (гипотеза, подтвердить в Plan/Code): промпт фазы Spec (шаг 5) требует «ровно один вызов», но перечисляет поля перечислением, не задавая критерий завершения; модель не имеет привычки читать applied из ответа и трактует «одно поле на вызов» как безопасную стратегию, а после применения всех полей не понимает, что работа сделана, и повторяет последний вызов. Защита в src/agent/loop.ts (VL-253, строки 880-960) срабатывает корректно — чинить нужно промпт, не детектор.

Ожидаемое поведение: один backlog_update_task со всеми полями, затем backlog_finish_phase с отчётом; при неполном описании — finish_phase без status и с вопросами, без серии уточняющих update-вызовов.

## Диагноз (подтверждён чтением кода)

Причина — в ШАБЛОНЕ фазы Spec, а не в детекторе. `templates/phases/phase-spec.md` (шаг 5, строки 52-73) требует «backlog_update_task РОВНО ОДИН РАЗ», но:
- поля перечислены одной строкой-примером (`title`, `type`, `priority`, `labels`, `description`, `references`, `acceptanceCriteria`) без явного «все поля — в ОДНОМ объекте» и без критерия завершения («после ok/`applied` — сразу шаг 6»);
- нет правила чтения ответа write-инструмента, хотя контракт `{ok, message, applied, skipped, idempotentReplay?}` существует с VL-262 (`src/mcp/tool-result.ts`, doc-8 §§«Контракт ответа write-инструментов»);
- в разделе «Правила» (строка 155) «Каждый MCP-инструмент вызывай РОВНО ОДИН РАЗ за фазу» соседствует с `reference_add`/`reference_link`, вызываемыми дважды → правило читается как нестрогое и модель выбирает стратегию «одно поле на вызов».

Детектор `src/agent/loop.ts` (строки ~885-970, VL-253) срабатывает КОРРЕКТНО: сигнатура `name|JSON(args)`, `streak >= repeatLimit` → блокировка, вторая блокировка той же сигнатуры → `fail()`. Трогать детектор НЕ нужно (иначе ослабим защиту от реальных лупов).

## Правки шаг за шагом

### 1. `templates/phases/phase-spec.md` — шаг 5 (строки 52-61)

Заменить вводную строку шага 5 на явную директиву:

- `5. Обнови задачу через MCP ОДНИМ вызовом (только если описание ПОЛНОЕ):`
- Добавить перед JSON-примером абзац: «**Все определённые тобой поля — title, type, priority, labels, description, references, acceptanceCriteria — передаются в ОДНОМ объекте аргументов одного вызова `backlog_update_task`.** Серия вызовов «по одному полю» запрещена: она сжигает контекст и попадает под loop detection (`src/agent/loop.ts`), фаза падает. Пример буквального вида вызова:»
- После JSON-примера — новый подпункт «**Критерий завершения шага 5 (читай ответ!)**»:
  - ответ write-инструмента — JSON `{ok, message, applied, skipped, ...}`; `applied` — значения полей ПОСЛЕ записи;
  - если поле уже присутствует в `applied` — НЕ передавай его повторно ни в этом, ни в следующем вызове;
  - `skipped` — поля, которые не записались (неизвестное имя поля или `null`): их не «дожимать» повтором того же вызова, а учесть в отчёте;
  - `idempotentReplay: true` — изменение уже применено ранее, второй эффект не нужен;
  - `ok: true` → шаг 5 закончен → сразу шаг 6 (`backlog_finish_phase`), без `backlog_view_task` и без проверок;
  - `ok: false` → `reason: 'not_confirmed'` (подтверждение не получено) → ОДИН повтор с `idempotencyKey`; `reason: 'denied'` (пользователь отказал) → НЕ повторять, отчёт-комментарий без status.
- Усилить существующий пункт (строка 60): оставить «Вызови backlog_update_task РОВНО ОДИН РАЗ» и добавить «Повторный вызов с уже применёнными полями (в т.ч. с идентичными аргументами) запрещён — это ровно та ситуация, которую блокирует loop detection».
