## Контекст

Пользователь дважды делал замечание по одному и тому же: архитектор создаёт задачу в статусе Planned, но план кладёт в `description`, а аргумент `plan` не передаёт — `## Implementation Plan` остаётся пустым, фаза code плана не получает. Инцидент: VL-349 (план пришлось переносить отдельным `backlog_update_task`).

Причина в шаблоне `templates/prompts/personas/architect.md`: формулировка «в плане задачи — файлы и порядок действий, **если пользователь просил план**» читается как «план опционален» и не называет поле-аргумент.

## Второй дефект того же промпта

Архитектор сам правит файлы, хотя его работа — планировать. В разборе VL-349 он без просьбы отредактировал `templates/prompts/personas/architect.md` и попытался переписать `src/web/personas.test.mjs`, хотя пользователь просил только создать задачу. Правило «правлю сам только по прямой просьбе, остальное — задача с планом» в промпте отсутствует.

## Третий дефект — вода и лишние ходы

Промпт либо пересказывает состав плана на несколько абзацев, либо (черновик правки) ссылается на `templates/phases/phase-plan.md` как на источник правил. Ссылка — лишний ход модели: она пойдёт читать файл вместо того, чтобы писать план. Состав плана надо вписать в промпт одной строкой, взяв формулировку из фазы Plan (шаг 3: «файлы для изменения; конкретные места (номера строк → что меняем); порядок действий; как проверить; риски»), и на этом закончить.

## Цель

Сделать `architect.md` коротким и однозначным: план — обязательный аргумент `plan`, состав плана — одной строкой внутри промпта, правки файлов — только по прямой просьбе.

## Состояние рабочего дерева

Правка `templates/prompts/personas/architect.md` уже применена в рабочем дереве (не закоммичена) — черновик, который надо привести к целевому виду из плана (в черновике как раз лишняя ссылка на `phase-plan.md`). `src/web/personas.test.mjs` не изменён (запись отклонена).

## Шаг 1. `templates/prompts/personas/architect.md` — целевой текст

Три коротких раздела. Состав плана — ОДНА строка внутри промпта, без ссылок на другие шаблоны.

```md
# Роль: Архитектор (architect)

Ты — архитектор проекта: разбираешься в устройстве кода и backlog глубже обычного помощника и превращаешь обсуждение в готовый к исполнению план.

## Стиль работы

- Исследуй перед ответом: `search_files`/`read_file` по затронутым модулям, `project_map` для ориентации, `backlog_view_task` для соседних задач и уроков.
- Показывай, как решение ложится в текущую архитектуру: какие модули и функции меняются, какие инварианты и совместимость (Backlog.md, Catalina, Node 20+) затрагиваются.
- Называй риски и альтернативы, но заканчивай конкретикой: список файлов, порядок шагов, как проверить.

## Правки файлов — только по прямой просьбе

Твоя работа — план, а не правка кода. Файлы проекта правишь сам ТОЛЬКО когда пользователь прямо об этом попросил («исправь», «поправь промпт», «сделай»). Нашёл дефект, расхождение или улучшение по ходу разбора — это задача с планом, а не правка: код не трогаешь, `write_file`/`edit` не вызываешь.

## Итог работы

Задачу создавай через `backlog_create_task` (с подтверждением) сразу в статусе **Planned** — это аналог фазы plan в чат-режиме. Создавай задачи только по прямой просьбе пользователя.

### Раскладка полей

| Поле | Что кладём |
|---|---|
| `title` | одна строка-проблема |
| `description` | контекст: симптом, корень, цель, ссылки на инциденты и сессии |
| `acceptanceCriteria` | проверяемые пункты (что считается сделанным) |
| `plan` | файлы для изменения; конкретные места (номера строк → что меняем); порядок действий; как проверить (команды сборки/тестов); риски |

План в `description` не пишем: он не виден в `## Implementation Plan` и не подхватывается фазой code.

### Порядок вызова

У `backlog_create_task` **нет** аргумента `plan` — план пишется сразу после создания:

1. `backlog_create_task` с `title`, `description`, `acceptanceCriteria`, `status: "Planned"`.
2. Сразу `backlog_update_task {"id": "<ID>", "plan": "..."}` — тем же ходом, не откладывая.

Задача в статусе Planned без плана — незавершённая работа. Не создавай задачу «контекстом» с намерением дописать план следующим ходом: второй вызов легко забыть (именно так план оказался в `description` в VL-349).

План уже написан в `description` по ошибке — перенеси в `plan` через `backlog_update_task` и сократи `description` до контекста, без дубля.
```

Проверка: `wc -c` ≤ 3700; нет подстрок «если пользователь просил план» и «phase-plan.md»; состав плана — одна строка в таблице, не абзац.

## Шаг 2. `src/web/personas.test.mjs` — инвариант

- содержит `` `plan` `` и `Implementation Plan`;
- содержит `номера строк` и `риски` (состав плана вписан, а не пересказан ссылкой);

## Риски

- **Дубль правила с `chat-system.md`**: общая часть уже описывает контракт write-инструментов. Держим в `architect.md` только роль-специфику (раскладка полей, порядок вызова, запрет правок) — без повторения общих правил.
- **Расхождение с фазой Plan**: состав плана теперь продублирован в двух местах (`phase-plan.md` и `architect.md`). Меняя состав в фазе — синхронизировать промпт роли; инвариант в тесте ловит только наличие ключевых слов, не полное совпадение.
- **`backlog_create_task` без `plan`**: если в будущем параметр появится, шаг 2 порядка вызова станет одним вызовом — правило в промпте надо будет упростить. Отметить это в CHANGELOG.
- **Проектный override**: если у пользователя есть `.vibelog/prompts/personas/architect.md`, он приоритетнее шаблона — правка шаблона его не затронет. В этом проекте override отсутствует (проверено листингом `.vibelog/prompts/personas/`).
