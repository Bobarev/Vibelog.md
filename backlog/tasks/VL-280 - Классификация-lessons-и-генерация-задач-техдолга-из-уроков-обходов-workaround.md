## Description

## Контекст

Часть уроков — не правила, а **обходные пути**, легализованные как «урок» и поэтому никогда не исправляемые. Примеры из текущего корпуса (141 урок):

- `lesson-113` / `lesson-120` — снимай `VIBELOG_*`-переменные через `env -u` перед тестами;
- `lesson-124` — не коммить симлинк `node_modules` в ветку worktree;
- `lesson-139` — откатывай эксперимент копией файла, а не `git checkout`;
- `lesson-26` — проверяй guard-фиксы скрипт-файлом, потому что MCP валидирует старым dist;
- `lesson-101` / `lesson-115` / `lesson-116` / `lesson-100` — ритуалы ручной диагностики тестов.

Каждый такой урок = техдолг, который зафиксирован как норма поведения. Пока он в статусе `active`, он подставляется в промпты Plan/Code (`src/web/phase-prompt.ts:225-233`) и модель учится обходить проблему вместо того, чтобы её решить.

## Цель

Из урока, описывающего обход, уметь получать **задачу на устранение причины** — вручную подтверждаемым шагом, не автоматически.

## Объём

1. **Классификация (LLM, opt-in)** — MCP-инструмент `lesson_classify`:
   - вход: `ids[]` либо фильтр (`status`, `tags`, `limit`);
   - выход: для каждого урока `kind ∈ {rule, workaround, fact, stale}` + краткое обоснование;
   - контекст для модели — findings из VL-279 (битый путь/протухание повышают шанс stale) и тело урока;
   - запись `kind` во фронтматтер — только `apply=true` или явный список ID.
2. **Кластеризация workaround'ов** — одна тема = одна задача техдолга (не 40 отдельных задач):
   - группировка по tags + пересечению упомянутых путей/символов;
   - description задачи: причина обхода, цитаты уроков-источников, критерий «workaround больше не нужен».
3. **Создание задач** — только по подтверждению, с лимитом задач за вызов (дефолт 1); двусторонняя связь `lesson_link`, ссылки на задачи в теле уроков.
4. **Замыкание цикла** — при закрытии задачи техдолга должно быть видно, какой урок пора пометить `outdated`/`superseded` (в задаче перечислены ID уроков; в Close-шаблоне — уже существует шаг сверки lessons по tags).

## Границы

- Ничего не пишется в файлы без явного `apply=true`/списка ID: LLM-классификация по умолчанию только отчёт.
- Автоматического создания задач из аудита нет — только «черновики/предложение», создание инициирует человек.
- LLM-вызовы не входят в CI-аудит (это отдельный, дорогой путь).

## Зависимость

Требует VL-279 (findings, `kind` в модели, `needs-review`, `lesson_audit`).

## Открытые вопросы

- Модель для классификации: брать дефолтную из settings (models) или отдельную дешёвую?
- Формат кластеров: детерминированная группировка по tags/путям или LLM-кластеризация (дороже, но точнее)? Начать с детерминированной + LLM только для названия кластера.
- Нужен ли `kind=fact` (утверждение о коде, проверяемое тестом) как отдельный путь «сгенерировать тест-инвариант» — потенциально отдельная задача.
