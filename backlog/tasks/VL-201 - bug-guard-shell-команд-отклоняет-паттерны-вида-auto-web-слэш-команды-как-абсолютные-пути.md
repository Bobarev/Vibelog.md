## Description
<!-- SECTION:DESCRIPTION:BEGIN -->
Предложено в VL-197. tools.ts:315-340: паттерн grep без regex-метасимволов (например grep -n "/auto" backlog/docs/..., "/web") после снятия кавычек не распознаётся isRegexPatternToken (проверяет только метасимволы) и отклоняется как абсолютный путь вне проекта. 3 случая в сессиях VL-193 (VL-197). Слэш-команды — штатный объект поиска в документации. Нужен контекстный анализ: токен в позиции аргумента-паттерна (grep/rg/sed -e/-n/…, следующий за командой-фильтром), либо правило «токен начинается с `/`, но не резолвится в существующий путь-каталог и сопровождается файловыми аргументами внутри проекта». Существующие отказы (~, $HOME, .., реальные абсолютные пути) должны остаться.

# План реализации (VL-201, фаза Plan)

Проблема: `checkShellCommandInProject` (`src/agent/tools.ts`) токенизирует команду, но не знает позиции токена. Слэш-паттерн без regex-метасимволов (`/auto`, `/web start`) после снятия кавычек не распознаётся `isRegexPatternToken` (стр. 270, проверяет только метасимволы) и падает в ветку `isAbsolute` (стр. 333) → ложный «Команда отклонена». Решение — позиционный (контекстный) анализ: токен в позиции аргумента-паттерна команды-фильтра не является путём по семантике shell и пропускается. Второе предложение из описания («не резолвится в существующий путь + файловые аргументы внутри проекта») отклонено: требует `existsSync` на путях вне проекта (само по себе внешнее обращение, в т.ч. TCC) и открывает дыру для несуществующих абсолютных путей.

## Изменения в src/agent/tools.ts

### 1. Новые константы — после `SPECIAL_FILES` (стр. 256)

```ts
// Команды, первый не-флаг-аргумент которых — паттерн, а не путь (VL-201).
const FILTER_COMMANDS = new Set(['grep', 'egrep', 'fgrep', 'rg', 'sed', 'awk']);
// Флаги с отдельным значением-паттерном: следующий токен — паттерн.
const PATTERN_VALUE_FLAGS = new Set(['-e', '--regexp']);
// Флаги, паттерн поступает из файла: значение — путь (проверяется), паттерн считается заданным.
const PATH_VALUE_FLAGS = new Set(['-f', '--file']);
// Флаги с отдельным значением-числом/действием: значение проверяется как обычный
// токен, но НЕ считается паттерном (иначе `grep -m 2 "/auto" f` сместит границу).
const CONTEXT_VALUE_FLAGS = new Set([
  '-m', '-A', '-B', '-C', '-d', '-D',
  '--max-count', '--after-context', '--before-context', '--context',
]);
```

Наполнять таблицы только флагами с **гарантированной** семантикой (GNU grep/rg, POSIX sed): ложное включение boolean-флага сдвигает границу паттерн/файл и может пропустить файловый аргумент (дыра); пропуск вхождения даёт только ложный отказ (fail-safe).

### 2. Токенизатор (стр. 312–313)

Добавить альтернативу-разделитель, чтобы команда после `|`/`&&`/`;`/`(` распознавалась как новая (сейчас разделители молча выбрасываются и границы команд не видно):

```ts
const tokens =
  command.match(/"(?:\\.|[^"\\])*"|'(?:\\.|[^'\\])*'|(?:\\[^\s]|[^\s;|&()<>])+|[;|&()<>]/g) ?? [];
```

Кавычечные альтернативы стоят первыми — `|` внутри кавычек не разбивает токен.

### 3. Цикл по токенам (стр. 314–348)

Перед циклом — состояние:
```ts
let commandName: string | null = null;   // текущая команда (последний разделитель)
let patternSupplied = false;             // паттерн уже позиционно занят
let expect: 'none' | 'pattern' | 'path' | 'value' = 'none';
```

В начале цикла (до проверок, порядок важен):
1. **Разделитель** `^[;|&()<>]$` → сброс всех трёх переменных → `continue`.
2. **Слово команды**: `commandName === null` → `commandName = token`; сброс `patternSupplied`/`expect`; далее токен идёт по обычным путевым проверкам (командное слово НЕ освобождается от проверки — `/usr/bin/foo` остаётся отказом).
3. **Позиционная проверка паттерна — ДО проверки `~`** (чтобы `grep "~"` пропускался):
   - `expect === 'pattern'` → паттерн;
   - иначе `expect === 'none' && FILTER_COMMANDS.has(commandName) && !patternSupplied && !token.startsWith('-')` → паттерн (первый не-флаг-аргумент grep/sed/rg/awk — всегда паттерн по семантике утилиты);
   - при позиции паттерна: `patternSupplied = true; expect = 'none'; continue;` (полный пропуск — паттерн не читает файлов).
4. Ветка `token.startsWith('-')` (стр. ~324): перед `continue` выставить `expect` по таблицам (`PATTERN_VALUE_FLAGS`→`pattern`, `PATH_VALUE_FLAGS`→`path`, `CONTEXT_VALUE_FLAGS`→`value`); для `--regexp=…`/`--file=…`/`-eX` (attached/equals) — `patternSupplied = true` только если `FILTER_COMMANDS.has(commandName)`.
5. После позиционной, но до путевых проверок: `expect === 'path'` → снять `expect`, выставить `patternSupplied = true` (паттерн задан через `-f`), токен проверяется как путь; `expect === 'value'` → снять `expect`, `patternSupplied` НЕ трогать, токен проверяется как путь (`2` в `grep -m 2 …` — относительный, пройдёт).
6. Остальное — без изменений: `~`/`~/` → reject; SPECIAL_FILES (326); `isRegexPatternToken` (331); `isAbsolute` (333); `..` (341–347).

Обновить JSDoc `checkShellCommandInProject` (стр. 273–293): добавить описание позиционного анализа (VL-201) и оговорку, что `~`/`$HOME` проверяются до токенизации.

## Риски

1. **Таблицы флагов**: пропущенный флаг-значение (`grep -A 2` без `-A` в таблице) → смещение границы → ложный отказ (fail-safe); ложное включение boolean-флага → возможный пропуск файлового аргумента (дыра) — поэтому в таблицы включать только гарантированные value-флаги.
2. **Разделители в токенизаторе** меняют состав токенов (`2>/dev/null` → `2`,`>`,`/dev/null`; `(foo\|bar)` → `(`,…,`)`) — обязательно прогон всех существующих describe VL-99/104/179.
3. **`-`-токены не валидируются как пути** (`grep --file=/etc/x`, `--regexp=/x`) — как и сегодня (любой `-`-токен пропускается), остаточный риск, не регрессия; в плане не расширяется.
4. **Верхнеуровневые `~`/`$HOME`** срабатывают до позиционного анализа: `grep -n ~ x` (без кавычек) и `grep "$HOME" x` отклоняются — ложные отказы вне AC; кавычирование `~` помогает, `$HOME` в паттерне — known limitation (ослаблять нельзя: AC-2 требует `cat ~/x` reject).
5. Список команд-фильтров фиксирован (grep/egrep/fgrep/rg/sed/awk) — иные команды позиционных привилегий не получают; расширение списка — отдельным решением.
