## Description
<!-- SECTION:DESCRIPTION:BEGIN -->
При выполнении команды analyze итоговое сообщение в боте обрезается: длинный результат не помещается в одно сообщение (лимит длины сообщения Telegram ~4096 символов) и хвост результата теряется.

Ожидаемое поведение (уточнено пользователем):
- Если результат analyze не помещается в одно сообщение — разбивать его на несколько последовательных сообщений.
- Части разбитого сообщения нумеровать (например, «часть 1/3»).
- Короткий результат (в пределах лимита) отправляется одним сообщением, без изменений.

Уточнение по охвату: пользователь не проверял, обрезаются ли длинные ответы других команд бота. Фикс в первую очередь для команды analyze; если механизм разбивки удастся сделать общим помощником — другие команды можно подключить позже отдельной задачей.

# План VL-148: разбивка длинного результата /analyze на нумерованные сообщения

## Корень проблемы

Итог фазы шлётся через `sendPhaseResult` (`src/bot/handlers.ts:244-254`): rich-рендер `renderPhaseResultRich` + fallback `formatPhaseResult`/`sendText`. Оба рендера **сами усекают ответ модели до 1500 символов** (`src/bot/rich.ts:605-607` и `src/bot/formatting.ts:205-209`: `res.result.length > 1500 ? res.result.slice(0, 1500) + '…'`). Хвост analyze-результата теряется ещё до отправки; `chunkRich` (лимит 32768) при этом почти никогда не задействуется, а MarkdownV2-fallback вообще не разбивается (лимит 4096).

## Изменяемые файлы

1. **`src/bot/formatting.ts`**
   - Константы: `TELEGRAM_TEXT_LIMIT = 4096`, `PART_SUFFIX_RESERVE = 32` (запас под «часть 99/99» с экранированием).
   - Новая чистая экспортируемая функция `splitNumbered(text: string, limit: number, fmtSuffix: (i: number, n: number) => string): string[]`:
     - короткий текст → один элемент без суффикса (AC3);
     - длинный → разрез ТОЛЬКО по границам строк (`\n`) в пределах `limit - PART_SUFFIX_RESERVE` (внутристрочный разрез может разорвать escape-последовательность MarkdownV2 `\x` — 400 «can't parse entities»); к каждой части добавляется суффикс от `fmtSuffix` (вызывающий сам решает MarkdownV2-escape или GFM);
     -极端но длинная одна строка (> limit) — жёсткий разрез с комментарием о риске.
   - `formatPhaseResult` (`src/bot/formatting.ts:180-232`): **удалить усечение 1500** (блок строк ~205-209, комментарий «Обрезка результата: Telegram-лимит 4096…») → `const body = res.result;`. Разбивкой теперь занимается слой отправки.

2. **`src/bot/rich.ts`**
   - `renderPhaseResultRich` (`src/bot/rich.ts:589-629`): **удалить усечение 1500** (строки ~605-607) → `const body = res.result;`. Лимит rich 32768 покрывается существующим `chunkRich` при отправке.

3. **`src/bot/handlers.ts`**
   - `sendPhaseResult` (`src/bot/handlers.ts:244-254`):
     - rich-путь: `const parts = chunkRich(rich);` если `parts.length > 1` — пронумеровать каждую часть суффиксом `\n\n_(часть i/N)_` (GFM italic), отправлять последовательно через `sendRichMessage` (AC2).
     - fallback-путь: вместо одного `sendText(bot, chatId, formatPhaseResult(...))` — `const parts = splitNumbered(text, TELEGRAM_TEXT_LIMIT, (i, n) => ...)`, суффикс в MarkdownV2-виде `\n\n_часть i\/N_` (в MarkdownV2 `/` и `(` `)` — спецсимволы; единственный спецсимвол в «часть i/N» — `/` → `\/`), каждую часть отправлять через существующий `sendText` последовательно. Это и есть **общий помощник разбивки** — другие команды подключат его позже отдельной задачей (sendTaskView/sendDiffView и др. НЕ трогаем).
   - Затронуты штатно и соседние вызовы того же шаблона (`/prompt`, уведомления о завершении фазы, `/comment`) — это не регрессия, а единообразие; в описании изменений отметить.

4. **`src/bot/formatting.test.mjs`** (+ при необходимости `src/bot/rich.test.mjs`) — юнит-тесты `splitNumbered`:
   - текст < limit → 1 часть, без суффикса (AC3);
   - текст > limit → N частей, каждая ≤ limit, суффиксы «часть i/N» подряд (AC1, AC2);
   - разрез идёт по границам строк: ни одна часть не начинается с обрывка escape-последовательности;
   - `renderPhaseResultRich`/`formatPhaseResult` с result > 1500 → в выводе присутствует полный текст (нет «…» на 1500-м символе).

5. **Документация** (DoD-2):
   - `README.md` (раздел бота, строки ~231-236): добавить предложение — длинный результат `/analyze` разбивается на несколько сообщений с нумерацией «часть i/N».
   - Руководство пользователя (doc-6, backlog/docs — правка через MCP `document_update` в фазе Code): раздел `/analyze` — примечание о разбивке.

## Порядок действий

2. `rich.ts`: снятие усечения в `renderPhaseResultRich`.
3. `handlers.ts`: нумерованная отправка в `sendPhaseResult` (rich + fallback).
4. Тесты в `formatting.test.mjs`/`rich.test.mjs`.
5. README + doc-6.
6. Сборка и прогон: `pnpm build && pnpm test` (или `pnpm test`, включает build).

## Как проверить

- `pnpm test` — все тесты зелёные (AC + DoD-1).
- Ручная проверка в боте: `/analyze vb:agent-<id>` на сессии с длинным вердиктом → приходят последовательные сообщения «часть 1/N», хвост присутствует; на коротком результате — одно сообщение без суффикса.
- Сравнить `git diff` — в diff не попали `sendTaskView`/`sendDiffView`/`sendCommitsView` (нет регрессий в других командах, DoD-3).

## Риски

- **MarkdownV2-разрез**: разрез строки внутри escape-последовательности → 400 и потеря сообщения. Митигируется разрезом только по `\n`; жёсткий разрез — только для аномально длинной одной строки.
- **Изменение поведения соседних шаблонов**: `/prompt` и уведомления о фазах с result > 1500 теперь приходят несколькими сообщениями вместо обрезанного одним — задокументировать в комментарии фикса.
- **Дубли при частичной отправке rich**: если `sendRichMessage` упал на k-й части, fallback шлёт весь текст заново — существующее поведение sendPhaseResult, не ухудшается (до фикса fallback и так шлёт усечённый текст).
- Порядковые файлы: 3 кодовых + 1 тест + README + doc-6; зависимостей на другие задачи нет.
