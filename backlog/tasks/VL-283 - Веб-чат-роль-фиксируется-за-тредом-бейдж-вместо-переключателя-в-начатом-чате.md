## Контекст

Пользователь: «Переключение роли в уже начатом чате мне кажется не нужно. Мы же выбрали уже роль и переключение роли тут вроде по смыслу не должно уже работать. Можно только где-то показать какая это роль».

Как устроено сейчас (VL-265): роль — module-state на клиенте (`web/src/components/chat/chat-runtime.tsx:161-168`, `activePersonaId`, дефолт `helper`, без localStorage), он уходит в `body.persona` каждого POST. Сервер (`src/web/chat.ts:605-618`) валидирует `body.persona` на каждом ходе и заново собирает system-промпт (`buildSystemPrompt` = общая часть → `## Текущая роль: <label>` → контекст). `PersonaPicker` рендерится в композере всегда (`web/src/components/chat/thread.tsx:455`), в т.ч. в непустом треде.

Следствия:
1. роль можно сменить посреди треда — история продолжается с другим system-промптом, поведение ассистента меняется «на ходу»;
2. роль не привязана к треду и нигде не хранится: после перезагрузки `activePersonaId` снова `helper`, и тред, начатый как «Архитектор», визуально и фактически продолжается как «Помощник» (показать реальную роль треда не из чего).

## Цель

Зафиксировать роль за тредом: выбирается при создании нового треда, в начатом треде не меняется и только отображается (бейдж с иконкой и названием). Роль сохраняется на сервере вместе с тредом, чтобы её можно было показать после перезагрузки/открытия треда.

## Входные данные

- `web/src/components/chat/pickers.tsx` — `PersonaPicker` (дропдаун, `PERSONA_ICONS`, `setActivePersonaId`); из него делать бейдж-режим.
- `web/src/components/chat/chat-runtime.tsx` — `activePersonaId` / `getActivePersonaId` / `setActivePersonaId`, отправка `body.persona`.
- `web/src/components/chat/thread.tsx` — `Composer` (строка 455, `PersonaPicker`), `EmptyState`/`ChatThread` (можно ли определить «тред начат» по `load.messages.length` или `ThreadPrimitive.If empty`), `ChatPage` (загрузка истории через `GET /api/chat/threads/:id`).
- `src/web/chat.ts:400` — `getChatThread(cwd, threadId)` (возвращает `ChatMessage[] | null`); `listChatThreads` (строка 373), `sessionFile` → `<threadId>.jsonl` в `.vibelog/chat-sessions`; образцы sidecar-файлов треда: `<threadId>.allow.json` (VL-264), `<threadId>.repeat.json` (VL-255) — имя с точкой, поэтому `listChatThreads` (фильтр `.jsonl`) их не видит.

## Варианты решения (решить в плане)

- Хранение роли за тредом: sidecar `<threadId>.persona.json` в `.vibelog/chat-sessions` (паттерн `.allow.json`, невидим для `listChatThreads`) против записи в сами сообщения jsonl / отдельный manifest. Sidecar дешевле и не ломает формат истории.

- Что показывать для старых тредов без sidecar: `helper` (дефолт) или «роль не зафиксирована».

## Решения плана

**Р1. Хранение роли за тредом — sidecar `<threadId>.persona.json`** в `.vibelog/chat-sessions/` (паттерн `<threadId>.allow.json`, VL-264). Формат: `{"persona":"architect","fixedAt":"<ISO>"}`. Точка в имени → `listChatThreads` (фильтр `.jsonl`) файл не видит, треды не задваиваются, формат jsonl-истории не трогаем.

**Р2. Первый ход фиксирует роль; последующие `body.persona` игнорируются.**
- sidecar ЕСТЬ → роль берётся ТОЛЬКО из sidecar; `body.persona` не валидируется и не влияет (расхождение — `console.warn('[chat] роль треда <id> уже зафиксирована: <stored>, body.persona=<x> игнорируется')`, ход продолжается, ошибки пользователю нет: клиент в начатом треде пикер не показывает, значит расхождение = сторонний клиент).
- sidecar НЕТ и в истории ещё нет user-сообщений (новый тред) → роль из `body.persona` (как сейчас, валидация сохраняется: неизвестный id → error-событие, sidecar НЕ пишется), затем sidecar записывается.
- sidecar НЕТ, но в истории уже есть сообщения (старый тред до VL-283) → фиксируется `helper` (`DEFAULT_PERSONA_ID`), `body.persona` игнорируется, в лог `console.warn('[chat] тред <id> создан до фиксации роли — зафиксирована роль helper')`. Выбор «helper, а не «не зафиксирована»»: старый чат фактически и работал как helper (дефолт module-state), это поведение не меняется; клиентский бейдж при этом всегда определён (AC3).
- sidecar содержит id, которого больше нет в реестре (роль удалена, напр. `orchestrator` VL-273) → fallback на `helper` + `console.warn`, sidecar не перезаписываем (роль восстановится, если проект вернёт id); ход не падает (fail-open здесь важнее fail-closed: старый тред не должен стать неработающим).

**Р3. Фиксация пишется ДО старта LLM-цикла, но ПОСЛЕ валидации** (сразу после блока резолва роли, до `loadChatHistory`/LLM): ошибка валидации (`Некорректная роль` / `Неизвестная роль`) не должна навсегда портить тред ролью helper.

**Р4. Клиент: пикер — только в пустом треде; в начатом — неинтерактивный бейдж.** `activePersonaId` (module-state) остаётся «выбором для НОВОГО треда» и НЕ меняется при открытии существующего треда (AC5): бейдж берёт роль из ответа `GET /api/chat/threads/:id`, а не из module-state.

## Риски

- **R1. Смена поведения для старых тредов** (через API больше нельзя сменить роль) — намеренно (AC1); смягчение: `console.warn` при расхождении, sidecar можно удалить вручную, чтобы пересоздать роль.
- **R2. Sidecar и удалённая роль (lesson-133)** — fallback `helper` без перезаписи файла, иначе возврат роли в реестр не восстановил бы тред.
- **R3. Запись sidecar до LLM-вызова** — при падении хода роль уже зафиксирована; это ожидаемо (роль — свойство треда, не хода), но ошибки валидации не должны фиксировать ничего → фиксация строго после валидации.
- **R4. Клиентское определение «тред начат»** — используем `load.persona`/наличие композера в `ViewportFooter` vs `EmptyState`, а не `messages.length`: у assistant-ui пустой тред без сообщений после ошибки загрузки остаётся `EmptyState`, поведение консистентно.

- **R6. Параллельные треды** — `fixThreadPersona` идемпотентна и пишет только при отсутствии файла (последний писатель не перетирает первый), гонки при этом безвредны.
