## Description
<!-- SECTION:DESCRIPTION:BEGIN -->
Что-то ломает форматирование RichMessage при ответе на /task VL-78.

## Диагноз (Фаза 1 Spec)

Первопричина: тело VL-78 (description, Implementation Plan, Notes) содержит СЫРЫЕ rich-теги прямо в тексте:

```
<tg-button type="callback_data" data="next:<id>">
<tg-button-row align="center">
<details><summary>Заголовок</summary>...</details>
```

renderTaskRich (src/bot/rich.ts) вставляет контент секций как есть: fenceSafe экранирует только последовательности ```, но НЕ трогает `<`/`>`. Поэтому сырые теги из текста задачи попадают в markdown rich-сообщения и интерпретируются парсером Telegram как настоящие элементы rich-разметки:

1. `<tg-button ...>` / `<tg-button-row ...>` в тексте — дублируются/ломают кнопки карточки.
2. `<details>` / `</details>` в тексте конфликтуют с `<details>`-обёртками секций (VL-78) — вложенные/несбалансированные details ломают весь рендер карточки.

## Направление фикса

Оборачивать сырые rich-теги пользовательского контента в code-блоки (указание Pavel в комментарии от 2026-10-04 21:19: «такие куски кода обязательно оборачивать в code блок. Так и читаемость лучше будет»). В renderTaskRich при вставке контента секций (описание, AC, DoD, plan, notes, комментарии) последовательности вида `<tg-button`, `<tg-button-row`, `<details`, `<summary` и парные закрывающие теги оборачиваются в code-разметку, чтобы rich-парсер Telegram не интерпретировал их как элементы, а показывал как код. Служебные теги самого рендера (шапка, tg-button-row, section/details) остаются нетронутыми — оборачивание применяется только к контенту задачи перед вставкой.

Фолбэк MarkdownV2 (formatTaskDetail) не трогаем — сырые теги в нём всегда были просто текстом.

## Алгоритм (src/bot/rich.ts)

### Шаг 1. Новая функция `richTagsSafe(text: string): string` (после `fenceSafe`, строки 27-29)

Оборачивает сырые rich-теги пользовательского контента в code-разметку, чтобы rich-парсер Telegram не интерпретировал их как элементы.

Паттерны (открывающие + парные закрывающие): `<tg-button`, `</tg-button>`, `<tg-button-row`, `</tg-button-row>`, `<details`, `</details>`, `<summary`, `</summary>`.

Алгоритм:
1. Разбить текст на строки, вести флаг «внутри ```-фенса»: строки внутри уже существующего fenced-блока ПРОПУСКАТЬ (не оборачивать повторно — иначе двойная вложенность ломает рендер).
2. Строка, целиком состоящая из тегов/пространства (содержит один из паттернов и после удаления тегов остаётся пустая/только пробелы): объединять с соседними такими строками в один fenced-блок ``` ... ``` — так читаемость примеров максимальна (указание Pavel 21:19 «оборачивать в code блок»).
3. Строка с тегами, смешанными с обычным текстом: каждое вхождение тега оборачивать в inline-код одинарными бэктиками (`` `<tg-button ...>` ``); если внутри тега есть бэктики — использовать двойные (`` ``...`` ``).

### Шаг 2. Новая функция-композит `contentSafe(text: string): string`

`contentSafe = (t) => richTagsSafe(fenceSafe(t))` — сначала гасим ``` (fenceSafe, строка 29), затем оборачиваем теги. Порядок обязателен: richTagsSafe вставляет бэктики, которые не должны попасть под замену fenceSafe.

### Шаг 3. Точки замены fenceSafe → contentSafe в renderTaskRich (строки 112-170)

- строка 146: `section('Описание', fenceSafe(task.description), true)` → `contentSafe(task.description)`;
- строка 63 (внутри `checklist()`): `- [${checked ? 'x' : ' '}] ${fenceSafe(text)}` → `${contentSafe(text)}` (AC + DoD — обе секции ходят через checklist);
- строка 155: `section('Implementation Plan', fenceSafe(task.implementationPlan))` → `contentSafe(...)`;
- строка 158: `Implementation Notes` — аналогично;
- строка 161: `Final Summary` — аналогично;
- строка 165: `**${c.author}** · ${c.created}\n\n${fenceSafe(c.text)}` → `contentSafe(c.text)`.

Служебные теги рендера (шапка, `<tg-button-row>` кнопок строки 122-134, `<details>/<summary>` обёртки `section()` строки 45-55) не затрагиваются — contentSafe применяется ТОЛЬКО к контенту задачи перед вставкой.

## Диагноз

1. **fence-guard пропускал теги между маркерами ` ` `, которые fenced-блоком в Telegram НЕ являются.** `contentSafe = richTagsSafe ∘ fenceSafe`: fenceSafe гасит ``` в ` ` `, а fence-guard считал регион между маркерами «уже в коде» и не оборачивал теги. Но ` ` ` — это не fence (нужны 3+ подряд бэктика), поэтому теги из ```-блоков контента (пример в Description VL-81 и в комментарии Фазы 1) оставались сырыми: парсер Telegram видел настоящие `<tg-button-row>`, `<tg-button>`, `<details><summary>Заголовок</summary>...` и ломал карточку.
2. **richTagInlineSafe оборачивал теги, уже сидящие в inline-коде.** Текст вида «`<details><summary>`» или «(`` `<tg-button ...>` ``)» (Implementation Plan и комментарии VL-81) получал повторные бэктики вокруг каждого тега — пары code-спанов ломались, и теги вываливались наружу как сырой текст.

## Исправление (src/bot/rich.ts)

- `richTagsSafe`: маркеры бывших ```-блоков (` ` ` и ```) обрабатываются как отложенный маркер — если регион целиком из теговых строк, маркеры поглощаются, теги уходят в **настоящий** fenced-блок; вокруг нетегового контента маркер остаётся текстом. Fence-guard (skipline) удалён.
- `richTagInlineSafe` → `codeSpans` + `wrapRichTags`: строка разбивается на код-спаны и текст по правилам markdown (ран N бэктиков закрывается следующим раном длины N); теги оборачиваются только ВНЕ спанов — теги внутри кода не изменяются.
- Служебные теги рендера (шапка, ряд кнопок, обёртки секций) не затронуты; фолбэк MarkdownV2 не изменён.
