## Description
<!-- SECTION:DESCRIPTION:BEGIN -->
Инцидент VL-98 (doc-12): loop.ts сравнивает только одинаковые сигнатуры tool-вызовов подряд — verify-loop из 5 ходов с РАЗНЫМИ grep-вызовами и одинаковым намерением («Приступаю к реализации… уточню якоря») прошёл мимо детектора и съел wall-time до убийства фазы.

Решение: guard по промежуточному тексту — N ходов (константа, напр. 4) подряд с идентичным текстом после нормализации (trim + схлопывание пробелов/переносов) → fail «Зацикливание: N ходов подряд с одним и тем же намерением — смени подход, проверь git status или уточни задачу». Сравнивать только промежуточный текст хода (до tool_calls); сигнатуры инструментов НЕ участвуют — легитимная работа (патч-скрипты, новые файлы) при каждом разном тексте не триггерит guard. Fail идёт штатным путём (контракт resume VL-103 сохраняется).

## Порядок действий (src/agent/loop.ts)

1. **Поле лимита** — в interface LoopLimits (строка 19, после `loopDetectionRepeat`, ~строка 40) добавить:
   ```ts
   /** Сколько ходов подряд с одним и тем же промежуточным текстом считать зацикливанием намерений (VL-119, дефолт 4). */
   intentLoopRepeat?: number;
   ```
   Единообразие с существующим `loopDetectionRepeat`; дефолт — константа.

2. **Константа** — после `LOOP_DETECTION_REPEAT_DEFAULT = 3` (строка 99):
   ```ts
   const INTENT_LOOP_REPEAT_DEFAULT = 4;
   ```

3. **Резолв лимита** — в runLoop рядом со строкой 112:
   ```ts
   const intentRepeatLimit = options.limits?.intentLoopRepeat ?? INTENT_LOOP_REPEAT_DEFAULT;
   ```

4. **Стейт** — после `let streak = 0;` (строка 151):
   ```ts
   let prevIntent: string | null = null;
   let intentStreak = 0;
   ```

5. **Guard** — в for(;;)-цикле СРАЗУ ПОСЛЕ блока `if (response.toolCalls.length === 0) { ... }` (закрывается на строке ~228), перед `if (response.text) partialText += ...` (строка 230) и перед pushMessage assistant(tool_calls) (строка ~232). Срабатывает только для ходов С tool_calls (промежуточный текст), ДО выполнения tool-вызовов этого хода (экономит wall-time — инцидент VL-98):
   ```ts
   // Guard зацикливания намерений (VL-119, инцидент VL-98): N ходов подряд
   // с идентичным промежуточным текстом (намерением) при РАЗНЫХ вызовах
   // инструментов сигнатурный детектор VL-83 пропускает. Сравнивается только
   // текст хода до tool_calls, после trim + схлопывания пробелов/переносов;
   // пустой текст не участвует (молчаливые tool-ходы легитимны) и streak
   // не сбрасывает. Fail идёт штатным fail()-путём (контракт resume VL-103).
   const intent = (response.text ?? '').trim().replace(/\s+/g, ' ');
   if (intent) {
     if (intent === prevIntent) {
       intentStreak++;
     } else {
       intentStreak = 1;
       prevIntent = intent;
     }
     if (intentStreak >= intentRepeatLimit) {
       return fail(
         `Зацикливание: ${intentStreak} ходов подряд с одним и тем же намерением — смени подход, проверь git status или уточни задачу.`,
       );
     }
   }
   ```

   Ключевые решения:
   - **Пустой текст пропускается без сброса streak** — иначе сломались бы все тесты VL-83/103 (там text:'' в tool-ходах), и молчаливые, но разные по инструментам ходы не должны фейлиться.
   - Fail — ДО pushMessage текущего assistant(tool_calls): несработавший 4-й ход не попадает в диалог и не выполняется; fail() сам дописывает assistant с текстом ошибки (контракт VL-103).
   - Сравнение регистрозасисимое — намеренно (простота, задача не требует регистронезависимости).

## Порядок действий (src/agent/loop.test.mjs)

Новый describe в конце файла (после блока VL-110, ~строка 440): `describe('runLoop guard по намерению (VL-119)', ...)`.

Использовать существующие фейки `fakeLlm` / `countingTool` (строки 14–59). Тесты:

1. **Срабатывание**: 4 хода, текст «Приступаю к реализации… уточню якоря» в каждом, tool-вызовы с РАЗНЫМИ аргументами ({x:1},{x:2},{x:3},{x:4}) → `is_error=true`, `assert.match(res.result, /Зацикливание/)`, `/4 ходов подряд/`, `/намерением/`; `toolState.calls === 3` (4-й ход не выполнен).
2. **Меняющийся текст — нет срабатывания**: 5 ходов с разными текстами и разными аргументами + финал «итог» → `is_error=false`, `result==='итог'`, `toolState.calls===5`.
3. **Порог**: 3 хода с одинаковым текстом + финал → без fail (ниже порога 4).
4. **Регресс VL-83/103 (пустой текст)**: 5 ходов с `text:''` и разными аргументами + финал → `is_error=false` — пустой текст guard не триггерит.
5. **Нормализация**: 4 хода с текстами, отличающимися только пробелами/переносами («Приступаю.\nУточню якоря.», «  Приступаю.  Уточню   якоря. » и т.п.) → fail.
6. **Контракт resume VL-103**: при срабатывании guard `res.messages` заканчивается assistant-сообщением с текстом ошибки; onMessage увидел это сообщение.

Существующие тесты НЕ менять.

## Риски

- **Ложные срабатывания**: агент 4 хода подряд с одним и тем же коротким текстом («Ок.») при разной работе — fail прервёт легитимную фазу. Смягчение: понятное сообщение, resume продолжает сессию; порог 4 (не 3). При частых ложных срабатываниях — поднять константу.
- **Регистрозависимое сравнение**: «Приступаю» ≠ «приступаю» — сознательное упрощение; при надобности уточнить отдельной задачей.
- **Пустой текст не сбрасывает streak**: «текст A → пустой ход → текст A → …» посчитается зацикливанием — это соответствует духу задачи (намерение не менялось), отражено в комментарии кода.
- **num_turns при fail**: 4-й ход уже засчитан в num_turns (запрос сделан) — корректно отражает расход.
