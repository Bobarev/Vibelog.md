## Description
<!-- SECTION:DESCRIPTION:BEGIN -->
Пятая задача реализации doc-25 (v1.3, §2.3, §4.3). Ядро `vb install` — доставка файлов компонента из реестра в проект.

**Все зависимости закрыты:** VL-333 (схемы, `readLock`/`writeLock`/`hashFile`/`resolveAliasPath`), VL-335 (`fetchRegistryItem`), VL-336 (секция `components` создаётся через `vb init --components`).

**Что делает команда:**
```
vb install vibelog.md/ui/button [--yes] [--force] [--dry-run] [--branch <b>]
```
1. Находит корень проекта и секцию `components` в `.vibelog/settings.json`.
2. Разбирает путь `alias/repo/name` (ровно три сегмента).
3. Скачивает `public/r/<name>.json` через VL-335.
4. Валидирует схему элемента.
5. Вычисляет целевые пути из `aliases` + `target`.
6. Разрешает конфликты по хешам из `installed.lock.json`.
7. Пишет файлы атомарно (temp + rename), обновляет lock.

**Границы.** Задача НЕ реализует: проверку npm-зависимостей и `registryDependencies` (это задача 6), `vb create` (задача 7). Здесь — только доставка файлов одного элемента и запись lock.

**Ключевое требование — атомарность.** Сценарий сбоя: элемент из трёх файлов, первые два записаны, третий падает (нет прав, диск полон). Проект не должен остаться в полуустановленном состоянии: либо все файлы на месте и lock обновлён, либо ничего не изменилось. Отсюда порядок «сначала всё во временный каталог, потом перемещения, потом lock».

**Идемпотентность.** Повторный `vb install` того же компонента — штатная операция (пользователь мог забыть, что уже ставил). При совпадении хешей файлы не трогаются, lock не переписывается: иначе каждый запуск даёт шумный diff в git.

**Связанные решения:** doc-25 §2.3 (флаги), §3.2 (схема lock), §3.3 (схема элемента), §4.3 (поток), §5.2 (коды), §8 п.7 (код 4 только при полном провале); decision-9 (install не инициализирует), decision-10 (хеши).

## Implementation Plan
<!-- SECTION:PLAN:BEGIN -->
**Файлы.** `src/cli/commands/install.ts` (команда и оркестрация), `src/core/install.ts` (логика без CLI: план, конфликты, запись), `src/core/install.test.mjs`, `src/cli/router.ts` (регистрация команды и справка). Переиспользовать: `components-config.ts` (VL-333), `registry-fetch.ts` (VL-335), `paths.ts` (корень проекта, `.vibelog/tmp`).

**Шаг 1. Разбор пути и предусловия.**

1. `parseInstallPath(raw): { alias, repo, name }` — ровно три непустых сегмента; иначе `InstallError` с кодом `1` и подсказкой формата `vibelog.md/ui/button`.
2. `resolveInstallContext(cwd)` — корень проекта, `readComponentsConfig`; `null` → код `2` «выполните `vb init --components`». Alias не найден в `registries` → код `2` со списком доступных.
3. Ветка: `--branch` приоритетнее `registries[alias].branch`.

**Шаг 2. Загрузка и валидация элемента.**

4. `fetchRegistryItem({ baseUrl: resolveRegistryBase(), owner, repo, branch, name })` из VL-335. Ошибки пробрасываются как есть (код `3`), но текст дополняется контекстом «элемент `<alias>/<repo>/<name>`».
5. Схема элемента уже валидируется в VL-335 (`validateRegistryItem`); здесь — дополнительная проверка, что `item.name === name` (защита от подмены).

**Шаг 3. План установки (чистая функция, без записи).**

6. `buildInstallPlan(cwd, config, lock, item): InstallPlan` — для каждого `files[]`:
   - `targetPath = resolveAliasPath(cwd, config, aliasForType(file.type), file.target)`; `aliasForType`: `registry:ui` → `ui`, `registry:lib` → `utils`, `registry:hook` → `components`, `registry:component` → `components`;
   - `absPath` — абсолютный путь; проверка выхода за корень (повторно, вторая линия защиты);
   - `existing` — есть ли файл; `existingHash` — `hashFile(absPath)`, если есть;
   - `lockedHash` — из `lock.components[item.name]?.files[relPath]?.hash`;
   - `action: 'create' | 'skip-identical' | 'conflict'`.
7. `InstallPlan` содержит: `item`, `files[]` с `action`, `conflicts[]`, `willWrite[]`, `willSkip[]`. План — единственный источник истины для `--dry-run` и для реальной установки (одна логика, два режима).

**Шаг 4. Разрешение конфликтов.**

8. `--force` → все `conflict` становятся `create` (перезапись).
9. `--yes` без `--force` → все `conflict` становятся `skip-conflict` с предупреждением.
10. Интерактив → `p.select` на каждый конфликт: «перезаписать» / «пропустить» / «показать diff». Diff — `p.note` с построчным сравнением (без внешних зависимостей: простой unified-подобный вывод, ограничить 40 строками).
11. `p.isCancel` → код `5`, ничего не записано.

**Шаг 5. Атомарная запись.**

12. `applyInstallPlan(cwd, plan)`:
    - создать `.vibelog/tmp/install-<pid>-<rand>/` (через `tmpDir` из `paths.ts`);
    - записать все `willWrite` файлы в этот каталог, сохраняя относительную структуру;
    - **после успешной записи всех** — переместить (`rename`) на целевые места, создавая родительские каталоги;
    - при ошибке на любом шаге: удалить temp, восстановить уже перемещённые файлы из temp (если они там ещё есть) либо из бэкапа, который делается перед первым перемещением; lock не трогать; код `3`.
13. Бэкап перед перемещением: для каждого существующего целевого файла сохранить копию в temp/backup/ — это позволяет откатить частично выполненные перемещения.
14. После успешных перемещений — `hashFile` каждого записанного файла, собрать новую запись `lock.components[item.name]`, `writeLock` (атомарно, VL-333).
15. Удалить temp-каталог в `finally`.

**Шаг 6. Идемпотентность.**

16. Если все файлы `skip-identical` и запись в lock уже совпадает (version, dependencies, хеши) — lock **не перезаписывать** (сравнить сериализованные объекты), вывести «уже установлено, изменений нет», код `0`.
17. `installedAt` обновляется только при реальной записи файлов — иначе повторный запуск меняет lock и даёт diff.

**Шаг 7. Вывод и коды.**

18. Итоговый блок: список записанных путей, пропущенных с причиной, обновлённая запись lock.
19. Коды: `0` — успех и частичный успех; `4` — все файлы пропущены по конфликту (ничего не записано); `2`/`3`/`5` — по doc-25 §5.2.
20. `--dry-run` — печатает план (пути, действия, конфликты) и выходит с `0`, не создавая даже temp-каталог.

**Шаг 8. Регистрация команды.**

21. `src/cli/router.ts`: `case 'install': return runInstall(positional, flags, cwd)`; справка — строка в общем списке и `showCommandHelp('install')`.
22. Флаги: `--yes`, `--force`, `--dry-run`, `--branch`. Неизвестный флаг — код `1`.

**Шаг 9. Тесты (`src/core/install.test.mjs`).**

23. Фикстура: временный проект с `.vibelog/settings.json` (секция `components`), локальный HTTP-сервер с `public/r/*.json` (через `VIBELOG_REGISTRY_BASE_URL`).
24. Успех: один файл → создан, lock содержит корректный хеш.
25. Мультифайловый элемент → все файлы на месте, все записи в lock.
26. Конфликт без `--force` в `--yes` → файл не перезаписан, код `0` (частичный успех), предупреждение в выводе.
27. Конфликт с `--force` → перезаписан, хеш в lock обновлён.
28. Все файлы конфликтуют и пропущены → код `4`.
29. `--dry-run` → ни одного нового файла, lock не изменён, план напечатан.
30. Идемпотентность: два прогона подряд → после второго `installed.lock.json` побайтово тот же.
31. Атомарность: элемент из трёх файлов, третий целевой путь сделать недоступным (каталог только для чтения) → ни один файл не появился, lock не изменён, temp удалён.
32. `target: "../evil.svelte"` → код `3`, ничего не записано.
33. Неизвестный alias → код `2`; отсутствие секции `components` → код `2`; путь из двух сегментов → код `1`.

**Риски.**
- `rename` между разными файловыми системами не работает — temp-каталог обязан быть **внутри проекта** (`.vibelog/tmp`), не в `os.tmpdir()`.
- Откат частичных перемещений — самая хрупкая часть: без бэкапа существующих файлов откат невозможен. Тест на атомарность должен проверять именно «файл был, стал прежним», а не только «файла нет».
- `installedAt` при идемпотентном повторе: обновление ломает побайтовую идемпотентность lock — обновлять только при реальной записи.
- Интерактивный diff без зависимостей: не тащить `diff`-пакет, ограничиться простым построчным сравнением.
- `--yes` + конфликт = пропуск: пользователь может не заметить, что компонент не установился. Итоговый блок должен явно писать «пропущено N файлов, используйте `--force`».

**Проверка.** `pnpm typecheck && pnpm test`; вручную — в чистом проекте `vb init --components`, затем `vb install vibelog.md/ui/base` против локального фикстура, повторный запуск (diff пустой), `--dry-run` (ничего не создано).
