## Description
<!-- SECTION:DESCRIPTION:BEGIN -->
## Контекст

Фича 3, шаг 3 из 3 (завершающий). Зависит от VL-315 (`gateway`/`vendor` в ModelConfig) и VL-316 (каталог шлюза + страница «Модели»).

Проблема из обсуждения с Pavel: RouterAI обслуживает одну и ту же модель через разных вендоров (baidu / makora / morph / Xiaomi / gmicloud), и цены у вендоров меняются в течение дня. Сейчас в `.vibelog/settings.json` лежат тарифы, вписанные руками в какой-то момент времени: если вендор поднял цену, мы узнаём об этом только по счёту. Сверки с живым каталогом нет никакой.

Данные для сверки уже доступны программно (ref-18): `GET /v1/models/{author}/{model}/endpoints` отдаёт цены по каждому вендору, без аутентификации. Каталог с кэшем и нормализацией цен будет готов в VL-316 (`src/core/provider-catalog.ts`).

## Цель

Перед запуском фазы или хода чата сверять текущую цену вендора в каталоге с ценой в settings. При расхождении выше настраиваемого порога (дефолт 10%) — сообщить пользователю. Поведение настраивается; по умолчанию — предложение пользователю, а не молчаливое продолжение.

## Решения (согласованы)

- **`on_drift` по умолчанию = `'ask'`** — предложение пользователю («цена выросла: было → стало, продолжить / перейти на другого вендора»).
- Режимы: `'ask'` (дефолт), `'auto'` (автоматический переезд на альтернативного вендора), `'warn'` (только предупреждение, работа идёт).
- **`'auto'` без альтернативного вендора деградирует в `'ask'`**: молчаливое продолжение по выросшей цене недопустимо.
- Порог — `threshold_percent`, дефолт **10**.
- Сверка **не блокирует работу при недоступном каталоге**: `offline: 'allow'` (дефолт) — продолжаем без сверки и пишем причину в лог; `'block'` — отказ с понятным текстом.
- Кэш каталога из VL-316 + свой TTL: повторная сверка в пределах TTL не делает сетевых запросов (иначе на каждый ход — сетевой вызов).

## План

1. `src/core/pricing-guard.ts` (new): `resolvePricingGuard(cwd)` (терпимый парсинг секции, паттерн `resolveChatLimits`), `checkPricingDrift(cwd, modelId)` → `{state: 'ok'|'drift'|'unknown', components: [{name, was, now, deltaPercent}], maxDeltaPercent, alternative?: vendorId}`, `formatDriftMessage()`.
2. Сверка по паре `(gateway, model, vendor)` из `ActiveModel` (VL-315) против `catalog.listVendors()` (VL-316); сравнение по каждому компоненту тарифа (input/output/cache) отдельно, дрейф фиксируется по максимальному отклонению.
3. `src/web/chat.ts` — сверка перед началом хода: при `disabled: false` и `state: 'drift'` по режиму `on_drift` либо карточка-подтверждение (новый тип data-части в SSE, по образцу `approval`), либо автопереключение vendor на ходу, либо предупреждение в ленте.
4. Точка перед фазой: проверка в оркестраторе до старта фазы; при `ask` — фаза не стартует, причина пишется в задачу/лог (уточнить точку: `src/web/orchestrator.ts` или `src/agent/llm-env.ts`, где уже валидируются models/providers).
5. `src/web/api.ts` — `GET /api/pricing/drift?model=<id>` и `POST /api/pricing/refresh` (обновить тариф в settings из каталога, с валидацией перед записью).
6. Клиент: карточка дрейфа в чате (по образцу `approval-card.tsx` / `stopp-run.tsx`, компоненты `surfaces.tsx`); на странице «Модели» — индикатор состояния цены и кнопка «Обновить тариф из каталога».
7. Страница настроек: блок `pricing_guard` (Switch enabled, Input threshold_percent, Select on_drift, Input catalog_ttl_minutes, Select offline) — по образцу существующих полей `chat_*`.
8. Тесты: расчёт дрейфа (ровно на пороге, выше/ниже, нулевой тариф — деление на ноль), три режима `on_drift`, деградация auto→ask без альтернативы, offline-поведение, работа кэша (нет повторного сетевого вызова в пределах TTL), сверка по паре вендора (не по модели вообще).
9. Документация: `docs/user-guide.md` (секция `pricing_guard`, объяснение режимов), README, CHANGELOG.

## Риски

- **R1. Неверная пара при сверке.** Если сверять с ценой «модели вообще», а не конкретного вендора, будут ложные срабатывания (у mimo-v2.6-flash цена у makora 13/29, у Xiaomi 14/29). Пара обязательна: gateway + model + vendor.
- **R2. `pricing_units`.** Цены в каталоге могут отдаваться за токен, а в settings — за 1M. Нормализация — в VL-316, здесь только потребление. Тест на ×1e6 обязателен.
- **R3. Сетевой вызов на каждый ход.** Без кэша с TTL сверка превращается в лишний запрос к шлюзу перед каждым сообщением — TTL обязателен, дефолт не меньше 15 минут.
- **R4. Автопереключение vendor посреди работы.** Формат запроса не меняется (vendor уходит в `body.provider.order`, VL-315), но смена вендора может изменить качество ответов. Поэтому `'auto'` не дефолт, а смена фиксируется в логе треда/фазы.
- **R5. Ложные срабатывания на нулевых тарифах.** `cache_per_1m: 0` (бесплатный кэш) даёт деление на ноль при расчёте процента — считать как «оба нуля → дрейфа нет», «было 0 → стало >0» → дрейф бесконечный (считать отдельным случаем).

## Решения по открытым вопросам (Pavel, 2026-11-02)

- **Точка проверки перед фазой — `ensureLlmEnv()` (`src/agent/llm-env.ts:247`, ветка `validateModelsConfig` на стр. 269).** Обоснование по коду:
  - вызывается из CLI агента (`src/agent/cli.ts:602`) — ровно перед стартом фазы, уже после резолва модели;
  - рядом живёт `resolveRunModel()` (`llm-env.ts:112`) — источник истины о том, какая модель реально пойдёт в запрос: приоритет `--model` → `--model-follow-settings` → мета сессии → `models.default`, с fail-open при битой мете;
  - `checkPricingDrift` получает готовый `ActiveModel` (с `gateway`/`model`/`vendor` из VL-315) — без повторного резолва и без риска разойтись с фактическим запросом.
  - Оркестратор (`src/web/orchestrator.ts`) НЕ подходит: `validateModelsConfig` там не вызывается (проверено поиском), он только спавнит CLI.
- **Сверяется модель, которая реально уйдёт в запрос, а НЕ `models.default`:**
  - для фаз — `ActiveModel` из `resolveRunModel` (учитывает мету сессии и `--model`);
  - для чата — тот же `ActiveModel`, что уходит в `createLlmClient`, то есть резолв из `body.model` через `resolveModelById` (`src/web/chat.ts:827`), а не `resolveActiveModel`. Иначе при модели, выбранной в пикере, сверялась бы цена `models.default`.
- **UI-часть «settings vs каталог» перенесена в VL-316** (решение по той задаче): на странице «Модели» уже видно состояние цены и есть кнопка «Обновить тариф из каталога». В VL-317 остаются `GET /api/pricing/drift`, режимы `on_drift` и проверка перед ходом/фазой — индикатор на странице моделей не дублируем.
