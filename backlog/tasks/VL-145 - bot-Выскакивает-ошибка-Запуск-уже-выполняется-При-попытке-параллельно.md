## Description
<!-- SECTION:DESCRIPTION:BEGIN -->
#bot Выскакивает ошибка: ⚠️ Запуск уже выполняется При попытке параллельно продолжить прерванную сессию у второй задачи (первая была удачно запущена).

## Уточнение постановки (Фаза 1 Spec)

**Проблема:** из бота не получается запустить «Резюме сессии» на нескольких задачах: при попытке параллельно продолжить прерванные сессии у второй задачи выводится ошибка «⚠️ Запуск уже выполняется», хотя первая задача была удачно запущена.

**Ожидаемое поведение:**
- Разные задачи должны выполняться параллельно — блокировка касается только повторного запуска той же самой задачи (не должна срабатывать на вторую, отличную задачу).
- Параллельность поддерживается в обоих режимах: CLI (ручной запуск, vibelog run) и web-оркестратор (автоматические фазы).

**Ограничения:** формат хранения данных Backlog.md не меняется; Node.js 20+, без нативных зависимостей (macOS 10.15 Catalina).

# План реализации VL-145: разрешить параллельный запуск разных задач

## Корневая причина (диагностика)

Единственный guard — `src/web/orchestrator.ts:270` (`if (activeRuns.has(runKey))` → `{ error: 'Запуск уже выполняется' }`), in-memory `Map activeRuns` (L70). Ключи (`runKey`):
- фазы задач — `taskId` (L133) → разные задачи уже параллельны;
- `/prompt` — глобальная строка `'prompt'` (L161);
- **`startResume` — глобальная строка `'resume'` (L215) → ВТОРОЙ resume любой задачи получает guard, хотя это разные задачи. Именно этот случай из инцидента** («Резюме сессии» на нескольких задачах из бота → «⚠️ Запуск уже выполняется»).

Дополнительная дыра того же guard'а: resume с метой задачи (`worktreeTaskId`) и фаза ЭТОЙ ЖЕ задачи живут под разными ключами (`'resume'` vs `'VL-N'`) — два агента могут одновременно работать в одном worktree (против ожидания «блокировка — только повторного запуска той же задачи»).

CLI: общих локов нет (grep по `src/cli`, `src/agent`, `bin/` — отсутствуют; ручные запуски — независимые процессы) — код CLI не меняется. Формат данных Backlog.md не меняется (только in-memory Map).

### 3. `getRun` (L570–577): регистронезависимый fallback

Прямой `map.get(taskId)` не найдёт канонический ключ при другом регистре вызова (`getRun('ot-5')` → stored `'OT-5'`). Добавить локальный helper (без `cwd`, поэтому без `taskIdPattern` — точное совпадение, затем линейный поиск по `toUpperCase()`; Map содержит единицы записей):
```ts
function lookupCI<V>(map: Map<string, V>, k: string): V | undefined {
  const direct = map.get(k);
  if (direct !== undefined) return direct;
  const up = k.toUpperCase();
  for (const [mk, mv] of map) if (mk.toUpperCase() === up) return mv;
  return undefined;
}
```
`getRun`: `lookupCI(activeRuns, taskId)` → иначе `lookupCI(lastRuns, taskId) ?? null`. Ключи `'prompt'`/`resume:<id>` бьются напрямую (первый шаг) — поведение прежнее.

Побочный эффект (желаемый): во время resume карточка задачи (`getRun(id)` в боте, L379/407/1013 handlers.ts; `GET /api/tasks/:id/trigger` в api.ts:75) показывает running — раньше resume в карточке не отражался.
