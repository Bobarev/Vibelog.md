# MCP-справочник Vibelog.md

49 инструментов MCP-сервера (stdio, JSON-RPC 2.0). Совместимо с Backlog.md.
Автоматическое подключение: `vibelog init` пишет `mcpServers` в `.qwen/settings.json`
(ручная настройка — в [MCP-SETUP.md](../MCP-SETUP.md)).

Формат вызова:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "backlog_create_task",
    "arguments": { "title": "Пример" }
  }
}
```

Смотрите также: [Руководство пользователя](user-guide.md) · [CLI-справочник](cli-reference.md)

Полный актуальный перечень инструментов с описаниями — `vibelog capabilities --json` (секция `data.mcpTools`), генерируется из `listTools()` и не устаревает; `vibelog capabilities` без флага печатает компактный markdown (VL-394).

## Handshake: поле `instructions` (VL-395)

Ответ на MCP `initialize` содержит поле **`instructions`** — необязательное строковое поле результата по спецификации MCP (2024-11-05), предназначенное для «нулевого хода» агента: клиент (qwen, opencode, claude) получает текст в handshake, ещё до первого `tools/list` и без чтения файлов проекта.

Что в нём (константа `MCP_INSTRUCTIONS` в `src/mcp/server.ts`, ≈1 КБ, лимит — 2000 символов):

- что такое Vibelog.md и что задачи в `backlog/tasks/*.md` правятся MCP-инструментами (`backlog_*`), а не `edit`/`write_file`;
- фазы workflow по умолчанию (`To Do --spec--> Spec --plan--> Planned --code--> Review --close--> Done`), ветка `reject` и fix-цикл `Review --code--> Review`, служебные фазы (`comment`, `prompt`, `analyze`, `resume`);
- явное «это дефолт в КОДЕ (`DEFAULT_WORKFLOW`), секции `workflows` в `.vibelog/settings.json` может не быть — её отсутствие нормально»;
- правило доступа: чтение — сразу, запись — через подтверждение пользователя;
- отсылка за полным справочником — `vibelog capabilities` / `vibelog instructions`.

Ориентир сознательно неполный: перечня MCP-инструментов (он в `tools/list`) и шаблонов фаз в нём нет. Текст статичен и не зависит от проекта — он не читает `settings.json`/`cwd`, поэтому не может разъехаться с протоколом при битом конфиге. Переопределять его не нужно и нечем; полный справочник — `vibelog capabilities` (генерируется из реестров кода).

#### Контракт ответа write-инструментов (VL-262)

`backlog_create_task`, `backlog_update_task`, `backlog_update_status`, `backlog_add_comment`, `backlog_update_dependencies` отвечают **JSON-снимком** вместо «голого» текста:

```json
{ "ok": true, "message": "Задача VL-42 обновлена: title, labels", 
  "applied": { "title": "…", "labels": ["a"] }, "skipped": [ { "field": "definitionOfDone", "reason": "неизвестное поле инструмента" } ] }
```

- `message` сохраняет прежние формулировки («создана»/«обновлена») — substring-проверки и промпты продолжают работать.
- `applied` — значения полей **после** записи (читаются из сохранённой задачи), а не перечисление аргументов; `applied` всегда атомарен: обновление с несколькими полями либо применяется целиком, либо не применяется вовсе (все валидации — до единственной записи файла).
- `skipped` — переданные ключи вне известного набора полей (опечатка, camelCase-вариант) и переданный `null`: раньше они молча игнорировались, теперь перечислены с причиной.
- `idempotentReplay: true` — ответ отдан из кэша идемпотентности (`.vibelog/idempotency.json`, TTL 24 ч, кап 200 записей), второй эффект не выполнялся.
- `missing` + `hint` (VL-319) — аддитивные поля ack-контракта: `missing: SkippedField[]` перечисляет поля, которые **по смыслу обязательны, но не заполнены** (например, пустое тело урока), а `hint` называет следующий шаг. Заполняются хелпером `ackNoopDetailed`/`ackErrorDetailed` (`src/mcp/tool-result.ts`); `ackNoop`/`ackError` остались обёртками, поэтому остальные инструменты отвечают как раньше. Причина: noop-ответ, где `applied` перечислял переданные поля, а отсутствующее (`content`) не называлось нигде, читался моделью как «применено» — модель дословно повторяла вызов до капа `MAX_NOOP_REPEATS_PER_RUN` (сессия `agent-1793712738536`, Close VL-318).
- **`outcome` + `next` — единый исход ответа (VL-357, протокол v2, doc-27).** Вместо свободной комбинации флагов ответ несёт **один** исход: `outcome: 'applied' | 'partial' | 'noop' | 'rejected' | 'read' | 'unknown'`, а следующий шаг — в объекте `next: { retryWith?, missing?, hint? }`. Семантика: `applied` — всё переданное записано; `partial` — записано что-то, но сущность осталась неполной (`next.missing` обязателен); `noop` — переданные значения уже были; `rejected` — не записано ничего, есть причина (`next.retryWith`/`next.hint`); `read` — эффекта не было по природе операции; `unknown` — не-JSON ответ, исход неизвестен. Флаги `ok`/`noop`/`denied`/`read` **вычисляются из `outcome`** при сериализации (`applied`/`partial`/`read` → `ok:true`; `noop` → `ok:false, noop:true, reason:'noop'`; `rejected`/`unknown` → `ok:false`), поэтому старые потребители (тесты, промпты фаз, веб-слой) читают ответ как раньше, а тексты `message` не менялись (инвариант VL-262). Единственное видимое изменение формы: `ackError` отдаёт три ключа `error/ok/outcome` вместо двух. Поля `missing`/`hint`/`retryWith` разворачиваются **в корень** ответа (плоская форма, см. ниже), `parsedErrorText`/`parsedAckNext` в цикле агента читают именно её. Инвариант «валидация одного поля не блокирует операцию» закреплён тестом обхода `listTools()` в `src/mcp/write-ack-contract.test.mjs`: write-инструмент, отвечающий `rejected` на отсутствие необязательного по смыслу поля, валит сборку.
- **Форма ответа — ПЛОСКАЯ, вложенного `next` в JSON нет (VL-369).** `next` — внутренняя структура `ToolAckInput`: `serializeAck` копирует `next.missing`/`next.hint`/`next.retryWith` в **корень** объекта. Реальный ответ инструмента всегда такой: `{ "ok": true, "outcome": "partial", "missing": [...], "hint": "...", "retryWith": {...} }`. Разбор `parsed.next?.x` в `src/agent/repeat-tracker.ts` был мёртвым кодом (он искал несуществующую вложенную форму) — удалён в VL-369; рабочий разбор `parsed.x` сохранён. Тесты, конструировавшие вложенную форму вручную, переписаны на реальную.
- **`extra` — служебные поля ответа (VL-359).** `ToolAckInput` (`src/mcp/tool-result.ts`) получил аддитивное `extra?: Record<string, unknown>`: `serializeAck` дописывает его ключи в ответ, **не перезаписывая** вычисленные из `outcome` (исход остаётся единственным источником правды). Нужно для ответов рантайма, у которых есть собственный машиночитаемый флаг: guard-ответы веб-чата `duplicateCallResult` (`outcome:'rejected', reason:'duplicate', extra:{duplicate:true}`), `limitCallResult` (`rejected`/`limit`), `noopRepeatCallResult` (`outcome:'noop', reason:'noop_repeat', extra:{noop_repeat:true}`) в `src/web/tool-dedup.ts`. До VL-359 они отдавали плоский JSON `{ok:false, duplicate:true}` в обход сериализатора, и модель в веб-чате видела два формата ответов: инструменты — с `outcome`, guard — без. Тексты `message` не менялись (инвариант VL-262); путь подтверждений не затронут (`ackDenied` не тронут).
- `retryWith` (VL-353) — аддитивное поле отказа: машиночитаемый набор аргументов, которые надо **добавить/изменить** в повторном вызове (например `{ "allowForeign": true }`). Отдаёт его инструмент, у которого исправление однозначно (`ackErrorDetailed(..., { retryWith })`); пустой объект не выводится. Поле читает цикл агента: директива loop detection собирает из аргументов повторённого вызова + `retryWith` **готовый вызов** и показывает его модели целиком — описательное «исправь аргументы» слабая модель не выполняет (инцидент `agent-1794050949211`, Close VL-351: 6 дословных повторов `git_commit` без `allowForeign` → `MAX_ERROR_REPEATS_PER_RUN`). Сейчас `retryWith` отдаёт `git_commit` при отказе `foreignPaths`; механизм общий — любой write-инструмент может его заполнить.
- `noop: true` + `ok: false` + `reason: 'noop'` (VL-303/VL-304, универсально с VL-310, `hint` — VL-326) — вызов **не изменил состояние**: все переданные поля уже имели запрошенные значения, поэтому файл не переписан (в частности, `updated_date`/mtime не сдвинулись). Маркер приходит от **любого** write-инструмента MCP с полями-значениями: `backlog_update_task`, `document_update`, `reference_update`, `lesson_update`, `backlog_update_status`, `backlog_update_dependencies`, `milestone_rename`, `lesson_link`, `reference_link`; инструменты, где noop неприменим по природе (create/remove/sync/add/audit/classify), перечислены с причиной в инвариант-тесте `src/mcp/write-ack-contract.test.mjs`. В ответе есть `applied` (фактические значения) и `message` с явным следующим шагом. **Noop — это ошибка, а не успех (lesson-92):** MCP-сервер дополнительно ставит протокольный `isError: true` (детект — экспорт `isNoopAck(text)`), нейтральный `ok: true` модели читаются как «принято, продолжай» и порождают луп:

```json
{ "ok": false, "noop": true, "reason": "noop",
  "message": "Изменений нет: type уже имеют эти значения. Следующий шаг: backlog_finish_phase (или следующий шаг плана) — повтор этого вызова ничего не изменит.",
  "applied": { "type": "feature" }, "skipped": [] }
```

Модель должна трактовать `noop` как «работа сделана, переходи к следующему шагу» — повтор вызова с теми же аргументами бесполезен; повтор уже применённой сигнатуры агентский цикл **не исполняет** и **не завершает ран терминально**: модели уходит директива «изменения применены — переходи к отчёту», серия подряд ограничена капом `MAX_APPLIED_REPEATS_PER_RUN = 3`, после чего — честный `fail()` с `is_error: true` (VL-310; до VL-310 первый повтор закрывал ран «штатно», из-за чего сессия `agent-1793637056809` оборвалась с несделанной работой). Сравнение «всё уже так» семантическое: массивы (`labels`, `assignee`, `references`, `lessons`, `modifiedFiles`, `dependencies`, `tags`) сравниваются как множества (порядок не значим), `acceptanceCriteria` — по текстам при условии, что все текущие пункты не отмечены, `type` — уже нормализованным, тело документа (`content`) и `reference.description` сравниваются с телом записи. Для `modifiedFiles` сверка идёт по **итоговому объединённому набору** (VL-376): повторный вызов с тем же набором путей даёт `noop`, а не ложную перезапись, хотя бы порядок был другим. Исключение: `append_notes` никогда не даёт `noop` — дописывание в заметки всегда меняет файл; `lesson_link`/`reference_link` сверяют **обе стороны** связи (расхождение — реальное изменение).

- **`hint` обязателен в noop-ответе (VL-326):** `ackNoopDetailed` (`src/mcp/tool-result.ts`) теперь **всегда** заполняет `hint`, если вызывающий не передал свой: универсальный текст «переданные поля уже имеют эти значения — файл не переписан; если нужны другие поля, передай их в ЭТОМ ЖЕ вызове, иначе переходи к следующему шагу». `toolUpdateTask` подставляет свой `hint` с перечнем полей, которые **не были переданы** — с VL-369 набор берётся из `spec.suggest` (поля, пустые в самой сущности и не переданные в вызове), а не из захардкоженного списка `missingTaskFields` (удалён). `ackNoop` осталась байт-в-байт обёрткой: тексты 9 сценариев `NOOP_SCENARIOS` не изменились (регресс-инвариант в `src/mcp/write-ack.test.mjs`). Причина: в инциденте VL-324 модель 12 раз повторяла `backlog_update_task` с уже применёнными `priority`/`type`, а текст noop советовал «Следующий шаг: backlog_finish_phase» — инструмент, которого в веб-чате нет, и не называл настоящую причину.

#### Единый пайплайн обновления сущностей (VL-369)

`backlog_update_task`, `backlog_update_status`, `lesson_update`, `document_update`, `reference_update` больше не содержат собственных циклов сверки «уже так», сборки `applied` и текстов следующего шага. Каждый инструмент — **описание сущности** (`EntitySpec` в `src/mcp/update-pipeline.ts`): `fields` (допустимые имена аргументов), `setFields` (сравниваемые как множества), `bodyArg`, `nonIdempotent`, `build(args, cwd, current)`, `read`/`write`, `snapshot`, `comparable`, `applied`, `completeness`, `suggest`, `message`, `beforeWrite`. Один исполнитель `runUpdate(spec, args, cwd)` проходит шесть шагов: чтение текущего состояния → сборка полей → отсев неизвестных и `null` в `skipped` → расчёт неполноты → сверка «уже так» → запись → сериализация через `serializeAck`.

**Таблица исходов — два булева вместо четырёх веток:** «записали × сущность полная».

| Записали | Сущность полная | `outcome` | Что в ответе |
|---|---|---|---|
| да | да | `applied` | применённые поля |
| да | нет | `partial` | применённые поля + `missing` + `hint`/`retryWith` |
| нет (менять нечего) | да | `noop` | фактическое состояние |
| нет (менять нечего) | нет | `noop` | фактическое состояние + `missing` + `hint` |
| нет (аргумент испорчен) | — | `rejected` | текст ошибки + `retryWith` |

**Инвариант:** write-инструмент делает ровно две вещи — применяет то, что попросили, и сообщает получившееся состояние. Он **никогда не отказывает из-за того, что сущность неполная**: неполнота — свойство сущности, о ней сообщают `missing` + готовым вызовом. `rejected` остаётся только для испорченного аргумента (явно пустое обязательное значение, несуществующий id, значение неверного типа). Четвёртая строка принципиальна: «ничего не изменилось, и сущность неполная» — это `noop`, а не отказ; именно здесь раньше стоял отказ, дававший серию повторов до ограничителя.

**`skipped` — у всех четырёх инструментов.** Неизвестное имя поля и переданный `null` попадают в `skipped` с причиной, а не игнорируются молча (раньше это умел только `backlog_update_task`, остальные отвечали `ok:true` на опечатку в имени поля).

**`missing` — от состояния сущности с учётом workflow и фазы (VL-370)**, а не от списка переданных аргументов. Набор обязательных полей — данные: `DEFAULT_COMPLETENESS` в `src/core/workflow.ts` (форма `workflow → фаза → сущность → поля`) плюс перезапись ключом `completeness` в `.vibelog/settings.json`. Функции: `loadCompleteness(cwd)` (семантика как у `loadWorkflows`: нет ключа / битый JSON / невалидная запись → дефолт, валидные именованные записи сохраняются; запись workflow заменяет дефолтную целиком, не сливается по фазам), `getCompletenessRules(cwd, task, phase)` (имя workflow через `getWorkflowName`; конкретная фаза + `'*'` объединяются; `phase === null` → только `'*'`; workflow объявлен в settings, но записи в `completeness` нет → набор пуст, дефолт не протекает), `taskCompletenessMissing(task, fields)` (расчёт неполноты) и `terminalStatusGateForTask(...)`. Смысл полей: `acceptanceCriteria`/`definitionOfDone` — «все пункты отмечены, пустой чеклист = полно»; остальные — «значение непустое». Фаза берётся только из `resolveGuardPhase` (env рана → мета сессии), аргумент модели её не переопределяет. Урок: набор полей (`content`) приходит из правил, а не из литерала в инструменте; `document_update`/`reference_update` — тело необязательно, `missing` пуст (`completeness: () => []`); неполнота для них правилами не объявлена. Низкоуровневая сборка текста (`terminalStatusGateCore`) не экспортируется (VL-378): единственный вход в правило терминальности — `terminalStatusGateForTask`, поэтому обойти расчёт неполноты из данных нельзя.

**Вызов без полей вообще** (`{id}` без изменяющих аргументов) — `noop` + `missing`, если сущность неполная, а не исключение «Не указаны поля для обновления». Исключение — `backlog_update_status` без `status`: обязательный аргумент → `rejected`.

**`append_notes` неидемпотентен:** в `EntitySpec` есть `nonIdempotent`, noop-сверка для него отключена, `build` получает текущее состояние для склейки заметок — повторное дописывание по-прежнему меняет файл.

**Границы:** `milestone_*` (rename меняет задачи, archive переносит файл), `backlog_manage_ac`/`backlog_manage_dod` (работают с индексами, а не полями), `lesson_link`/`reference_link` (две стороны связи), `git_commit` (явные пути) в пайплайн НЕ переведены — у них другая семантика.

Отказ подтверждения приходит как `{ "ok": false, "denied": true, "reason": "denied" | "not_confirmed", "applied": {}, "skipped": [...], "message": "...", "hint": "..." }`:
`reason='denied'` — пользователь отказал (повтор без нового решения бессмыслен); `reason='not_confirmed'` — подтверждение не получено (не отказ: вызов можно безопасно повторить с тем же `idempotencyKey`). В обоих случаях состояние не изменено, `skipped` перечисляет неприменённые поля.

### backlog_manage_ac / backlog_manage_dod — чеклисты

| Параметр | Тип | Required | Описание |
|---|---|---|---|
| `id` | string | ✓ | |
| `action` | string | ✓ | add / check / uncheck / remove / list |
| `text` | string \\\\| string[] | | Для action=add: строка — один пункт; массив непустых строк — несколько за один вызов (batch-add, ответ «Добавлено критериев: N (…)»); JSON-строка массива (`'["A", "B"]'`) тоже принимается — разбирается, каждый элемент становится отдельным критерием (симметрия с `index`; битый JSON или не-массив уходит в scalar-текст как есть; VL-183) |
| `index` | number \\\\| string \\\\| (number\\\\|string)[] | | Для check/uncheck/remove: целое с 1; строка-число (`"3"`); массив `[1,2,3]` — несколько за один вызов; строка-массив `"[1, 2]"` тоже принимается; `"all"` — все пункты списка. Валидация каждого элемента: целое ≥1 и ≤ длины, иначе ошибка со списком пунктов (дробь/NaN/пусто — с подсказкой формата). Батч-ответ: «Отмечено пунктов: N (1, 2, 3)» / «Снято пунктов» / «Удалено пунктов»; scalar-ответ — прежний («Отмечены критерии #2»). Внимание: `action:'remove', index:'all'` чистит весь чеклист |

**Форма ответа — JSON-ack во всех ветках (VL-351).** Раньше `manageChecklist` отвечал плоским текстом, и цикл агента не мог отличить чтение от записи: страховка VL-306 считала не-JSON ответ write-инструмента «применённым», поэтому повтор `action:'list'` получал ложную директиву «уже применён ранее» (сессия `agent-1794047067509`, Close VL-349). Теперь:

- `action: list` — **read-семантика**: `{ "ok": true, "read": true, "message": "<прежний текст: «1. ✓ …» или «Чеклист пуст.»>", "applied": { "items": [{ "index": 1, "checked": true, "text": "…" }] }, "skipped": [] }` (`ackRead`, `src/mcp/tool-result.ts`). Признак `read: true` говорит циклу «эффекта не было»: сигнатура не пополняет ни `appliedSignatures`, ни `noopSignatures`, повтор исполняется заново и отдаёт свежий снимок.
- `add` / `check` / `uncheck` / `remove` — `ackOk` с прежним текстом в `message` и машиночитаемым `applied`: `{ added: [...], total }`, `{ checked: indexes, action }`, `{ removed: indexes, total }`.
- Неизвестное `action` — по-прежнему `throw` (ошибка вызова, а не ack).

Инвариант «каждый write-инструмент реестра отвечает JSON-ack хотя бы в одной ветке» закреплён тестом `src/mcp/write-ack-contract.test.mjs` (`ACK_SCENARIOS`): новый текстовый write-инструмент валит тест.

**Ранжирование (VL-237).** Запрос токенизируется (lowercase, разделители — пробелы и пунктуация; дефис/подчёркивание сохраняются, чтобы `VL-237` и `deps.ts` не разваливались). Требуется вхождение **всех** токенов (И-логика) хотя бы в одном поле: для одного слова поведение ≈ прежнему substring плюс усечение основы. Веса: точное совпадение `id` (1000) » `id` содержит (500) » `title` (100) » `labels` (50) » `description` (10); порядок при равном счёте детерминирован: score desc → `created_date` desc → `id` asc. Морфология — усечение основы: для токенов длиной ≥6 символов сравниваются первые 5 символов (полноценного стеммера нет, ложные срабатывания на коротких основах приемлемы); слова с дефисом не усекаются.

**Форма ответа:** объект `{ found, returned, tasks }` — `found` — полное число совпадений (до `limit`), `returned` — сколько отдано. Массив верхнего уровня больше не возвращается (VL-237): агент видит полноту выдачи и не переформулирует запрос вслепую. При `fields` с неизвестными ключами к объекту добавляется `_warning` (VL-260); карточки в `tasks` содержат только запрошенные поля.

Атомарно по файлу: статус + отчётный комментарий + modifiedFiles + батч-отметки AC/DoD за один вызов (замена цепочки `add_comment` → `update_status` → `update_task(modifiedFiles)` → `manage_ac/dod check`).

| `comment` | string | ✓ | Отчётный комментарий (author фиксирован `@agent`). Отсутствующий/пустой — **жёсткая ошибка** `Неполный вызов: … comment (report) не передан` (VL-251); файл задачи и usage при этом не трогаются |

Если не передан **или все значения нулевые** (VL-251) — fallback: env `VIBELOG_SESSION_ID` → мета сессии → JSONL (`sumUsageFromMessages`); без сессии — ошибка в сводку, остальное применяется |

Используется аварийными ветками шаблонов `phase-close*.md` вместо отчёта без `status`. Переданный вместе с `aborted` явный `status` всё равно применяется (приоритет действия агента) |
| `dodOverride` | string | | Причина закрытия задачи с невыполненными пунктами DoD (VL-248). Проверка выполняется ДО любых записей: если итоговый (терминальный по workflow) статус ставится при непустом списке непройденных DoD (эффективный список = `updates.definitionOfDone ?? task.definitionOfDone`, т.е. учитываются `dodChecks` этого же вызова) и `dodOverride` пуст или отсутствует — вызов отклоняется (MCP `isError: true`), файл задачи, комментарий и usage не меняются. Причина попадает в комментарий-отчёт строкой `DoD override: <причина>`. Поле НЕ в `required` — условная обязательность enforced только ошибкой |

**Аварийное завершение (VL-244).** Флаг `aborted` — единственный надёжный сигнал: без него завершение процесса с кодом 0 применяет `produces_status`, и, например, close-фаза с незавершённым merge поставит задаче Done (инцидент VL-219). Fallback по финальному тексту/`logTail` («не завершена», «прервана») остаётся только диагностикой. В сводке результат виден строкой `aborted: фаза помечена прерванной (статус не применён)`, а если записи транзиента нет (служебная фаза) — `aborted: фаза вне транзиента (флаг не сохранён)`, без ошибки.

Частичное применение: невалидное поле (статус вне конфига, битый индекс) пропускается с понятным сообщением, вызов не падает; все валидные обновления применяются одной записью (файл атомарен). Результат — сводка вида «Статус: Review; отчёт добавлен; отмечено AC: 2, DoD: 1; файлов: 3» (+ `Ошибки: …` при наличии). Несуществующая задача — фатальная ошибка.

**Жёсткая валидация (VL-251)** выполняется до любых записей и бросает ошибку (MCP `isError: true`): отсутствующий `comment` и `status`, **равный текущему** статусу задачи (`Фаза уже завершена: статус «X» совпадает с текущим` + дата/автор/начало существующего отчёта + следующий шаг). Причина: нейтральный успех на no-op выглядел для модели как «принято, но чего-то не хватает» и провоцировал байт-в-байт повторы (инцидент VL-234). Сценарий «повторный finish безопасен» сознательно убран.

**Валидация перехода по фазе workflow (VL-245).** Кроме проверки по `config.statuses`, статус проверяется на право перехода относительно фазы вызывающего — иначе инварианты workflow (их знал только оркестратор) не действовали на MCP-границе, и служебная фаза `comment` выставила `Done` незавершённой задаче (инцидент VL-219/VL-231).

- **Служебная фаза** (`comment`, `prompt`, `analyze`, `investigation`, `resume` и прочие из `SERVICE_PHASES`) не меняет workflow-статус вообще: переход отклоняется, статус не пишется, отчёт и AC/DoD/modifiedFiles применяются (частичное применение). Ручной перевод задачи из comment-фазы — через CLI (`vibelog task edit --status`) или веб-API (`PATCH /api/tasks/:id`).
- **Рабочая фаза** может выставить ровно `produces_status` перехода «текущий статус + фаза» (`getStatusAfterPhase`). Например, `close` из `Review` → `Done` разрешено, `close` из `To Do` → `Done` — нет. Правило считается по `getWorkflowForTask(cwd, task)`, поэтому кастомные `workflows`/`task_workflows` из `.vibelog/settings.json` уважаются; кастомная фаза без перехода статус не двигает.
- **Источник фазы — только доверенный:** `VIBELOG_RUN_PHASE` → `VIBELOG_PHASE_NAME` (кроме служебного `prompt`) → `meta.lastRunPhase` → `meta.phase` меты сессии. Аргумент `phase` самого инструмента в проверке **не участвует** — он остаётся только для учёта `token_usage.by_phase` (VL-259), иначе модель могла бы выписать себе разрешение, передав `phase: "close"`.
- **База проверки — статус до фазы.** Во время рана транзиент VL-196 временно держит задачу в `In Progress`, а агент передаёт статус, посчитанный от исходного; поэтому из `.vibelog/phase-in-progress.json` берётся `prevStatus` (только если запись принадлежит той же фазе), иначе — физический статус задачи.
- **Fail-open:** фаза не резолвится вообще (ручной вызов из стороннего MCP-клиента) — работают прежние правила по `config.statuses`.

**Терминальный статус при невыполненном DoD (VL-248).** Смена статуса на терминальный
при непустом списке непройденных пунктов DoD больше не проходит молча: вызов отклоняется
жёсткой ошибкой до любых записей, а в тексте ошибки перечислены номера невыполненных пунктов
и три законных пути — отметить пункты в `dodChecks`, передать непустой `dodOverride` с причиной
(если задача честно закрывается с перенесённым пунктом) либо `aborted: true`, если фаза реально
не выполнена. Терминальность определяется не хардкодом имён, а workflow задачи
(`isTerminalStatus` в `src/core/workflow.ts`): у статуса нет исходящих фаз, и он либо объявлен
финальным маркером, либо достижим как `produces_status`/`initial_status` — поэтому кастомные
финалы из `.vibelog/settings.json` тоже покрыты. Проверка учитывает `dodChecks` этого же вызова
(обход «отмечу что есть» не работает). Для любого терминального статуса в сводке остаётся
предупреждение `терминальный статус при непройденных DoD: #2, #3` (+ `(override: <причина>)`
при override); жёсткое требование применяется только к явно запрошенному терминальному статусу —
вызовы без `status` (комментарий к уже закрытой задаче) не блокируются. Известное ограничение:
автоматический `produces_status` оркестратора (`finalizePhaseStatus`) вне зоны действия инструмента.

## Фазы и супервизор (VL-268, doc-19)

Четыре инструмента дают чату управление фазами и очередью. Три из них — write-операции по природе (`trigger`/`queue`/`supervisor` в маркерах `isWriteOperation`), `backlog_phase_status` — read. Развязывает их не исключение из политики, а **grant на прогон** (§15 doc-19): внутри подтверждённого прогона вызовы с разрешёнными инструментами не требуют Allow/Deny, вне прогона работает обычная карточка подтверждения.

### backlog_supervisor — прогон (план, старт, стоп, статус)

| Параметр | Тип | Required | Описание |
|---|---|---|---|
| `action` | `plan` \| `start` \| `stop` \| `status` | ✓ | `plan` — сухой прогон; `start` — запустить (нужно подтверждение); `stop` — остановить и отозвать grant; `status` — состояние |
| `ids` | string[] | | ID задач прогона (для `plan`/`start`) |
| `expiresInHours` | number | | Срок действия grant в часах (по умолчанию 8, максимум 336) |
| `expiresAt` | string | | Явный срок действия grant (ISO 8601), приоритетнее `expiresInHours` |

`plan` ничего не пишет и не запускает: состав, порядок (High → Medium → Low, затем порядок `ids`), волны по внутренним зависимостям, `skipped` с причинами, текстовое обоснование.

**Grant на прогон** — файл `.vibelog/supervisor/grants/<runId>.json`:

```json
{
  "runId": "run-2026-10-31T22-00-00",
  "taskIds": ["VL-263", "VL-264", "VL-268"],
  "allowedTools": ["backlog_trigger_phase", "backlog_phase_status", "backlog_auto_queue", "backlog_supervisor", "backlog_create_task"],
  "grantedAt": "2026-10-31T21:58:00Z",
  "expiresAt": "2026-11-01T06:00:00Z"
}
```

Правила проверки (перед **каждым** вызовом, не при старте хода):

- задача вне `taskIds` → отказ «Задача VL-N вне прогона run-…: расширь прогон и подтверди заново»;
- инструмент вне `allowedTools` → обычный Allow/Deny;
- `expiresAt` истёк → текущая фаза доводится, новые не стартуют (карточка сообщает об истечении);
- отзыв — при `stop` и при завершении прогона (все задачи в терминальном статусе): файл получает `revokedAt`, `findActiveGrant` его больше не видит, следующие вызовы снова требуют подтверждений;
- `write_file`, `edit` и прочие файловые write-инструменты модели в grant **не входят никогда** — фильтр `GRANTABLE_TOOLS`, не пользовательский ввод;
- `backlog_finish_phase` остаётся в `CHAT_DISALLOWED_TOOLS` — grant не открывает обходного пути к завершению фазы.

**Пример.**

```json
{ "name": "backlog_supervisor", "arguments": { "action": "plan", "ids": ["VL-268", "VL-269"] } }
{ "name": "backlog_supervisor", "arguments": { "action": "start", "ids": ["VL-268", "VL-269"], "expiresInHours": 4 } }
{ "name": "backlog_trigger_phase", "arguments": { "id": "VL-268", "comment": "продолжаем после падения" } }
{ "name": "backlog_phase_status", "arguments": { "id": "VL-268" } }
```

HTTP-эндпоинты карточки: `POST /api/chat/supervisor/grant-draft` (правки состава инструментов и срока до нажатия «Разрешить») и `GET /api/chat/supervisor/grant` (активный grant + последний прогон — для восстановления карточки после перезагрузки).

### document_edit — точечная правка тела (VL-399)

| Параметр | Тип | Required | Описание |
|---|---|---|---|
| `id` | string | ✓ | ID документа |
| `old_string` | string | ✓ | Точный текст для поиска в теле |
| `new_string` | string | ✓ | Текст замены |
| `replace_all` | boolean | | Заменить все вхождения (по умолчанию `false` — требуется ровно одно) |

Семантика — как у файлового `edit`: без `replace_all` `old_string` обязан встречаться **ровно один раз**, иначе отказ без записи. 0 совпадений → «old_string не найден в теле документа … Проверь точный текст: `document_view`» (в `hint` — в том числе «возможно, документ восстановлен из git и текст в нём другой»); >1 → отказ с числом совпадений и `retryWith {replace_all: true}`. Неоднозначный отказ файл не трогает (возврат до записи). Замена — `split/join`, а не `String.replace`: `$1`, `$&`, `{{taskPlan}}` в `new_string` вставляются буквально. `old_string === new_string` → noop (`{ok:false, noop:true, reason:'noop'}`) без перезаписи файла. Успех: `applied {id, replaced, bodyLengthBefore, bodyLengthAfter, truncated}`; заголовок/тип/теги не меняются — они остаются за `document_update`. Пустой `old_string` → отказ (иначе `split('')` развалил бы тело на символы). Идемпотентность — обычный `idempotencyKey`.

## Lessons learned (lessons, VL-153)

Workflow-уроки из опыта задач — предотвращают повторение ошибок. Файлы — `backlog/lessons/lesson-N-<slug>.md` (YAML-фронтматтер: id, title, status, tags, source_tasks, linked_tasks, created_date, updated_date, supersedes, last_verified, verified_by, applies_to, kind; тело — «Проблема / Решение / Пример»). Статусы: `active` (по умолчанию) / `needs-review` / `outdated` / `superseded`.

Поля актуальности (VL-279, additive — старые файлы без них читаются с дефолтами): `last_verified` (YYYY-MM-DD — когда урок последний раз проверен), `verified_by` (`auto|agent|human`), `applies_to` (string[] — glob путей и/или имена символов, которые аудит валидирует механически), `kind` (`rule|workaround|fact`). Настройки аудита — секция `lessons` в `.vibelog/settings.json`: `duplicate_threshold` (0.35), `stale_days` (180), `prompt_limit` (5).

`loadLessonsForTask` подставляет в промпт Plan/Code только `active`-уроки, отбрасывая `needs-review`/`outdated`/`superseded` и протухшие (`last_verified`/`updated_date` старше `stale_days`), сортирует по свежести и капит top-N — устаревшая инструкция не попадает в промпт.

Отличие от других сущностей: references — внешние источники; decisions — архитектурные решения («почему X, не Y»); docs — документация проекта; **lessons — workflow-уроки**, которые эволюционируют независимо от замороженных задач. Двусторонняя связь с задачами: `lesson.linked_tasks` ↔ `task.lessons`. Plan-фаза получает активные lessons по tags/labels задачи в промпт через `{{taskLessons}}` (0 дополнительных ходов модели); Close-фаза пишет уроки автоматически (шаг 6.5), Code связывает применённые.

| Параметр | Тип | Required | Описание |

id генерируется (`lesson-N`), даты — сегодня. Сервер склеивает тело урока сам (`lessonBodyFromParts`): `## Проблема` + `problem`, `## Решение` + `solution`, `## Пример` + `example` (секция примера опускается, если `example` не передан или пуст).

**Урок-скелет на MCP-пути исчез как класс (VL-379).** До VL-379 тело урока передавалось одной строкой `content` с экранированным markdown (`\n`, `##`) — слабая модель физически не вставляет такую строку в JSON, и Close-сессии падали на дословных повторах вызова без `content` (четвёртый рецидив: сессия `agent-1794146250210`, Close VL-377). Пустой `content` тогда создавал урок со скелетом `LESSON_BODY_SKELETON` — непустую заглушку, которую невозможно дозаполнить: чтобы дописать тело, нужен `content`, а чтобы сформировать `content`, нужен текст урока. Теперь `problem`/`solution` — обязательные аргументы (`required` в схеме), но `inputSchema` сервером при `tools/call` **не валидируется**, поэтому защита реализована в `toolLessonCreate`: при отсутствии или пустоте `problem`/`solution` (после `trim()`) вызов отклоняется — `ackErrorDetailed`, `missing: [{field:'problem', …}]`, `hint` и `retryWith` с тремя полями-плейсхолдерами, файл урока **не создаётся**. `LESSON_BODY_SKELETON` остался только у CLI-пути (`vibelog lesson create` без `-d`), где сидит человек и может сохранить черновик. Накопленные ранее уроки-скелеты дозаполняются `lesson_update {id, problem, solution}`; их перечисляет `lesson_audit` (finding `empty_body`).

### lesson_update — обновить lesson

| Параметр | Тип | Required | Описание |

| `title`, `status`, `tags`, `sourceTasks`, `linkedTasks`, `problem`, `solution`, `example`, `lastVerified`, `verifiedBy`, `appliesTo`, `kind` | | | Только переданные поля; смена title переименовывает файл; **`problem`+`solution` — полная замена тела урока** (сервер склеивает markdown; `example` необязателен), семантика прежнего `content` сохранена (VL-379); `lastVerified`/`verifiedBy` — отметка проверки актуальности, `appliesTo` — glob путей/имена символов, `kind` — rule/workaround/fact (VL-279) |

**`content` удалён из `lesson_create`/`lesson_update` (VL-379).** Поле не оставлено «для совместимости»: два способа передать одно и то же — двойная форма, и модель выбирает худшую (урок VL-369). Переданный `content` попадает в `skipped` с причиной «поле удалено: передай problem и solution (markdown-тело сервер склеит сам)» — через необязательный хук `EntitySpec.removedFields` в `src/mcp/update-pipeline.ts`, а не с общей причиной «неизвестное поле». Тело урока по-прежнему хранится в `content` внутри ядра (`UpdateLessonInput`), поэтому noop-сверка тела (`bodyArg: 'content'` → `BODY_FIELD`) работает как раньше.

**Незаполненное тело урока (VL-319, расширено VL-349/355, переведено на части VL-379).** «Незаполнено» — это пустое/пробельное тело **или** тело, равное дефолтному скелету `LESSON_BODY_SKELETON` после нормализации (`trim()` с обеих сторон). Единая точка правды — экспортируемый предикат `isLessonBodyUnfilled(body)` (`src/core/lesson.ts`); его используют `lessonSpec.completeness` в MCP (поле `missing` теперь называется `problem`) и finding `empty_body` в `lesson_audit`. Для новых уроков ветка недостижима по конструкции — урок без тела MCP-путём не создаётся (VL-379); предикат нужен для накопленных скелетов.

Проверка формы аргумента стоит в хуке `beforeWrite` (после noop-сверки) и различает случаи:

- **(а) `problem`/`solution` переданы пустыми/пробельными (или только один из пары, или `example` без пары)** → `ok:false` (rejected) + `hint`/`retryWith` с тремя полями, файл не перезаписывается.
- **(б) тело не заполнено, `problem`/`solution` не переданы, но есть другие изменения** → переданные НЕ-body поля (`linkedTasks`, `status`, `tags`, `sourceTasks`, `verifiedBy`, `appliesTo`, `kind`, `supersedes`, `title`) **применяются**, ответ `ackOkDetailed`: `ok:true`, `applied` — фактические значения, `missing: [{field:'problem', reason:'тело урока не заполнено (пустое или дефолтный скелет) — передай problem и solution'}]` и `hint`. Работа не блокируется.
- **(в) тело не заполнено, частей нет, других полей в вызове нет вообще** (только `id`) → `ackErrorDetailed` с `missing: problem`: noop здесь был бы петлёй, модель не узнала бы про тело.
- **(г) повтор уже применённых полей** → обычный noop (`ok:false`, `noop:true`) с `missing: problem` — **не** отказ: серия отказов на повторе и есть механизм падения по `MAX_ERROR_REPEATS_PER_RUN`.

Все отказы — `ackErrorDetailed` **без** `noop: true`, поэтому сигнатура не попадает в `noopSignatures`: повтор исполняется заново и снова отдаёт текст ошибки (цикл «noop → кап → fail → авто-resume» рвётся).

**Почему частичное применение (VL-355).** VL-349 расширил предикат до скелета, но проверка стояла ДО noop-сверки и отсекала **любой** вызов `lesson_update` на уроке-скелете: нельзя было обновить ни `linkedTasks`, ни `status`, ни `tags`. Сессия `agent-1794053090709` (Close VL-346) пришла привязать урок к задаче (`lesson_update {id:'lesson-232', linkedTasks:['VL-346'], verifiedBy:'agent'}`), получила отказ «в вызове нет `content`» и повторила его дословно 6 раз → `MAX_ERROR_REPEATS_PER_RUN` → fail. Выхода из тупика не было: чтобы привязать — нужен `content`, чтобы передать `content` — нужно придумать текст урока. Теперь привязка применяется, а `missing`/`hint` напоминают про тело.

**Почему скелет — отдельное состояние (VL-349).** Защита VL-319 проверяла `body.trim() === ''`, а `createLessonFile` подставляет скелет — непустую строку. Урок-заглушка перестал отличаться от заполненного: вызов `lesson_update {id, title, tags}` без `content` уходил в noop-сверку с `hint: «Переходи к следующему шагу»`, модель повторяла его дословно 4 раза → `MAX_NOOP_REPEATS_PER_RUN` → fail (сессия `agent-1794045441657`, Close VL-346).

### lesson_audit — механический аудит актуальности (VL-279)

Детерминированный (без LLM) аудит корпуса уроков: возвращает `findings[]` по каждому lesson (тип + детали) и сводку по типам. **Read-only по умолчанию** — записи только по явному перечислению ID.

| Параметр | Тип | Required | Описание |
|---|---|---|---|
| `threshold` | number | | Порог схожести дублей 0..1 (дефолт — `lessons.duplicate_threshold` или 0.35) |
| `staleDays` | number | | Порог протухания в днях (дефолт — `lessons.stale_days` или 180) |
| `write` | boolean | | Записать отчёт в `backlog/lessons/AUDIT.md` (по умолчанию `false` — только ответ) |
| `verified` | string[] | | ID уроков: отметить проверенными (`last_verified=today`, `verified_by=auto`) |
| `needsReview` | string[] | | ID уроков: перевести в статус `needs-review` |

Типы находок: `missing_path` (путь/`applies_to`-glob из тела урока не существует в репо), `dangling_task` (`source_tasks`/`linked_tasks` на несуществующую задачу), `broken_supersede` (`supersedes` на несуществующий ID или на себя), `supersede_cycle` (цикл замен), `duplicate_of` (кандидаты на объединение: взвешенная схожесть заголовка/tags/тела), `stale` (нет `linked_tasks` и source-задачи закрыты, либо `updated_date`/`last_verified` старше порога; уроки `superseded`/`outdated` в stale не попадают), `empty_body` (VL-319, расширено VL-349: тело урока пустое/пробельное **или** равно дефолтному скелету `LESSON_BODY_SKELETON` — проверка через `isLessonBodyUnfilled`; в `details` флаг `skeleton: true` для скелета, у пустого тела флага нет; детерминированно, без порогов и настроек; накопленный склад уроков-заглушек виден механически, пары дублей для таких уроков не считаются). Массовых изменений без флагов/ID инструмент не делает — путь мог исчезнуть из-за рефакторинга, а урок при этом остаётся верным по смыслу.

### lesson_classify — классификация уроков и техдолг из workaround (VL-280)

LLM-путь, **opt-in**: не входит ни в один автоматический прогон и в CI-аудит (`lesson audit` остаётся детерминированным и дешёвым). Решает проблему «обход, легализованный как урок»: такой урок в статусе `active` подставляется в промпты Plan/Code, и модель учится обходить проблему вместо того, чтобы её решить.

| Параметр | Тип | Required | Описание |
|---|---|---|---|
| `ids` | string[] | | ID уроков (`lesson-N`); приоритетнее фильтра |
| `status` | string | | Фильтр по статусу (`active`/`needs-review`/`outdated`/`superseded`) |
| `tags` | string[] | | Фильтр по меткам (любое пересечение) |
| `limit` | number | | Максимум уроков в выборке (по умолчанию 20 — дорогой путь не уходит на весь корпус) |
| `apply` | boolean | | Записать `kind` во фронтматтер всем классифицированным (по умолчанию `false`) |
| `confirmIds` | string[] | | ID уроков, которым `kind` разрешено записать (точечное подтверждение вместо `apply`) |
| `createClusters` | string[] | | ID кластеров (из ответа), для которых создавать задачи техдолга — единственный способ создания |
| `maxTasks` | number | | Лимит задач за вызов (дефолт — `lessons.tech_debt_max_tasks` или 1) |

Выход: для каждого урока `kind` ∈ `rule` (правило поведения), `workaround` (обход причины дефекта), `fact` (утверждение о коде, проверяемое тестом), `stale` (устаревший контекст) + обоснование 1–2 предложения. Контекст модели — тело урока (кап 1800 символов) и **findings `lesson_audit`** (`missing_path`, `dangling_task`, `stale`, `duplicate_of`) как факты: порог «протухания» передаётся в промпт, а не хардкодится в коде. `stale` никогда не пишется в `kind` — это вердикт статуса (`needs-review`/`outdated`), его проставляет человек.

Кластеризация `workaround`-уроков детерминированная: union-find по общим путям (`extractLessonPaths` + `applies_to`) и по «специфичным» tags (метка, встречающаяся у ≤ 1/3 уроков-обходов; `tests`/`workflow` не склеивают корпус в одну задачу). ID кластера — `tag:…` / `path:…` / `lesson:…`, он и передаётся в `createClusters`.

Черновик задачи техдолга (`buildTechDebtDraft`) содержит причину обхода, цитаты уроков-источников, затронутые пути, критерий «workaround больше не нужен» и строку «что переводить в `outdated`/`superseded`». Создание — только по `createClusters`, не более `maxTasks` задач за вызов; идемпотентность — поиск существующей задачи с меткой `tech-debt` и ID урока в тексте. Каждая созданная задача двусторонне связана с уроками (`lesson_link`), а в теле урока появляется раздел `## Устранение` со ссылкой на задачу — при её закрытии видно, какой урок пора снять.

Ошибки LLM (таймаут, невалидный JSON, неизвестный `kind`) не пишут ничего в файлы: они возвращаются отчётом по конкретному уроку, остальные продолжают обрабатываться.

```
lesson_classify {"tags":["tests"], "limit":10}
lesson_classify {"ids":["lesson-113","lesson-120"], "apply":true,
                 "createClusters":["tag:env"]}
```

### lesson_consolidate — консолидация корпуса lessons (VL-400)

Детерминированный (без LLM и сети) шаг «накопленное → правило»: корпус уроков не консолидировался, и правило, которое нарушают снова и снова, жило в 3–4 дублях-уроках вместо одной строки в `AGENTS.md` (файл инжектится в каждый ход каждой фазы, кап `AGENTS_MD_MAX_CHARS` = 8000). **Read-only по умолчанию** — записи только по явным спискам (паттерн `lesson_audit`, lesson-147).

| Параметр | Тип | Required | Описание |
|---|---|---|---|
| `threshold` | number | | Порог схожести дублей 0..1 (дефолт — `lessons.duplicate_threshold` или 0.35) |
| `supersede` | string[] | | ID уроков: применить supersede-план их кластера/пары (канон → остальные, не-канон → он сам) |
| `appendAgentsMd` | string[] | | Строки, дописываемые в секцию-маркер `<!-- lessons:consolidated -->` AGENTS.md (дедуп по нормализованному тексту) |

Выход плана: `ruleClusters[]` (группы активных уроков `kind: rule` и связные компоненты графа `duplicate_of`; для каждой — предлагаемая строка для AGENTS.md из заголовка самого свежего урока, `canonId` и список ID на supersede), `duplicatePairs[]` (пары `duplicate_of` из `auditLessons`, дедуплицированные по паре — аудит даёт по находке на урок, то есть каждую пару дважды), `emptyBodies[]` (finding `empty_body`), `summary`.

Кластеры строятся из **компонент связности графа дублей**, а не union-find по пересечению tags: пересечение меток сливало весь корпус в один мега-кластер, а группировка по одной метке давала десятки «кластеров» из несвязанных уроков (общая метка `тесты`/`docs` — область, а не правило). Связные tag-группы принимаются только при смысловой близости заголовков (Jaccard ≥ 0.12) и размере ≤ 4.

`appendAgentsMd` идемпотентен: повторный apply не дублирует строки (сравнение по нормализованному тексту — без маркера списка, регистр и пробелы не значимы). Флага «применить всё» нет намеренно: порог 0.35 даёт ложные пары (например lesson-158/lesson-229 при 0.37 — разные уроки), а мусор в AGENTS.md дороже отсутствующего правила.

```
lesson_consolidate {}
lesson_consolidate {"supersede":["lesson-211"], "appendAgentsMd":["Перед merge проверяй, не выполнен ли он уже"]}
```

## Git

### git_commit — детерминированный коммит явными путями (VL-311)

Узкий write-инструмент: коммит только переданных путей, с автоматическим трейлером `Co-authored-by` и сверкой с задачей. Заменил текстовые правила шаблонов фаз («никогда `git add -A`», «передай трейлер вторым `-m`»), которые держались только на дисциплине модели.

| Параметр | Тип | Required | Описание |
|---|---|---|---|
| `paths` | string[] | ✓ | Явные пути коммита относительно проекта; непустой массив. Выполняется только `git add -- <paths>` |
| `message` | string | ✓ | Сообщение коммита: тема и (опционально) тело |
| `amend` | boolean | | `true` — переписать последний коммит: сообщение собирается из полного тела `git log -1 --pretty=%B`, тело сохраняется, трейлер не дублируется |
| `allowForeign` | boolean | | Разрешить пути вне `modified_files` задачи (осознанный случай) |

Что делает: (1) резолвит пути внутри проекта коммита — абсолютный путь, `.`, `-A`/`--all`, маски и выход за пределы проекта отклоняются до любых git-команд; (2) сверяет пути с `modified_files` задачи — чужие отклоняются с перечислением и подсказкой `allowForeign: true` (пустой список задачи сверку не блокирует, вне фазовой сессии она пропускается); (3) коммитит **ровно переданные пути** — `git commit --only -- <paths>` (VL-360): staged-файлы вне `paths` в коммит не попадают и остаются в индексе, о них сообщает `applied.warnings` (не блокировка); (4) ставит трейлер через `appendCommitTrailer`/`resolveCommitCoauthor` (`src/core/commit-trailer.ts`, настройка `commit_coauthor`, по умолчанию включена); (5) отвечает JSON-ack.

**Не-ASCII пути (VL-360).** Все git-вызовы инструмента идут с `-c core.quotepath=false`, поэтому кириллица в именах файлов приходит из `git diff --cached --name-only` как есть, а не в octal-экранировании (`"\320\232..."`). Дополнительно каждая строка вывода нормализуется чистой функцией `unquoteGitPath` (снятие обрамляющих кавычек, раскрытие C-style escape-последовательностей `\ooo` → байты → UTF-8, `\n`, `\t`, `\\`, `\"` и др.) и приведением разделителей `\` → `/` со снятием ведущего `./` — сравнение устойчиво к юникоду и к чужому `core.quotepath=true` в конфиге репозитория. В `applied.paths` и в текстах предупреждений выводятся читаемые пути.

Ответ — контракт write-инструментов (VL-306/VL-310):

```json
{ "ok": true, "message": "Коммит a1b2c3d создан: feat: VL-42 — суть",
  "applied": { "hash": "a1b2c3d…", "subject": "feat: VL-42 — суть", "paths": ["src/core/foo.ts"] } }
```

- нет изменений по переданным путям → `{ "ok": false, "noop": true, "reason": "noop", "applied": { "paths": [...] } }` — коммит **не создан**, это сигнал «переходи к следующему шагу» (совместимо с `appliedSignatures`/`noopSignatures` из VL-310);
- отказ (чужой путь, путь вне проекта, ошибка git) → `ackError` с русским текстом и готовым следующим шагом;
- `applied.warnings` — файлы чужого worktree с mtime позже `VIBELOG_RUN_STARTED_AT` (предупреждение о возможной гонке, не блокировка), а также staged-файлы вне `paths` («в индексе остались staged-файлы вне paths: … — они НЕ вошли в коммит (`git commit --only`) и остались в индексе»);
- `applied.amended: true` — коммит был amend'ом.

Все git-вызовы — `spawnSync('git', args, { cwd })` без shell: `message` и пути передаются аргументами, инъекция невозможна. Необязательный параметр `cwd` (путь внутри проекта) нужен шагу 2 шаблона `phase-close-worktree.md`, который коммитит worktree задачи из фазы close.

Граница: инструмент узкий — только commit. `status`, `log`, `diff`, `merge`, `worktree remove`, `branch -d`, `stash` остаются `run_shell_command` (чтение и редкие операции, обёртка не даёт выигрыша).

`isWriteOperation('git_commit') === true` (маркер `commit` в `WRITE_MARKERS`, `src/core/tool-classify.ts`); в `GRANTABLE_TOOLS` супервизора инструмент не входит.

```
git_commit {"paths": ["src/mcp/git-commit.ts","src/mcp/tools.ts"], "message": "feat: VL-311 — инструмент git_commit"}
```

## GitVerse Issues (VL-363)

### upstream_report_bug — репорт бага в upstream-проект

Write-инструмент: создаёт issue в репозитории из секции `upstream` и возвращает его номер как ack. Нужен дочерним проектам (`ui`/`templates`) — их агент не может завести задачу в родительском `backlog/`, потому что инструменты ограничены корнем проекта.

| Параметр | Тип | Required | Описание |
|---|---|---|---|
| `title` | string | ✓ | Заголовок issue, непустой |
| `body` | string | | Что произошло: описание, шаги, ожидаемое поведение |
| `severity` | string | | `low` \| `medium` \| `high` \| `critical` — в секцию «Окружение» |
| `area` | string | | `cli` \| `mcp` \| `web` \| `agent` \| `install` \| … — в «Окружение» |
| `source_task` | string | | ID задачи проекта-источника — в секцию «Источник» |
| `labels` | string[] | | Дополнительные метки поверх `upstream.labels` |

**Настройка.** `GITVERSE_TOKEN` в `.env` (права: Запись на репозиторий) + секция `upstream` в `.vibelog/settings.json`: `{repo: "owner/name", labels: [...], type: "bug"}`. `repo` обязателен; `labels` по умолчанию `upstream` + `from-<prefix>`; `type` по умолчанию `bug`.

**Тело issue детерминировано.** `buildIssueBody` формирует фиксированные секции «Что произошло», «Воспроизведение», «Окружение», «Источник» — текст не отдаётся на волю модели, иначе формат поедет и импорт на принимающей стороне не разберёт секции.

**Метки создаются автоматически.** `ensureLabels` проверяет `GET /labels` и создаёт отсутствующие (лимит имени — 20 символов), идемпотентно.

Ответ — контракт write-инструментов (VL-306):

```json
{ "ok": true, "applied": { "number": 42, "url": "https://gitverse.ru/…/issues/42", "labels": ["upstream","from-ui"] },
  "message": "Issue #42 создан: …" }
```

- нет секции `upstream` → `{ "ok": false, "error": "секция upstream не настроена — …", "hint": "…" }`;
- нет токена → `ok: false` с подсказкой, где создать токен и какие права нужны;
- ошибка API → `ok: false` с текстом GitVerse; токен в тексте замаскирован.

`isWriteOperation('upstream_report_bug') === true` (`TOOL_KINDS`, `src/core/tool-kinds.ts`); в `GRANTABLE_TOOLS` супервизора не входит.

```
upstream_report_bug {"title": "git_commit падает на кириллице", "body": "…", "severity": "high", "area": "mcp", "source_task": "UI-12"}
```

### project_map — карта src/: путь + назначение + экспорты (VL-235)

Read-only. Один вызов вместо серии `read_file`: список модулей `src/` (файлы `.ts`, без `*.test.*`/`*.d.ts`), сгруппированный по каталогам, с первой строкой шапки-комментария и экспортами.

|---|---|---|---|
| `query` | string | | Подстрока по пути/описанию/экспортам; включает полные описания и все экспорты (ответ на «где реализован X») |
| `exports` | boolean | | Показать блоки экспортов (по умолчанию — если помещается в бюджет) |
| `dir` | string | | Каталог карты, по умолчанию `src` |
| `limit` | number | | Максимум модулей (по умолчанию 150); усечение помечается в ответе |

## Workflow (конструктор, VL-398)

Две тонкие обёртки над ядром `src/core/workflow-config.ts` — тот же код, что у `vibelog workflow show|validate|apply`. Нужны, чтобы агент в новом проекте мог получить схему workflow и провалидировать правку без shell и без `write_file` в конфиг.

### workflow_get — эффективный workflow + диагностика (read)

Без аргументов. Возвращает `describeWorkflow` (имя, источник — «дефолт из кода `DEFAULT_WORKFLOW`» либо «из settings.json», `initial_status`, `transitions`, `task_workflows`, `completeness`, `statuses` из `backlog/config.yml`) и `validateWorkflowConfig` (findings с `severity`). Подтверждения не требует.

### workflow_apply — запись секций в `.vibelog/settings.json` (write)

| Параметр | Тип | Required | Описание |
|---|---|---|---|
| `patch` | object | да | Фрагмент с ключами `workflows` / `task_workflows` / `completeness`; прочие ключи попадают в `skipped` |
| `dryRun` | boolean | | Показать, что было бы записано, ничего не писать |
| `syncStatuses` | boolean | | Дописать статусы из `transitions` в `backlog/config.yml` `statuses` |
| `idempotencyKey` | string | | Повтор с тем же ключом не применяет изменение второй раз |

Валидация выполняется **до записи**: при `severity: 'error'` возвращается `{ok: false}` и файл не меняется. Повтор того же патча — `noop` (файл не трогается); нечитаемый `settings.json` — отказ без записи (файл не затирается). Ответ — JSON-ack `{ok, applied, skipped}`; write-инструмент, требует подтверждения Allow/Deny.

```
workflow_apply {"patch": {"workflows": {"default": {"initial_status": "To Do",
  "transitions": [{"status": "To Do", "phase": "spec", "produces_status": "Spec"},
                  {"status": "Spec", "phase": "code", "produces_status": "Done"},
                  {"status": "Done", "phase": null, "produces_status": null}]}}},
  "syncStatuses": true}
```
