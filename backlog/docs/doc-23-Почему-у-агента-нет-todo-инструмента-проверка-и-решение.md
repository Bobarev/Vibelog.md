# Почему у агента нет todo-инструмента (проверка и решение)

**Дата:** 2026-11-02
**Статус:** решение принято — инструмент не заводим
**Связанные:** doc-10 (§5 «Инструменты», §6 «Loop detection и лимиты»), VL-119 (intentStreak), VL-229/VL-254/VL-284 (guard повторов), VL-303/VL-304/VL-306/VL-309 (appliedSignatures, noop, авто-отчёт)

## Вопрос

Нужен ли агенту инструмент внутреннего списка подзадач на время сессии (`todo_write` / `write_todos`, как в Claude Code и qwen-code)? Сейчас его нет: вместо него — внешние задачи `backlog_*` и `intentStreak` против зацикливания.

## Проверка (факты)

| Утверждение | Проверено | Результат |
|---|---|---|
| `todo_write` отсутствует у агента | `src/agent/tools.ts:1547` `listLocalTools` | Подтверждено: 8 инструментов — `read_file`, `write_file`, `edit`, `run_shell_command`, `grep_search`, `glob`, `search_files`, `agent_session_outline` |
| `todo_write` отсутствует в MCP | реестр `listTools()` | Подтверждено: только `backlog_*`, `milestone_*`, `document_*`, `reference_*`, `lesson_*`, `project_map`, супервизорные |
| `edit` есть у агента | `src/agent/tools.ts:862` `makeEdit` | Подтверждено: строгая замена `old_string`→`new_string`, отказ при 0 вхождениях и при >1 без `replace_all` |
| `edit` есть у веб-чата | `src/web/tool-policy.ts:236` `chatToolDefs` | **Нет** — только `read_file`/`write_file`/`search_files` (отдельная задача) |
| Code-фазы теряют шаги плана | поиск «не все шаги плана / пропущен шаг» по `backlog/tasks` | **Не подтверждено**: 0 совпадений |
| Close-фазы не доходят до конца | поиск «Фаза Close прервана» | Подтверждено, но причина — **merge-конфликты** (VL-137/144/147/163/169/171/172/181/212/219/233/234/235), а не забытые шаги |
| Модель не доходит до `finish_phase` | поиск «авто-отчёт (comment не передан моделью)» | 4 случая: VL-302, VL-306, VL-307, VL-308 — закрыто VL-309 |

## Решение: не заводить

1. **Шаблон фазы уже и есть todo-лист.** `templates/phases/phase-*.md` — нумерованная последовательность (шаги 1→6.6) с лимитами («сборка — один раз», «полный прогон — один»). Модель не выбирает, что делать дальше. Второй список рядом = два источника правды.
2. **Состояние плана уже персистентно и вне сессии.** `Implementation Plan`, AC/DoD живут в файле задачи. `todo_write` жил бы только в jsonl и умирал при resume/смене фазы (plan → code → close). Наш resume опирается на файл задачи, а не на память рана.
3. **Это новая поверхность для лупа.** История VL-303/304/306/309 — про write-инструменты, которые модель повторяет, и про механизмы, которые это лечат. `todo_write` — write-операция без побочного эффекта в данных, идеальный кандидат на «перепишу-ка список ещё раз»; `isWriteOperation('todo_write')` вернёт `true`, и 8-я правка упрётся в `REPEAT_WRITE_BLOCK_DEFAULT`, но контекст уже сожжён.
4. **Токены.** Наши болячки — payload (508 КБ в инциденте VL-284) и число `requests`, а не забывчивость. Каждый `todo_write` — tool-результат в истории на весь ран.
5. **`intentStreak` — не замена, а другой механизм.** Он ловит «модель ходит кругами с одинаковым намерением». Todo-список ничего не ловит: он декларирует намерение, и зацикленная модель зациклится на `todo_write` точно так же.

## Что делать вместо

- **Прогресс уже виден:** `buildRunProgress`/`progress` на аварийных ветках, `repeat_stats`, `logTail`, `runs[]` в мете.
- **Если нужен чек-лист внутри Code-фазы** для многошаговых правок — дешевле добавить в шаблон фазы раздел «Шаги работы (из плана)» с отметками в комментарии фазы, а не новый инструмент.
- **Если появится автономный ран без шаблона** (чат-режим с длинной многошаговой задачей, фаза `do` с плавающим скоупом) — тогда todo оправдан, но с условиями: JSON-ack в контракте VL-306, кап 1–2 записи (guard по сигнатуре), запись в **файл задачи** (комментарий / `Implementation Notes`), а не в память сессии — чтобы переживал resume и был виден человеку.

## Побочная находка (не про todo)

В мете `agent-1793647788155.meta.json` **отсутствует `repeat_stats`**, хотя `src/agent/cli.ts:1080` его пишет. Мета содержит только `billing_recorded` и `runs[]` — `finish()` оркестратора перезаписывает мету, и диагностика повторов для close-ранов теряется. Требует отдельной задачи.
