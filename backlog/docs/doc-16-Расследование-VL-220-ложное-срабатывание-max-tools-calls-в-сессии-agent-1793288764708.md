# Расследование VL-220: ложное срабатывание max-tools-calls в сессии agent-1793288764708

## Выводы

### Хронология (файл `.vibelog/agent-sessions/agent-1793288764708.jsonl`, 1077 записей)

Сессия — VL-219 (plan + code), одна jsonl на все раны (контракт resume VL-103: append-only):

| 871–977 | 100 | fail (строка 976) |
| 977–1077 (финал) | 96 | штатное завершение, `backlog_finish_phase` выполнен |

Всего в jsonl: **1227 tool_calls** в 60 assistant-сообщениях (glob:623, grep_search:352, read_file:182, edit:43 и др.), 1002 tool-результата. Маркер «Превышен лимит --max-tool-calls (100)» — **8 вхождений** (строки 109, 340, 446, 552, 658, 764, 870, 976).

### Откуда взялось «51 вызов»

Мета-файл `.vibelog/agent-sessions/agent-1793288764708.meta.json`:

```json
"usage_recorded": {"input": 12811442, ..., "requests": 51, ...}
```

`requests: 51` — это **количество LLM-запросов (ходов модели)** за фазу, записанное в usage. Это НЕ счётчик tool-calls. Счётчики независимы: 51 LLM-ход × до ~25 tool_calls в одном ходе (модель шлёт батчи по 20–40 вызовов glob/grep) = сотни tool-calls. Расхождение 100-vs-51 — не ложное срабатывание лимита, а **разные метрики**: лимит считает tool-calls, провайдер-записи — LLM-запросы.

Проверка: первый ран упёрся в лимит ровно на 100-м tool-call (100 tool-результатов до fail-строки 109) — счётчик в `src/agent/loop.ts` отработал корректно, без двойного учёта и без учёта вызовов агента MCP.

### Где и как считается лимит

- `src/agent/loop.ts:187` — `maxToolCalls = options.limits?.maxToolCalls ?? MAX_TOOL_CALLS_DEFAULT (100)` (`src/agent/loop.ts:124`).
- `src/agent/loop.ts:234` — `let toolCallsTotal = 0` объявляется **внутри `runLoop`**, т.е. сбрасывается при каждом запуске цикла (новый ран / resume).
- `src/agent/loop.ts:507–512` — проверка `toolCallsTotal + 1 > maxToolCalls` ДО выполнения вызова, затем `toolCallsTotal++`. Учитываются только tool_calls из ответов LLM; MCP-инструменты агента (инициируемые им самим) в этот счётчик не входят (они — часть tool_calls модели, один счётчик на вызов).
- Дублирования счётчиков нет: один инкремент на tool-call, фантомы (VL-215) фильтруются до записи и до счётчика.

### Почему «многократно прерывалась»

Каждый ран съедал ровно 100 tool-calls и падал, потому что:
1. **Раны сбрасывают счётчик** (toolCallsTotal живёт в замыкании одного runLoop) — resume продолжает с 0, а не с кумулятивного значения сессии. Это по дизайну (иначе resume после первого же лимита был бы мертв), но суммарно по сессии лимит срабатывал 8 раз.
2. **Поисковая стратегия модели** — массовый батчинг: один ход = 30–40 glob/grep-вызовов (623 glob + 352 grep_search из 1227). При таком профиле 100 tool-calls ≈ 3 хода модели. Лимит достижим за минуты.
3. **«Продолжи» после fail** (11 из 14 user-сообщений) — каждый рестарт заново отдавал 100-tool-call бюджет; итог — 8 лимитов за 47 минут.

### Затронутые компоненты

- `src/agent/loop.ts` (счётчик и guard лимита) — работает корректно.
- `src/agent/cli.ts:563` (проброс `--max-tool-calls`) — флаг не передавался, работал дефолт 100.
- Мета/usage (`requests: 51`) — источник ложной интерпретации как «число вызовов».
- Промпты фаз (VL-202/VL-142/VL-109) — правило пакетного чтения не сдержало массовый glob/grep.

### Повторяемость

Высокая: любая фаза с интенсивным поиском (plan/расследования) при дефолтном лимите 100 и батчинге 30–40 вызовов/ход повторит картину. Сами прерывания не теряли работу (append-only jsonl, resume продолжал с места fail).

## Предложение задач

**№1**
- title: Разграничить в диагностике лимит tool-calls и число LLM-запросов (51 vs 100 в VL-220)
- type: docs
- priority: Low
- описание: Мета сессии и usage пишут `requests` (LLM-ходы), а промпты/отчёты интерпретируют это как «число tool-вызовов», из-за чего лимит max-tool-calls выглядит ложным. Уточнить тексты fail-сообщения и промптов фаз: «лимит — tool-calls за ран (счётчик сбрасывается при resume); requests в usage — LLM-запросы». Добавить в вывод меги/финального отчёта обе метрики рядом.
- AC:
  1. Текст fail `--max-tool-calls` явно указывает «tool-calls текущего рана» и текущее/лимитное значения
  2. Документация промптов/README различает requests (LLM-ходы) и tool-calls
  3. Тесты проходят

**№2**
- title: Усилить правило пакетного поиска в промптах фаз (glob/grep-шторм 623+352 вызова)
- type: enhancement
- priority: Medium
- описание: В сессии VL-219 модель сделала 623 glob + 352 grep_search при лимите 100 tool-calls/ран — лимит достигался за ~3 LLM-хода. Существующие VL-202/VL-142/VL-109 не сработали. Ужесточить промпты фаз: один целевой glob/grep-проход → точечное чтение; запрет повторных переборов тех же паттернов; при resume — «не переоткрывай уже найденное».
- AC:
  1. В промптах фаз есть явное правило против повторных mass-glob/grep с теми же паттернами
  2. На репро-сценарии (фаза с интенсивным поиском) доля повторных glob/grep снижается
  3. Тесты промптов/статические проверки проходят

**№3**
- title: Опциональный кумулятивный лимит tool-calls по сессии с учётом resume-ранов
- type: feature
- priority: Low
- описание: Сейчас `toolCallsTotal` сбрасывается при каждом resume (loop.ts:234), поэтому за сессию лимит 100 срабатывал 8 раз, а суммарно выполнено 1227 вызовов. Предложить настраиваемую политику: либо считать кумулятивно по jsonl при resume (восстанавливая счётчик из истории), либо явный флаг `--tool-calls-per-session`. Не блокирует работу (resume и так продолжал), но даёт честный общий бюджет и раннее предупреждение.
- AC:
  1. При resume счётчик tool-calls восстанавливается из jsonl либо предоставляется флаг выбора политики

  3. Тесты покрывают обе политики, регрессий нет
