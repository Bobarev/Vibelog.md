# Анализ сессии Фазы 3 (Code) VL-85: луп или нет

**Дата анализа:** 2026-10-05  
**Задача:** VL-85 «CLI vibelog-agent (headless JSON) и интеграция с оркестратором»  
**Журнал сессии:** `~/.qwen/projects/-Users-bob-Dev-ton-ai-Vibelog-md/chats/50efba14-6528-4a1e-99be-84c53eb38b4b.jsonl`

## 1. Резюме

**Жёсткого лупа в сессии НЕ было.** Идентичных повторов вызовов инструментов — ноль, повторов текстов ассистента — ноль, компакшенов контекста — ноль. Сессия завершилась штатно: сборка, тесты 547/547, AC/DoD отмечены, комментарий оставлен, статус Review, финальное «Готово».

**Но час съеден «мягким лупом» планирования:** с 11:42:56 по 12:09:36 (~27 минут) модель **12 раз** подряд заявляла «у меня достаточно контекста, вот план: 1. src/web/phase-prompt.ts…» — и после каждой такой мысли шла читать файлы дальше, вместо записи кода. Первый `write_file` случился только через 34 минуты после старта (12:15:40). Ещё ~15 минут ушло на фазу «Wait —» самоисправлений. Реальная реализация + проверки заняли ~6 минут (12:43–12:47) — и прошли безупречно быстро.

**Вывод:** время потеряно не из-за зависания или компакшенов, а из-за поведения модели `xiaomi/mimo-v2.5` на крупной задаче без инструкции «хватит читать» — каждый цикл «достаточно контекста» превращался в новое чтение.

## 5. Аномалии сессии

1. **Галлюцинированная мысль (запись [53], 11:44:26):** «The user asks for a math proof. Prove: every graph with n vertices and more than n−1 edges contains a cycle…» — модель кратковременно потеряла контекст задачи и сгенерировала мысль из чужого домена. Работа продолжилась нормально; разовый эпизод, но признак нестабильности длинного контекста у mimo-v2.5.
2. **6 самоисправлений «Wait —»** — в основном **продуктивные**, пойманы реальные баги: можно ли создавать новые файлы через `write_file` (правило AGENTS.md), self-exec check в шиме `bin/vibelog-agent.mjs`, `__dirname` в ESM-тесте `orchestrator.test.mjs`, ссылки `renderPrompt` на вынесенные в `phase-prompt.ts` символы, семантика AC#4 относительно decision-5. Но каждое самоисправление стоило 2–7 минут паузы на генерацию.
3. **Ошибка macOS sed** (`N,+M` не поддерживается) — исправлена мгновенно, потерь нет.
4. **Повторные `tool_search` для MCP-инструментов** (3 раза) — by design (deferred tools), overhead минимален.
5. **decision-5 в статусе `proposed`** — модель трижды перепроверяла статус и осознанно не добавляла тест `VIBELOG_AGENT_BIN` (правильно по плану), но перепроверки стоили времени.

## 6. Корневая причина

Не компакшены, не зависание API, не бесконечный цикл инструментов. Причина — **совокупность трёх факторов**:

1. **Крупная задача.** VL-85 совмещала рефакторинг `orchestrator.ts` (вынос `phase-prompt.ts`), новый CLI `vibelog-agent`, тесты, CHANGELOG и docs — модель вынуждена была прочитать ~15 файлов, и после каждого чтения её «план» не закреплялся.
2. **Поведение модели.** `xiaomi/mimo-v2.5` на длинном контексте склонна повторно формулировать план вместо перехода к записи: каждая мысль «I have a good picture now» заканчивалась новым `sed/grep`, а не `write_file`.
3. **Отсутствие анти-луп инструкции в шаблоне промпта фазы.** Ничто не запрещало модели читать дальше после объявления «достаточно контекста» и не обязывало зафиксировать план во внешнем файле.

## 7. Рекомендации

### 7.1. Шаблон промпта Фазы 3 (приоритет — дёшево и сразу)

Добавить в шаблон code-фазы явный анти-луп блок, например:

```text
## Режим отсутствия лупов
- После первого «у меня достаточно контекста» — сразу переходи к записи файлов
  (write_file контента в /tmp + патч-скрипт). Повторное чтение тех же файлов запрещено.
- Зафиксируй план списком в /tmp/<task>-plan.txt и исполняй его построчно.
- Максимум один цикл уточняющих чтений; всё остальное — по памяти или по плану.
```

### 7.2. Разбивать крупные задачи до запуска фазы

VL-85 объединяла 4 самостоятельных блока работы. При размере «прочитать >10 файлов» задачу стоит дробить на подзадачи — каждая фаза-сессия должна укладываться в один проход чтения. Проверять готовность задач к Фазе 3 по числу файлов из Implementation Plan.

### 7.3. Модель для code-фаз

`xiaomi/mimo-v2.5` показала слабость на длинном горизонте планирования (12-кратный re-plan, галлюцинация мысли). Для рефакторинг-тяжёлых Фаз 3 рассмотреть более сильную модель или per-phase настройку модели в `.vibelog/` конфиге (если поддерживается оркестратором).

### 7.4. Наблюдаемость оркестратора (продолжение VL-58/60)

Добавить heartbeat-детект: если headless-сессия N минут не производит записи файлов/прогресса — писать метку в timeline-лог и уведомлять пользователя. Дешёвый вариант уже сегодня: считать по `~/.qwen/projects/<slug>/chats/<sessionId>.jsonl` время между последним `write_file` и текущим моментом (скрипт анализа из §8 пригодится как основа).

### 7.5. Прояснить AGENTS.md: новые файлы репозитория

Модель потратила паузу на сомнение «можно ли write_file для новых файлов». Зафиксировать в AGENTS.md: контент новых файлов готовится через `write_file` **в /tmp**, в репозиторий файл кладётся патч-скриптом (`writeFileSync`) — однозначно, без пространства для интерпретаций.

### 7.6. Закрывать решения (decision-*) до старта фазы

Pending decision-5 заставлял модель трижды перепроверять статус и осознанно отказываться от теста. Перед запуском Фазы 3 все решения по задаче должны иметь статус confirmed/rejected — иначе фаза тратит время на интерпретацию.

### 7.7. Ограничить «Wait —» самопроверки одним проходом

Самоисправления были полезны (пойманы реальные баги) — механику стоит оставить, но ограничить: один верификационный проход **после применения патча** (проверка diff и сборки), без возврата к перепланированию. Повторный цикл «Wait → новое чтение → новый план» — и есть то, что превратило 15 минут в 15 минут пауз.

### 7.8. Не трогать настройки компакшенов

Компакшенов в сессии не было — оптимизация в этом направлении бесполезна. Фокус — на поведении модели (§7.1, §7.3) и размере задач (§7.2).

## 8. Методика анализа

Инструменты (только Node.js, `/tmp`):

- `/tmp/vl85-analyze.mjs` — таймлайн всех 220 записей, поиск повторов functionCalls (хэш name+args), повторов текстов, маркеров компакшенов.
- `/tmp/vl85-deep.mjs` — модель, типы записей, разрывы >45с, счётчики инструментов, объём tool-ответов, паттерны «достаточно контекста» и «Wait —», галлюцинации.

Источник истины — журнал сессии `~/.qwen/projects/<slug>/chats/<sessionId>.jsonl` (Gemini-стиль: `message.parts[]` с `functionCall`/`functionResponse`/`text`+`thought`). `.vibelog/qwen-debug/` для рабочих сессий пуст — см. память о диагностике qwen-сессий.

Критерий «луп vs медленная модель» из этой диагностики применён: повторы одинаковых мыслей при наличии прогресса (патч-скрипты в /tmp, новые правки) — не тупик; критерий зависания (живой процесс, журнал не растёт десятки минут) — **не выполнен**, журнал рос постоянно, просто с повторяющимся содержанием планирования.
