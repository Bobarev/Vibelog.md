# Агент Vibelog (vibelog-agent)

Собственный LLM-агент Vibelog — headless-замена Qwen Code в фазах оркестратора (spec / plan / code / close / comment / prompt) и интерактивный TUI-исполнитель для терминала.

Документ описывает **фактическое поведение кода** (`src/agent/*`, `bin/vibelog-agent.mjs`) на 2026-10-14 (VL-83..86, эпик VL-75; TUI без зависимостей — VL-155; запуск чата — `vibelog agent` — VL-158).

## 1. Назначение и мотивация

Оригинальный оркестратор запускал headless-сессии **Qwen Code** (`@qwen-code/qwen-code` 0.24.7 — база агента, см. VL-77/doc-3 §12). Это работало, но расход токенов на типовых фазах был большим:

- Фаза Comment (обычный комментарий к задаче) — до **96k** токенов;
- Фаза Spec (разбор фичи на задачи) — до **935k** токенов.

Причины: полный CLI qwen со своей системной инструкцией, плагинами и MCP-обвязкой на каждую фазу. Агент Vibelog решает это минимальным tool-calling loop без «вагона» промпта.

**Зачем свой агент, а не просто `--model`:**

- Полный контроль над лимитами (tool-calls, wall-time) и loop detection — см. §6.
- Headless-контракт stdout совместим с `parseQwenResult` (`src/web/qwen-result.ts`) — оркестратор и бот не менялись (decision-5).
- LLM — любой OpenAI-совместимый endpoint (Cloud.ru по умолчанию) через свои env.
- Работает на macOS 10.15 Catalina: без нативных модулей; с VL-155 TUI — собственный ANSI-рендер на чистом Node.js (zero deps, без Ink/React).

**Решения по агенту** (backlog/decisions/, статус proposed на 2026-10-05):

| Решение | Суть |
|---|---|
| decision-1 | MCP-клиент минимальный самописный (без typescript-sdk) |
| decision-2 | TUI на Ink (кандидат — официальный 7.0.3, реализован в VL-86; заменён собственным zero-deps TUI в VL-155 — см. ниже) |
| decision-3 | LLM-клиент Cloud.ru через fetch (undici-штатный Node 20), без openai-SDK |
| decision-4 | Loop detection + двойной предел (tool-calls / wall-time), дедупликация вызовов |
| decision-5 | Headless: stdout — JSON `type=result`, формат parseQwenResult; qwen-фолбэк сохранён |

## 2. Установка и настройка

### Требования

- **Node.js 20+** (нужен глобальный `fetch` для LLM-клиента).
- Собранный `dist/`: бинарь `bin/vibelog-agent.mjs` импортирует `dist/agent/cli.js`.

```bash
pnpm install
pnpm build
```

### LLM (Cloud.ru)

Агенту нужен доступ к LLM. Три переменных окружения:

| Переменная | Обязательна | Назначение |
|---|---|---|
| `VIBELOG_LLM_API_KEY` | да | API-ключ (без него агент отказывается стартовать) |
| `VIBELOG_LLM_MODEL` | да | Имя модели (без неё агент отказывается стартовать) |
| `VIBELOG_LLM_BASE_URL` | нет | Endpoint; дефолт — `https://foundation-models.api.cloud.ru/v1` (decision-3) |
| `VIBELOG_LLM_DEBUG_USAGE` | нет | `=1` — сырой `usage` каждого ответа LLM в stderr (диагностика кэш-токенов, VL-96) |

Пример в shell:

```bash
export VIBELOG_LLM_BASE_URL="https://foundation-models.api.cloud.ru/v1"
export VIBELOG_LLM_API_KEY="sk-..."
export VIBELOG_LLM_MODEL="your-model-name"
```

Пример `.env` (TUI-чат `vibelog agent` читает `.env` проекта и секцию `env` в `.vibelog/settings.json` сам — VL-102/143, поведение как у бота VL-37: реальное окружение → `.env` → `env`-секция settings.json; для `vibelog-agent` в фазах/orchestration переменные приходят из окружения):

```
VIBELOG_LLM_BASE_URL=https://foundation-models.api.cloud.ru/v1
VIBELOG_LLM_API_KEY=sk-...
VIBELOG_LLM_MODEL=your-model-name
```

**Режим LLM API (`api_mode`, VL-205).** Ключ `api_mode` в `.vibelog/settings.json` выбирает wire-протокол LLM-клиента: `"chat"` (дефолт) — `POST <base_url>/chat/completions` (текущее поведение, без изменений); `"responses"` — `POST <base_url>/responses` (OpenAI Responses API): вход `input[]` (items `message` / `function_call` / `function_call_output`), ответ `output[]` вместо `choices`, typed SSE-события (`response.output_text.delta`, `response.function_call_arguments.delta/done`, `response.completed`, `error`), tool calls через `call_id` (результат — item `function_call_output`, не `role:tool`), `session_id` в теле запроса (дубль заголовка `X-Session-Id` безвреден, ref-18), usage по `input_tokens`/`output_tokens` (+ `reasoning_tokens` в `output_tokens_details`, кэш в `input_tokens_details.cached_tokens`); `stream_options` в responses не передаётся (строгий провайдер ответит 400); stateful `previous_response_id` не используется — stateless, вся история каждый ход (ref-20: MiMo несовместим).

Битое или отсутствующее значение → `chat` (конфиг не должен ронять агента). Приоритет над settings.json — флаг `--api-mode chat|responses` (для тестов и ручных прогонов). Чтение — `loadApiMode(cwd)` в `src/agent/llm-env.ts`; в branch-mode (агент в worktree) settings.json берётся по `VIBELOG_CWD ?? cwd`, иначе настройка молча игнорировалась бы. TUI-чат (`interactive.ts`) и веб-чат (`src/web/chat.ts`) читают тот же ключ.

## 3. Запуск

### Синтаксис

```bash
# Фаза: промпт собирается из шаблона templates/qwen-commands/phase-<N>.md
vibelog-agent <phase> <taskId> [--comment "<текст>"]

# Готовый промпт (qwen-совместимый сценарий: один позиционный аргумент)
vibelog-agent "<промпт целиком>"

# Справка
vibelog-agent --help

# TUI-чат с агентом (VL-158, ранее — пустой запуск vibelog/vb по VL-102):
# vibelog agent — чат без задачи; vibelog agent <task-id> — чат с задачей
# в контексте system prompt (интерактивный терминал, stdin+stdout TTY)
vibelog agent
vb agent VL-123
```

`<phase>` — spec | plan | code | close | comment | prompt. Шаблоны фаз лежат в `templates/qwen-commands/`; в них подставляются `{{taskId}}` и `{{comment}}` (пустая строка, если `--comment` не задан — в шаблонах есть инструкция об этом). Фаза `prompt` — шаблон промпта без требований к Vibelog MCP.

### Режимы

- **Интерактивный (TUI):** stdout — TTY, нет `--headless`/`--output-format json`, фаза ≠ `prompt`, нет `--no-tui`. Рендер — собственный ANSI-рендер на чистом Node.js (`src/agent/tui.ts`, zero deps — VL-155): вывод на **stderr** в альтернативном буфере терминала: лента чата (VL-113), посимвольный стриминг текста модели, карточки tool calls (имя, аргументы с обрезкой, статус ⏳/✅/❌, длительность), счётчики (ход, токены in/out/cache, время фазы), блок ошибок. Поведение stdout не меняется — контракт оркестратора сохраняется.
- **Headless:** `--headless`, либо `--output-format json` (qwen-совместимость), либо не-TTY stdout. В stdout — ровно одна JSON-строка (см. §4), прогресс/логи — в stderr.
- **TUI-чат (VL-158, ранее VL-102):** `vibelog agent` без подкоманд — multi-turn TUI-чат с инструментами (локальные + MCP Vibelog); `vibelog agent <task-id>` — тот же чат, но карточка задачи добавляется в system prompt. `vibelog agent analyze <session-ref> [комментарий]` (VL-141/169) — анализ сессии; необязательный комментарий уточняет разбор и подставляется в промпт фазы analyze. Требуется интерактивный терминал (stdin+stdout TTY) — в не-TTY ошибка с подсказкой `vibelog-agent --headless`. Строка ввода внизу TUI (Enter — отправить, Ctrl+C/Ctrl+D — выход, на время хода ввод блокируется), ответ стримится, история чата растёт в памяти, транскрипт сессии сохраняется в `.vibelog/agent-sessions/` **после каждого хода**. Отказ MCP — предупреждение, чат продолжается без vibelog-инструментов; `VIBELOG_LLM_*` читаются из окружения, из `.env` проекта или из секции `env` `.vibelog/settings.json` (загрузка как у бота, VL-37/143), нет ключей — понятная ошибка до рендера (exit 1). Запуск `vibelog`/`vb` без аргументов — всегда справка (exit 0), TUI не запускается.
- **Лента чата (VL-113):** диалог оформлен как типичный AI-чат (по образцу qwen code/opencode). Реплика пользователя при Enter остаётся в истории с префиксом `>` акцентным цветом — не стирается с экрана. Завершённый ответ ассистента переносится из стрима в ленту и отображается с сохранением переносов строк (многострочный ответ не склеивается в одну строку); стрим/карточки инструментов сбрасываются между ходами. Лента показывает последние 30 записей (обрезка сверху); текущий ход стримится под лентой. Оркестраторный TUI (`renderTui`) не меняется.

### Флаги

| Флаг | Дефолт | Назначение |
|---|---|---|
| `--headless` | без TTY | JSON-результат в stdout |
| `--comment <текст>` | `""` | Комментарий пользователя к фазе (`{{comment}}`) |
| `--no-mcp` | выкл. | Не подключать MCP-инструменты Vibelog |
| `--no-tui` | выкл. | Отключить TUI в интерактивном режиме (отладка) |
| `--max-tool-calls <N>` | 100 | Лимит tool-calls одного рана (сбрасывается при resume); fail-текст показывает `текущее/лимит` и отделяет tool-calls от LLM-запросов (VL-221, §6) |
| `--tool-calls-per-session <N>` | без лимита | Кумулятивный лимит tool-calls сессии через resume-раны (VL-223): счётчик восстанавливается из jsonl истории |
| `--max-wall-time <сек>` | 900 | Лимит времени фазы (wall-time) |
| `--max-requests <N>` | без лимита | Лимит LLM-запросов фазы (ходов модели; ≠ tool-calls) |
| `--no-compact` | компакшн включён | Отключить усечение истории LLM-запроса (VL-122) |
| `--compact-tail <N>` | 50 | Сколько последних сообщений хвоста сохранять при компакшне (VL-122) |
| `--compact-at-tokens <N>` | 850000 | Порог usage-токенов, при котором включается компакшн (VL-122) |
| `--api-mode <chat\|responses>` | `chat` (иначе settings.json `api_mode`) | Режим LLM API: chat — `/chat/completions`, responses — `/responses` (VL-205) |
| `--resume <sessionId>` | — | Продолжить сохранённую сессию (VL-95; префикс `vb:` игнорируется) |
| `--continue` | — | Продолжить последнюю сессию текущего каталога (VL-95) |
| `--help` | — | Справка |

**Qwen-совместимые флаги** (принимаются и игнорируются либо приравниваются): `--approval-mode <...>`, `--output-format json` (приравнивается к `--headless`), `--allowed-mcp-server-names <...>`. Это позволяет подставить агент вместо qwen без правок шаблонов фаз.

## 3.1. Сессии (VL-95)

Каждый запуск агента сохраняет транскрипт диалога в `.vibelog/agent-sessions/<sessionId>.jsonl` (каталог проекта, покрыт `.gitignore` через `.vibelog/`) — JSONL, по строке на сообщение. `session_id` в JSON-результате — **реальный идентификатор файла сессии** (формат `agent-<мс epoch>` — его же матчит `extractSessionRef` бота; менять формат нельзя, иначе бот определит сессию как qwen-сессию).

**Флаги:**

- `--resume <sessionId>` — загрузка транскрипта и продолжение loop с полной историей (старые сообщения + новый промпт). Работает **только с готовым промптом** — в режиме `<фаза> <taskId>` отклоняется (промпт собирается из шаблона, история не подставлялась бы). Бот передаёт sessionId с префиксом `vb:` — агент снимает его сам.
- `--continue` — то же, но сессия берётся автоматически: последний `*.jsonl` каталога по mtime. Нет сессий — ошибка «Нет сохранённых сессий» (exit 1).
- `--resume` и `--continue` одновременно — ошибка валидации.

**Инкрементальная запись (VL-103):**

- jsonl дописывается по мере выполнения фазы: стартовый набор (system + история + новый промпт) записывается **до** запуска loop, каждое сообщение цикла (assistant с tool_calls, tool-результат, финальный/ошибочный assistant) — сразу после появления. При обрыве процесса (SIGKILL/таймаут оркестратора) транскрипт сохранён до последнего дописанного сообщения — «в сессии нет последнего результата» больше не воспроизводится.
- `--resume`/`--continue` дописывают в файл **только** новый user-промпт (системный промпт и история в файле не переписываются; в памяти system заменяется свежесобранным — файл мог измениться между запусками).
- Финальный `saveSession` остаётся нормализацией: полная перезапись файла идемпотентна и подчищает любые расхождения append'ов.
- Ошибка записи сессии — предупреждение в stderr, фаза не роняется.

**Обрыв LLM-запроса (VL-103):**

- Обрыв соединения во время чтения SSE-тела (`terminated`/`ECONNRESET` от undici) переживается: ретраи стриминг-попытки (та же `maxRetries`/пауза, что у HTTP-запроса), затем non-stream фолбэк; retryable-ошибка фолбэка продолжает общий цикл ретраев. Abort (`Ctrl+C`) не ретраится — фаза прерывается сразу.
- При исчерпании всех попыток — понятная русская ошибка `Сетевая ошибка LLM (обрыв соединения: …) после N попыток и non-stream фолбэка` с диагностикой (логи stderr, `.vibelog/agent-sessions/`), а не сырой `terminated`.
- На повторных попытках `onToken` подавляется — TUI не показывает задублированный частичный текст; авторитетен `result` финальной успешной попытки.
- Сессии qwen (UUID в `~/.qwen/projects/`) резюмируются штатным `--resume <UUID>` самого qwen — механизм агента к ним не относится.

## 3.2. Системный промпт и кэш-токены (VL-96)

**Системный промпт.** Каждый запрос к LLM начинается с system-сообщения: встроенная базовая часть (роль Vibelog-agent, русский язык, границы рабочего каталога, запрет необратимых действий) + содержимое `AGENTS.md` проекта из cwd, если файл есть. Лимит вставки — 8000 символов (обрезка с пометкой); ошибка чтения — предупреждение в stderr, фаза продолжается без AGENTS.md. При `--resume` сохранённый system заменяется свежесобранным (файл мог измениться). Лог: `[vibelog-agent] Системный промпт: N символов (AGENTS.md: да/нет)`. В TUI-чате `vibelog agent <task-id>` (VL-158) к system-промпту дополнительно добавляется карточка задачи (`taskToMarkdown`) — чат стартует с задачей в контексте.

**Кэш-токены.** Поле `usage.cache_read_input_tokens` в JSON-результате суммирует кэш по итерациям. Провайдеры отдают кэш под разными именами — `mapUsage` читает все известные варианты: прямые `cache_read_input_tokens` / `cache_read_tokens` / `prompt_cache_hit_tokens` и вложенное `prompt_tokens_details.cached_tokens` (OpenAI-стиль Cloud.ru), для Responses — `input_tokens_details.cached_tokens`. Tools сортируются по имени перед отправкой — стабильный префикс запроса повышает шанс prefix-caching.

**Отладка usage.** `VIBELOG_LLM_DEBUG_USAGE=1` — в stderr печатается сырой `usage` каждого ответа (JSON) — по нему видно, под каким именем приходят кэш-токены:

```bash
VIBELOG_LLM_DEBUG_USAGE=1 node bin/vibelog-agent.mjs "промпт" --no-mcp --headless
```

## 4. Интеграция с оркестратором

Оркестратор (`src/web/orchestrator.ts`) берёт бинарь из переменной `VIBELOG_QWEN_BIN` (дефолт — `qwen` в PATH). Значение по умолчанию не менялось — qwen-фолбэк сохранён (decision-5).

```bash
VIBELOG_QWEN_BIN=$(pwd)/bin/vibelog-agent.mjs vibelog browser
```

Никаких правок кода оркестратора не требуется: агенту приходит тот же вызов `<bin> <phase> <taskId> [--comment ...] --output-format json`, что уходил qwen.

### Интеграция с Telegram-ботом (/prompt:vb и команды фаз, VL-92/94)

Команда `/prompt:vb <запрос>` Telegram-бота (VL-92) запускает встроенный агент вместо qwen без правок шаблонов: `startPrompt` оркестратора получает агента и спавнит `bin/vibelog-agent.mjs` (или `VIBELOG_AGENT_BIN`) с теми же qwen-совместимыми флагами `<промпт> --approval-mode yolo --output-format json`. Guard от двойного запуска (ключ `prompt`) общий для обоих агентов — одновременно активен только один `/prompt`. Переменные `VIBELOG_LLM_*` наследуются из process.env: бот применяет `.env` и секцию `env` `.vibelog/settings.json` через `loadDotEnv` → `applySettingsEnv` (VL-37/143, приоритет: реальное окружение → `.env` → `env`-секция); при отсутствии ключа агент печатает JSON-результат `is_error: true` — уходит в чат штатным механизмом фаз.

Команды фаз бота (`/spec`, `/plan`, `/code`, `/close`, `/comment`, VL-94) принимают тот же суффикс `:<agent>`: `startPhase` оркестратора получает агента опциональным параметром и спавнит `bin/vibelog-agent.mjs` вместо qwen — шаблоны фаз и JSON-контракт результата не меняются, guard-ключ фазы общий для обоих агентов. Агент по умолчанию задаётся командой `/set agent <qwen|vb>` (хранится в `.vibelog/settings.json`, ключ `default_agent`; единый файл настроек VL-143 — замена `bot.yml`/`settings.yml`): без суффикса запускают его все команды фаз и кнопок действий карточки задачи. **Лимиты фаз для vb** (VL-104): `/set max-wall-time <сек>` и `/set max-requests <N>` сохраняются в том же `settings.json` (ключи `max_wall_time`/`max_requests`); оркестратор при спавне `vibelog-agent` прокидывает их флагами `--max-wall-time`/`--max-requests` (только для агента vb — qwen эти флаги не поддерживает). Значение `0` — сброс настройки (дефолт агента). Без настроек флаги не передаются — поведение прежнее.

**Resume vb-сессии по reply (VL-95):** reply на информационное сообщение бота с `vb:<session_id>` возобновляет сессию агента — `startResume` оркестратора получает агента из `extractSessionRef` и спавнит `bin/vibelog-agent.mjs` с `--resume <sessionId>` (sessionId с префиксом `vb:` — strip делает CLI агента). Сессии хранятся JSONL в `.vibelog/agent-sessions/` (раздел 3.1); resume-запуск перезаписывает файл старыми + новыми сообщениями. Поведение qwen-resume не менялось (VL-93).

### Labels в Spec-фазе (VL-154)

Фаза Spec расставляет labels новым задачам (старые задачи без labels не мигрируются — метки появятся только у новых задач, созданных с этой версией workflow):

- **Подстановка:** в промпт phase-1 подставляется блок «Доступные labels: {{availableLabels}}» — переменная заполняется `taskExtraVars` (`src/web/phase-prompt.ts`) из поля `labels` в `backlog/config.yml` через `loadConfig` (та же механика подстановки полей задачи VL-137); fallback — пустая строка, если конфиг недоступен или labels в нём нет.
- **Выбор:** Spec выбирает 1–3 labels из списка, отражающих область задачи (напр. MCP → [core, mcp]; веб → [web]), и передаёт их в `backlog_update_task` (параметр `labels: string[]`) вместе с title/type/acceptanceCriteria.
- **Ведущие #теги (VL-157):** если заголовок или начало описания задачи начинается с одного или нескольких #тегов (например `#agent`) — Spec убирает их из заголовка и начала описания и добавляет в labels (объединяя с выбранными из списка; теги пользователя добавляются даже если их нет в списке — это явное намерение). Снятие тегов — поле `description` того же единственного вызова `backlog_update_task`.
- **Новые labels:** если ни один label из списка не подходит — Spec предлагает новый label в комментарии отчёта по форме «Предлагаю добавить label X (обоснование). Создайте: vibelog config set labels ...». Автоматически labels **не создаются** — `vibelog config set labels` выполняет пользователь. С версии VL-157 при предложении нового label ответ агента = «Готово» + пустая строка + строка предложения — она видна в чате бота, т.к. `sendPhaseResult` пересылает финальный ответ агента без фильтрации (код бота не менялся).
- **Кто расставляет:** только Spec (фаза уточнения видит задачу первой, классифицирует без чтения кода). Plan и Code labels не трогают.
- Round-trip с Backlog.md сохранён: поле `labels` есть в оригинале, core читает/пишет его без изменений формата (в т.ч. одиночная строка → массив).

### Переносимость промптов фаз (VL-157)

Промпты фаз (`templates/qwen-commands/*.md`) не содержат внутренних ID задач репозитория (VL-N/VL-XX — контролируется тестом `phase-prompt.test.mjs`), чтобы переноситься на внешние проекты без правок. Дополнения Фазы Spec (`phase-1.md`):

- **Чтение явно упомянутой задачи:** если пользователь в описании или комментарии (`{{comment}}` — новая подстановка с фолбэком) явно ссылается на другую задачу — Spec читает её через `backlog_view_task` **один раз** для понимания контекста; других задач не читает (общее правило «backlog-инструментов в Spec нет» сохраняется, исключение прописано в промпте).
- **References из текста пользователя:** упомянутые внешние источники (URL, репозиторий, файл, документация) регистрируются через `reference_add` + `reference_link`, и ref-N добавляется в поле `references` того же **единственного** вызова `backlog_update_task` (правило «один вызов» не нарушается). Содержимое референсов Spec не читает — их разбирает Фаза 2. В блоке подстановки задачи появилась строка `References: (нет)` — для дедупа при регистрации.
- **Финал:** при предложении нового label ответ = «Готово» + пустая строка + строка предложения (см. раздел «Labels в Spec-фазе»); без предложения — ровно одно слово «Готово».

### Контракт stdout

Headless-агент печатает в stdout **ровно одну JSON-строку** формата `parseQwenResult` (`src/web/qwen-result.ts` — парсит последнюю валидную JSON-строку лога с `type=result`):

```json
{
  "type": "result",
  "result": "текст фазы (финальный ответ модели или partial + текст ошибки)",
  "is_error": false,
  "num_turns": 3,
  "tool_calls_total": 5,
  "duration_ms": 42100,
  "duration_api_ms": 42100,
  "session_id": "agent-1728000000000",
  "usage": {
    "input_tokens": 12000,
    "output_tokens": 3400,
    "cache_read_input_tokens": 8000,
    "total_tokens": 15400
  }
}
```

- `is_error: true` → exit code 1; иначе 0.
- Логи, предупреждения (например, MCP недоступен) — в stderr.
- `duration_api_ms` приравнен к `duration_ms` (агент не меряет API-время отдельно).
- `tool_calls_total` — tool-calls текущего рана (VL-221); опционален в `parseQwenResult` (у qwen-ранов и старых логов поля нет).
- Ошибки лимитов/loop detection не роняют процесс исключением: текст ошибки и partial-результат фазы идут в поле `result`, `is_error: true`.

### Vibelog MCP

Подключается автоматически (кроме фазы `prompt` и флага `--no-mcp`): **36 инструментов** — `backlog_*` (create/list/view/update status/update task/manage ac/manage dod/add comment/update dependencies/search/ready/finish phase), `milestone_*` (list/add/rename/remove/archive), `document_*` (list/view/create/update/search), `reference_*` (list/add/view/search/remove/link/sync, VL-152), `lesson_*` (create/list/view/update/search_lessons/link/supersede, VL-153). ### Ограничения

- **Пути:** все файловые инструменты резолвят путь от cwd проекта и отказываются от выхода за его пределы (`Путь выходит за пределы проекта: ...`). Путь не может быть самим корнем-директорией (кроме `cwd` у shell).
- **Shell:** без `shell:true` на уровне Node; `cwd` команды — только внутри проекта. Строка команды тоже валидируется (VL-99, `checkShellCommandInProject`): токены `~`/`~/…`, `$HOME`/`${HOME}`, абсолютные пути и `..`-переходы наружу от cwd отклоняются до запуска bash — модель получает текст «Команда отклонена: обращение к путям вне проекта (<путь>). Разрешены только пути внутри <cwd>». Лексическая проверка не закрывает динамическое построение путей (командные подстановки, base64) — остаточный риск минимизируется правилом системного промпта. Спецфайлы POSIX (`/dev/null`, `/dev/stdout`, `/dev/stderr`, `/dev/stdin`) и regex/глоб-паттерны grep/sed (токены с метасимволами `|`, `*`, `^$` и т.п.) пропускаются — они не пути к данных пользователя (VL-104: ложные отказы по `2>/dev/null` губили tool-call целиком).

## 6. Loop detection и лимиты

Двойной предел (decision-4), проверяется на каждой итерации tool-calling loop:

| Предел | Дефолт | Флаг | Поведение при срабатывании |
|---|---|---|---|
| Одинаковые вызовы подряд | 3 | — (константа) | `Loop detection: инструмент <имя> вызван 3 раза подряд с одинаковыми аргументами — фаза прервана...` |
| Всего tool-calls (ран) | 100 | `--max-tool-calls <N>` | `Превышен лимит --max-tool-calls (N) tool-calls текущего рана: X/N — фаза прервана. Лимит считает tool-calls за ран (счётчик сбрасывается при resume); requests в usage — это LLM-запросы (ходы модели), а не tool-calls.` (VL-221) |
| Всего tool-calls (сессия) | без лимита | `--tool-calls-per-session <N>` | `Превышен кумулятивный лимит tool-calls сессии (--tool-calls-per-session N): использовано X из N (включая прошлые раны)` (VL-223) |
| Wall-time фазы | 900 сек | `--max-wall-time <N>` | `Превышен лимит --max-wall-time (N секунд) — фаза прервана.` |
| LLM-запросов фазы | без лимита | `--max-requests <N>` | `Превышен лимит --max-requests (N) — фаза прервана.` |

- Сигнатура для loop detection — имя инструмента + JSON его аргументов; счётчик обнуляется при смене сигнатуры.
- Лимит tool-calls проверяется **до** выполнения вызова — лишний вызов не выполняется.
- **Две независимые политики tool-calls (VL-223):** `--max-tool-calls <N>` (per-run, дефолт 100) сбрасывается при каждом resume; `--tool-calls-per-session <N>` (per-session, опционально) считает cumulatively всю сессию — при `--resume` счётчик восстанавливается из jsonl истории (`countToolCallsInMessages`, фантомные tool_calls с пустым name/id не тратят бюджет — фильтр `isValidToolCall`, как в самом loop). Без `--tool-calls-per-session` кумулятивного лимита нет, поведение прежнее. При resume с флагом в stderr пишется `Кумулятивный лимит tool-calls: N из M (прошлые раны)`. Обе проверки идут до выполнения вызова; per-session проверяется после per-run — при одновременном превышении модели показывается более специфичный текст про сессию.
- `--max-requests` — лимит **LLM-запросов** (ходов модели, numTurns), а не tool-calls: проверяется до отправки запроса в LLM. Дефолта нет — без флага предела нет. Для агента задаётся командой бота `/set max-requests <N>` (VL-104, см. docs/user-guide.md).
- **Два независимых счётчика в диагностике (VL-221):** `--max-tool-calls` считает **tool-calls текущего рана** (счётчик обнуляется при resume), а `requests` (`num_turns`, `usage.requests` в мете сессии) — **LLM-запросы** (ходы модели). В VL-220 эти числа путали: 51 LLM-запрос при 1227 фактических tool-calls выглядел как «51 tool-call из 100». Поэтому fail-текст лимита называет и текущее, и лимитное значение (`X/N`); в итоговой stderr-строке фазы обе метрики печатаются рядом — `запросов=N (LLM-запросы/ходы модели), tool-calls=M (лимит L, счётчик рана)`; в JSON-результате (`tool_calls_total`) и в отчётах бота — подпись «Количество LLM-запросов» плюс строка tool-calls рана (у qwen-ранов поля нет — строка не печатается).
- При срабатывании любого предела: partial-накопленный текст модели + текст ошибки уходят в JSON-результат (`is_error: true`), TUI показывает блок ошибки. Исключений наружу loop не бросает.
- Ошибки выполнения отдельного инструмента фатальны только для вызова: текст ошибки уходит модели как tool-результат, фаза продолжается.

## 6.1. Компакшн истории LLM-запроса (VL-122)

В длинных сессиях `messages` раздувается (десятки ходов с правками и тестами) — запросы замедляются до 5–15 минут и деградируют. Решение — **детерминированный wire-компакшн** внутри `runLoop` перед `streamChat` (по doc-13 §4.1):

- **Усекается только payload запроса** — `messages` в памяти и jsonl-транскрипт сессии остаются ПОЛНЫМИ: `onMessage`, resume-контракт (VL-103), loop-guard VL-119 и guard пустого финала VL-110 работают с полной историей.
- **Триггер** — по usage-токенам последнего ответа (`input_tokens + cache_read_input_tokens`) ≥ `--compact-at-tokens` (дефолт 850 000, 85% окна MiMo-V2.5 1M). Редкое срабатывание не бьёт по prefix-caching.
- **Липкий якорь**: после срабатывания запросы = system + первый user + последние `--compact-tail` сообщений (дефолт 50) — append-only префикс, кэш стабилен; повторное раздувание сдвигает якорь вперёд.
- **Служебная заметка** дописывается в wire-копию первого user-сообщения один раз в момент компакшна: «[История усечена: опущено K сообщений. Полный транскрипт — в сессии.]».
- **Орфан-гард**: хвост не начинается с `role: tool` без парного assistant(tool_calls) — якорь сдвигается вперёд past tool-сообщений; если отсекать нечего — исходный payload без маркера.
- **Выключение/настройка**: `--no-compact` (дефолт — компакшн включён); бот — `/set compact on|off` → `settings.json` (VL-143) → оркестратор передаёт `--no-compact` при следующем запуске фазы (только агент vb), перезапуск бота не нужен.

## 6.2. Cap tool-выводов и автоповтор при отказе провайдера (VL-178)

Инцидент VL-172: два вывода `chrome_devtools__take_snapshot` по 624 КБ ушли в один запрос целиком → провайдер отклонил его («The request was rejected because it was considered high risk»), работа продолжилась только вручную. Защита в четыре слоя:

- **Ingestion-cap** (`src/agent/loop.ts`): `truncateToolOutput` (8 КБ, маркер обрезки) применяется после вызова **любого** handler'а — встроенных и внешних MCP (через `toolsAsSpecs`). Раньше кап был только внутри handler'ов встроенных инструментов — MCP-выводы писались в историю целиком. В jsonl сессии пишется уже обрезанный вывод.
- **Wire-cap** (`toWireMessages`, `src/agent/llm.ts`): tool-сообщения усекаются при отправке в LLM — защита при `--resume` старых jsonl-сессий, где гигантские выводы уже лежат на диске.
- **Автоповтор LLM-клиента**: тело не-ok ответа читается и включается в `apiError`; маркер `high risk` (и аналогичные отказы модерации, `isHighRiskBody`) → повтор с `shrinkMessages` (tool-выводы до 4096, затем 1024 символов; сообщения не выбрасываются — сохраняется парность tool_calls↔tool), максимум 2 повтора, затем throw с текстом провайдера. Обычные 400 без маркера — без shrink-повторов.
- **Guard финализации в loop** (VL-199, `src/agent/loop.ts`): отказ провайдера может прийти валидным финальным текстом **без tool_calls при HTTP 200** (инцидент VL-197) — раньше такой ответ трактовался как успех (is_error=false, exit 0) и авто-resume ниже не срабатывал. Перед финализацией текст сверяется с `isHighRiskBody` → `fail()` с русским пояснением и обрезанным оригиналом: `is_error=true`, exit 1, маркер в result. Диагностика причины content-based отказов: `streamChat` в `src/agent/llm.ts` пишет в stderr (попадает в `logTail` оркестратора) размер wire-payload в байтах, число сообщений и usage — на HTTP-200-пути и на не-ok/исключении (включая shrink-уровни).
- **Фолбэк оркестратора** (`finish()` в `src/web/orchestrator.ts`): если результат фазы `is_error` с маркером high risk и есть `session_id` — один автоматический перезапуск той же фазы с `--resume` (счётчик 1 на runKey, цикл исключён). Благодаря guard'у VL-199 срабатывает и для HTTP-200-отказов.
- **Диагностика payload и usage фазы (VL-203):** wire-body LLM-запроса сериализуется в одной точке до `fetch` (`requestWithRetry`, `src/agent/llm.ts`) — байты считаются от фактического тела запроса (включая `stream`/`stream_options`), closure-переменные `lastRequestBytes`/`lastUsage` хранятся в клиенте. (1) После завершения фазы в stderr печатается итоговая строка `[vibelog-agent] фаза: запросов=N, payload последнего запроса=X байт (макс Y), usage={...}` (после `tui.unmount()`) — она попадает в `logTail` оркестратора и отвечает на вопрос «сколько весил запрос фазы». (2) Лог HTTP-отказа провайдера содержит usage **предыдущего успешного запроса** (JSON + пометка; «н/д» — только если успеха ещё не было). (3) JSONL-транскрипт: assistant-сообщения несут поля `payload_bytes` и `shrink_level` (0=full, 1=4096, 2=1024) — уровень компакшна tool-выводов по ходам; usage по ходам пишется с VL-198. (4) Мета сессии `<id>.meta.json` и JSON-результат фазы — `last_payload_bytes`/`max_payload_bytes`. Новые поля в assistant-сообщениях провайдеру не уходят: `toWireMessages`/`messagesToInput` собирают сообщения явно (role/content/tool_calls) — покрыто wire-регрессией в `llm.test.mjs`.
- **Валидация tool_calls и санация wire-пар с пустым id (VL-215/216):** ответ модели с фантомными tool_call (пустые name/id, инцидент VL-214) не отравляет историю: невалидные вызовы фильтруются до записи пары assistant+tool (isValidToolCall), а уже накопленные в старых jsonl-сессиях отравленные пары вырезаются на wire-границе (sanitizeWireMessages) — resume не падает guard'ом VL-110. Подробнее — §6.4.
- **Guard пустого финала: диагностика и один повтор (VL-217):** при пустом финальном ответе в stderr печатается диагностика (payload >140КБ-гипотеза, сообщений, есть-пустые-tool_calls, usage — уходит в logTail), выполняется ≤1 повтор после wire-санации; повторная пустота → fail с маркером «Пустой ответ модели». Подробнее — §6.5.

Параллельно промпты запрещают дорогие браузерные выводы: `take_screenshot` не использовать, вместо него `evaluate_script` (нужный кусок DOM) или `take_snapshot` с `filePath` (снапшот на диск, в контекст — только подтверждение).

- **Байтовый автокомпакт истории (VL-230):** байтовый лимит провайдера — отдельный риск от токенового: сессии VL-221 (`last_payload=894265`) и VL-226 (`payload=644142`) упёрлись в `max_payload_bytes`, потому что история (включая усечённые на 8 КБ tool-выводы прошлых ходов) уходила в каждый запрос целиком. Перед каждым `streamChat` loop оценивает байты wire-копии (`JSON.stringify` — та же граница сериализации, что у клиента): при `>= PAYLOAD_WARN_BYTES` (70% от `MAX_PAYLOAD_BYTES = 900_000`, то есть 630 000) в stderr (→ `logTail` оркестратора) пишется `[vibelog-agent] предупреждение payload: N байт >= порог … — история компактизируется перед запросом`, а tool-выводы на wire усекаются до `PAYLOAD_COMPACT_TOOL_CHARS = 2048` символов с маркером (эскалация до `PAYLOAD_COMPACT_TOOL_CHARS_ESCALATED = 1024`, если после усечения байты всё ещё у жёсткого лимита). Усечение затрагивает только `role: tool`: `messages` и jsonl-транскрипт не мутируются, AC и Implementation Plan задачи (system/user/assistant) побайтово не меняются, парность `tool_calls ↔ tool` сохраняется. Пороги — экспортируемые константы `src/agent/llm.ts`, override для тестов — `LoopLimits.maxPayloadBytes`/`payloadWarnBytes` (порог пересчитывается от лимита). Это защита от отказа провайдера, а не токеновый компакшн VL-122: работает и при `--no-compact`, дополняя его — при больших tool-выводах байтовый триггер срабатывает раньше токенового.

## 6.3. Пакетное чтение файлов (VL-202)

Правило в промптах фаз (`templates/phases/phase-plan/phase-code/phase-do/phase-investigate.md` + `templates/agent-prompt.md`): целевой файл анализируй **одним `read_file`** — при файле >200 строк читай последовательными чанками `offset`/`limit` подряд, а не через промежуточные grep-выборки границ; точечные правки вноси только после полного чтения файла; связанные проверочные команды (ls/grep/git/сборка/тесты) объединяй в один вызов через `&&`.

Согласование с лимитом «не читать файлы >200 строк целиком»: чанки `offset`/`limit` остаются обязательными — запрещён именно промежуточный grep-поиск границ между чанками (иначе ~12 чтений doc-6 вместо 3-4). Зачем: в сессии VL-193 README затронут в 20+ shell-вызовах — прямой вклад в исчерпание max_wall_time (VL-197, code-1 упала на 40-й минуте); тестовый прогон VL-202 дал 1 обращение к README вместо 20+.

## 6.4. Валидация фантомных tool_calls (VL-215)

Инцидент VL-214: модель mimo-v2.6-flash вернула `tool_call` с пустыми `name`/`id` (строка 36 jsonl) — loop не валидировал их и дописал в историю пару `assistant(tool_calls id="") + tool(tool_call_id="")`; следующий ход отклонён LLM API из-за отравленного ключа. Защита:

- **`isValidToolCall(tc)`** (`src/agent/llm.ts`, общий экспорт): name и id — непустые строки после `trim()` (с `typeof`-гардом). Фильтрация — **до** записи assistant-сообщения в диалог/jsonl: пара с пустым ключом не создаётся; зеркальная точка `src/web/chat.ts` импортирует ту же функцию (фикс VL-213, lesson-37 — копии не создаются).
- **Только фантомы** (`validCalls.length === 0`): assistant(tool_calls) не пишется, модели отдаётся текст-ошибка отдельным user-сообщением (не tool-результат — без пары с пустым `tool_call_id`), ход повторяется — модель может перезапустить вызов корректно. Счётчик фантомных ходов подряд `phantomStreak` ≥ 3 (`PHANTOM_CALL_LIMIT_DEFAULT`, по образцу loop detection VL-83) → `fail()`.
- **Фантом + валидный**: выполняются только валидные вызовы (`tool_calls: validCalls` в assistant-push, цикл — по `validCalls`), после выполнения — user-заметка «проигнорировано N tool_call(ов) с пустым name/id» (видно в jsonl).
- Фильтр не расширяется: name с пробелами по краям (« a ») валиден; путь «Неизвестный инструмент: <name>» работает только для валидных непустых имён — регрессий VL-95/VL-103 нет. Тесты: `loop.test.mjs`, блок «фантомные tool_calls VL-215» (Т1–Т3).
- **Wire-санация отравленных jsonl при resume (VL-216):** пары, уже лежащие на диске в старых сессиях (`assistant.tool_calls` с пустым `id`/`name` + парный `tool` с `tool_call_id=""`, инцидент VL-214), при записи не фильтруются (jsonl — append-only, контракт resume VL-103), но вырезаются на wire-границе функцией `sanitizeWireMessages` (`src/agent/llm.ts`), применяемой во всех точках ухода запроса: `toWireMessages` (chat), `messagesToInput` (responses) и payload-точка `runLoop` (`src/agent/loop.ts`, после компакшна — фантомная пара проходит орфан-гард, т.к. хвост начинается с assistant, а не tool). Валидные tool_calls сохраняются (id сравниваются через trim с объявленными), assistant только из фантомов переписывается в текстовую форму (при пустом/null content — вырезается целиком), `tool` с пустым или необъявленным `tool_call_id` вырезается; функция идемпотентна — двойное применение loop→wire безопасно и не ломает prefix-caching (детерминирована между запросами). `--resume` старых отравленных jsonl-сессий (включая `agent-1793269309877`) больше не падает guard'ом VL-110. Тесты: `llm.test.mjs` (describe «Санация отравленных пар (VL-216)»), `loop.test.mjs`, `cli.test.mjs` (AC2-resume `agent-vl216-poison`).

## 6.5. Guard пустого финала: диагностика и один повтор (VL-217)

Guard пустого финального ответа (VL-110, `src/agent/loop.ts`) раньше падал с первого раза без диагностики — в stderr/logTail не попадали ни payload, ни признаки отравленной истории, ни usage. Теперь:

- **Диагностика в точке пустоты:** при пустом финале до ветвления в stderr печатается `[vibelog-agent] пустой финал (попытка 1|2): payload=... байт (>140КБ=да/нет/н/д), сообщений=..., есть-пустые-tool_calls=да/нет, usage=...` (по образцу логов `streamChat` VL-199/VL-203 — строка уходит в `logTail` оркестратора; при активном TUI допустимо, прецедент VL-199). Гипотеза `>140КБ` — порог content-based отказа провайдера VL-197 (~140 КБ); `есть-пустые-tool_calls` — признак отравленных пар `assistant(tool_calls id:"") + tool(tool_call_id:"")` (VL-214/216); `payload` берётся из `response.payloadBytes ?? lastPayload` (иначе `н/д`).
- **≤1 повтор после санации wire-истории:** при первой пустоте запрос повторяется (`continue` цикла) — payload пересобирается на точке компакшна с `sanitizeWireMessages` (VL-216 — «санация после которой повтор»), в `messages` ничего не дописывается (пустой финал не пишет сообщений): транскрипт чист, `onMessage` не зовётся. Стейт — флаг `emptyFinalRetried` в пределах одной фазы, сброс не нужен (цикл финализируется сходу).
- **Повторная пустота → fail:** текст ошибки сохраняет маркер «Пустой ответ модели» (его матчат guard'ы VL-110) и добавляет: повтор после санации истории (VL-216/217) тоже пуст — вероятна отравленная история (пары с пустым id) либо отказ провайдера; payload/сообщений/есть-пустые-tool_calls/usage.
- При выставленном `--max-requests 1` лимит проверяется до запроса (loop.ts) — повтор упрётся в fail «Превышен лимит --max-requests» после диагностического лога (диагностика при этом уже в stderr).

Порядок guard'ов не менялся: пустой финал → high-risk (VL-199) → финализация. Тесты: `loop.test.mjs` (describe «Пустой финал: диагностика и один повтор (VL-217)» — две пустоты → is_error с одним повтором и логом payload/usage, успешный повтор, гипотеза VL-197, отравленная пара), `cli.test.mjs` (AC1: обе строки «пустой финал (попытка 1|2)» в stderr → logTail).
