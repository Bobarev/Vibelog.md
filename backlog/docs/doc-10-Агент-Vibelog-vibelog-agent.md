# Агент Vibelog (vibelog-agent)

Собственный LLM-агент Vibelog — headless-замена Qwen Code в фазах оркестратора (spec / plan / code / close / comment / prompt) и интерактивный TUI-исполнитель для терминала.

Документ описывает **фактическое поведение кода** (`src/agent/*`, `bin/vibelog-agent.mjs`) на 2026-10-14 (VL-83..86, эпик VL-75; TUI без зависимостей — VL-155; запуск чата — `vibelog agent` — VL-158).

## 1. Назначение и мотивация

Оригинальный оркестратор запускал headless-сессии **Qwen Code** (`@qwen-code/qwen-code` 0.24.7 — база агента, см. VL-77/doc-3 §12). Это работало, но расход токенов на типовых фазах был большим:

- Фаза Comment (обычный комментарий к задаче) — до **96k** токенов;
- Фаза Spec (разбор фичи на задачи) — до **935k** токенов.

Причины: полный CLI qwen со своей системной инструкцией, плагинами и MCP-обвязкой на каждую фазу. Агент Vibelog решает это минимальным tool-calling loop без «вагона» промпта.

**Зачем свой агент, а не просто `--model`:**

- Полный контроль над лимитами (tool-calls, wall-time) и loop detection — см. §6.
- Headless-контракт stdout совместим с `parseQwenResult` (`src/web/qwen-result.ts`) — оркестратор и бот не менялись (decision-5).
- LLM — любой OpenAI-совместимый endpoint (Cloud.ru по умолчанию) через свои env.
- Работает на macOS 10.15 Catalina: без нативных модулей; с VL-155 TUI — собственный ANSI-рендер на чистом Node.js (zero deps, без Ink/React).

**Решения по агенту** (backlog/decisions/, статус proposed на 2026-10-05):

| Решение | Суть |
|---|---|
| decision-1 | MCP-клиент минимальный самописный (без typescript-sdk) |
| decision-2 | TUI на Ink (кандидат — официальный 7.0.3, реализован в VL-86; заменён собственным zero-deps TUI в VL-155 — см. ниже) |
| decision-3 | LLM-клиент Cloud.ru через fetch (undici-штатный Node 20), без openai-SDK |
| decision-4 | Loop detection + двойной предел (tool-calls / wall-time), дедупликация вызовов |
| decision-5 | Headless: stdout — JSON `type=result`, формат parseQwenResult; qwen-фолбэк сохранён |

## 2. Установка и настройка

### Требования

- **Node.js 20+** (нужен глобальный `fetch` для LLM-клиента).
- Собранный `dist/`: бинарь `bin/vibelog-agent.mjs` импортирует `dist/agent/cli.js`.

```bash
pnpm install
pnpm build
```

### LLM (Cloud.ru)

Агенту нужен доступ к LLM. Три переменных окружения:

| Переменная | Обязательна | Назначение |
|---|---|---|
| `VIBELOG_LLM_API_KEY` | да | API-ключ (без него агент отказывается стартовать) |
| `VIBELOG_LLM_MODEL` | да | Имя модели (без неё агент отказывается стартовать) |
| `VIBELOG_LLM_BASE_URL` | нет | Endpoint; дефолт — `https://foundation-models.api.cloud.ru/v1` (decision-3) |
| `VIBELOG_LLM_DEBUG_USAGE` | нет | `=1` — сырой `usage` каждого ответа LLM в stderr (диагностика кэш-токенов, VL-96) |

Пример в shell:

```bash
export VIBELOG_LLM_BASE_URL="https://foundation-models.api.cloud.ru/v1"
export VIBELOG_LLM_API_KEY="sk-..."
export VIBELOG_LLM_MODEL="your-model-name"
```

Пример `.env` (TUI-чат `vibelog agent` читает `.env` проекта и секцию `env` в `.vibelog/settings.json` сам — VL-102/143, поведение как у бота VL-37: реальное окружение → `.env` → `env`-секция settings.json; для `vibelog-agent` в фазах/orchestration переменные приходят из окружения):

```
VIBELOG_LLM_BASE_URL=https://foundation-models.api.cloud.ru/v1
VIBELOG_LLM_API_KEY=sk-...
VIBELOG_LLM_MODEL=your-model-name
```

**Режим LLM API (`api_mode`, VL-205).** Ключ `api_mode` в `.vibelog/settings.json` выбирает wire-протокол LLM-клиента: `"chat"` (дефолт) — `POST <base_url>/chat/completions` (текущее поведение, без изменений); `"responses"` — `POST <base_url>/responses` (OpenAI Responses API): вход `input[]` (items `message` / `function_call` / `function_call_output`), ответ `output[]` вместо `choices`, typed SSE-события (`response.output_text.delta`, `response.function_call_arguments.delta/done`, `response.completed`, `error`), tool calls через `call_id` (результат — item `function_call_output`, не `role:tool`), `session_id` в теле запроса (дубль заголовка `X-Session-Id` безвреден, ref-18), usage по `input_tokens`/`output_tokens` (+ `reasoning_tokens` в `output_tokens_details`, кэш в `input_tokens_details.cached_tokens`); `stream_options` в responses не передаётся (строгий провайдер ответит 400); stateful `previous_response_id` не используется — stateless, вся история каждый ход (ref-20: MiMo несовместим).

Битое или отсутствующее значение → `chat` (конфиг не должен ронять агента). Приоритет над settings.json — флаг `--api-mode chat|responses` (для тестов и ручных прогонов). Чтение — `loadApiMode(cwd)` в `src/agent/llm-env.ts`; в branch-mode (агент в worktree) settings.json берётся по `VIBELOG_CWD ?? cwd`, иначе настройка молча игнорировалась бы. TUI-чат (`interactive.ts`) и веб-чат (`src/web/chat.ts`) читают тот же ключ.

## 3. Запуск

### Синтаксис

```bash
# Фаза: промпт собирается из шаблона templates/qwen-commands/phase-<N>.md
vibelog-agent <phase> <taskId> [--comment "<текст>"]

# Готовый промпт (qwen-совместимый сценарий: один позиционный аргумент)
vibelog-agent "<промпт целиком>"

# Справка
vibelog-agent --help

# TUI-чат с агентом (VL-158, ранее — пустой запуск vibelog/vb по VL-102):
# vibelog agent — чат без задачи; vibelog agent <task-id> — чат с задачей
# в контексте system prompt (интерактивный терминал, stdin+stdout TTY)
vibelog agent
vb agent VL-123
```

`<phase>` — spec | plan | code | close | comment | prompt. Шаблоны фаз лежат в `templates/qwen-commands/`; в них подставляются `{{taskId}}` и `{{comment}}`. Контракт `{{comment}}` (VL-307): подставляется **всегда** — при отсутствии комментария строкой «без комментария», поэтому литерала `{{comment}}` в собранном промпте не бывает никогда (см. §4, подраздел «Контракт `{{comment}}`»). Фаза `prompt` — шаблон промпта без требований к Vibelog MCP.

### Режимы

- **Интерактивный (TUI):** stdout — TTY, нет `--headless`/`--output-format json`, фаза ≠ `prompt`, нет `--no-tui`. Рендер — собственный ANSI-рендер на чистом Node.js (`src/agent/tui.ts`, zero deps — VL-155): вывод на **stderr** в альтернативном буфере терминала: лента чата (VL-113), посимвольный стриминг текста модели, карточки tool calls (имя, аргументы с обрезкой, статус ⏳/✅/❌, длительность), счётчики (ход, токены in/out/cache, время фазы), блок ошибок. Поведение stdout не меняется — контракт оркестратора сохраняется.
- **Headless:** `--headless`, либо `--output-format json` (qwen-совместимость), либо не-TTY stdout. В stdout — ровно одна JSON-строка (см. §4), прогресс/логи — в stderr.
- **TUI-чат (VL-158, ранее VL-102):** `vibelog agent` без подкоманд — multi-turn TUI-чат с инструментами (локальные + MCP Vibelog); `vibelog agent <task-id>` — тот же чат, но карточка задачи добавляется в system prompt. `vibelog agent analyze <session-ref> [комментарий]` (VL-141/169) — анализ сессии; необязательный комментарий уточняет разбор и подставляется в промпт фазы analyze. Требуется интерактивный терминал (stdin+stdout TTY) — в не-TTY ошибка с подсказкой `vibelog-agent --headless`. Строка ввода внизу TUI (Enter — отправить, Ctrl+C/Ctrl+D — выход, на время хода ввод блокируется), ответ стримится, история чата растёт в памяти, транскрипт сессии сохраняется в `.vibelog/agent-sessions/` **после каждого хода**. Отказ MCP — предупреждение, чат продолжается без vibelog-инструментов; `VIBELOG_LLM_*` читаются из окружения, из `.env` проекта или из секции `env` `.vibelog/settings.json` (загрузка как у бота, VL-37/143), нет ключей — понятная ошибка до рендера (exit 1). Запуск `vibelog`/`vb` без аргументов — всегда справка (exit 0), TUI не запускается.
- **Запуск фазы без отдельного бинаря (VL-305):** `vibelog agent run <фаза> <task-id> [флаги]` — тот же headless-исполнитель фаз, что и `vibelog-agent`, но через основную CLI. Команда делегирует в `main()` из `dist/agent/cli.js` (динамический импорт — агентский стек не грузится в путях чата и `analyze`) и возвращает его exit code. **Флаги передаются сырым argv** (additive-параметр `rawArgs` у `runAgent` в `src/cli/router.ts`), а не собираются обратно из разобранного роутером объекта: сохраняются порядок, повторяющиеся флаги и значения с пробелами; парсер `vibelog` (`src/cli/args.ts`) флаги после `run` не интерпретирует. Без аргументов / с одним позиционным / с флагом первым — справка по фазам из общего реестра `PHASES` (`src/web/phase-prompt.ts`) и exit 1 без стектрейса; `--help`/`-h` — справка и exit 0; неизвестная фаза — ошибка агента со списком фаз. Отдельный бинарь `vibelog-agent` и его спавн оркестратором не менялись: `bin/vibelog.mjs` перед роутингом делает проверку обновлений (до 3 с) и печатает заголовки, а `dist/cli/router.js` статически тянет все модули команд — для спавна это лишнее.
- **Лента чата (VL-113):** диалог оформлен как типичный AI-чат (по образцу qwen code/opencode). Реплика пользователя при Enter остаётся в истории с префиксом `>` акцентным цветом — не стирается с экрана. Завершённый ответ ассистента переносится из стрима в ленту и отображается с сохранением переносов строк (многострочный ответ не склеивается в одну строку); стрим/карточки инструментов сбрасываются между ходами. Лента показывает последние 30 записей (обрезка сверху); текущий ход стримится под лентой. Оркестраторный TUI (`renderTui`) не меняется.

| Флаг | Дефолт | Назначение |
|---|---|---|
| `--headless` | без TTY | JSON-результат в stdout |
| `--comment <текст>` | `""` | Комментарий пользователя к фазе (`{{comment}}`) |
| `--no-mcp` | выкл. | Не подключать MCP-инструменты Vibelog |
| `--no-tui` | выкл. | Отключить TUI в интерактивном режиме (отладка) |
| `--max-tool-calls <N>` | 100 | Лимит tool-calls одного рана (сбрасывается при resume); fail-текст показывает `текущее/лимит` и отделяет tool-calls от LLM-запросов (VL-221, §6) |
| `--tool-calls-per-session <N>` | без лимита | Кумулятивный лимит tool-calls сессии через resume-раны (VL-223): счётчик восстанавливается из jsonl истории |
| `--max-wall-time <сек>` | 900 | Лимит времени фазы (wall-time) |
| `--idle-timeout <сек>` | 600 | Idle-таймаут фазы (VL-274): максимум тишины (нет токенов стрима, нет завершённых tool-вызовов); `0` — выключено |
| `--max-requests <N>` | без лимита | Лимит LLM-запросов фазы (ходов модели; ≠ tool-calls) |

| `--compact-tail <N>` | 50 | Сколько последних сообщений хвоста сохранять при компакшне (VL-122) |
| `--compact-at-tokens <N>` | 850000 | Порог usage-токенов, при котором включается компакшн (VL-122) |
| `--api-mode <chat\|responses>` | `chat` (иначе settings.json `api_mode`) | Режим LLM API: chat — `/chat/completions`, responses — `/responses` (VL-205) |
| `--model <id>` | — | Разовая модель рана вместо модели сессии (VL-239); неизвестный id — ошибка |
| `--model-follow-settings` | выкл. | Взять активную модель из `.vibelog/settings.json`, игнорируя модель сессии (VL-239); несовместим с `--model` |
| `--resume <sessionId>` | — | Продолжить сохранённую сессию (VL-95; префикс `vb:` игнорируется) |
| `--continue` | — | Продолжить последнюю сессию текущего каталога (VL-95) |
| `--help` | — | Справка |

**Qwen-совместимые флаги** (принимаются и игнорируются либо приравниваются): `--approval-mode <...>`, `--output-format json` (приравнивается к `--headless`), `--allowed-mcp-server-names <...>`. Это позволяет подставить агент вместо qwen без правок шаблонов фаз.

## 3.1. Сессии (VL-95)

Каждый запуск агента сохраняет транскрипт диалога в `.vibelog/agent-sessions/<sessionId>.jsonl` (каталог проекта, покрыт `.gitignore` через `.vibelog/`) — JSONL, по строке на сообщение. `session_id` в JSON-результате — **реальный идентификатор файла сессии** (формат `agent-<мс epoch>` — его же матчит `extractSessionRef` бота; менять формат нельзя, иначе бот определит сессию как qwen-сессию).

**Флаги:**

- `--resume <sessionId>` — загрузка транскрипта и продолжение loop с полной историей (старые сообщения + новый промпт). Работает **только с готовым промптом** — в режиме `<фаза> <taskId>` отклоняется (промпт собирается из шаблона, история не подставлялась бы). Бот передаёт sessionId с префиксом `vb:` — агент снимает его сам.
- `--continue` — то же, но сессия берётся автоматически: последний `*.jsonl` каталога по mtime. Нет сессий — ошибка «Нет сохранённых сессий» (exit 1).
- `--resume` и `--continue` одновременно — ошибка валидации.

**Инкрементальная запись (VL-103):**

- jsonl дописывается по мере выполнения фазы: стартовый набор (system + история + новый промпт) записывается **до** запуска loop, каждое сообщение цикла (assistant с tool_calls, tool-результат, финальный/ошибочный assistant) — сразу после появления. При обрыве процесса (SIGKILL/таймаут оркестратора) транскрипт сохранён до последнего дописанного сообщения — «в сессии нет последнего результата» больше не воспроизводится.
- `--resume`/`--continue` дописывают в файл **только** новый user-промпт (системный промпт и история в файле не переписываются; в памяти system заменяется свежесобранным — файл мог измениться между запусками).
- Финальный `saveSession` остаётся нормализацией: полная перезапись файла идемпотентна и подчищает любые расхождения append'ов.
- Ошибка записи сессии — предупреждение в stderr, фаза не роняется.

**Обрыв LLM-запроса (VL-103):**

- Обрыв соединения во время чтения SSE-тела (`terminated`/`ECONNRESET` от undici) переживается: ретраи стриминг-попытки (та же `maxRetries`/пауза, что у HTTP-запроса), затем non-stream фолбэк; retryable-ошибка фолбэка продолжает общий цикл ретраев. Abort (`Ctrl+C`) не ретраится — фаза прерывается сразу.
- При исчерпании всех попыток — понятная русская ошибка `Сетевая ошибка LLM (обрыв соединения: …) после N попыток и non-stream фолбэка` с диагностикой (логи stderr, `.vibelog/agent-sessions/`), а не сырой `terminated`.
- На повторных попытках `onToken` подавляется — TUI не показывает задублированный частичный текст; авторитетен `result` финальной успешной попытки.
- Сессии qwen (UUID в `~/.qwen/projects/`) резюмируются штатным `--resume <UUID>` самого qwen — механизм агента к ним не относится.

**Модель фиксируется на сессии (VL-239).** Сессия помнит модель, с которой начата: при создании задачной сессии (режим `<фаза> <taskId>` и env-путь с `VIBELOG_PHASE_TASK_ID`) CLI пишет в мету `model_id`, `model_provider`, `model_name`, `api_mode` — до `createLlmClient` и первого запроса. Поле `model` остаётся фактической моделью последнего рана (его пишет пост-ран и billing); model-поля сессии пост-ран не перезаписывает.

Приоритет резолва модели рана (`resolveRunModel` в `src/agent/llm-env.ts`): `--model <id>` (`source: explicit`) → `--model-follow-settings` (активная из settings) → мета сессии (`source: session`) → активная модель (`source: settings`) → env `VIBELOG_LLM_MODEL` (`source: env`, для конфигов без секции `models`). Идентичность модели — пара `provider` + wire-имя `model` (стабильна при переименовании id), id из `available` — подпись: резолв пробует `model_id` через `resolveModelById`, при промахе ищет по паре (`findModelByProviderName` в `src/core/models.ts`), при промахе — fail-open на активную модель с предупреждением. `api_mode` берётся из меты приоритетнее конфига (флаг `--api-mode` выше всех); расхождение с `api_mode` модели в settings — отдельное предупреждение.

Лог старта рана печатает фактическую модель и источник: `Модель: <label> (<id>), api_mode: <mode> — из сессии` (`— из настроек`, `— из env`, `— явный --model`). Расхождение меты и активной модели — предупреждение в stderr (→ `logTail` оркестратора) с обеими моделями, применённой моделью и подсказкой `--model <id2> | --model-follow-settings`. `ensureLlmEnv` валидирует **фактическую** модель рана (`opts.active`), поэтому сломанный `models.default` не блокирует resume живой сессии.

Ограничение: мета пишется только там, где она и так писалась (инвариант VL-110) — сессии `/prompt` и TUI-чат мету не создают и продолжаются на активной модели, как раньше; сессии без model-полей (старые) — тоже. Retry авто-очереди (VL-200) и resume через бота наследуют поведение автоматически: `extraArgs` содержат только `--resume <sid>`, модель не передаётся.

## 3.2. Системный промпт и кэш-токены (VL-96)

**Системный промпт.** Каждый запрос к LLM начинается с system-сообщения: встроенная базовая часть (роль Vibelog-agent, русский язык, границы рабочего каталога, запрет необратимых действий) + содержимое `AGENTS.md` проекта из cwd, если файл есть. Лимит вставки — 8000 символов (обрезка с пометкой); ошибка чтения — предупреждение в stderr, фаза продолжается без AGENTS.md. При `--resume` сохранённый system заменяется свежесобранным (файл мог измениться). Лог: `[vibelog-agent] Системный промпт: N символов (AGENTS.md: да/нет)`. В TUI-чате `vibelog agent <task-id>` (VL-158) к system-промпту дополнительно добавляется карточка задачи (`taskToMarkdown`) — чат стартует с задачей в контексте.

**Чат-режим агента — opt-in (VL-238).** Поведенческие правила чата («ответ раньше полноты» с названием недостающего факта, тайм-бокс ~8–10 вызовов инструментов на вопрос с пометкой «не проверено: …», «Продолжи»/«Давай ответ»/«Ну?» = запрос результата) намеренно НЕ входят в базовую часть промпта: она одна и та же у интерактивного чата и у headless-фаз, поэтому правила подключены отдельным шаблоном и только по явному флагу сборки — `buildSystemPrompt(cwd, { chat: true })`. Флаг передаёт лишь `src/agent/interactive.ts`; `src/agent/cli.ts` (фазы оркестратора) вызывает `buildSystemPrompt(cwd)` без opts, поэтому фазовый промпт не меняется (инвариант закреплён тестом от обратного). Правила лежат в `templates/agent-prompt-chat.md` с проектным переопределением `.vibelog/prompts/agent-prompt-chat.md`; порядок сборки — база → блок чат-режима → AGENTS.md проекта. Как и у базового шаблона, отсутствие обоих файлов — fail-closed (`loadAgentChatRules` бросает с русским текстом). Веб-чат получает те же по смыслу правила другим каналом — из собственного шаблона `templates/prompts/chat-system.md` (см. README, раздел «Системная инструкция»).

**Кэш-токены.** Поле `usage.cache_read_input_tokens` в JSON-результате суммирует кэш по итерациям. Провайдеры отдают кэш под разными именами — `mapUsage` читает все известные варианты: прямые `cache_read_input_tokens` / `cache_read_tokens` / `prompt_cache_hit_tokens` и вложенное `prompt_tokens_details.cached_tokens` (OpenAI-стиль Cloud.ru), для Responses — `input_tokens_details.cached_tokens`. Tools сортируются по имени перед отправкой — стабильный префикс запроса повышает шанс prefix-caching.

**Отладка usage.** `VIBELOG_LLM_DEBUG_USAGE=1` — в stderr печатается сырой `usage` каждого ответа (JSON) — по нему видно, под каким именем приходят кэш-токены:

```bash
VIBELOG_LLM_DEBUG_USAGE=1 node bin/vibelog-agent.mjs "промпт" --no-mcp --headless
```

## 3.3. Учёт токенов и billing (VL-198, уточнён VL-243 и VL-259)

Usage каждого рана пишется в три уровня: мета сессии `.vibelog/agent-sessions/<sessionId>.meta.json` (`usage`, `startedAt/finishedAt/durationMs`, `model`, `agent`, история ранов `runs[]`), frontmatter задачи `token_usage` (суммы + `by_phase`, кумулятив по фазе рана) и append-only журнал `.vibelog/billing/<taskId>.json` (одна запись на ран — источник правды).

**`phase` в billing — фаза РАНА, не фазы сессии (VL-243).** У resume-рана (например `code` в сессии `plan` при `code_same_session`, VL-147) в записи стоит `code`, а исходная фаза сессии уходит в необязательное поле `sessionPhase`. Раньше обе точки учёта брали фазу из меты (`existing.phase`/`metaNow.phase`), и code-ран маскировался под `plan` с тем же `sessionId` — при сверке журнала фаза выглядела «потерянной». Правило lesson-40 «resume-ран не перезаписывает мету» сохраняется.

**История ранов в мете (VL-259).** `meta.phase` — фаза **создания** сессии, её нельзя переприсваивать фазе рана: по ней работает `findTaskPhaseSessionSync` (`code_same_session` VL-147, retry авто-очереди VL-200), и смена значения воскрешает инцидент VL-185/lesson-40. Поэтому правда о ранах пишется аддитивно: `meta.runs[]` — записи `{sessionId, phase, sessionPhase?, startedAt, finishedAt, durationMs?, usage?, agent?, billing?: 'run'|'fallback'}` (кап `RUN_HISTORY_MAX = 50`, старые вытесняются; сообщения не дублируются — только usage и времена) и `meta.lastRunPhase` — фаза последнего рана. Заполняется на каждом ране: CLI-пост-ран (`appendSessionRun`) и `finish()` оркестратора (qwen-блок — `billing: 'run'`, vb-fallback — `'fallback'`). Отсутствие полей у старых мет — не ошибка.

**`startedAt` billing — фактическое начало рана (VL-259).** Раньше в записях стояло время создания сессии (`metaNow.startedAt`/`existing.startedAt`), поэтому у 4 resume-ранов VL-235 оказался один и тот же `startedAt` и длительность рана по журналу не восстанавливалась. Теперь оркестратор кладёт в env `VIBELOG_RUN_STARTED_AT` (считается до `spawn`) и `VIBELOG_RUN_PHASE`, а CLI берёт старт из env с фолбэком на старт своего процесса; запись помечается `startedAtKind: 'run'`. Старые записи без этого поля считаются имеющими 'session'-семантику, начало рана для них восстанавливает хелпер `billingRunStart` (`finishedAt − durationMs`, без `durationMs` → `finishedAt`, ничего нет → `undefined`; не бросает).

**`by_phase` — по фазе РАНА (VL-259).** CLI-пост-ран (`addTaskTokenUsage(..., runPhase, ...)`), `finish_phase` MCP (`args.phase` → `VIBELOG_RUN_PHASE` → `VIBELOG_PHASE_NAME` кроме служебного `prompt` → `meta.phase`) и qwen-блок оркестратора пишут ключ рана, а не фазы сессии — иначе расход Code-ранов оседал под `plan` (у VL-235 в `by_phase` был только `plan`). Ключа `prompt` в `by_phase` не бывает: 'prompt' — не фаза workflow.

**Инвариант «каждый ран оставил запись».** CLI-пост-ран ставит в мету маркер `billing_recorded {sessionId, finishedAt}`; `finish()` оркестратора для vb-ранов без маркера дописывает запись сам с `fallback: true` (случай «ран убит сигналом/упал до учёта»). Двойного учёта нет — маркер живой, а fallback-запись видна в журнале. SIGINT у агента не вызывает немедленный `process.exit(130)`: цикл прерывается, MCP закрывается, `process.exitCode = 130` выставляется, и основной поток успевает выполнить пост-ран (страховочный таймер 5 с от зависания).

**Фаза Close учитывается как любая другая.** Раньше `phaseTaskId` в `spawnQwenRun` исключал close, поэтому close-ран не получал `VIBELOG_PHASE_TASK_ID/NAME`, `finish()` пропускал мету/frontmatter/billing, а CLI-пост-ран не резолвил `taskId`. Историческая причина исключения — VL-112: закрытие с merge ветки и `docs(task)`-коммитом выполняется **только в главном репо**, «Продолжи» на close-сообщении не должно уводить в worktree. Это ограничение теперь выражено явно параметром `noWorktree` (включается в `startResume` при `meta.phase === 'close'`) и гардом `meta.phase !== 'close'`; учёт общий для всех фаз.

## 3.4. Сводка сессии (VL-261)

Разбор сессии раньше начинался с ручного чтения JSONL: 237 строк по 8 КБ, руками считались «сколько было `run_shell_command`», границы ранов, payload по ранам — и цифры регулярно получались неверными (в VL-254 из-за ручного счёта в описание попала неверная фаза и неверные границы ранов). Теперь есть одна команда:

```bash
vibelog session summary <sessionId> [--json]     # или алиас agent-session
vibelog agent-session summary agent-1793328615846
vb session summary --task VL-235 [--json]        # последняя сессия задачи из *.meta.json
```

Ядро подсчётов — чистый модуль `src/agent/session-summary.ts` (`buildSessionSummary`/`formatSessionSummary`, без fs — тестируется на массиве сообщений); чтение файлов — тонкая обёртка `src/cli/commands/session.ts` (sync-парсеры `session.ts`, битые строки jsonl пропускаются). Одна реализация используется и CLI, и будущим `/analyze` — никакого дублирования логики в промптах.

**Раны.** Границы определяются по user-сообщениям: маркер промпта фазы `/^Ты — /` (все `templates/phases/*.md` начинаются с «Ты — автоматический …») и маркер resume-рана `/^Продолжи/` (кнопка «▶ Продолжить» VL-212, авто-повтор VL-178). Прочие user-сообщения внутри рана (guard повтора VL-229, «Ошибка ответа модели» и «Замечание: проигнорировано … tool_call» VL-215) границей НЕ являются; system-строки ран не создают.

**Фаза рана** (приоритет): запись billing задачи, отфильтрованная по `sessionId` и упорядоченная по `finishedAt` (поле `phase`, fallback `sessionPhase` — VL-243) → разбор текста маркера (11 фаз + `prompt`) → `meta.phase`. Расхождение числа записей billing и ранов печатается предупреждением (`⚠️ billing`), а не ошибкой: billing пишется только для задачных ранов.

**Что печатается:**

- Строк, ранов, LLM-запросов, tool-calls, токены (input/output/cache/reasoning/total) — по сессии и по каждому рану.
- По рану: фаза, диапазон строк jsonl, начало/конец из billing, длительность, `max payload_bytes`, `tool -> count`, правки файлов.
- Агрегаты: `tool -> count` по сессии, топ-5 скелетов `run_shell_command` (флаги сохраняются, аргументы отбрасываются: `node -e …` → `node -e`, `git status --porcelain` → `git status`), топ-5 путей чтения, топ-5 правленых файлов раздельно `edits` (`edit`) и `writes` (`write_file`), `repeatStats` — готовый `analyzeToolRepeats(messages)` из `repeat-tracker`.

**`--json`** — стабильная схема (`schemaVersion: 1`, `kind: 'session-summary'`): `meta`, `lines`, `runs[]`, `totals{runs, requests, toolCalls, токены, tools, shellTop, topReadPaths, editedFiles, repeatStats}`. Порядок ключей фиксирован, все числа — числа, отсутствующие данные — `null`/`0`/`[]`; содержимое сообщений в вывод не попадает (инвариант экономии контекста VL-178).

**Каталоги.** jsonl и мета — `.vibelog/agent-sessions/` (в claw/branch-режиме — `VIBELOG_CWD ?? cwd`); billing ищется в кандидатах `[cwd, meta.cwd]` — в worktree-ране журнал живёт в главном репозитории, отсутствие файла не ошибка (`billingSessions: []`).

## 3.5. Как читать транскрипт: обзор → целевые строки (VL-258)

Транскрипт сессии (`.vibelog/agent-sessions/<id>.jsonl`) — по одной гигантской строке на сообщение (в разобранной VL-235/254 сессии строка достигала ~22 КБ: полный текст задачи + план вставлялись в каждое resume-сообщение). При лимите tool-вывода 8 КБ обычный `read_file` отдаёт 1–2 строки из 238 — «какая фаза была активна» и «сколько было ранов» требовало ~15 чтений. Теперь чтение идёт **обзором**, а целевые строки добираются диапазоном.

**Обзор — один вызов на сессию** (`src/agent/session-outline.ts`, чистый модуль `buildSessionOutline`/`formatSessionOutline`, без fs):

```bash
vibelog session outline <sessionId> [--offset N] [--limit N] [--json]   # или --task VL-N
```

то же из агента — локальный инструмент `agent_session_outline {path, offset?, limit?}` (8-й локальный инструмент). Вывод — шапка, секция «Раны» и таблица по строке:

```
Сессия agent-…: 238 строк, 4 ранов, макс. строка 22841 байт
Раны: 1 → стр. 1 (plan), 2 → стр. 107 (code), …
 12  user       1.2 KB   run 2 → Plan   Ты — автоматический исполнитель Vibelog (Фаза 2: Plan) …
 13  assistant  4.8 KB    3 tools (read_file, edit, run_shell_command)   Правлю tools.ts …
 14  tool       8.1 KB                  exit code: 0 …
```

- Колонки: индекс (0-based, как `offset`), роль, `payload_bytes` исходной jsonl-строки, число и имена **валидных** tool_calls (фантомные отброшены, VL-215), маркер рана/фазы, первые 80 символов `content` одной строкой.
- Маркеры ранов — реюз `session-summary.ts` (`isPhasePromptMarker`, `phaseFromPromptText`), второй парсер маркеров не создаётся: новый ран — user-сообщение `Ты — … (Фаза N: …)` или `Продолжи`. Секция «Раны» печатается **до** таблицы: «какая фаза где» читается без просмотра строк.
- Бюджет вывода — 8 КБ по фактическим форматированным строкам; при усечении печатается хвост `…[обзор усечён: показаны строки X–Y из N; продолжение — offset=Z]`, продолжение читается `offset=Z`.
- `payload_bytes` — индикатор дублей: повторяющиеся большие user-строки означают, что промпт вставляется заново (до VL-258 так и было).
- `--json` — стабильная схема `{schemaVersion, kind: 'session-outline', sessionId, path, lines, runs, maxBytes, entries[], truncated, nextOffset, warnings}`; тексты сообщений в обзор не попадают целиком (инвариант экономии контекста VL-178).
- Файл > 8 МБ не читается целиком — ответ просит сузить диапазон через `offset`/`limit`. Расхождение `lineBytes` и числа сообщений — warning, а не исключение.

**Resume не дублирует неизменный блок задачи** (`src/agent/prompt-dedup.ts`, применяется в `src/agent/cli.ts`). Блок «Задача (подставлена автоматически): … до ближайшего `## `» хэшируется (sha256, 8 символов) и сравнивается с user-сообщениями истории сессии. Хэш совпал — в `messages` и в стартовую jsonl-строку пишется одна строка `Задача (подставлена автоматически): без изменений с рана N (строка M, хэш abc12345) — текст блока уже есть в истории сессии`; изменился (например, план записан в Plan → Code-ран видит новый план) — блок уходит полностью. Fail-open: истории/блока нет — исходный промпт; не-resume запуск не меняется. Диагностика в stderr: «блок задачи без изменений (хэш …, строка M)» либо «изменён — включён полностью».

**Порядок чтения транскрипта:** обзор (один вызов) → границы нужного рана из секции «Раны» → целевые строки `read_file path:НАЧАЛО-КОНЕЦ` (диапазоны VL-252). Не читать jsonl подряд.

## 4. Интеграция с оркестратором

Оркестратор (`src/web/orchestrator.ts`) берёт бинарь из переменной `VIBELOG_QWEN_BIN` (дефолт — `qwen` в PATH). Значение по умолчанию не менялось — qwen-фолбэк сохранён (decision-5).

```bash
VIBELOG_QWEN_BIN=$(pwd)/bin/vibelog-agent.mjs vibelog browser
```

Никаких правок кода оркестратора не требуется: агенту приходит тот же вызов `<bin> <phase> <taskId> [--comment ...] --output-format json`, что уходил qwen.

### Интеграция с Telegram-ботом (/prompt:vb и команды фаз, VL-92/94)

Команда `/prompt:vb <запрос>` Telegram-бота (VL-92) запускает встроенный агент вместо qwen без правок шаблонов: `startPrompt` оркестратора получает агента и спавнит `bin/vibelog-agent.mjs` (или `VIBELOG_AGENT_BIN`) с теми же qwen-совместимыми флагами `<промпт> --approval-mode yolo --output-format json`. Guard от двойного запуска (ключ `prompt`) общий для обоих агентов — одновременно активен только один `/prompt`. Переменные `VIBELOG_LLM_*` наследуются из process.env: бот применяет `.env` и секцию `env` `.vibelog/settings.json` через `loadDotEnv` → `applySettingsEnv` (VL-37/143, приоритет: реальное окружение → `.env` → `env`-секция); при отсутствии ключа агент печатает JSON-результат `is_error: true` — уходит в чат штатным механизмом фаз.

Команды фаз бота (`/spec`, `/plan`, `/code`, `/close`, `/comment`, VL-94) принимают тот же суффикс `:<agent>`: `startPhase` оркестратора получает агента опциональным параметром и спавнит `bin/vibelog-agent.mjs` вместо qwen — шаблоны фаз и JSON-контракт результата не меняются, guard-ключ фазы общий для обоих агентов. Агент по умолчанию задаётся командой `/set agent <qwen|vb>` (хранится в `.vibelog/settings.json`, ключ `default_agent`; единый файл настроек VL-143 — замена `bot.yml`/`settings.yml`): без суффикса запускают его все команды фаз и кнопок действий карточки задачи. **Лимиты фаз для vb** (VL-104): `/set max-wall-time <сек>` и `/set max-requests <N>` сохраняются в том же `settings.json` (ключи `max_wall_time`/`max_requests`); оркестратор при спавне `vibelog-agent` прокидывает их флагами `--max-wall-time`/`--max-requests` (только для агента vb — qwen эти флаги не поддерживает). Значение `0` — сброс настройки (дефолт агента). Без настроек флаги не передаются — поведение прежнее. **Idle-таймаут для vb** (VL-274): `/set idle-timeout <сек>` пишет ключ `idle_timeout_seconds`, оркестратор передаёт `--idle-timeout` тем же правилом «только vb»; здесь `0` — **выключить watchdog** (а не сброс, как у прочих числовых), сброс к дефолту 600 — удалением ключа (в веб-API `null`); ключа нет — флаг не передаётся, агент берёт дефолт.

**Resume vb-сессии по reply (VL-95):** reply на информационное сообщение бота с `vb:<session_id>` возобновляет сессию агента — `startResume` оркестратора получает агента из `extractSessionRef` и спавнит `bin/vibelog-agent.mjs` с `--resume <sessionId>` (sessionId с префиксом `vb:` — strip делает CLI агента). Сессии хранятся JSONL в `.vibelog/agent-sessions/` (раздел 3.1); resume-запуск перезаписывает файл старыми + новыми сообщениями. Поведение qwen-resume не менялось (VL-93).

### Labels в Spec-фазе (VL-154)

Фаза Spec расставляет labels новым задачам (старые задачи без labels не мигрируются — метки появятся только у новых задач, созданных с этой версией workflow):

- **Подстановка:** в промпт phase-1 подставляется блок «Доступные labels: {{availableLabels}}» — переменная заполняется `taskExtraVars` (`src/web/phase-prompt.ts`) из поля `labels` в `backlog/config.yml` через `loadConfig` (та же механика подстановки полей задачи VL-137); fallback — пустая строка, если конфиг недоступен или labels в нём нет.
- **Выбор:** Spec выбирает 1–3 labels из списка, отражающих область задачи (напр. MCP → [core, mcp]; веб → [web]), и передаёт их в `backlog_update_task` (параметр `labels: string[]`) вместе с title/type/acceptanceCriteria.
- **Ведущие #теги (VL-157):** если заголовок или начало описания задачи начинается с одного или нескольких #тегов (например `#agent`) — Spec убирает их из заголовка и начала описания и добавляет в labels (объединяя с выбранными из списка; теги пользователя добавляются даже если их нет в списке — это явное намерение). Снятие тегов — поле `description` того же единственного вызова `backlog_update_task`.
- **Новые labels:** если ни один label из списка не подходит — Spec предлагает новый label в комментарии отчёта по форме «Предлагаю добавить label X (обоснование). Создайте: vibelog config set labels ...». Автоматически labels **не создаются** — `vibelog config set labels` выполняет пользователь. С версии VL-157 при предложении нового label ответ агента = «Готово» + пустая строка + строка предложения — она видна в чате бота, т.к. `sendPhaseResult` пересылает финальный ответ агента без фильтрации (код бота не менялся).
- **Кто расставляет:** только Spec (фаза уточнения видит задачу первой, классифицирует без чтения кода). Plan и Code labels не трогают.
- Round-trip с Backlog.md сохранён: поле `labels` есть в оригинале, core читает/пишет его без изменений формата (в т.ч. одиночная строка → массив).

### Переносимость промптов фаз (VL-157)

Промпты фаз (`templates/qwen-commands/*.md`) не содержат внутренних ID задач репозитория (VL-N/VL-XX — контролируется тестом `phase-prompt.test.mjs`), чтобы переноситься на внешние проекты без правок. Дополнения Фазы Spec (`phase-1.md`):

- **Чтение явно упомянутой задачи:** если пользователь в описании или комментарии (`{{comment}}` — подстановка, с VL-307 всегда непустая: «без комментария» при отсутствии) явно ссылается на другую задачу — Spec читает её через `backlog_view_task` **один раз** для понимания контекста; других задач не читает (общее правило «backlog-инструментов в Spec нет» сохраняется, исключение прописано в промпте).
- **References из текста пользователя:** упомянутые внешние источники (URL, репозиторий, файл, документация) регистрируются через `reference_add` + `reference_link`, и ref-N добавляется в поле `references` того же **единственного** вызова `backlog_update_task` (правило «один вызов» не нарушается). Содержимое референсов Spec не читает — их разбирает Фаза 2. В блоке подстановки задачи появилась строка `References: (нет)` — для дедупа при регистрации.
- **Финал:** при предложении нового label ответ = «Готово» + пустая строка + строка предложения (см. раздел «Labels в Spec-фазе»); без предложения — ровно одно слово «Готово».

### Контракт `{{comment}}` (VL-307)

До VL-307 `{{comment}}` подставлялся только при непустом комментарии, а в 6 шаблонах лежала фолбэк-строка «Если вместо комментария остался неподставленный `{{comment}}` (запуск без комментария) — просто продолжай». Так как `renderPrompt` делает `replaceAll`, при наличии комментария текст подставлялся **дважды** — в том числе внутрь фолбэк-строки. Контракт после VL-307:

- **Подставляется всегда.** `src/web/orchestrator.ts` (`startTaskPhase` → `renderPrompt`) передаёт `comment: extraVars?.comment || 'без комментария'` после `...extraVars` (явный комментарий приоритетнее, пустая строка трактуется как отсутствие). Тот же контракт в CLI-режиме фаз — `src/agent/cli.ts` (`comment: opts.comment || 'без комментария'`); иначе CLI оставлял литерал.
- **Литерала не бывает.** `{{comment}}` в собранном промпте не встречается никогда — ни при пустом, ни при непустом комментарии (инвариант-тест `src/web/phase-prompt.test.mjs`), а текст комментария встречается ровно один раз (регресс-тест `startTaskPhase`, дублирование из VL-307).
- **Фолбэк-строки удалены** из `phase-spec.md`, `phase-plan.md`, `phase-code.md`, `phase-do.md`, `phase-investigate.md`, `phase-materialize.md` — при подстановке строки «без комментария» проверять нечего.
- **`phase-comment.md` / `phase-reject.md`** используют `{{comment}}` как сам запрос, поэтому их фолбэк переписан на **сравнение с «без комментария»**, а не на проверку литерала: Comment при подставленном «без комментария» не выполняет этот текст как запрос, а берёт запрос из строки «Последний комментарий»; Reject не выдумывает причину и берёт её из того же источника.

### Lessons learned в фазах (VL-153)

Workflow-уроки из опыта задач (`backlog/lessons/`, отдельная сущность — задача Done заморожена, а урок эволюционирует). Интеграция в три фазы:

- **Plan читает автоматически.** В промпт phase-2 подставляется блок «Lessons learned (подставлены автоматически по tags задачи): {{taskLessons}}» — переменная заполняется `taskExtraVars` (`src/web/phase-prompt.ts`) через `loadLessonsForTask(cwd, taskId)`: берутся labels задачи, фильтруются активные lessons с пересекающимися tags (case-insensitive), формат — компактные строки `- [lesson-N] <title>`; fallback «(нет)» при отсутствии совпадений или ошибке чтения. 0 дополнительных ходов модели — тот же механизм подстановки полей задачи (VL-137). Plan учитывает применимые уроки при планировании, но не создаёт и не обновляет lessons.
- **Close пишет автоматически** (шаг 6.5 в phase-close.md и phase-close-worktree.md). Если задача была в Code (непустые modified_files или отчёт Фазы 3 в комментариях) — Close формулирует 1–3 урока (императив, конкретика, 1 предложение), ищет похожие активные lessons (`lesson_search_lessons` / `lesson_list` с tags задачи), похожий есть → `lesson_update` (linked_tasks += taskId, updated_date обновляется сама), нет → `lesson_create` + `lesson_link`, затем `backlog_update_task` с `lessons: [...]`. Если задача в Code не была — шаг пропускается.
- **Close коммитит refs и lessons** (VL-170, шаг 6.6 в phase-close.md и шаг 7.6 в phase-close-worktree.md): references и lessons, созданные/обновлённые в фазе, закоммичиваются в главном репо одним `docs(task)`-коммитом по явным путям — ID затронутых файлов берутся из полей задачи (`backlog_view_task` с `fields: ["references","lessons"]`), точные пути — только через `ls` (slug файла отличается от ID, ловушка VL-121); после шага 6.5 повторно ls-ается разбогатевший файл задачи (поле lessons); `backlog/references/data/` не коммитится (.gitignore); нечего коммитить — шаг пропускается (пустой коммит запрещён). После Фазы Close `git status` по `backlog/lessons` и `backlog/references` пуст.
- **Code связывает применённые** (шаг 6.5 в phase-3.md): использовал существующий lesson из поля `lessons` задачи — связь уже есть, ничего не делает; создал новый полезный урок — `lesson_create` + `lesson_link`; применил существующий, добавив в поле lessons — `backlog_update_task`.
- **Трейлер `Co-authored-by` в коммитах** (VL-302): если настройка `commit_coauthor` не равна явному `false` (дефолт — включена, битый/отсутствующий ключ тоже даёт «включено»), в сообщение коммита после описания добавляется пустая строка и строка `Co-authored-by: vibelog-agent <vb@xw2.ru>`. Единый источник правды — `src/core/commit-trailer.ts` (`COMMIT_TRAILER`, `resolveCommitCoauthor`, `appendCommitTrailer` — идемпотентен по `includes(COMMIT_TRAILER)`, `commitMessageArgs`, `commitTrailerText`). Framework добавляет трейлер кодом: `commitTaskFile` (`src/agent/task-commit.ts`) — и в новый `docs(task)`-коммит, и в ветку amend (там `--amend --no-edit` заменён на `--amend -m <полное сообщение из git log -1 --pretty=%B>`, чтобы сохранить тему и тело), `commitProgressChanges` (`src/agent/run-progress.ts`) — в WIP-коммит. Агент получает трейлер подстановкой `{{commitTrailer}}` в шаблонах фаз (`phase-code.md`, `phase-do.md`, `phase-close.md`, `phase-close-worktree.md`): при выключенной настройке подставляется пустая строка, и шаблон требует второй `-m` ТОЛЬКО при непустом значении (иначе git создал бы пустой абзац). Двойного трейлера не бывает: `appendCommitTrailer` не дублирует уже присутствующую строку (amend поверх коммита агента).

Форматы и CLI — в [user-guide.md](user-guide.md#14-lessons-learned-vl-153) (раздел 14) и [mcp-reference.md](mcp-reference.md) (секция lessons).

### Контракт stdout

Headless-агент печатает в stdout **ровно одну JSON-строку** формата `parseQwenResult` (`src/web/qwen-result.ts` — парсит последнюю валидную JSON-строку лога с `type=result`):

```json
{
  "type": "result",
  "result": "текст фазы (финальный ответ модели или partial + текст ошибки)",
  "is_error": false,
  "num_turns": 3,
  "tool_calls_total": 5,
  "duration_ms": 42100,
  "duration_api_ms": 42100,
  "session_id": "agent-1728000000000",
  "usage": {
    "input_tokens": 12000,
    "output_tokens": 3400,
    "cache_read_input_tokens": 8000,
    "total_tokens": 15400
  }
}
```

- `is_error: true` → exit code 1; иначе 0.
- Логи, предупреждения (например, MCP недоступен) — в stderr.
- `duration_api_ms` приравнен к `duration_ms` (агент не меряет API-время отдельно).
- `tool_calls_total` — tool-calls текущего рана (VL-221); опционален в `parseQwenResult` (у qwen-ранов и старых логов поля нет).
- Ошибки лимитов/loop detection не роняют процесс исключением: текст ошибки и partial-результат фазы идут в поле `result`, `is_error: true`.

### Vibelog MCP

Подключается автоматически (кроме фазы `prompt` и флага `--no-mcp`): **45 инструментов** — `backlog_*` (create/list/view/update status/update task/manage ac/manage dod/add comment/update dependencies/search/ready/finish phase), `milestone_*` (list/add/rename/remove/archive), `document_*` (list/view/create/update/search), `reference_*` (list/add/view/search/remove/link/sync, VL-152), `lesson_*` (create/list/view/update/search_lessons/link/supersede, VL-153), `git_commit` (VL-311). Схемы — в `docs/mcp-reference.md`.

**Контракт коммитов (VL-311, ранее VL-302):** коммит агента в фазах идёт через write-инструмент `git_commit { paths, message, amend?, allowForeign? }`, а не через `git commit -m` в shell по тексту шаблона. Инструмент детерминированно: принимает только явные пути (`git add -- <paths>`, никогда `-A`/`.`), сверяет их с `modified_files` задачи (чужой путь → отказ с `allowForeign: true` для осознанного случая — инциденты VL-137/VL-169/VL-172), дописывает трейлер `Co-authored-by` через `src/core/commit-trailer.ts` (настройка `commit_coauthor`, по умолчанию включена; `amend` сохраняет полное тело `%B` и не дублирует трейлер) и отвечает JSON-ack (`ackOk`/`ackNoop`/`ackError`) с полями `hash`/`subject`/`paths`. Поэтому в `templates/phases/*.md` больше нет ни одного `git commit`, ни запрета «никогда `git add -A`», ни подстановки `{{commitTrailer}}`: правило, которое должно выполняться всегда, живёт в коде, а не в тексте промпта (правило в промпте — не гарантия, а надежда на дисциплину модели; lesson-180). Framework-коммиты (автокоммит файла задачи, WIP-прогресс фазы) ставят трейлер кодом, как и раньше.

**Отказ MCP не фатален:** если MCP-сервер недоступен, в stderr печатается предупреждение, и фаза продолжается без MCP-инструментов (локальные работают).

### Ограничения

- **Пути:** все файловые инструменты резолвят путь от cwd проекта и отказываются от выхода за его пределы (`Путь выходит за пределы проекта: ...`). Путь не может быть самим корнем-директорией (кроме `cwd` у shell).
- **Shell:** без `shell:true` на уровне Node; `cwd` команды — только внутри проекта. Строка команды тоже валидируется (VL-99, `checkShellCommandInProject`): токены `~`/`~/…`, `$HOME`/`${HOME}`, абсолютные пути и `..`-переходы наружу от cwd отклоняются до запуска bash — модель получает текст «Команда отклонена: обращение к путям вне проекта (<путь>). Разрешены только пути внутри <cwd>». Лексическая проверка не закрывает динамическое построение путей (командные подстановки, base64) — остаточный риск минимизируется правилом системного промпта. Спецфайлы POSIX (`/dev/null`, `/dev/stdout`, `/dev/stderr`, `/dev/stdin`) и regex/глоб-паттерны grep/sed (токены с метасимволами `|`, `*`, `^$` и т.п.) пропускаются — они не пути к данных пользователя (VL-104: ложные отказы по `2>/dev/null` губили tool-call целиком).
- **Собственный cwd (VL-249, `checkSelfCwdDestruction`):** второй guard строки команды, вызывается после проверки путей и **до** `execFile` — bash не запускается, поэтому потеря рабочего каталога процесса физически невозможна. Сравнение идёт против фактического `workDir` команды (`args.cwd` внутри проекта, иначе корень проекта), а не против корня. Три правила: (1) `rm`/`rmdir`/`unlink`/`shred` и `find … -delete`/`-exec rm` — если не-флаговый аргумент резолвится в `workDir` или в его предка, отказ (ловит `rm -rf .`, `rm -rf ./`, `rm -rf ..`, абсолютный собственный путь); (2) `git worktree remove|move` — если путь аргумента резолвится в `workDir`/предка, отказ (удаление *другого* worktree из главного cwd — штатный шаг Фазы Close — разрешено); (3) `node` с eval-флагом (`-e`/`--eval`/`--input-type`), тело которого содержит `rmSync|rmdirSync|fs.rm|fs.rmdir|rimraf` — кандидаты путей (`process.cwd()`, `'.'`, `'./'`, `'..'`, строковые литералы) проверяются так же. Токенизатор общий с `checkShellCommandInProject` (константа `SHELL_TOKEN_RE`, один парсер). Единый русский текст отказа: «удаление собственного рабочего каталога агента (<путь>)» + правильный способ — «Запусти команду из главного каталога проекта: `git worktree remove .vibelog/worktrees/<id>`, затем `git worktree prune`». Лексическая эвристика не закрывает динамическое построение путей (конкатенация, base64) — остаточный риск компенсируется правилом `templates/agent-prompt.md`. Guard действует только в `run_shell_command` vb-агента: MCP/веб-чат shell не имеют, qwen-агент — отдельный рантайм.

## 6. Loop detection и лимиты

Двойной предел (decision-4), проверяется на каждой итерации tool-calling loop:

| Предел | Дефолт | Флаг | Поведение при срабатывании |
|---|---|---|---|
| Одинаковые вызовы подряд | 3 | — (константа) | Вызов **не исполняется**: директива `Loop detection: инструмент <имя> вызван 3 раза подряд с одинаковыми аргументами — вызов заблокирован… Следующий шаг: …` уходит модели **tool-результатом** (VL-251); вторая блокировка подряд → `фаза прервана` |
| Всего tool-calls (ран) | 100 | `--max-tool-calls <N>` | `Превышен лимит --max-tool-calls (N) tool-calls текущего рана: X/N — фаза прервана. Лимит считает tool-calls за ран (счётчик сбрасывается при resume); requests в usage — это LLM-запросы (ходы модели), а не tool-calls.` (VL-221) |
| Всего tool-calls (сессия) | без лимита | `--tool-calls-per-session <N>` | `Превышен кумулятивный лимит tool-calls сессии (--tool-calls-per-session N): использовано X из N (включая прошлые раны)` (VL-223) |
| Wall-time фазы | 900 сек | `--max-wall-time <N>` | `Превышен лимит --max-wall-time (N секунд) — фаза прервана.` |
| Idle-таймаут фазы (VL-274) | 600 сек | `--idle-timeout <N>` | `Превышен idle-таймаут (N секунд без активности) — фаза прервана.` — reason `idle` в мете сессии/`run_progress.reason`, не путается с `wall-time`/`max-requests` |
| LLM-запросов фазы | без лимита | `--max-requests <N>` | `Превышен лимит --max-requests (N) — фаза прервана.` |

- Сигнатура для loop detection — имя инструмента + JSON его аргументов; счётчик обнуляется при смене сигнатуры.
- **Повтор уже применённого вызова не завершает ран (VL-304, пересмотрено VL-310):** если ответ инструмента распарсился как JSON с `ok: true`, сигнатура попадает в `appliedSignatures`; сам вызов при повторе **не исполняется** (иначе `document_update` с неизменяющими аргументами крутился бы вечно), модели уходит директива `appliedNoopDirective` («изменения применены — переходи к следующему пункту/отчёту»), и цикл **продолжается**. Терминальный «штатный» выход через `finishAppliedRepeat()` (`is_error: false`) остаётся единственному случаю — отчёт этой сессии уже записан (`reportWritten`: успешный `backlog_finish_phase`/`backlog_add_comment` в текущем ране, guard по образцу `src/agent/auto-report.ts`). Серия подряд ограничена капом `MAX_APPLIED_REPEATS_PER_RUN = 3`, счётчик сбрасывается любым реально исполненным вызовом (`resetRepeatSeries`); исчерпание → честный `fail()` (`is_error: true` → оркестратор откатывает статус и запускает авто-resume). Причина пересмотра (VL-310): VL-304 завершал ран на ПЕРВОМ повторе, поэтому сессия `agent-1793637056809` (Code VL-124) оборвалась кодом 0 с текстом «ран завершён штатно» после 4 вызовов, хотя реально модель 20+ раз повторила `document_update {id:'doc-2', type:'guide'}` и работа не была сделана.
- **noop универсален для write-инструментов MCP (VL-303/306, расширено VL-310):** любой write-инструмент, у которого переданные поля совпадают с текущими, отвечает `{ok:false, noop:true, reason:'noop'}` через `ackNoop` и файл НЕ перезаписывает (`updated_date`/mtime не сдвигаются) — модель получает явный сигнал «изменений нет, переходи к следующему шагу». Сверка вынесена в общий хелпер `sameFieldsUpToDate`/`sameValue` (`src/mcp/tool-result.ts`, массивы сравниваются как множества, тело документа/reference подаётся под ключом `BODY_FIELD`), его используют `backlog_update_task`, `lesson_update`, `document_update`, `reference_update`, `backlog_update_status`, `backlog_update_dependencies`, `milestone_rename`, `lesson_link`, `reference_link`. Инструменты, где noop неприменим по природе (create/remove/sync/add/audit/classify), перечислены с причиной в инвариант-тесте `src/mcp/write-ack-contract.test.mjs` — новый write-инструмент без noop-детекции и без записи в списке-исключении валит тест. Причина (VL-310): noop был только у 2 из 10 write-инструментов, поэтому `document_update` на неизменяющих аргументах отвечал `ackOk` и модель крутила его повторно до обрыва фазы.
- **noop ≠ «работа сделана» (VL-309):** noop-ответ (`ok:false` + `reason:'noop'`, VL-303/306) в `appliedSignatures` **не попадает** — он означает «изменений нет», а не «сделано». Такие сигнатуры живут в отдельном наборе `noopSignatures`: повтор noop-вызова **не исполняется**, но и ран **не завершается** — модели уходит директива `noopRepeatDirective`, фатальные счётчики блокировок не растут, цикл продолжается. Круг «noop-директива → повтор» ограничен капом `MAX_NOOP_REPEATS_PER_RUN = 3`; при превышении — честный `fail()` (`is_error: true` → оркестратор откатывает статус и запускает авто-resume), а не ложный «ран завершён штатно» (инцидент Close VL-307: повтор `lesson_update` с noop-JSON обрывал Close до написания документации). Страховка VL-306 для не-JSON ответов write-инструментов noop-JSON больше не перекрывает — он классифицируется раньше.
- **Директива noop-повтора не утверждает «выполнено» (VL-319):** текст `noopRepeatDirective` (`src/agent/loop.ts`) говорит «вызов `<имя>` **НЕ исполнен** (поля уже такие). Повтор ничего не изменит. Следующий шаг: прочитай состояние (`lesson_view`) или смени аргумент — добавь отсутствующее поле». Прежняя формулировка «вызов с теми же аргументами уже был выполнен и ничего не изменил» была **неверным фактом**: вызов не исполнялся ни разу, с первого раза ответ был noop, — модель читала «не выполнен» и повторяла дословно. Длина директивы держится < 400 байт (инвариант VL-310). Парная правка на стороне MCP: noop-ответ `lesson_update` заполняет `missing`/`hint` (см. doc-8), а урок с пустым телом без `content` отвечает `ok:false` вместо noop — сигнатура не попадает в `noopSignatures`, повтор исполняется и снова отдаёт текст ошибки. Причина (сессия `agent-1793712738536`, Close VL-318): шаблон Close создал `lesson-191` с пустым телом, `lesson_update` без `content` четыре раза вернул noop, кап сработал → `fail()` → откат статуса → авто-resume с нуля — рецидив семейства VL-303/304/309/310/318.
- **Три исхода классификации ответа write-инструмента (VL-318):** ответ распарсился как JSON — `ok:true` → «применён» (сигнатура в `appliedSignatures`), `noop:true` → «изменений нет» (`noopSignatures`), `ok:false` → **ошибка** (`failed`: `ackError`/`ackDenied`). Отказ НЕ пополняет ни `appliedSignatures`, ни `noopSignatures`, поэтому повтор такого вызова **исполняется заново** и модель получает свежий текст ошибки (например, подсказку `allowForeign: true` от `git_commit`); страховка VL-306 для не-JSON ответов получила условие `!failed` — она существует ровно для «ответ не JSON», а не для распознанного отказа. Причина (VL-318): `ackError` от `git_commit` (JSON, начинается с `{`, не с «Ошибка») попадал под страховку VL-306 и считался применённым — модель 4 раза получала ложное «уже применено» вместо подсказки и ран падал по капу `MAX_APPLIED_REPEATS_PER_RUN` (сессия `agent-1793705489953`, Close VL-316). Частичный успех по-прежнему кодируется `ok:true` + `skipped` и остаётся в `appliedSignatures`.
- **Авто-отчёт не ставит терминальный статус при неотмеченных пунктах (VL-309):** если ран завершился без вызова `backlog_finish_phase`, отчёт записывается автоматически в пост-ране CLI: `writeAutoReportIfMissing` (`src/agent/auto-report.ts`) вызывается до `recordRunProgress`/`finalizePhaseStatus` — комментарий `@agent` с текстом `buildAutoReport` (общий модуль `src/mcp/auto-report.ts`, + перечисление неотмеченных AC/DoD) и смена статуса по `getStatusAfterPhase`; пропуск при `isError`, служебной фазе или уже записанном отчёте (guard по последнему `@agent`-комментарию с `created >= runStartedAt` — нет двойного отчёта с `finish_phase`). **Гейт терминальности:** если `getStatusAfterPhase` даёт терминальный статус (`isTerminalStatus` из `src/core/workflow.ts`), а у задачи остались неотмеченные пункты AC или DoD — статус НЕ меняется (остаётся прежним), а в текст отчёта добавляется строка «Статус не изменён: терминальный «Done» при неотмеченных пунктах (DoD: #2; AC: #5) возможен только через backlog_finish_phase с dodOverride или aborted (VL-248/VL-309)». Причина: правило VL-248 (терминальный статус при невыполненном DoD требует явного `dodOverride`/`aborted`) живёт внутри `backlog_finish_phase`, и авто-отчёт его обходил — Close VL-307 получил Done с неотмеченными AC5/DoD2, хотя документация не была написана. Текстовые (не-JSON) ответы внешних MCP-инструментов применёнными не считаются — `JSON.parse` в `try/catch`, поведение прежнее.
- **Блокировка вместо исполнения (VL-251):** при достижении порога повторный вызов НЕ выполняется, а его сигнатура (`<имя>|<JSON(args)>`) попадает в `LoopResult.blocked_signatures`; директива уходит модели как tool-результат заблокированного вызова (не `role: assistant` — модель читает её как результат инструмента, а не как собственный текст) и содержит явный «Следующий шаг». Две блокировки подряд (без успешного вызова с другой сигнатурой) → `fail()` с «Следующий шаг».
- **Персист блокировок (VL-251):** `blocked_signatures` пишутся в мету сессии (`.vibelog/agent-sessions/<id>.meta.json`, дедуп + кап 20) и при `--resume` подаются обратно в `LoopLimits.blockedSignatures`: повтор такой сигнатуры после resume блокируется без исполнения (раньше «Продолжить» открывало луп по второму кругу).
- Лимит tool-calls проверяется **до** выполнения вызова — лишний вызов не выполняется.
- **Две независимые политики tool-calls (VL-223):** `--max-tool-calls <N>` (per-run, дефолт 100) сбрасывается при каждом resume; `--tool-calls-per-session <N>` (per-session, опционально) считает cumulatively всю сессию — при `--resume` счётчик восстанавливается из jsonl истории (`countToolCallsInMessages`, фантомные tool_calls с пустым name/id не тратят бюджет — фильтр `isValidToolCall`, как в самом loop). Без `--tool-calls-per-session` кумулятивного лимита нет, поведение прежнее. При resume с флагом в stderr пишется `Кумулятивный лимит tool-calls: N из M (прошлые раны)`. Обе проверки идут до выполнения вызова; per-session проверяется после per-run — при одновременном превышении модели показывается более специфичный текст про сессию.
- `--max-requests` — лимит **LLM-запросов** (ходов модели, numTurns), а не tool-calls: проверяется до отправки запроса в LLM. Дефолта нет — без флага предела нет. Для агента задаётся командой бота `/set max-requests <N>` (VL-104, см. docs/user-guide.md).
- **Idle-таймаут vs wall-time (VL-274, doc-19 §8):** пять ограничителей независимы — idle срабатывает **раньше** wall-time только при реальном простое, wall-time остаётся жёстким потолком безопасности. Активность (новый токен стрима или завершённый tool-вызов) перевзводит idle-таймер, поэтому «длинная-но-живая» фаза не обрывается никогда (решение проблемы VL-254). Таймер **снимается на время выполнения инструмента** (`pause()`/`resume()` вокруг хендлера): легитимный долгий `pnpm test` (20+ минут без вывода) не считается простоем — зависший инструмент ловят его собственные таймауты (`bashTimeoutMs`, `remainingWallTimeMs`) и wall-time. Прерывание идёт через существующий `AbortSignal`-путь `streamChat` (висящий HTTP-запрос не остаётся), а reason попадает в мету сессии отдельным значением `idle`. Настройка — `idle_timeout_seconds` в `.vibelog/settings.json` (`/set idle-timeout <сек>`; **`0` — выключено**, а не сброс, в отличие от прочих числовых настроек; сброс к дефолту 600 — удалением ключа), оркестратор прокидывает её флагом `--idle-timeout` только агенту `vb`. Битое значение откатывается к дефолту с предупреждением `[vibelog-settings]`.
- **Два независимых счётчика в диагностике (VL-221):** `--max-tool-calls` считает **tool-calls текущего рана** (счётчик обнуляется при resume), а `requests` (`num_turns`, `usage.requests` в мете сессии) — **LLM-запросы** (ходы модели). В VL-220 эти числа путали: 51 LLM-запрос при 1227 фактических tool-calls выглядел как «51 tool-call из 100». Поэтому fail-текст лимита называет и текущее, и лимитное значение (`X/N`); в итоговой stderr-строке фазы обе метрики печатаются рядом — `запросов=N (LLM-запросы/ходы модели), tool-calls=M (лимит L, счётчик рана)`; в JSON-результате (`tool_calls_total`) и в отчётах бота — подпись «Количество LLM-запросов» плюс строка tool-calls рана (у qwen-ранов поля нет — строка не печатается).
- При срабатывании любого предела: partial-накопленный текст модели + текст ошибки уходят в JSON-результат (`is_error: true`), TUI показывает блок ошибки. Исключений наружу loop не бросает.
- Ошибки выполнения отдельного инструмента фатальны только для вызова: текст ошибки уходит модели как tool-результат, фаза продолжается.

## 6.1. Компакшн истории LLM-запроса (VL-122)

В длинных сессиях `messages` раздувается (десятки ходов с правками и тестами) — запросы замедляются до 5–15 минут и деградируют. Решение — **детерминированный wire-компакшн** внутри `runLoop` перед `streamChat` (по doc-13 §4.1):

- **Усекается только payload запроса** — `messages` в памяти и jsonl-транскрипт сессии остаются ПОЛНЫМИ: `onMessage`, resume-контракт (VL-103), loop-guard VL-119 и guard пустого финала VL-110 работают с полной историей.
- **Триггер** — по usage-токенам последнего ответа (`input_tokens + cache_read_input_tokens`) ≥ `--compact-at-tokens` (дефолт 850 000, 85% окна MiMo-V2.5 1M). Редкое срабатывание не бьёт по prefix-caching.
- **Липкий якорь**: после срабатывания запросы = system + первый user + последние `--compact-tail` сообщений (дефолт 50) — append-only префикс, кэш стабилен; повторное раздувание сдвигает якорь вперёд.
- **Служебная заметка** дописывается в wire-копию первого user-сообщения один раз в момент компакшна: «[История усечена: опущено K сообщений. Полный транскрипт — в сессии.]».
- **Орфан-гард**: хвост не начинается с `role: tool` без парного assistant(tool_calls) — якорь сдвигается вперёд past tool-сообщений; если отсекать нечего — исходный payload без маркера.
- **Выключение/настройка**: `--no-compact` (дефолт — компакшн включён); бот — `/set compact on|off` → `settings.json` (VL-143) → оркестратор передаёт `--no-compact` при следующем запуске фазы (только агент vb), перезапуск бота не нужен.

## 6.2. Cap tool-выводов и автоповтор при отказе провайдера (VL-178)

Инцидент VL-172: два вывода `chrome_devtools__take_snapshot` по 624 КБ ушли в один запрос целиком → провайдер отклонил его («The request was rejected because it was considered high risk»), работа продолжилась только вручную. Защита в четыре слоя:

- **Ingestion-cap** (`src/agent/loop.ts`): `truncateToolOutput` (8 КБ, маркер обрезки) применяется после вызова **любого** handler'а — встроенных и внешних MCP (через `toolsAsSpecs`). Раньше кап был только внутри handler'ов встроенных инструментов — MCP-выводы писались в историю целиком. В jsonl сессии пишется уже обрезанный вывод.
- **Wire-cap** (`toWireMessages`, `src/agent/llm.ts`): tool-сообщения усекаются при отправке в LLM — защита при `--resume` старых jsonl-сессий, где гигантские выводы уже лежат на диске.
- **Автоповтор LLM-клиента**: тело не-ok ответа читается и включается в `apiError`; маркер `high risk` (и аналогичные отказы модерации, `isHighRiskBody`) → повтор с `shrinkMessages` (tool-выводы до 4096, затем 1024 символов; сообщения не выбрасываются — сохраняется парность tool_calls↔tool), максимум 2 повтора, затем throw с текстом провайдера. Обычные 400 без маркера — без shrink-повторов.
- **Guard финализации в loop** (VL-199, `src/agent/loop.ts`): отказ провайдера может прийти валидным финальным текстом **без tool_calls при HTTP 200** (инцидент VL-197) — раньше такой ответ трактовался как успех (is_error=false, exit 0) и авто-resume ниже не срабатывал. Перед финализацией текст сверяется с `isHighRiskBody` → `fail()` с русским пояснением и обрезанным оригиналом: `is_error=true`, exit 1, маркер в result. Диагностика причины content-based отказов: `streamChat` в `src/agent/llm.ts` пишет в stderr (попадает в `logTail` оркестратора) размер wire-payload в байтах, число сообщений и usage — на HTTP-200-пути и на не-ok/исключении (включая shrink-уровни).
- **Фолбэк оркестратора** (`finish()` в `src/web/orchestrator.ts`): если результат фазы `is_error` с маркером high risk и есть `session_id` — один автоматический перезапуск той же фазы с `--resume` (счётчик 1 на runKey, цикл исключён). Благодаря guard'у VL-199 срабатывает и для HTTP-200-отказов.
- **Диагностика payload и usage фазы (VL-203):** wire-body LLM-запроса сериализуется в одной точке до `fetch` (`requestWithRetry`, `src/agent/llm.ts`) — байты считаются от фактического тела запроса (включая `stream`/`stream_options`), closure-переменные `lastRequestBytes`/`lastUsage` хранятся в клиенте. (1) После завершения фазы в stderr печатается итоговая строка `[vibelog-agent] фаза: запросов=N, payload последнего запроса=X байт (макс Y), usage={...}` (после `tui.unmount()`) — она попадает в `logTail` оркестратора и отвечает на вопрос «сколько весил запрос фазы». (2) Лог HTTP-отказа провайдера содержит usage **предыдущего успешного запроса** (JSON + пометка; «н/д» — только если успеха ещё не было). (3) JSONL-транскрипт: assistant-сообщения несут поля `payload_bytes` и `shrink_level` (0=full, 1=4096, 2=1024) — уровень компакшна tool-выводов по ходам; usage по ходам пишется с VL-198. (4) Мета сессии `<id>.meta.json` и JSON-результат фазы — `last_payload_bytes`/`max_payload_bytes`. Новые поля в assistant-сообщениях провайдеру не уходят: `toWireMessages`/`messagesToInput` собирают сообщения явно (role/content/tool_calls) — покрыто wire-регрессией в `llm.test.mjs`.
- **Валидация tool_calls и санация wire-пар с пустым id (VL-215/216):** ответ модели с фантомными tool_call (пустые name/id, инцидент VL-214) не отравляет историю: невалидные вызовы фильтруются до записи пары assistant+tool (isValidToolCall), а уже накопленные в старых jsonl-сессиях отравленные пары вырезаются на wire-границе (sanitizeWireMessages) — resume не падает guard'ом VL-110. Подробнее — §6.4.
- **Guard пустого финала: диагностика и один повтор (VL-217):** при пустом финальном ответе в stderr печатается диагностика (payload >140КБ-гипотеза, сообщений, есть-пустые-tool_calls, usage — уходит в logTail), выполняется ≤1 повтор после wire-санации; повторная пустота → fail с маркером «Пустой ответ модели». Подробнее — §6.5.

Параллельно промпты запрещают дорогие браузерные выводы: `take_screenshot` не использовать, вместо него `evaluate_script` (нужный кусок DOM) или `take_snapshot` с `filePath` (снапшот на диск, в контекст — только подтверждение).

- **Байтовый автокомпакт истории (VL-230):** байтовый лимит провайдера — отдельный риск от токенового: сессии VL-221 (`last_payload=894265`) и VL-226 (`payload=644142`) упёрлись в `max_payload_bytes`, потому что история (включая усечённые на 8 КБ tool-выводы прошлых ходов) уходила в каждый запрос целиком. Перед каждым `streamChat` loop оценивает байты wire-копии (`JSON.stringify` — та же граница сериализации, что у клиента): при `>= PAYLOAD_WARN_BYTES` (70% от `MAX_PAYLOAD_BYTES = 900_000`, то есть 630 000) в stderr (→ `logTail` оркестратора) пишется `[vibelog-agent] предупреждение payload: N байт >= порог … — история компактизируется перед запросом`, а tool-выводы на wire усекаются до `PAYLOAD_COMPACT_TOOL_CHARS = 2048` символов с маркером (эскалация до `PAYLOAD_COMPACT_TOOL_CHARS_ESCALATED = 1024`, если после усечения байты всё ещё у жёсткого лимита). Усечение затрагивает только `role: tool`: `messages` и jsonl-транскрипт не мутируются, AC и Implementation Plan задачи (system/user/assistant) побайтово не меняются, парность `tool_calls ↔ tool` сохраняется. Пороги — экспортируемые константы `src/agent/llm.ts`, override для тестов — `LoopLimits.maxPayloadBytes`/`payloadWarnBytes` (порог пересчитывается от лимита). Это защита от отказа провайдера, а не токеновый компакшн VL-122: работает и при `--no-compact`, дополняя его — при больших tool-выводах байтовый триггер срабатывает раньше токенового.

## 6.3. Пакетное и параллельное чтение файлов (VL-202, уточнено VL-312)

Правило в промптах (канон — `templates/agent-prompt.md`; в шаблонах фаз `phase-plan`/`phase-code`/`phase-do`/`phase-investigate` — по одной ссылке с буллетом «Параллельные вызовы», VL-312): целевой файл анализируй **одним `read_file`** — при файле >200 строк читай последовательными чанками `offset`/`limit` подряд, а не через промежуточные grep-выборки границ; точечные правки вноси только после полного чтения файла; связанные проверочные команды (ls/grep/git/сборка/тесты) объединяй в один вызов через `&&`.

**Независимые вызовы — в один ход (VL-312).** Несколько чтений, поисков и команд по независимым файлам модель собирает в **одно** assistant-сообщение несколькими `tool_call`: протокол это допускает, а `runLoop` (`src/agent/loop.ts`) исполняет их циклом `for (const call of validCalls)` за один ход модели — последовательные ходы на каждый файл жгут контекст и бюджет рана. В веб-чате на один ответ модели действует лимит `CHAT_MAX_TOOL_CALLS_DEFAULT = 16` (`src/web/tool-dedup.ts`).

**Отдельный `read_many_files` не нужен и вреден (VL-312).** Батчинг уже есть на уровне протокола (см. выше), а свой инструмент с единым капом `TOOL_OUTPUT_MAX_CHARS = 8 * 1024` (`src/agent/tools.ts:70`) в одном ответе дал бы 8 КБ на ВСЕ файлы вместо 8 КБ на каждый. Поэтому правило живёт в промпте, а не в новом инструменте; дубли правила в шаблонах ловит тест-сторож `src/web/phase-prompt.test.mjs` (блок VL-312).

Согласование с лимитом «не читать файлы >200 строк целиком»: чанки `offset`/`limit` остаются обязательными — запрещён именно промежуточный grep-поиск границ между чанками (иначе ~12 чтений doc-6 вместо 3-4). Зачем: в сессии VL-193 README затронут в 20+ shell-вызовах — прямой вклад в исчерпание max_wall_time (VL-197, code-1 упала на 40-й минуте); тестовый прогон VL-202 дал 1 обращение к README вместо 20+.

## 6.4. Валидация фантомных tool_calls (VL-215)

Инцидент VL-214: модель mimo-v2.6-flash вернула `tool_call` с пустыми `name`/`id` (строка 36 jsonl) — loop не валидировал их и дописал в историю пару `assistant(tool_calls id="") + tool(tool_call_id="")`; следующий ход отклонён LLM API из-за отравленного ключа. Защита:

- **`isValidToolCall(tc)`** (`src/agent/llm.ts`, общий экспорт): name и id — непустые строки после `trim()` (с `typeof`-гардом). Фильтрация — **до** записи assistant-сообщения в диалог/jsonl: пара с пустым ключом не создаётся; зеркальная точка `src/web/chat.ts` импортирует ту же функцию (фикс VL-213, lesson-37 — копии не создаются).
- **Только фантомы** (`validCalls.length === 0`): assistant(tool_calls) не пишется, модели отдаётся текст-ошибка отдельным user-сообщением (не tool-результат — без пары с пустым `tool_call_id`), ход повторяется — модель может перезапустить вызов корректно. Счётчик фантомных ходов подряд `phantomStreak` ≥ 3 (`PHANTOM_CALL_LIMIT_DEFAULT`, по образцу loop detection VL-83) → `fail()`.
- **Фантом + валидный**: выполняются только валидные вызовы (`tool_calls: validCalls` в assistant-push, цикл — по `validCalls`), после выполнения — user-заметка «проигнорировано N tool_call(ов) с пустым name/id» (видно в jsonl).
- Фильтр не расширяется: name с пробелами по краям (« a ») валиден; путь «Неизвестный инструмент: <name>» работает только для валидных непустых имён — регрессий VL-95/VL-103 нет. Тесты: `loop.test.mjs`, блок «фантомные tool_calls VL-215» (Т1–Т3).
- **Wire-санация отравленных jsonl при resume (VL-216):** пары, уже лежащие на диске в старых сессиях (`assistant.tool_calls` с пустым `id`/`name` + парный `tool` с `tool_call_id=""`, инцидент VL-214), при записи не фильтруются (jsonl — append-only, контракт resume VL-103), но вырезаются на wire-границе функцией `sanitizeWireMessages` (`src/agent/llm.ts`), применяемой во всех точках ухода запроса: `toWireMessages` (chat), `messagesToInput` (responses) и payload-точка `runLoop` (`src/agent/loop.ts`, после компакшна — фантомная пара проходит орфан-гард, т.к. хвост начинается с assistant, а не tool). Валидные tool_calls сохраняются (id сравниваются через trim с объявленными), assistant только из фантомов переписывается в текстовую форму (при пустом/null content — вырезается целиком), `tool` с пустым или необъявленным `tool_call_id` вырезается; функция идемпотентна — двойное применение loop→wire безопасно и не ломает prefix-caching (детерминирована между запросами). `--resume` старых отравленных jsonl-сессий (включая `agent-1793269309877`) больше не падает guard'ом VL-110. Тесты: `llm.test.mjs` (describe «Санация отравленных пар (VL-216)»), `loop.test.mjs`, `cli.test.mjs` (AC2-resume `agent-vl216-poison`).

## 6.5. Guard пустого финала: диагностика и один повтор (VL-217)

Guard пустого финального ответа (VL-110, `src/agent/loop.ts`) раньше падал с первого раза без диагностики — в stderr/logTail не попадали ни payload, ни признаки отравленной истории, ни usage. Теперь:

- **Диагностика в точке пустоты:** при пустом финале до ветвления в stderr печатается `[vibelog-agent] пустой финал (попытка 1|2): payload=... байт (>140КБ=да/нет/н/д), сообщений=..., есть-пустые-tool_calls=да/нет, usage=...` (по образцу логов `streamChat` VL-199/VL-203 — строка уходит в `logTail` оркестратора; при активном TUI допустимо, прецедент VL-199). Гипотеза `>140КБ` — порог content-based отказа провайдера VL-197 (~140 КБ); `есть-пустые-tool_calls` — признак отравленных пар `assistant(tool_calls id:"") + tool(tool_call_id:"")` (VL-214/216); `payload` берётся из `response.payloadBytes ?? lastPayload` (иначе `н/д`).
- **≤1 повтор после санации wire-истории:** при первой пустоте запрос повторяется (`continue` цикла) — payload пересобирается на точке компакшна с `sanitizeWireMessages` (VL-216 — «санация после которой повтор»), в `messages` ничего не дописывается (пустой финал не пишет сообщений): транскрипт чист, `onMessage` не зовётся. Стейт — флаг `emptyFinalRetried` в пределах одной фазы, сброс не нужен (цикл финализируется сходу).
- **Повторная пустота → fail:** текст ошибки сохраняет маркер «Пустой ответ модели» (его матчат guard'ы VL-110) и добавляет: повтор после санации истории (VL-216/217) тоже пуст — вероятна отравленная история (пары с пустым id) либо отказ провайдера; payload/сообщений/есть-пустые-tool_calls/usage.
- При выставленном `--max-requests 1` лимит проверяется до запроса (loop.ts) — повтор упрётся в fail «Превышен лимит --max-requests» после диагностического лога (диагностика при этом уже в stderr).

Порядок guard'ов не менялся: пустой финал → high-risk (VL-199) → финализация. Тесты: `loop.test.mjs` (describe «Пустой финал: диагностика и один повтор (VL-217)» — две пустоты → is_error с одним повтором и логом payload/usage, успешный повтор, гипотеза VL-197, отравленная пара), `cli.test.mjs` (AC1: обе строки «пустой финал (попытка 1|2)» в stderr → logTail).

## 6.6. Бюджет времени, shell-повторы и прогресс до обрыва (VL-254)

Разбор авто-прогона 30.10 (VL-235): фаза Code сгорела на `max_wall_time` после 157 LLM-запросов и payload до 486 КБ — без коммита и без отчёта, ветка осталась с незакоммиченными M-файлами, транскрипт был единственным источником правды. wall-time проверялся только между итерациями и просто убивал фазу; агент не знал, что у него осталось 3 минуты, и стартовал `pnpm test` с `timeout_ms: 1500000`. shell-вызовы составили 72 из 110 tool-calls (65%), и guard повторов их не видел (для `run_shell_command` ключ возвращался `null`).

Четыре механизма, введённые в VL-254 (`src/agent/{repeat-tracker,loop,tools,run-progress,cli,session}.ts`):

**1. Мягкий wall-time guard (обратная связь агенту).** Жёсткая проверка `duration() > maxWallTimeMs` осталась, но дополнительно на 70% и 90% бюджета (`LoopLimits.wallTimeWarnRatios`, дефолт `[0.7, 0.9]`) в историю инжектируется **одно** `role: 'user'`-сообщение `wallTimeWarnText(remainingMs, totalMs, payloadBytes, warnBytes)`: «Осталось N с из M (X%). Payload последнего запроса: B байт, порог компакта: W байт. Не запускай команды дольше остатка: сократи проверку до затронутых тестов; при нехватке времени — заверши фазу честным отчётом…». Дедуп по `Set`, инъекция на границе хода (после всех tool-результатов — парность `assistant(tool_calls)`↔`tool` не ломается, lesson-91). Для детерминированных тестов времени в `RunLoopOptions` есть хук `now?: () => number` (дефолт `Date.now`).

**2. Усечение `timeout_ms` до остатка бюджета.** `ToolHandlerContext.remainingWallTimeMs?: () => number` — loop прокидывает остаток в каждый handler. `clampShellTimeout(requestedMs, remainingMs)` (чистая, `src/agent/tools.ts`): если `requestedMs > remainingMs`, таймаут усекается до остатка (минимум 1000 мс), а **первой строкой** tool-вывода уходит предупреждение «timeout N мс превышает остаток бюджета фазы M мс — таймаут усечён…; команда может быть убита, сократи проверку». Маркер «превышает остаток бюджета фазы» стабилен — его матчат тесты (lesson-76).

**3. shell-скелет в guard повторов и в `repeat_stats`.** Новый `RepeatKind: 'shell'`, порог `REPEAT_SHELL_LIMIT_DEFAULT = 3`. Ключ `shellCommandKey(command)` (чистая, FNV-1a без Node-API): первый сегмент цепочки `&&`/`||`/`;`/`|`; `node -e`/`--eval`/`-p`/`--input-type=module -e` → `node-e|<hash первых 200 символов скрипта>`; иначе — первая команда + отсортированный набор значимых путей/паттернов, длина ≤ 80. На 3-м одинаковом скелете — предупреждение «команда уже выполнялась N раз — используй ранее полученный результат; для обзора — `project_map`/`read_file` каталога». В `RepeatStats` появились отдельные поля `shell_tool_calls`, `shell_repeat_calls`, `shell_share`, `shell_top` (в `tool_calls_total`/`top` shell теперь тоже входит — доля честнее, но видна раздельно); в итоговой stderr-строке фазы печатается `shell-повторов=X/Y`.

**4. Прогресс до обрыва (`src/agent/run-progress.ts`).** На путях wall-time и max-requests `LoopResult.progress` заполняется `buildRunProgress({messages, reason, durationMs, payloadBytes})`: список путей из `edit`/`write_file` (≤10) + последняя текстовая реплика модели (≤300 символов) как «Сделано» и фиксированный чек-лист «Осталось» (проверки не завершены, отчёта фазы нет, DoD не отмечен). `recordRunProgress()` в `src/agent/cli.ts` по `is_error && progress` пишет блок в мету сессии (`SessionMeta.run_progress`: reason/phase/finishedAt/text/done/pending/commit) и комментарий в задачу (`addComment` по `VIBELOG_CWD`), а для фазы code дополнительно делает WIP-коммит: `commitProgressChanges` — `git status --porcelain`, фильтр путей `backlog/`, `git add -u` + явные новые пути (`-A` не используется, `--no-verify`), `git commit -m "wip(<taskId>): прогресс фазы code до обрыва (<reason>)"`, short-hash в `progress.commit`; любая ошибка гасится в `console.error` и не меняет exit-код фазы.

Промпты: `templates/phases/phase-code.md` («Экономия ходов») — при остатке бюджета < 5 минут не запускать полный прогон, проверять только затронутые файлы и фиксировать прогресс комментарием; `templates/phases/phase-plan.md` и `templates/agent-prompt.md` — для обзора дерева/модулей `project_map` и `read_file` каталога вместо `node -e`-обходчиков `fs.readdirSync`, для выборки строк — `read_file` с диапазоном (`файл:N-M`) вместо `sed`/`node -e` (последние допустимы только внутри проверочной `&&`-цепочки).

Тесты: `repeat-tracker.test.mjs` (shell-скелет, три `node -e` → один ключ), `tools.test.mjs` (`clampShellTimeout`: 1500 с при остатке 5 с → усечение + warning), `loop.test.mjs` (предупреждения 70%/90% без sleep через `now`, `progress` по wall-time/max-requests, guard shell в loop, проброс остатка в ctx), `run-progress.test.mjs` (билдер + git в mkdtemp), `run-progress-cli.test.mjs` (мета + комментарий задачи + WIP-коммит, фаза plan не коммитит), `src/web/phase-prompt.test.mjs` (инвариант трёх правил в шаблонах).

## 6.7. Guard повторов: write-порог и эскалация до блокировки (VL-284)

Инцидент close-фазы VL-280: 5 попыток без прогресса, цикл `edit src/mcp/tools.ts` + `pnpm build`, payload 508 387 байт, 6.2M токенов. Guard повторов (VL-229) этот сценарий не поймал по двум причинам: категория `write` держала порог `0` («только в метрике», предупреждения нет вовсе), а сработавшее предупреждение всё равно **исполняло** вызов — модель на длинном ране совет игнорирует.

**1. Write-порог предупреждения.** `REPEAT_WRITE_LIMIT_DEFAULT = 6` — 6-я правка (`edit`/`write_file`) одного пути за ран даёт предупреждение в контекст. Итеративная правка легитимна, 6 обращений — уже подозрительно. `RepeatGuardOptions.writeLimit` (и `LoopLimits.repeatWriteLimit`), `0` — выключатель порога (поведение до VL-284, обратная совместимость).

**2. Эскалация до блокировки.** `REPEAT_WRITE_BLOCK_DEFAULT = 8` для write, `limit × repeatBlockMultiplier` (дефолт 2) для search/read/shell. Достигнув порога блокировки, loop **не исполняет** handler и кладёт модели tool-результат с директивой `repeatBlockDirective(key, count, kind)`: маркер `Повтор заблокирован: <ключ> — N обращений за ран` + следующий шаг по категории (write — «правь другой участок либо зафиксируй аварийный итог фазы», read — «возьми нужный диапазон одним `read_file`», shell — «используй ранее полученный вывод»). Порядок в точке учёта: `note()` (инкремент + предупреждение) → `shouldBlock()` (проверка по накопленному счётчику, без инкремента) → блокирующая ветвь **до** `if (!spec)`.

**3. Парность и кап.** Блокировка реализована как обычный tool-результат (`pushMessage({role:'tool', tool_call_id})`), а не как пропуск вызова — иначе провайдер отклоняет payload (`assistant(tool_calls)` без пары `tool`). Блокировок не больше `REPEAT_BLOCK_MAX_PER_RUN = 5` за ран, чтобы сами директивы не раздували контекст. `repeatGuardDisabled` по-прежнему выключает guard целиком (fail-open), `repeat_stats` считается всегда (блокированный вызов — тоже обращение). Число блокировок печатается в stderr-диагностике рана (`блокировок=N`, `LoopResult.repeat_blocked`) — по `logTail` оркестратора видно, спасла ли эскалация.

**4. Контракт фазы Close.** `templates/phases/phase-close.md` и `phase-close-worktree.md` получили правила «Close не правит код» (любые `edit`/`write_file` по `src/`, `web/src/`, `templates/` запрещены; упавшая сборка/тесты → `aborted: true`, исправление — новой фазой Code) и «Сборка проекта — не более одного раза за фазу» (повторная сборка без правок кода бессмысленна). Маркеры матчит инвариант-тест `src/web/phase-prompt.test.mjs`.
