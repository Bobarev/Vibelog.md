# Агент Vibelog (vibelog-agent)

Собственный LLM-агент Vibelog — headless-замена Qwen Code в фазах оркестратора (spec / plan / code / close / comment / prompt) и интерактивный TUI-исполнитель для терминала.

Документ описывает **фактическое поведение кода** (`src/agent/*`, `bin/vibelog-agent.mjs`) на 2026-10-05 (VL-83..86, эпик VL-75).

## 1. Назначение и мотивация

Оригинальный оркестратор запускал headless-сессии **Qwen Code** (`@qwen-code/qwen-code` 0.24.7 — база агента, см. VL-77/doc-3 §12). Это работало, но расход токенов на типовых фазах был большим:

- Фаза Comment (обычный комментарий к задаче) — до **96k** токенов;
- Фаза Spec (разбор фичи на задачи) — до **935k** токенов.

Причины: полный CLI qwen со своей системной инструкцией, плагинами и MCP-обвязкой на каждую фазу. Агент Vibelog решает это минимальным tool-calling loop без «вагона» промпта.

**Зачем свой агент, а не просто `--model`:**

- Полный контроль над лимитами (tool-calls, wall-time) и loop detection — см. §6.
- Headless-контракт stdout совместим с `parseQwenResult` (`src/web/qwen-result.ts`) — оркестратор и бот не менялись (decision-5).
- LLM — любой OpenAI-совместимый endpoint (Cloud.ru по умолчанию) через свои env.
- Работает на macOS 10.15 Catalina: без нативных модулей (TUI — Ink 7.0.3, yoga-layout WASM).

**Решения по агенту** (backlog/decisions/, статус proposed на 2026-10-05):

| Решение | Суть |
|---|---|
| decision-1 | MCP-клиент минимальный самописный (без typescript-sdk) |
| decision-2 | TUI на Ink (кандидат — официальный 7.0.3, реализован в VL-86) |
| decision-3 | LLM-клиент Cloud.ru через fetch (undici-штатный Node 20), без openai-SDK |
| decision-4 | Loop detection + двойной предел (tool-calls / wall-time), дедупликация вызовов |
| decision-5 | Headless: stdout — JSON `type=result`, формат parseQwenResult; qwen-фолбэк сохранён |

## 2. Установка и настройка

### Требования

- **Node.js 20+** (нужен глобальный `fetch` для LLM-клиента).
- Собранный `dist/`: бинарь `bin/vibelog-agent.mjs` импортирует `dist/agent/cli.js`.

```bash
pnpm install
pnpm build
```

### LLM (Cloud.ru)

Агенту нужен доступ к LLM. Три переменные окружения:

| Переменная | Обязательна | Назначение |
|---|---|---|
| `VIBELOG_LLM_API_KEY` | да | API-ключ (без него агент отказывается стартовать) |
| `VIBELOG_LLM_MODEL` | да | Имя модели (без неё агент отказывается стартовать) |
| `VIBELOG_LLM_BASE_URL` | нет | Endpoint; дефолт — `https://foundation-models.api.cloud.ru/v1` (decision-3) |
| `VIBELOG_LLM_DEBUG_USAGE` | нет | `=1` — сырой `usage` каждого ответа LLM в stderr (диагностика кэш-токенов, VL-96) |

Пример в shell:

```bash
export VIBELOG_LLM_BASE_URL="https://foundation-models.api.cloud.ru/v1"
export VIBELOG_LLM_API_KEY="sk-..."
export VIBELOG_LLM_MODEL="your-model-name"
```

Пример `.env` (чат `vibelog`/`vb` без аргументов читает `.env` проекта сам — VL-102, поведение как у бота VL-37: реальное окружение приоритетнее файла; для `vibelog-agent` в фазах/orchestration переменные приходят из окружения):

```
VIBELOG_LLM_BASE_URL=https://foundation-models.api.cloud.ru/v1
VIBELOG_LLM_API_KEY=sk-...
VIBELOG_LLM_MODEL=your-model-name
```

## 3. Запуск

### Синтаксис

```bash
# Фаза: промпт собирается из шаблона templates/qwen-commands/phase-<N>.md
vibelog-agent <phase> <taskId> [--comment "<текст>"]

# Готовый промпт (qwen-совместимый сценарий: один позиционный аргумент)
vibelog-agent "<промпт целиком>"

# Справка
vibelog-agent --help

# Чат с агентом без задачи (VL-102): multi-turn TUI-чат в интерактивном
# терминале — запуск vibelog или алиас vb без аргументов (stdin+stdout TTY)
vibelog
vb
```

`<phase>` — spec | plan | code | close | comment | prompt. Шаблоны фаз лежат в `templates/qwen-commands/`; в них подставляются `{{taskId}}` и `{{comment}}` (пустая строка, если `--comment` не задан — в шаблонах есть инструкция об этом). Фаза `prompt` — шаблон промпта без требований к Vibelog MCP.

### Режимы

- **Интерактивный (TUI):** stdout — TTY, нет `--headless`/`--output-format json`, фаза ≠ `prompt`, нет `--no-tui`. TUI рендерится **на stderr** в альтернативном буфере терминала: лента чата (VL-113), посимвольный стриминг текста модели, карточки tool calls (имя, аргументы с обрезкой, статус ⏳/✅/❌, длительность), счётчики (ход, токены in/out/cache, время фазы), блок ошибок. Поведение stdout не меняется — контракт оркестратора сохраняется.
- **Headless:** `--headless`, либо `--output-format json` (qwen-совместимость), либо не-TTY stdout. В stdout — ровно одна JSON-строка (см. §4), прогресс/логи — в stderr.
- **Чат по умолчанию (VL-102):** запуск `vibelog`/`vb` без аргументов в интерактивном терминале — multi-turn TUI-чат с инструментами (локальные + MCP Vibelog): строка ввода внизу TUI (Enter — отправить, Ctrl+C/Ctrl+D — выход, на время хода ввод блокируется), ответ стримится, история чата растёт в памяти, транскрипт сессии сохраняется в `.vibelog/agent-sessions/` **после каждого хода**. Отказ MCP — предупреждение, чат продолжается без vibelog-инструментов; `VIBELOG_LLM_*` читаются из окружения или из `.env` проекта (загрузка как у бота, VL-37), нет ключей — понятная ошибка до рендера (exit 1). В не-TTY пустой запуск — справка; headless-контракт JSON не печатается.
- **Лента чата (VL-113):** диалог оформлен как типичный AI-чат (по образцу qwen code/opencode). Реплика пользователя при Enter остаётся в истории с префиксом `>` акцентным цветом — не стирается с экрана. Завершённый ответ ассистента переносится из стрима в ленту и отображается с сохранением переносов строк (многострочный ответ не склеивается в одну строку); стрим/карточки инструментов сбрасываются между ходами. Лента показывает последние 30 записей (обрезка сверху); текущий ход стримится под лентой. Оркестраторный TUI (`renderTui`) не меняется.

### Флаги

| Флаг | Дефолт | Назначение |
|---|---|---|
| `--headless` | без TTY | JSON-результат в stdout |
| `--comment <текст>` | `""` | Комментарий пользователя к фазе (`{{comment}}`) |
| `--no-mcp` | выкл. | Не подключать MCP-инструменты Vibelog |
| `--no-tui` | выкл. | Отключить TUI в интерактивном режиме (отладка) |
| `--max-tool-calls <N>` | 100 | Лимит tool-calls фазы |
| `--max-wall-time <сек>` | 900 | Лимит времени фазы (wall-time) |
| `--max-requests <N>` | без лимита | Лимит LLM-запросов фазы (ходов модели; ≠ tool-calls) |
| `--no-compact` | компакшн включён | Отключить усечение истории LLM-запроса (VL-122) |
| `--compact-tail <N>` | 50 | Сколько последних сообщений хвоста сохранять при компакшне (VL-122) |
| `--compact-at-tokens <N>` | 850000 | Порог usage-токенов, при котором включается компакшн (VL-122) |
| `--resume <sessionId>` | — | Продолжить сохранённую сессию (VL-95; префикс `vb:` игнорируется) |
| `--continue` | — | Продолжить последнюю сессию текущего каталога (VL-95) |
| `--help` | — | Справка |

**Qwen-совместимые флаги** (принимаются и игнорируются либо приравниваются): `--approval-mode <...>`, `--output-format json` (приравнен к `--headless` — оркестратор шлёт этот флаг всем фазам), `--allowed-mcp-server-names <...>`. Это позволяет подставить агент вместо qwen без правок шаблонов фаз.

## 3.1. Сессии (VL-95)

Каждый запуск агента сохраняет транскрипт диалога в `.vibelog/agent-sessions/<sessionId>.jsonl` (каталог проекта, покрыт `.gitignore` через `.vibelog/`) — JSONL, по строке на сообщение. `session_id` в JSON-результате — **реальный идентификатор файла сессии** (формат `agent-<мс epoch>` — его же матчит `extractSessionRef` бота; менять формат нельзя, иначе бот определит сессию как qwen-сессию).

**Флаги:**

- `--resume <sessionId>` — загрузка транскрипта и продолжение loop с полной историей (старые сообщения + новый промпт). Работает **только с готовым промптом** — в режиме `<фаза> <taskId>` отклоняется (промпт собирается из шаблона, история не подставлялась бы). Бот передаёт sessionId с префиксом `vb:` — агент снимает его сам.
- `--continue` — то же, но сессия берётся автоматически: последний `*.jsonl` каталога по mtime. Нет сессий — ошибка «Нет сохранённых сессий» (exit 1).
- `--resume` и `--continue` одновременно — ошибка валидации.

**Инкрементальная запись (VL-103):**

- jsonl дописывается по мере выполнения фазы: стартовый набор (system + история + новый промпт) записывается **до** запуска loop, каждое сообщение цикла (assistant с tool_calls, tool-результат, финальный/ошибочный assistant) — сразу после появления. При обрыве процесса (SIGKILL/таймаут оркестратора) транскрипт сохранён до последнего дописанного сообщения — «в сессии нет последнего результата» больше не воспроизводится.
- `--resume`/`--continue` дописывают в файл **только** новый user-промпт (системный промпт и история в файле не переписываются; в памяти system заменяется свежесобранным — файл мог измениться между запусками).
- Финальный `saveSession` остаётся нормализацией: полная перезапись файла идемпотентна и подчищает любые расхождения append'ов.
- Ошибка записи сессии — предупреждение в stderr, фаза не роняется.

**Обрыв LLM-запроса (VL-103):**

- Обрыв соединения во время чтения SSE-тела (`terminated`/`ECONNRESET` от undici) переживается: ретраи стриминг-попытки (та же `maxRetries`/пауза, что у HTTP-запроса), затем non-stream фолбэк; retryable-ошибка фолбэка продолжает общий цикл ретраев. Abort (`Ctrl+C`) не ретраится — фаза прерывается сразу.
- При исчерпании всех попыток — понятная русская ошибка `Сетевая ошибка LLM (обрыв соединения: …) после N попыток и non-stream фолбэка` с диагностикой (логи stderr, `.vibelog/agent-sessions/`), а не сырой `terminated`.
- На повторных попытках `onToken` подавляется — TUI не показывает задублированный частичный текст; авторитетен `result` финальной успешной попытки.
- Сессии qwen (UUID в `~/.qwen/projects/`) резюмируются штатным `--resume <UUID>` самого qwen — механизм агента к ним не относится.

## 3.2. Системный промпт и кэш-токены (VL-96)

**Системный промпт.** Каждый запрос к LLM начинается с system-сообщения: встроенная базовая часть (роль Vibelog-agent, русский язык, границы рабочего каталога, запрет необратимых действий) + содержимое `AGENTS.md` проекта из cwd, если файл есть. Лимит вставки — 8000 символов (обрезка с пометкой); ошибка чтения — предупреждение в stderr, фаза продолжается без AGENTS.md. При `--resume` сохранённый system заменяется свежесобранным (файл мог измениться). Лог: `[vibelog-agent] Системный промпт: N символов (AGENTS.md: да/нет)`.

**Кэш-токены.** Поле `usage.cache_read_input_tokens` в JSON-результате суммирует кэш по итерациям. Провайдеры отдают кэш под разными именами — `mapUsage` читает все известные варианты: прямые `cache_read_input_tokens` / `cache_read_tokens` / `prompt_cache_hit_tokens` и вложенное `prompt_tokens_details.cached_tokens` (OpenAI-стиль Cloud.ru). Tools сортируются по имени перед отправкой — стабильный префикс запроса повышает шанс prefix-caching.

**Отладка usage.** `VIBELOG_LLM_DEBUG_USAGE=1` — в stderr печатается сырой `usage` каждого ответа (JSON) — по нему видно, под каким именем приходят кэш-токены:

```bash
VIBELOG_LLM_DEBUG_USAGE=1 node bin/vibelog-agent.mjs "промпт" --no-mcp --headless
```

## 4. Интеграция с оркестратором

Оркестратор (`src/web/orchestrator.ts`) берёт бинарь из переменной `VIBELOG_QWEN_BIN` (дефолт — `qwen` в PATH). Значение по умолчанию не менялось — qwen-фолбэк сохранён (decision-5).

```bash
VIBELOG_QWEN_BIN=$(pwd)/bin/vibelog-agent.mjs vibelog browser
```

Никаких правок кода оркестратора не требуется: агенту приходит тот же вызов `<bin> <phase> <taskId> [--comment ...] --output-format json`, что уходил qwen.

### Интеграция с Telegram-ботом (/prompt:vb и команды фаз, VL-92/94)

Команда `/prompt:vb <запрос>` Telegram-бота (VL-92) запускает встроенный агент вместо qwen без правок шаблонов: `startPrompt` оркестратора получает агента и спавнит `bin/vibelog-agent.mjs` (или `VIBELOG_AGENT_BIN`) с теми же qwen-совместимыми флагами `<промпт> --approval-mode yolo --output-format json`. Guard от двойного запуска (ключ `prompt`) общий для обоих агентов — одновременно активен только один `/prompt`. Переменные `VIBELOG_LLM_*` наследуются из process.env: бот загружает `.env` через `loadDotEnv` (VL-37); при отсутствии ключа агент печатает JSON-результат `is_error: true` — уходит в чат штатным механизмом фаз.

Команды фаз бота (`/spec`, `/plan`, `/code`, `/close`, `/comment`, VL-94) принимают тот же суффикс `:<agent>`: `startPhase` оркестратора получает агента опциональным параметром и спавнит `bin/vibelog-agent.mjs` вместо qwen — шаблоны фаз и JSON-контракт результата не меняются, guard-ключ фазы общий для обоих агентов. Агент по умолчанию задаётся командой `/set agent <qwen|vb>` (хранится в `.vibelog/bot.yml`, ключ `default_agent`): без суффикса запускают его все команды фаз и кнопки действий карточки задачи. **Лимиты фаз для vb** (VL-104): `/set max-wall-time <сек>` и `/set max-requests <N>` сохраняются в том же `bot.yml` (ключи `max_wall_time`/`max_requests`); оркестратор при спавне `vibelog-agent` прокидывает их флагами `--max-wall-time`/`--max-requests` (только для агента vb — qwen эти флаги не поддерживает). Значение `0` — сброс настройки (дефолт агента). Без настроек флаги не передаются — поведение прежнее.

**Resume vb-сессии по reply (VL-95):** reply на информационное сообщение бота с `vb:<session_id>` возобновляет сессию агента — `startResume` оркестратора получает агента из `extractSessionRef` и спавнит `bin/vibelog-agent.mjs` с `--resume <sessionId>` (sessionId с префиксом `vb:` — strip делает CLI агента). Сессии хранятся JSONL в `.vibelog/agent-sessions/` (раздел 3.1); resume-запуск перезаписывает файл старыми + новыми сообщениями. Поведение qwen-resume не менялось (VL-93).

### Контракт stdout

Headless-агент печатает в stdout **ровно одну JSON-строку** формата `parseQwenResult` (`src/web/qwen-result.ts` — парсит последнюю валидную JSON-строку лога с `type=result`):

```json
{
  "type": "result",
  "result": "текст фазы (финальный ответ модели или partial + текст ошибки)",
  "is_error": false,
  "num_turns": 3,
  "duration_ms": 42100,
  "duration_api_ms": 42100,
  "session_id": "agent-1728000000000",
  "usage": {
    "input_tokens": 12000,
    "output_tokens": 3400,
    "cache_read_input_tokens": 8000,
    "total_tokens": 15400
  }
}
```

- `is_error: true` → exit code 1; иначе 0.
- Логи, предупреждения (например, MCP недоступен) — в stderr.
- `duration_api_ms` приравнен к `duration_ms` (агент не меряет API-время отдельно).
- Ошибки лимитов/loop detection не роняют процесс исключением: текст ошибки и partial-результат фазы идут в поле `result`, `is_error: true`.

## 5. Инструменты

### Локальные (6)

| Инструмент | Что делает |
|---|---|
| `read_file` | Читает файл проекта (offset/limit — строки) |
| `write_file` | Создаёт/перезаписывает файл (создаёт родительские директории) |
| `edit` | Точечная замена текста в файле (replace_all опционален) |
| `run_shell_command` | Запуск shell-команды |
| `grep_search` | Поиск по содержимому файлов |
| `glob` | Поиск файлов по шаблону |

### Vibelog MCP

Подключается автоматически (кроме фазы `prompt` и флага `--no-mcp`): **22 инструмента** — `backlog_*` (create/list/view/update status/update task/manage ac/manage dod/add comment/update dependencies/search/ready/finish phase), `milestone_*` (list/add/rename/remove/archive), `document_*` (list/view/create/update/search). Схемы — в `docs/mcp-reference.md`.

**Отказ MCP не фатален:** если MCP-сервер недоступен, в stderr печатается предупреждение, и фаза продолжается без MCP-инструментов (локальные работают).

### Ограничения

- **Пути:** все файловые инструменты резолвят путь от cwd проекта и отказываются от выхода за его пределы (`Путь выходит за пределы проекта: ...`). Путь не может быть самим корнем-директорией (кроме `cwd` у shell).
- **Shell:** без `shell:true` на уровне Node; `cwd` команды — только внутри проекта. Строка команды тоже валидируется (VL-99, `checkShellCommandInProject`): токены `~`/`~/…`, `$HOME`/`${HOME}`, абсолютные пути и `..`-переходы наружу отклоняются до запуска bash — модель получает текст «Команда отклонена: обращение к путям вне проекта (<путь>). Разрешены только пути внутри <cwd>». Лексическая проверка не закрывает динамическое построение путей (командные подстановки, base64) — остаточный риск минимизируется правилом системного промпта. Спецфайлы POSIX (`/dev/null`, `/dev/stdout`, `/dev/stderr`, `/dev/stdin`) и regex/глоб-паттерны grep/sed (токены с метасимволами `|`, `*`, `^$` и т.п.) пропускаются — они не пути к данным пользователя (VL-104: ложные отказы по `2>/dev/null` губили tool-call целиком).

## 6. Loop detection и лимиты

Двойной предел (decision-4), проверяется на каждой итерации tool-calling loop:

| Предел | Дефолт | Флаг | Поведение при срабатывании |
|---|---|---|---|
| Одинаковые вызовы подряд | 3 | — (константа) | `Loop detection: инструмент <имя> вызван 3 раза подряд с одинаковыми аргументами — фаза прервана...` |
| Всего tool-calls | 100 | `--max-tool-calls <N>` | `Превышен лимит --max-tool-calls (N) — фаза прервана.` |
| Wall-time фазы | 900 сек | `--max-wall-time <сек>` | `Превышен лимит --max-wall-time (N секунд) — фаза прервана.` |
| LLM-запросов фазы | без лимита | `--max-requests <N>` | `Превышен лимит --max-requests (N) — фаза прервана.` |

- Сигнатура для loop detection — имя инструмента + JSON его аргументов; счётчик обнуляется при смене сигнатуры.
- Лимит tool-calls проверяется **до** выполнения вызова — лишний вызов не выполняется.
- `--max-requests` — лимит **LLM-запросов** (ходов модели, numTurns), а не tool-calls: проверяется до отправки запроса в LLM. Дефолта нет — без флага предела нет. Для агента задаётся командой бота `/set max-requests <N>` (VL-104, см. docs/user-guide.md).
- При срабатывании любого предела: partial-накопленный текст модели + текст ошибки уходят в JSON-результат (`is_error: true`), TUI показывает блок ошибки. Исключений наружу loop не бросает.
- Ошибки выполнения отдельного инструмента фатальны только для вызова: текст ошибки уходит модели как tool-результат, фаза продолжается.

## 6.1. Компакшн истории LLM-запроса (VL-122)

В длинных сессиях `messages` раздувается (десятки ходов с правками и тестами) — запросы замедляются до 5–15 минут и деградируют. Решение — **детерминический wire-компакшн** внутри `runLoop` перед `streamChat` (по doc-13 §4.1):

- **Усекается только payload запроса** — `messages` в памяти и jsonl-транскрипт сессии остаются ПОЛНЫМИ: `onMessage`, resume-контракт (VL-103), loop-guard VL-119 и guard пустого финала VL-110 работают с полной историей.
- **Триггер** — по usage-токенам последнего ответа (`input_tokens + cache_read_input_tokens`) ≥ `--compact-at-tokens` (дефолт 850 000, 85% окна MiMo-V2.5 1M). Редкое срабатывание почти не бьёт по prefix-caching.
- **Липкий якорь**: после срабатывания запросы = system + первый user + последние `--compact-tail` сообщений (дефолт 50) — append-only префикс, кэш стабилен; повторное раздувание сдвигает якорь вперёд.
- **Служебная заметка** дописывается в wire-копию первого user-сообщения один раз в момент компакшна: «[История усечена: опущено K сообщений. Полный транскрипт — в сессии.]».
- **Орфан-гард**: хвост не начинается с `role: tool` без парного assistant(tool_calls) — якорь сдвигается вперёд past tool-сообщений; если отсекать нечего — исходный payload без маркера.
- **Выключение/настройка**: `--no-compact` (дефолт — компакшн включён); бот — `/set compact on|off` → `bot.yml` → оркестратор передаёт `--no-compact` при следующем запуске фазы (только агент vb), перезапуск бота не нужен.
