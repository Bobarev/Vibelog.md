# GitVerse Issues: канал баг-репортов между проектами (VL-363)

Документ описывает транспорт баг-репортов из дочерних проектов Vibelog (`Vibelog-md/ui`, `Vibelog-md/templates`) в родительский. Основной транспорт — **git-инбокс** (общий репозиторий отчётов, раздел 9, VL-375); транспорт через Публичный API GitVerse (VL-363) сохранён и включается конфигом, но упирается в закрытый доступ к API «Задачи 2.0» (doc-29).

---

## 1. Зачем

Дочерние проекты — самостоятельные проекты Vibelog со своими `backlog/` и своими агентами. Инструменты агента ограничены корнем проекта:

- `resolveInProject` не пускает за пределы проекта;
- `ensureTaskWorktree` создаёт worktree только внутри проекта;
- `git_commit` отклоняет `cwd` вне проекта.

Поэтому агент `ui` физически не может завести задачу в `backlog/` родителя. Прежний обход — «сформулируй баг промптом, человек скопирует и передаст» — ручной шаг, который и устраняет этот канал.

GitVerse Issues выбран как транспорт, потому что он:

- работает между людьми, машинами и проектами (не требует общей файловой системы);
- даёт **номер issue как естественный ack** — дочерний агент сразу знает, что репорт принят;
- даёт **дедуп по номеру** — повторный репорт виден;
- симметричен: у `ui` могут быть свои баги, он читает их тем же механизмом.

## 2. Настройка

### 2.1. Токен

Токен кладётся в `.env` в корне проекта (файл в `.gitignore`, секреты только там — правило VL-329):

```
GITVERSE_TOKEN=<токен>
```

Создать: https://gitverse.ru/settings/tokens (показывается один раз). Права: **Запись** на репозиторий — для создания issues и меток; для чтения достаточно **Чтения**.

Приоритет чтения: shell env → `.env`. Имя переменной зафиксировано константой `GITVERSE_TOKEN_ENV` и переопределяется полем `token_env` в секции `upstream` (для нестандартных случаев — например, отдельный токен на другой репозиторий).

Токен **никогда** не попадает в текст ошибки или ack — маскируется функцией `maskToken`.

### 2.2. Секция `upstream` в `.vibelog/settings.json`

```json
{
  "upstream": {
    "repo": "bobarev/Vibelog.md",
    "labels": ["upstream", "from-ui"],
    "type": "bug",
    "project_id": 42,
    "done_column": "Done"
  }
}
```

| Поле | Обязательно | Описание |
|---|---|---|
| `repo` | ✓ | Репозиторий-получатель в формате `owner/name` |
| `labels` | | Метки issue. По умолчанию `upstream` + `from-<prefix>`, где prefix — `task_prefix` из `backlog/config.yml` |
| `type` | | `task` \| `bug` \| `story` \| `epic`. По умолчанию `bug` |
| `token_env` | | Имя переменной с токеном. По умолчанию `GITVERSE_TOKEN` |
| `project_id` | | id проекта GitVerse (Kanban). Нужен для закрытия — следующая задача |
| `done_column` | | Имя колонки «Done». Нужен для закрытия — следующая задача |

Запись секции — read-modify-write через `saveSettingsPatch`: чужие секции (`chats`, `models`, `providers`, `components`) сохраняются байт-в-байт.

### 2.3. Куда репортить

Два варианта, выбор — при настройке:

- **В свой репозиторий** (`Vibelog-md/ui` → issues в `Vibelog-md/ui`): токен нужен только на запись в свой репозиторий, родитель читает оттуда. Безопаснее.
- **Напрямую в родительский** (`repo: bobarev/Vibelog.md`): проще, но токен с правом записи в чужой репозиторий лежит в каждом дочернем проекте.

Код поддерживает оба — разница только в значении `repo`.

## 3. MCP-инструмент `upstream_report_bug`

Write-инструмент (`TOOL_KINDS` → `write`), требует Allow/Deny в веб-чате.

| Параметр | Тип | Required | Описание |
|---|---|---|---|
| `title` | string | ✓ | Заголовок issue, непустой |
| `body` | string | | Что произошло: описание, шаги, ожидаемое поведение |
| `severity` | string | | `low` \| `medium` \| `high` \| `critical` — попадает в «Окружение» |
| `area` | string | | `cli` \| `mcp` \| `web` \| `agent` \| `install` \| … — попадает в «Окружение» |
| `source_task` | string | | ID задачи проекта-источника (например `UI-12`) — секция «Источник» |
| `labels` | string[] | | Дополнительные метки поверх `upstream.labels` |

Ответ — JSON-ack по контракту VL-306:

```json
{ "ok": true, "applied": { "number": 42, "url": "https://gitverse.ru/…/issues/42", "labels": ["upstream","from-ui"] },
  "message": "Issue #42 создан: …" }
```

Ошибка:

```json
{ "ok": false, "error": "секция upstream не настроена — добавь в .vibelog/settings.json секцию upstream: …",
  "hint": "…" }
```

### Тело issue собирается детерминированно

Не отдаётся на волю модели — иначе формат поедет от вызова к вызову, и импорт на принимающей стороне не сможет разобрать секции. Функция `buildIssueBody` формирует фиксированные разделы:

```markdown
## Что произошло
<текст body или title>

## Воспроизведение
1. Открыть проект и выполнить действие, описанное выше.
2. Наблюдать поведение из раздела «Что произошло».

## Окружение
- severity: high
- area: mcp
- vibelog: 1.14.0

## Источник
- проект: Vibelog UI
- задача: UI-12
- отчёт создан автоматически (vibelog upstream report)
```

## 4. CLI `vibelog upstream report`

Тот же путь, что MCP-инструмент (общая функция `reportBug`) — формат тела и ack не расходятся. Нужен, когда в дочернем проекте глобальный пакет `vibelog` старой версии и MCP-инструмента ещё нет.

```
vibelog upstream report --title <t> [--body <b>|--body-file <f>] [--severity s] [--area a] [--source-task ID] [--label l] [--json]
```

| Флаг | Назначение |
|---|---|
| `--title <t>` | Заголовок issue (обязателен) |
| `--body <b>` | Что произошло |
| `--body-file <f>` | То же из файла (`--body` приоритетнее) |
| `--severity <s>` | `low` \| `medium` \| `high` \| `critical` |
| `--area <a>` | `cli` \| `mcp` \| `web` \| `agent` \| `install` \| … |
| `--source-task <ID>` | ID задачи проекта-источника |
| `--label <l>` | Дополнительная метка (можно повторять) |
| `--json` | ack как есть (контракт VL-306) |

Коды выхода: `0` — успех, `1` — использование, `2` — конфиг не настроен, `3` — сеть/данные, `4` — нет токена.

## 5. Публичный API GitVerse — что нужно знать

Полные конспекты — в reference: **ref-26** (общая информация), **ref-27** (issues и метки), **ref-28** (проекты и колонки).

### 5.1. База и заголовки

- Base URL: **`https://api.gitverse.ru`** — не `gitverse.ru`.
- `Authorization: Bearer <token>`
- `Accept: application/vnd.gitverse.object+json;version=1`
- `Content-Type: application/json` — для POST/PATCH.

### 5.2. Создание задачи

`POST /repos/{owner}/{repo}/issues`

```json
{ "title": "…", "body": "…", "type": "bug", "labels": ["upstream"] }
```

`title` обязателен. `type` ∈ `task|bug|story|epic`. **`labels` — массив строк, метки должны уже существовать в репозитории.**

### 5.3. Метки

`POST /repos/{owner}/{repo}/labels` — `{name, color, description, exclusive}`, `name` ≤ 20 символов, ответ `201`.
`GET /repos/{owner}/{repo}/labels` — список. Пагинация: `page`, **`limit`** (по умолчанию 30) и `sort`; параметра `per_page` у этого эндпоинта НЕТ — GitVerse отвечает `400 VALIDATION_ERROR` на неизвестный query-параметр (VL-367). У `GET /issues` — наоборот, `per_page`; имена параметров у эндпоинтов разные.

Перед созданием issue `ensureLabels` проверяет список и создаёт отсутствующие — идемпотентно, дублей не появляется.

### 5.4. Ошибки

Две формы, обе поддерживаются парсером:

```json
{ "error": { "code": "BAD_REQUEST", "message": "…", "documentation_url": "…", "status": 400 } }
```

```json
{ "message": "Not Found", "documentation_url": "…" }
```

Вторая встречается в разделе проектов. Ответы с ошибками не содержат диагностики — только машиночитаемый код и краткое сообщение.

### 5.5. Пагинация

Параметры `page` и `per_page` (максимум 100), навигация — заголовок `Link` с `rel="next"|"prev"|"first"|"last"`. Ходить по URL из `Link`, а не собирать параметры вручную.

## 8. Что дальше (следующая задача)

- **Импорт:** `GET /repos/{o}/{r}/issues?labels=upstream&state=open&per_page=100` → дедуп по номеру в локальном журнале → создание задачи Vibelog.
- **Ack:** `POST /repos/{o}/{r}/issues/{n}/comments` с номером созданной задачи — дочерний агент видит «принято как VL-N».
- **Закрытие:** `PATCH /repos/{o}/{r}/issues/{n}` с `{project_id, project_status_id}` колонки «Done». Поле `state` для задачи **игнорируется** — состояние определяется колонкой проекта (ref-28).

## 9. Git-транспорт: общий репозиторий-инбокс (VL-375)

### 9.1. Почему не Issues

`GET /issues` и `POST /issues` отдают `403` при том, что `GET /repos/…` и `GET /labels` с тем же токеном дают `200` (у токена `permissions.push: true`, `role_name: admin`). Без токена тот же путь отвечает `401 UNAUTHORIZED` — аутентификация проходит, гейт стоит на фиче: это API уровня «Задачи 2.0» (`pull-and-issues_2`), доступ к которому аккаунту не выдан. Код VL-363 остаётся и включится при появлении доступа; разбор — doc-29.

Отвергнутые альтернативы: «у себя + reference-клон» (не масштабируется на 20 проектов: 19 клонов, `reference sync` по всем, нет единой точки сборки) и любой issue-трекер (упирается в тот же закрытый доступ).

### 9.2. Схема данных

Общий репозиторий-инбокс — разделяемое состояние для mesh-топологии «многие ко многим» (до 20 проектов). Каталог верхнего уровня — префикс проекта-источника:

```
reports/
  ui/2026-11-08-UI-12-git_commit-kirillica.md
  tpl/2026-11-08-TPL-3-shablon-ne-sobiraetsya.md
```

Фронтматтер отчёта (порядок полей — `REPORT_FIELDS` в `src/core/upstream-git.ts`, источник истины формата):

```yaml
---
report_id: <sha1(source_project + source_task + title)>   # дедуп
source_project: Vibelog UI
source_prefix: UI
source_task: UI-12
title: git_commit и кириллица в путях
target: vl                  # КОМУ адресован — маршрутизация «многие ко многим»
severity: high
area: mcp
created: 2026-11-08
status: open                # open → accepted → done
accepted_as: ""             # заполняет получатель: VL-367
---
<тело отчёта в markdown>
```

Поле `target` — ключевое: отчёт адресуется конкретному получателю, а не «в родителя». `ui` может писать `tpl`, `tpl` — в `ui`, оба — в `vl`. Сравнение терпимо к регистру и к вариантам записи префикса (`targetMatches`).

Имя файла — `reports/<prefix>/<YYYY-MM-DD>-<source_task>-<slug>.md`, где `slug` — **строго латиница `[a-z0-9-]`**: кириллица транслитерируется, не-ASCII и пустой результат заменяются на `report` (не-ASCII имена ломали сравнение путей в git-инструментах, VL-360).

`report_id` = sha1 от `source_project + source_task + title`: повторный `writeReport` с теми же данными не создаёт второй файл, а возвращает `{ created: false, path }`.

### 9.3. Модель доступа — три независимых слоя

В git нет прав на подкаталог, права даются на репозиторий целиком. Поэтому контроль строится тремя слоями:

1. **Права репозитория:** Write — только своим проектам и их агентам; внешние — без Write, только fork + PR.
2. **Branch protection на `main`:** прямой push запрещён всем, кроме бота-мейнтейнера; изменения — через PR.
3. **CI-валидация путей:** workflow проверяет, что изменённые файлы принадлежат префиксу автора (`reports/<prefix>/**`), а в чужих файлах разрешено менять только `status`/`accepted_as` (ack). Не прошло — красный статус, merge блокируется.

Третий слой — главный: он ловит типовые аварии агентов (`git add -A` с мусором, force-push, коммит чужих файлов), от которых внутри своего проекта защищает `git_commit` с явными путями. Workflow живёт в репозитории инбокса (вне этого репозитория).

**Порядок проверок внутри третьего слоя важен** (VL-387): сначала классифицируется **что именно изменено**, и только потом — **чей это каталог**. Ack (`M*` с изменёнными ровно `status` и `accepted_as`) — операция, разрешённая **всем** акторам, включая авторов без маппинга в `prefixes.yml`: она не требует владения каталогом, потому что смысл протокола — «получил отчёт → подтвердил получение». Не-ack `M*` (правка тела) и `A*` (создание) проваливаются дальше в проверку владения: свой каталог — законная правка, чужой — отказ. Обратный порядок (владение раньше класса изменения с безусловным `continue` в ветке владения) отклонял легальный ack не-мейнтейнера — дефект жил незамеченным, пока все акторы были мейнтейнерами (VL-387, lesson-268).

### 9.4. Архитектурное ограничение: пушит CLI, не агент

Агент не может пушить в инбокс сам: `resolveInProject`, `ensureTaskWorktree`, `git_commit` ограничены корнем своего проекта. Поэтому:

- клон инбокса живёт **внутри проекта-источника** — `.vibelog/upstream-inbox/` (в `.gitignore`, вложенный git-репозиторий);
- пишет и пушит **CLI** `vibelog upstream report` (запускается процессом пользователя/оркестратора — файловые границы агента на него не действуют);
- агент вызывает CLI через `run_shell_command` — одна команда, никаких обходов.

`git add` в инбоксе — **только явным путём файла отчёта** (`assertExplicitPath` отсекает флаги, маски и `..`). Никогда `-A`, `.`, маски — тот же инвариант, что у `git_commit` (VL-311/VL-360).

### 9.5. Конфиг: discriminated union по `mode`

```json
{
  "upstream": {
    "mode": "git",
    "inbox": "git@gitverse.ru:Vibelog-md/upstream-reports.git",
    "prefix": "vl"
  }
}
```

| Поле | Обязательно | Описание |
|---|---|---|
| `mode` | | `git` \| `api`. Отсутствует → `git` (основной транспорт) |
| `inbox` | ✓ для `git` | URL/путь репозитория-инбокса |
| `prefix` | | Префикс проекта-источника = каталог в `reports/`. По умолчанию — `task_prefix` из `backlog/config.yml` |
| `repo` | ✓ для `api` | Репозиторий-получатель `owner/name` |
| `labels`, `type`, `token_env` | | Только для `api` (см. 2.2) |

`resolveUpstreamConfig` валидирует комбинацию и возвращает union; невалидная комбинация → ошибка с указанием, какого поля не хватает. Оба транспорта живут рядом: `upstream_report_bug` не удалён, а ветвится по `mode` (`git` → `src/core/upstream-git.ts`, `api` → `src/core/gitverse-issues.ts`). `TOOL_KINDS` не меняется (`write`).

### 9.6. Условная видимость MCP-инструмента

`handleToolsList(id, cwd, send)` в `src/mcp/server.ts` фильтрует `upstream_report_bug` по `isUpstreamConfigured(cwd)`: без валидной секции `upstream` инструмент **не попадает** в `tools/list`. `listTools()` остаётся без параметров — реестр описывает возможности системы (нужен доктору, тестам паритета, валидации персон), поэтому тесты паритета и счётчик реестра не затрагиваются. Веб-чат (`chatToolDefs` в `src/web/tool-policy.ts`) фильтрует тем же предикатом.

`isUpstreamConfigured(cwd)` — fail-closed: `true` только при валидной секции (`git` + `inbox`, либо `api` + `repo`); ошибки чтения и невалидные данные → `false`. Прямой `tools/call` скрытого инструмента возвращает `ackError` с подсказкой про `.vibelog/settings.json`, а не «Неизвестный инструмент» — это закрывает устаревший кэш списка у клиента.

### 9.7. CLI

```
vibelog upstream report --title <t> --target <префикс> [--body <b>|--body-file <f>] [--severity s] [--area a] [--source-task ID] [--json]
vibelog upstream pull [--json] [--no-fetch]
vibelog upstream ack <report_id> --as VL-N [--json] [--no-fetch]
```

- `report` ветвится по `mode`; `--target` — получатель (для `git` — префикс получателя, обязателен: без него код `2` с подсказкой).
- `pull` — входящие отчёты для своего префикса (`target === prefix && status === 'open'`, сортировка по `created`); `--no-fetch` читает локальный клон без сети. В списке печатаются первые 8 символов `report_id`, а подсказка «Подтвердить: …» явно говорит, что годится префикс.
- `ack <report_id> --as <PREFIX>-<номер>` — находит файл по `report_id` и меняет **только** `status: accepted` и `accepted_as`, остальное тело байт-в-байт; коммит одним явным путём.
  - `<report_id>` — **полный sha1 либо уникальный префикс не короче 4 символов** (git-стиль, регистр hex не важен): `pull` печатает 8 символов, и ровно их можно скопировать в `ack`. Неоднозначный префикс — ошибка `config` (код `2`) со списком кандидатов (полные `report_id` + `source_task`), а не молчаливый выбор первого и не «не найден».
  - `--as` валидируется по формату `<PREFIX>-<число>`: `VL-388`, `vl-388` (нормализуется в `VL-388`), `UI-444` проходят; `VL_388`, `VL388`, `что угодно` и пустая строка — ошибка `usage` (код `1`) с примером корректного значения.
  - **Существование задачи получателя не проверяется** — осознанно: CLI работает в дочернем проекте и не имеет доступа к `backlog/` получателя. Это архитектурное ограничение, а не недоделка; проверяется только формат.
  - Идемпотентность `writeReport` префиксом не затрагивается: она сравнивает `report_id` точно (`{ exact: true }`), поэтому два разных отчёта с общим началом id не склеиваются.

Коды выхода без изменений: `0` успех, `1` использование, `2` конфиг, `3` сеть/git, `4` нет токена/доступа.

### 9.8. Устойчивость git-транспорта

| Механизм | Поведение |
|---|---|
| Клон | `ensureInboxClone`: клон при отсутствии, `pull --rebase` при наличии |
| Ошибки | `UpstreamGitError` с `kind`: `config` \| `usage` \| `network` \| `auth` \| `conflict` \| `git`; `code` совпадает по смыслу с `GitverseError.code` (`usage` → `1`) |
| Конфликты | Разные файлы — конфликтов нет; один файл правят двое (источник + ack) → `pull --rebase`, при конфликте понятная ошибка «разреши вручную в `.vibelog/upstream-inbox/`» |
| Идемпотентность | Повторный `writeReport` с тем же `report_id` → `{ created: false }` |
| Внешние репортеры | fork + PR — путь ручной: PR-API GitVerse в том же закрытом разделе. Осознанное ограничение |

### 9.9. Проверка

```bash
# локальный bare-репозиторий как инбокс
git init --bare /tmp/inbox.git
# в .vibelog/settings.json: {"upstream": {"mode": "git", "inbox": "/tmp/inbox.git", "prefix": "vl"}}

vibelog upstream report --title "тест" --target ui --source-task VL-999   # файл + коммит + push
vibelog upstream pull                                                     # отчёт виден
vibelog upstream ack <report_id> --as VL-999                              # поля обновлены
```

Плюс: без секции `upstream` в `tools/list` инструмента нет. Тесты: `src/core/upstream-git.test.mjs`, `src/mcp/upstream-tool.test.mjs`, `src/cli/upstream.test.mjs`, `src/core/gitverse-issues.test.mjs`.
