# Расследование VL-231

Предмет: фазы Close у VL-212 и VL-219 не завершали свои шаги (merge/тесты/документация/уборка), но задача получала статус **Done**. Цель — установить конкретный механизм и предложить исправление.

## Выводы

### 0. Короткая версия

Механизм **детерминированный и в двух местах независимый**:

1. **`finalizePhaseStatus` считает «успех» по exit code.** Промпт Close в аварийных ветках (конфликт merge, чужой незавершённый merge, красные тесты) велит агенту «отчитайся и завершай» — модель отвечает обычным текстом, ран завершается **exit 0** (`src/agent/cli.ts:782` — `process.exitCode = loopResult.is_error ? 1 : 0`). Тогда `finalizePhaseStatus` (`src/core/phase-transient.ts:191-235`) идёт в success-ветку и применяет `produces_status` перехода `Review --close--> Done` (`src/core/workflow.ts:91`). Фаза формально «успешна» → **Done ставится молча, без комментария** (success-ветка пишет только console.log).
2. **`backlog_finish_phase` не проверяет фазу и переход.** `toolFinishPhase` (`src/mcp/tools.ts:1156`) валидирует присланный статус только по `config.statuses` — любой вызывающий (включая **служебные** фазы `comment`/`prompt`/`analyze`/`resume`, которые по контракту статус не меняют) может выставить Done. Именно так VL-219 получила финальный Done: его поставил **Phasa Comment**, а не Close.

Третий, способствующий фактор: close-фазы в главном репозитории **не сериализованы** — параллельная close VL-219 оставила незавершённый merge (`MERGE_HEAD 532c590`, `UU CHANGELOG.md`), из-за чего close VL-212 не смогла начать merge и ушла в аварийную ветку, которая (см. п.1) закрывается как «успех».

### 1. VL-219: Done пришёл от прерванной close-фазы, а потом от фазы Comment

Ключевой факт: на 23:43 close-фаза отчиталась «Статус и DoD **не изменены**», а через 18 минут следующая фаза уже видела **Done**. Единственный актор между ними — `finalizePhaseStatus` завершившегося close-рана: статус был транзиентным `In Progress` (его ставит `markPhaseStarted`), ран завершился с exit 0 (аварийная ветка не выставляет `is_error`), значит success-ветка применила `Review → Done`.

То есть **Done был выставлен прерванной фазой**, а фактическая работа Close была сделана позже — уже в фазе Comment, по пользовательскому комментарию «Разреши конфликт и сделай коммит». Побочный эффект этого: уборка worktree выполнялась не из главного cwd, агент удалил каталог, в котором сам находился → `fatal: Unable to read current working directory` (строки 214–217), затем создал вложенный `.vibelog/worktrees/vl-219/.vibelog/worktrees/vl-219` и снёс каталог через `node -e rmSync` (строки 230–253); пустой `.vibelog/worktrees/vl-219` остался до сих пор.

### 2. VL-212: close #1 прервана чужим merge, аварийная ветка → Done

`agent-1793306598743.jsonl` (промпт `«Фаза Close: ветка задачи VL-212»`, `статус: Review`):

- строка 5: `git merge --no-ff vb/vl-212` → `error: Merging is not possible because you have unmerged files` (чужой незавершённый merge VL-219, `MERGE_HEAD 532c590`, `UU CHANGELOG.md`);
- строки 14–20: агент честно ждёт (30–60 с раунды), MERGE_HEAD не уходит;
- строка 26: `backlog_finish_phase` **без `status`** — отчёт «Фаза Close прервана: слияние vb/vl-212 → master невозможно…», сводка «Статус: не менялся»;
- строка 29: в ту же сессию приходит пользовательское сообщение «VL-219 закончила работу. Заверши фазу.» → агент **продолжает уже прерванную фазу**;
- строка 126: `backlog_finish_phase {"status":"Done","dodChecks":[1,2,3],"modifiedFiles":[…]}` → «Статус: Done; … отмечено DoD: 1».

Здесь аварийная ветка промпта сработала правильно (отчёт без status), но: (а) if бы ран завершился на строке 28, тот же `finalizePhaseStatus` выставил бы Done для незавершённой close; (б) фактическое закрытие произошло после ручного «продолжения» — **вне штатного жизненного цикла фазы**; (в) DoD «Тесты проходят» отмечен при красном полном прогоне (в отчёте прямо: `pnpm test` — 1539 passed, **24 failed** в `src/agent/llm.test.mjs`, обосновано как пре-существующее — но формально пункт DoD «Тесты проходят» не выполнен).

### 3. Затронутые компоненты

| Компонент | Роль в инциденте |
|---|---|
| `src/core/phase-transient.ts` (`finalizePhaseStatus`) | ставит `produces_status` по признаку «exit 0 и не is_error»; аварийная ветка промпта это признак не сбрасывает |
| `src/agent/cli.ts:782` | exit code = `is_error ? 1 : 0` → «прервано по инструкции» неотличимо от «успешно завершено» |
| `src/mcp/tools.ts` (`toolFinishPhase`) | принимает любой статус из конфига без проверки фазы/перехода; служебная фаза может поставить Done |
| `src/core/workflow.ts` | `SERVICE_PHASES` («статуса не меняют») и переход `Review → close → Done` — инварианты существуют только для `isPhaseAllowed`/transient, но не для MCP-записи |
| `templates/phases/phase-close-worktree.md` (шаг 4), `phase-close.md` (шаг 5) | аварийные ветки полностью полагаются на текст отчёта; явного сигнала «фаза провалена» нет |
| оркестратор/web (`src/web/orchestrator.ts:1120`, `startPhase`) | нет сериализации close-фаз в главном репозитории: два Close одновременно → чужой незавершённый merge блокирует следующий |

### 4. Повторяемость

Механизм **детерминированный** (не флак): любая close-фаза, ушедшая в аварийную ветку промпта (конфликт merge, чужой `MERGE_HEAD`, красные тесты после merge), заканчивается exit 0 и получает Done от `finalizePhaseStatus`. Подтверждение в этом же прогоне: close VL-230 стартовала в 22:02 (`phase-in-progress.json`: `{"VL-230":{"phase":"close","prevStatus":"Review"}}`) — она тоже кандидат на тот же исход.

Второй канал (MCP без guard'а) воспроизводится любым запросом пользователя в комментарии, который модель трактует как «доделай и закрой»: VL-219 — прямой пример (запрос был только «разреши конфликт и сделай коммит»).

### 5. Как воспроизвести (шаги)

1. Взять задачу в `Review` и запустить close-фазу в branch-mode.
2. Заранее оставить в главном репозитории чужой незавершённый merge (или получить конфликт в `CHANGELOG.md` при `git merge --no-ff vb/<id>`).
3. Агент по шагу 4 промпта отчитается «Фаза Close прервана…» через `backlog_finish_phase` **без** `status`.
4. Дождаться завершения рана → `phase-transient` success-ветка выставит `Done` (логи: `[phase-transient] VL-N: фаза close завершилась — статус Review → Done`), при этом ни merge, ни документация, ни уборка worktree не выполнены.

Проверка того же канала для MCP: из фазы `comment` вызвать `backlog_finish_phase {"id":"VL-N","status":"Done"}` — вызов проходит, статус меняется.

## Предложение задач

### №1
- **title**: Close-фаза: не применять produces_status, если фаза отчиталась о прерывании (exit 0 ≠ успех)
- **type**: bug
- **priority**: High
- **описание**: `finalizePhaseStatus` (`src/core/phase-transient.ts`) применяет `produces_status` при `exitCode === 0 && !is_error`. Аварийные ветки `templates/phases/phase-close*.md` заканчиваются обычным текстом агента → exit 0 → для перехода `Review → close → Done` ставится Done без фактического завершения (VL-219: Done зафиксирован в 00:01 при пустом merge/незаписанной документации). Ввести явный сигнал итога фазы: `backlog_finish_phase` принимает `aborted: true` (или `outcome: "aborted"`), tool пишет флаг в запись transient-кэша (через новый экспорт `markPhaseAborted` в `phase-transient.ts`); `finalizePhaseStatus` при наличии флага уходит в fail-ветку — откат к `prevStatus` + комментарий-причина. Дополнительно: fallback по `logTail`/финальному тексту («не завершена», «прервана») не использовать как единственный критерий — только как диагностику. Тест: exit 0 + `aborted` → статус откатан, Done не выставлен.
- **AC**:
  1. `backlog_finish_phase` с `aborted: true` в close-фазе не приводит к `Done`: статус возвращается к `prevStatus` и в задачу пишется комментарий-причина.
  2. Тест `src/core/phase-transient.test.mjs`: `finalizePhaseStatus` с `exitCode: 0` и флагом `aborted` откатывает статус (а без флага — прежнее поведение сохраняется).
  3. Флаг `aborted` отражён в `inputSchema` инструмента и в шаблонах `phase-close*.md` (аварийные ветки используют его вместо «отчёт без status»).

### №2
- **title**: backlog_finish_phase: отклонять смену статуса фазой, которой workflow не разрешает переход
- **type**: bug
- **priority**: High
- **описание**: `toolFinishPhase` (`src/mcp/tools.ts:1156`) валидирует статус только по `config.statuses` — поэтому фаза `comment` выставила Done у VL-219 (`agent-1793307529535.meta.json`: `"phase":"comment"`), а `SERVICE_PHASES` («статуса не меняют», `src/core/workflow.ts:100`) проверяются лишь в `isPhaseAllowed`/transient. Добавить на границе MCP проверку: фаза вызывающего (env `VIBELOG_PHASE_NAME` / мета сессии) должна быть той, что в workflow даёт переход `текущий статус + фаза → запрошенный статус` (`getStatusAfterPhase`); для служебных фаз смена статуса на workflow-статус запрещена, кроме явного «ручного» флага, доступного только CLI/веб-API. Невалидный переход — понятная ошибка в сводке (паттерн частичного применения, как у невалидного статуса), запись не выполняется.
- **AC**:
  1. Из фазы `comment` вызов `backlog_finish_phase {status: "Done"}` отклоняется с сообщением о запрещённом переходе, статус задачи не меняется.
  2. Из close-фазы при статусе `Review` вызов `{status: "Done"}` работает как раньше (регрессии нет).
  3. Тесты в `src/mcp/server.test.mjs`: запрет для служебной фазы, запрет перехода не из того статуса, разрешённый штатный переход.

### №3
- **title**: Сериализовать Close в главном репозитории: предпроверка MERGE_HEAD и очередь close-фаз
- **type**: enhancement
- **priority**: Medium
- **описание**: Close VL-212 не смогла начать merge, потому что в главном репозитории уже шёл незавершённый merge от VL-219 (`MERGE_HEAD 532c590`, `UU CHANGELOG.md`) — параллельные Close конкурируют за master. Сейчас спасает только текстовое правило «не резолвь и не abort чужой merge» (lesson-82). Добавить в `startPhase`/`spawnQwenRun` (`src/web/orchestrator.ts`) предпроверку для `phase === 'close'` при `branch_mode`: наличие `MERGE_HEAD` или активной close-фазы для другого ключа → фаза не стартует (или ставится в очередь с понятным сообщением), статус задачи не меняется.
- **AC**:
  1. При активном `MERGE_HEAD` в главном репозитории старт close-фазы отклоняется с понятным сообщением и без смены статуса задачи.
  2. Параллельный старт второй close-фазы в том же проекте блокируется (очередь/отказ) — тест `orchestrator`/`phase-transient`.

### №4
- **title**: Промпты фаз Close: аварийные ветки должны явно оформлять провал фазы, а не текстовый отчёт
- **type**: bug
- **priority**: Medium
- **описание**: `templates/phases/phase-close-worktree.md` (шаг 4: «отчёт (шаг 9) сделай сразу, БЕЗ status») и `templates/phases/phase-close.md` (шаг 5) полагаются на то, что отсутствие `status` = фаза провалена; но фреймворк определяет успех по exit code (см. №1). Переписать аварийные ветки: вызов `backlog_finish_phase {id, comment, aborted: true}` (после реализации №1), явное «не завершай цикл как успех», запрет продолжать прерванную фазу по пользовательскому сообщению без нового рана (кейс VL-212: «Заверши фазу.» внутри уже прерванной close).
- **AC**:
  1. Все аварийные ветки `phase-close*.md` используют единый явный сигнал провала (тот же механизм, что в №1), текст согласован между обоими шаблонами.
  2. `src/web/phase-prompt.test.mjs` фиксирует наличие сигнала в обоих шаблонах.

### №5
- **title**: Не ставить терминальный статус при невыполненном DoD: предупреждение/отказ в backlog_finish_phase
- **type**: bug
- **priority**: Medium
- **описание**: VL-212 закрыта с отмеченным DoD «Тесты проходят» при красном полном прогоне (1539 passed / 24 failed в `src/agent/llm.test.mjs`), VL-219 — аналогично по отчёту самой фазы. `toolFinishPhase` принимает `dodChecks` без проверки, а `status: Done` без требования пройденных DoD. Добавить в сводку `backlog_finish_phase` явное предупреждение «терминальный статус при непройденных DoD: #…», а для перехода в Done — требование явного `dodOverride` с причиной, которая попадает в комментарий-отчёт.
- **AC**:
  1. `finish_phase {status: "Done"}` с непройденными DoD без override возвращает ошибку/предупреждение и не меняет статус (или меняет только с записанной причиной override).
  2. Тест в `src/mcp/server.test.mjs` на оба исхода.

### №6
- **title**: Уборка worktree — только из главного cwd через git worktree remove, запрет удаления собственного cwd фазы
- **type**: chore
- **priority**: Low
- **описание**: В фазе Comment у VL-219 агент удалил каталог, в котором работал (`node -e rmSync`, `.vibelog/worktrees/vl-219`), получив `fatal: Unable to read current working directory`, и оставил пустой `.vibelog/worktrees/vl-219`. Добавить в правила фаз/guard shell-инструмента запрет деструктивных операций с собственным cwd, а пустой каталог worktree убрать (`git worktree prune`).
- **AC**:
  1. Удаление текущего рабочего каталога агентом отклоняется инструментом с понятной ошибкой.
  2. `.vibelog/worktrees/vl-219` удалён, `git worktree list` не содержит лишних записей.
