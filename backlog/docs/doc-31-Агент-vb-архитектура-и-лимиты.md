# Агент vb: архитектура и лимиты

`vibelog-agent` — собственный LLM-исполнитель фаз Vibelog. Он собирает промпт фазы, ведёт диалог с моделью, вызывает инструменты (локальные и Vibelog-MCP) и возвращает результат в формате, который ждёт оркестратор. Плюс интерактивный чат в терминале и веб-чате.

**Дата актуализации:** 2026-11-10.
**Источники (по ним документ проверен):** `src/agent/{cli,loop,llm,llm-env,mcp-client,external-mcp,tools,repeat-tracker,session,system-prompt,tui,tui-input,idle-guard}.ts`, `src/cli/commands/agent.ts`, `src/web/qwen-result.ts`, `package.json`.

Документ описывает **устройство и правила работы**. Полные списки флагов и значений — `vibelog-agent --help` и `vibelog instructions` (машинный справочник из кода: VL-394/VL-395/VL-396).

## 1. Назначение

Агент исполняет фазу целиком: держит диалог с моделью, вызывает инструменты, сам решает, когда работа сделана, и завершает фазу через `backlog_finish_phase`. Фазовый процесс (какие бывают фазы, что делает каждая, как настраивается workflow) — в doc-30.

Точки входа:

```bash
vibelog-agent <фаза> <task-id> [флаги]   # headless-исполнение фазы
vibelog-agent "<готовый промпт>"         # исполнение произвольного промпта
vibelog agent                            # интерактивный чат в терминале
vibelog agent <task-id>                  # чат с карточкой задачи в system prompt
vibelog agent analyze <session-ref>      # разбор сессии
vibelog agent run <фаза> <task-id>       # то же, что vibelog-agent <фаза>, но из vibelog
```

## 2. Tool-calling loop

Цикл (`src/agent/loop.ts`): сообщения → LLM → если ответ содержит tool_calls, инструменты выполняются, результаты дописываются в историю → следующий запрос; ответ без tool_calls — финальный текст результата фазы.

- Режим headless: ошибки loop не кидаются наружу, а превращаются в `is_error: true` с текстом причины; частичный результат при этом сохраняется и дописывается к тексту ошибки.
- Режим чата: тот же loop, но история живёт между ходами пользователя.
- Компакшн истории включается сам при росте usage: порог по токенам и размер хвоста настраиваются (`--compact-at-tokens`, `--compact-tail`, отключение — `--no-compact`). Полный перечень порогов — в справочнике из кода.

## 3. Лимиты

Лимиты — по ранy (один запуск фазы), счётчики не «протекают» из прошлых ранов:

| Лимит | Флаг | Назначение |
|---|---|---|
| tool-calls | `--max-tool-calls N` | число вызовов инструментов за ран |
| tool-calls сессии | `--tool-calls-per-session N` | кумулятивно по resume-ранам (защита от «Продолжи» × N) |
| wall-time | `--max-wall-time <сек>` | общее время фазы |
| LLM-запросы | `--max-requests N` | число ходов модели (без флага — без лимита) |
| idle-таймаут | `--idle-timeout <сек>` | максимум тишины без токенов стрима и завершённых инструментов; `0` — выключено |

- wall-time ограничивает фазу целиком, поэтому долгая, но активная работа может быть оборвана на общем таймере. idle-таймаут (`src/agent/idle-guard.ts`) сторожит именно простой: пока идут токены и завершаются инструменты, он не срабатывает; на время выполнения инструмента таймер снимается (легитимный долгий `pnpm test` не считается зависанием).
- В branch-mode (задача в git worktree) файлы задач, настройки и сессии читаются из главного репозитория (`VIBELOG_CWD`), рабочие файлы — в worktree.
- По итогам рана в stderr печатается диагностическая строка: запросы, tool-calls и лимит, доля повторов, число блокировок guard'а, размер payload последнего запроса, usage. Она попадает в хвост лога фазы.

## 4. Loop detection и guard повторов

Два независимых механизма (`loop.ts` + `repeat-tracker.ts`):

1. **Пороги повторов обращения** — одинаковые подряд вызовы поиска, чтения файла, shell-команды (по «скелету» команды), правки файла. При превышении модель получает в контекст директиву «используй уже полученный результат» вместо очередного дублирующего вызова; для правки файла порог предупреждения ниже порога блокировки, и после него вызов блокируется.
2. **Пороги повторов исходов** — сколько раз за ран допустимо повторить вызов, который уже применился, вернул «изменений нет» или вернул отказ. У каждого свой кап и своя директива; блокировки тоже капнуты, чтобы сами директивы не раздували контекст.

Дополнительно:

- **Guard зацикливания намерений**: несколько ходов подряд с одинаковым промежуточным текстом — сигнал, что модель ходит по кругу.
- **Валидация фантомных tool_calls** (пустые `name`/`id`): единичный ход модель исправляет сама по тексту ошибки, серия подряд — признак сломанного провайдера, ран завершается ошибкой.
- **Повторы переносятся в мету сессии**: `blocked_signatures` объединяются между ранами с капом, поэтому «Продолжи» не даёт заново прокрутить уже заблокированное; флаг `--reset-limits-on-resume` сбрасывает накопленное (per-run семантика).
- Пост-фактум статистика повторов (`repeat_stats`) пишется в мету и используется разбором сессии: топ повторяющихся ключей и их доля от всех вызовов.

## 5. Защита от переполнения запроса

Провайдер отказывает не только по контексту, но и по размеру тела запроса, поэтому клиент (`src/agent/llm.ts`) считает байты payload и действует ступенчато:

- при приближении к порогу — предупреждение и уплотнение (обрезка) старых tool-результатов;
- при повторном росте — более агрессивное уплотнение;
- выше жёсткого порога — запрос не отправляется, ран завершается ошибкой с диагностикой.

Обрезка вывода инструментов работает и на уровне инструментов: вывод усекается до фиксированного лимита символов, содержимое файлов читается диапазонами.

## 6. MCP-клиент

`src/agent/mcp-client.ts` — минимальный stdio JSON-RPC 2.0 поверх NDJSON: спавнит `vibelog mcp start` (cwd процесса — корень проекта, чтобы сервер нашёл `backlog/`), делает handshake, получает список инструментов и проксирует вызовы в loop.

- Таймаут на каждый вызов: зависший сервер не должен вешать фазу.
- Закрытие: EOF stdin — сервер выходит сам; если не вышел, процесс добивается сигналом.
- Внешние MCP-серверы (`src/agent/external-mcp.ts`): любые stdio-серверы из секции `mcpServers` `.vibelog/settings.json`; их инструменты получают префикс `<имя>__`, чтобы не конфликтовать. Отказ одного сервера — предупреждение в stderr, остальные подключаются, фаза продолжается.
- Отказ MCP Vibelog в чате — предупреждение: чат продолжается без Vibelog-инструментов. В headless-фазе отказ означает, что фаза не сможет отчитаться, — это видно по результату.

## 7. Модели и протокол LLM

- Модель берётся из реестра в `.vibelog/settings.json` (`models`/`gateways`), а при его отсутствии — из переменных окружения (`VIBELOG_LLM_BASE_URL`, `VIBELOG_LLM_API_KEY`, `VIBELOG_LLM_MODEL`). Секреты живут в `.env` проекта или в shell-окружении; приоритет — shell-окружение, затем `.env`.
- При resume ран идёт на модели, зафиксированной в мете сессии; `--model <id>` переопределяет её разово, `--model-follow-settings` — осознанно продолжает на активной модели из настроек.
- Протокол API (`api_mode`): `chat` (дефолт) — `POST <base_url>/chat/completions`; `responses` — OpenAI Responses API (`input[]`/`output[]`, tool calls через `call_id`, typed SSE-события). Значение задаётся у модели в реестре (или устаревшим топ-уровневым ключом), переопределяется флагом `--api-mode`. Битое значение → `chat`: конфигурация не должна ронять агента.
- Перед стартом окружение валидируется (`src/agent/llm-env.ts`): нет ключа или модели — понятная ошибка до запуска, а не падение посреди фазы.

## 8. Системный промпт

Собирается из трёх частей (`src/agent/system-prompt.ts`):

1. встроенная базовая часть — роль, язык, границы рабочего каталога, правила экономии ходов (`templates/agent-prompt.md`, переопределяется `.vibelog/prompts/agent-prompt.md`);
2. содержимое `AGENTS.md` проекта из корня рабочего каталога (читается только оттуда, с лимитом вставки; ошибка чтения — предупреждение, не падение);
3. для интерактивного чата — дополнительный блок правил чата (`templates/agent-prompt-chat.md` → `.vibelog/prompts/agent-prompt-chat.md`); headless-фазы его не получают.

Веб-чат собирает промпт отдельно (`buildSystemPrompt` в `src/web/chat.ts`): общая часть → блок роли (промпт персоны) → **блок `## Память персоны`** → **блок `## Уроки проекта`** → **блок `## Правила проекта`** → контекст поиска. Память читается из `.vibelog/prompts/personas/<prompt>.memory.md` (`loadPersonaMemory` в `src/web/personas.ts`), лимит — `persona_memory.max_chars` в `.vibelog/settings.json` (дефолт 2500, при превышении — обрезка по границе строки с явной пометкой). Пустой/отсутствующий файл — блока нет. В headless-фазы и TUI память не попадает: `src/agent/system-prompt.ts` её не читает (инвариант закреплён тестом от обратного, как чат-блок VL-238).

Блок `## Уроки проекта` (VL-404) — recall уроков по смыслу разговора: `recentConversationText` берёт последние `chat_lessons.max_messages` сообщений пользователя (ответы модели исключены), `selectLessonsForText` в `src/core/lesson.ts` токенизирует текст (`tokenizeQuery`/`stemToken`), фильтрует `active` + не протухшие по `stale_days` и ранжирует `scoreLessonForTask` (VL-400), свежесть — tie-breaker. Кап — минимум из `chat_lessons.limit` и `lessons.prompt_limit`; порог минимального score отсекает совпадения по общему слову. Формат строки — `- [lesson-N] <title> (kind)`, как в фазах. Уроки убраны из контекста `globalSearch`, чтобы не приходить дважды. `chat_lessons.enabled: false` — блока нет. В headless-фазы и TUI блок не протекает: собирается только в `src/web/chat.ts` (инвариант закреплён тестом от обратного).

Блок `## Правила проекта` (VL-405) — **ссылка, а не вставка**: `describeAgentsMd(cwd)` в `src/web/chat.ts` делает `statSync` корневого `AGENTS.md` и возвращает короткую строку с числом символов и императивом «Прочитай его через read_file, если вопрос касается правил проекта. В промпт он не вставлен». Файла нет (`ENOENT`) — блока нет; прочие ошибки (`EACCES`, `EISDIR`) — `null` + `console.error`, чат не падает. Сам текст `AGENTS.md` в чат-промпт не попадает: чат интерактивный, модель читает файл через `read_file` только когда вопрос действительно про правила (вставка 8000 символов в каждый ход — дорого). В отличие от TUI-агента и headless-фаз, где `src/agent/system-prompt.ts` вставляет `AGENTS.md` целиком с капом `AGENTS_MD_MAX_CHARS = 8000` — там ничего не меняется (инвариант закреплён тестом от обратного). Блок идёт после уроков и до контекста поиска: контекст поиска всегда последний, он рантаймовый и меняется каждый ход.

## 9. Headless-контракт

Headless — единственная строка JSON в stdout (`type: "result"` + текст результата, `is_error`, число ходов, длительность, tool-calls, `session_id`, usage). Прогресс, логи и предупреждения идут в stderr: stdout зарезервирован под результат и читается оркестратором.

- Headless включается флагом `--headless`, флагом `--output-format json` или автоматически, когда stdout не TTY.
- Код выхода: 0 — ран без ошибки, 1 — фаза завершилась с ошибкой.
- Оркестратор и Telegram-бот разбирают результат существующим парсером (`src/web/qwen-result.ts`), поэтому добавление полей в JSON их не ломает.

## 10. TUI и чат

- Интерактивный вывод — append-режим в stderr: шапка один раз, токены модели стримятся в транскрипт, карточки tool-вызовов (имя, аргументы с обрезкой, статус, длительность) и ошибки дописываются по завершении, перерисовывается только нижняя строка со счётчиками. Ничего вышедшего не стирается, скролл не теряется.
- Интерактив (спиннер, заметки, ввод, подтверждения) — библиотеки `@clack/prompts`/`@clack/core`: чистый JS, нативной сборки нет (работает на старых macOS).
- Чат требует TTY: в не-TTY — ошибка с подсказкой про headless. Ввод блокируется на время хода, история растёт в памяти, транскрипт сохраняется после каждого хода. Ctrl+C/Ctrl+D — выход.
- Подтверждения инструментов — готовая точка `createConfirmPrompt`; loop выполняет инструменты без согласования, поэтому поток подтверждений сегодня используется тестами и будущими интерактивными ветками.

## 11. Сессии и транскрипты

- Сессия — каталог `.vibelog/agent-sessions/`: `<sessionId>.jsonl` (по строке на сообщение) и `<sessionId>.meta.json` (taskId/фаза, модель, usage, длительность, история ранов, статистика повторов, блокированные сигнатуры, итог последнего рана).
- `--resume <sessionId>` продолжает сессию, `--continue` — последнюю сессию текущего каталога. При resume к промпту добавляется компактный блок состояния задачи, чтобы агент не тратил ход на чтение задачи; неизменный блок задачи большого промпта дедуплицируется.
- На мете строится диагностика: `vibelog session summary <session-ref>` (сводка рана) и обзор транскрипта `agent_session_outline` (строки с ролью, размером, tool_calls и сниппетом) — транскрипт читают обзором, а не целиком.
- Запись транскрипта и меты в branch-mode идёт в главный репозиторий (`VIBELOG_CWD`), чтобы resume из бота находил сессию.

## 12. Что учтено в дизайне

- Лимиты, guard повторов и диагностика обязательны: без них ран либо сгорает по времени, либо крутится на повторах, сжигая контекст и деньги.
- Пороги повторов и капы объявлены в одном модуле (`repeat-tracker.ts`), чтобы директивы для модели говорили на одном языке с отчётом о повторах.
- Инструмент внутреннего списка подзадач не заводится: шаблон фазы сам является нумерованным чек-листом, а состояние плана живёт в файле задачи и переживает resume (решение и обоснование — doc-23).
