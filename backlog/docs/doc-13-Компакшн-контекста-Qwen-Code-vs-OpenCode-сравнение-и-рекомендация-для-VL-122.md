# Компакшн контекста: Qwen Code vs OpenCode — сравнение и рекомендация для VL-122

> Документ создан в рамках VL-136 (обратная связь для VL-122 «Усечение payload запроса»).
> Ссылки на файлы/строки привязаны к снапшоту референсов от **2026-10-13** (`refs/qwen-code`, `refs/opencode`) — при обновлении refs номера строк могут устареть.
> **Ключевое ограничение внедрения (комментарий Pavel, 2026-10-14):** основная модель сейчас — **MiMo-V2.5 с окном контекста 1M токенов и очень дешёвым чтением кэшированных токенов**. Все рекомендации ниже учитывают это.

## 1. Как Qwen Code решает рост контекста (два слоя)

Архитектура — гибрид: детерминистический микро-компакшн + LLM-саммари по трёхуровневым порогам.

### 1.1. Microcompact — детерминистический слой

Файл: `refs/qwen-code/packages/core/src/services/microcompaction/microcompact.ts` (~1093 стр.)

- Старые **tool-результаты** заменяются на фиксированный плейсхолдер `"[Old tool result content cleared]"` (стр. 14, константа `MICROCOMPACT_CLEARED_MESSAGE`). Никакого LLM — чистая эвристика по возрасту/позиции сообщения.
- Порог запуска — **low-watermark = 50%** от порога LLM-компакшна (~стр. 652): сначала пробуем дешёвую зачистку, и только при продолжении роста — тяжёлый LLM-саммари.
- Есть **time-based триггер** `evaluateTimeBasedTrigger` (стр. 299) — зачистка по давности tool-вызова, независимо от токенов.
- Семантика сообщений не меняется: роль, tool_calls, текст ассистента остаются; чистятся только громкие tool-выводы.

### 1.2. ChatCompression — LLM-саммари по трёхуровневой лестнице порогов

Файл: `refs/qwen-code/packages/core/src/services/chatCompressionService.ts` (~1362 стр.)

- `computeThresholds` (~стр. 180–240): пороги **пропорциональны context window** — три уровня **warn / auto / force** (в духе claude-code, см. комментарии WARN/AUTO buffer ~стр. 119–128). Т.е. агент предупреждает пользователя до автоматического компакшна, а force — крайняя мера.
- Триггеры компакшна (~стр. 248–320, 419–465):
  - `auto` — превышен порог токенов;
  - `manual` — явная команда пользователя `/compact`;
  - `payload_overflow` — HTTP 413 от провайдера (провайдер отверг payload → компакшн как recovery);
  - `image_overflow` — переполнение из-за скриншотов.
- `COMPACTION_BUDGET_SAFETY_MARGIN = 1024` (стр. 69) — запас до верхней границы, чтобы саммари не упёрлось в лимит.
- Дополнительно `compactionInputSlimming.ts` (~531 стр.) уtrimming tool-**входов** перед компакшном — уменьшает вес диалога ещё до срабатывания основной логики.
- Результат — новое «синтетическое» сообщение-саммари, история схлопывается; триггер фиксируется в notice (`payload_overflow` / `manual` / `auto`, ~стр. 422–432).

**Итого у Qwen Code:** два слоя, усечение всегда **отмечается** (плейсхолдер или notice о триггере), пороги масштабируются с окном модели.

## 2. Как OpenCode решает рост контекста (один слой)

Файл: `refs/opencode/packages/core/src/session/compaction.ts` (~248 стр.)

- Один слой — **LLM-саммари** с фиксированным markdown-шаблоном `SUMMARY_TEMPLATE` (стр. ~15–55). Секции: `## Objective`, `## Important Details`, `## Work State` (Completed / Active / Blocked), `## Next Move`, плюс инструкции «Relevant Files».
- Константы (стр. 12–15):
  - `DEFAULT_BUFFER = 20_000` — сколько токенов резервируется «под грядущее»;
  - `DEFAULT_KEEP_TOKENS = 8_000` — хвост диалога (recent) сохраняется дословно;
  - `TOOL_OUTPUT_MAX_CHARS = 2_000` — tool-выводы длиннее 2000 символов обрезаются с маркером `[truncated]` (стр. 86) — **детерминистический слой внутри одного файла**;
  - `SUMMARY_OUTPUT_TOKENS = 4_096` — жёсткий потолок размера саммари (стр. 189).
- `select()` (~стр. 138–160): с конца набираются keep-токены («recent»), всё остальное уходит в «head» → в LLM-саммари. Т.е. разбиение head/recent детерминировано по токенам.
- Автотриггер `compactAfterOverflow` (~стр. 180) — по оценке `Token.estimate` оверфлоя (buffer+keep сверх окна).
- Саммари **инкрементально обновляется** (prior-summary + `SUMMARY_UPDATE_INSTRUCTIONS`) — повторные компакшны не накапливают старые саммари, а переписывают одно.
- Конфиг: `refs/opencode/packages/core/src/config/compaction.ts` (~15 стр.) — `auto` / `buffer` / `keep.tokens`.

**Итого у OpenCode:** один слой, но с внутренней детерминистической зачисткой tool-выводов; шаблон саммари — жёсткая структура, что хорошо для стабильности.

## 3. Сравнение по критериям, важным для Vibelog.md

| Критерий | Qwen Code (2 слоя) | OpenCode (1 слой) | Что важно нам |
|---|---|---|---|
| **Простота** | Низкая: 1362 + 1093 + 531 стр., много взаимозависимых порогов | Средняя: 248 стр., один файл + конфиг | Нам нужен минимальный объём кода |
| **Детерминизм** | Высокий у микро-слоя; LLM-слой недетерминирован | Только tool-truncate детерминирован; саммари — LLM | Полный детерминизм критичен для loop-guard (VL-119) и тестов |
| **Node.js 20+, без нативных зависимостей** | Да (TypeScript/Bun-совместимый код) | Да | Оба варианта переносимы |
| **Сохранение jsonl-транскрипта для resume (VL-103)** | Компакшн схлопывает историю целиком — требует отдельной механики «не трогать jsonl» | То же самое: компакшн мутирует историю сессии | **Ключевое:** у нас jsonl пишется инкрементально через `onMessage` (`src/agent/session.ts:32,67`; `src/agent/cli.ts:393–425`) — любое wire-усечение должно происходить **после** записи в jsonl |
| **Совместимость с мета-логикой (loop-guard VL-119)** | Плейсхолдеры сохраняют role/структуру — loop-guard продолжает работать | Саммари заменяет структуру — loop-guardу сложнее | Предпочтительны плейсхолдеры, а не пересборка истории |
| **Учёт usage-метрик** | Пороги из context window; usage-поля мониторятся | `Token.estimate` (локальная оценка) | У нас уже есть `input_tokens` / `cache_read_input_tokens` в `LlmUsage` (`src/agent/llm.ts:45–47, 100–111`) — точнее любой локальной оценки |

## 4. Рекомендация для VL-122

### 4.0. Влияние MiMo-V2.5 (1M контекст, дешёвый cache read) — читать первым

Комментарий Pavel к запуску Фазы 3 меняет экономику решения:

1. **Оверфлоу при 1M окне наступают редко.** Активная сессия в 200–400K токенов — это 20–40% окна. Значит компакшн — не частая операция «каждые 50 сообщений», а редкая аварийная/профилактическая. Пороги должны быть **пропорциональны окну** (как `computeThresholds` у Qwen Code), а не абсолютные: например warn ≈ 70%, auto ≈ 85% от 1M.
2. **Дешёвый cache read переворачивает приоритеты: выгоднее слать длинную историю, чем часто усекать.** Каждое усечение ломает префикс кэша → следующий запрос идёт по полной цене input. Поэтому:
   - wire-усечение должно быть **редким** (срабатывает только близко к лимиту);
   - префикс запроса должен быть **стабильным между запросами** (append-only: system + первый user + история + новые сообщения) — это максимизирует cache hit;
   - **не вставлять** усечение-маркер в середину префикса при каждом запросе — маркер появляется один раз, в момент компакшна.
3. **Слой «зачистка tool-результатов» (microcompact) — отложить.** Он полезен, когда окно узкое; при 1M + дешёвом cache read выгода сомнительна, а риск (сломать мета-логику, потерять данные для loop-guard) реален. Можно вернуться позже как опция.
4. **Latency, а не стоимость — главный аргумент усечения при 1M.** Длинный prompt медленнее prefill'ится даже с кэшем. Поэтому триггер — по usage-токенам (точным, из `LlmUsage`), а не по количеству сообщений.

### 4.1. Этап 1 (основной): детерминистическое wire-усечение «system + первый user + хвост»

Ровно то, что намечено в VL-122, с уточнениями из анализа референсов:

- **Где:** в `src/agent/llm.ts` (`toWireMessages`, стр. 237) или неперед ним — в `src/agent/loop.ts` перед `streamChat` (стр. 207). Важно: **jsonl и resume не затрагиваются** — они пишутся через `onMessage` (`src/agent/session.ts`) до любого wire-усечения.
- **Что сохраняем дословно:** system-промпт + первое user-сообщение + последние N токенов истории (хвост, по образцу `select()` из OpenCode — набор с конца).
- **Что усекаем:** середина («head» после первого user) заменяется **одним** синтетическим сообщением-маркером, например:
  `"[История усечена: N сообщений (~T токенов) опущено. Полный транскрипт — в jsonl сессии.]"`.
  Формат — по образцу `MICROCOMPACT_CLEARED_MESSAGE` (`microcompact.ts:14`): один плейсхолдер, роль assistant (или user — решить на этапе реализации, чтобы не ломать формат провайдера), структура остальных сообщений не меняется.
- **Триггер:** `usage.input_tokens + usage.cache_read_input_tokens` из последнего ответа (`src/agent/llm.ts:45–47`) ≥ порога. Пороги пропорциональны context window MiMo-V2.5: warn ≈ 70% (подсказка в stderr), auto ≈ 85%. Оверфлоу по факту (HTTP 413/400 от провайдера) — fallback-триггер по образцу `payload_overflow` (`chatCompressionService.ts:431`): один раз пытаемся усечь жёстче и повторить запрос.
- **N подбирается** из расчёта «хвост ≈ 10–15% окна» — при 1M это ~100–150K токенов, т.е. в подавляющем большинстве сессий усечение просто не сработает (это нормально и правильно).
- **Почему не копировать chatCompressionService целиком:** 1362 стр. решают проблемы, которых у нас нет (image_overflow, картинки-скриншоты, интеграция с Gemini-специфичными полями, multi-provider notice-цепочки). Нам достаточно ~100–200 стр. детерминистической логики. LLM-саммари (шаг 4.2) — отдельный опциональный этап, когда появится реальная потребность.

### 4.2. Этап 2 (опционально, позже): LLM-саммари по шаблону OpenCode

Если этап 1 не покроет потребности (очень длинные сессии, где хвоста 150K не хватает):

- Брать шаблон OpenCode (`SUMMARY_TEMPLATE`: Objective / Important Details / Work State / Next Move) — он структурный и короткий (SUMMARY_OUTPUT_TOKENS=4096 — хороший потолок).
- Инкрементальное обновление prior-summary (как в OpenCode) — чтобы повторные компакшны не раздувались.
- При MiMo-V2.5 этап 2 имеет смысл включать **только вручную** (`/compact` по образцу триггера `manual`), автоматически — лишь на пороге force (~95% окна).

### 4.3. Итоговая схема (этап 1)

```
история сообщений (полная, в памяти и jsonl)
        │
        ▼
usage-токены ≥ warn-порога (70% от 1M)?  ── да ──► stderr-подсказка
        │ нет
        ▼ (редко: ≥ 85% окна или HTTP 413)
wire-усечение перед streamChat:
  [system] [первый user] [СИНТЕТИЧЕСКИЙ МАРКЕР] [последние N токенов]
        │
        ▼
jsonl / resume / loop-guard — без изменений
```
