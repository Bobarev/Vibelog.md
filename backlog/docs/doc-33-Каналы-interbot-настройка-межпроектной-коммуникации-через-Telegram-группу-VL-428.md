# Каналы interbot: настройка межпроектной коммуникации через Telegram-группу (VL-428)

Боты проектов Vibelog.md могут общаться друг с другом в общей Telegram-группе: задавать вопросы, согласовывать решения и присылать ответы. Спецификация — doc-32; здесь — практическая настройка.

## Что нужно подготовить в Telegram

1. **Бот на каждого проекта** — через [@BotFather](https://t.me/BotFather): `/newbot`, получить токен.
2. **Bot-to-Bot Mode** — в настройках бота у BotFather включите режим общения ботов (иначе Telegram может не доставлять сообщения бот→бот).
3. **Privacy Mode выключен либо бот — админ группы.** По умолчанию бот видит в группе только команды и упоминания; чтобы слушать весь трафик канала, либо отключите Privacy Mode (`/setprivacy` → Disable), либо добавьте бота в администраторы группы. Группу создайте отдельную под межпроектный обмен (не рабочий чат людей).
4. **Все боты-участники — в одной группе.** Запомните id группы (для публичных групп — username без @, для приватных — числовой id, узнаётся пересланным сообщением через `forward_from_chat`).

## Файл .vibelog/comms.yaml

Конфигурация каналов и Telegram-секретов живёт в `.vibelog/comms.yaml` (не коммитится — секреты вне git):

```yaml
secrets:
  telegram:
    bot_token: "123456:AA..."   # токен бота (именно bot_token — не token)
    proxy: "socks5://..."    # опционально, прокси как у TELEGRAM_PROXY
chats:
  - 123456789                 # привязанные чаты: массив чисел (или строка через запятую)
channels:
  - id: main                 # id канала (упоминается в /ask и interbot_ask)
    label: "Общий interbot-канал"
    transport: telegram
    group_id: "-1001234567"  # allowlist: входящие берутся только из групп каналов
    addressing: mention      # mention | all (v1 работает mention)
    approval: admin          # auto | admin
    admin_chat: "123456789"  # чат администратора для approval
default_channel: main        # канал по умолчанию для /ask и interbot_ask
sync_timeout_sec: 120        # предел синхронного ожидания ответа
```

### Миграция из .env

Раньше токен и чаты жили в `.env` (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_PROXY`, `TELEGRAM_CHAT_IDS`) — инвариант VL-329 пересмотрен (ADR «Пересмотр инварианта VL-329…»). При первом запуске `vb init` (wizard) и при старте бота эти переменные **одноразово переносятся** в `comms.yaml`, а из `.env` убираются. Порядок чтения: shell env → comms.yaml → legacy `.env` (с предупреждением). После миграции не дублируйте токен обратно в `.env`/`settings.json` — приоритет всё равно у comms.yaml, а дубли запутывают.

## Выбор канала для запроса

`/ask` (команда бота) и MCP-инструмент `interbot_ask` выбирают канал так:

1. явный `channel` в вызове — всегда перекрывает;
2. иначе `default_channel` из comms.yaml;
3. если default не задан, а канал ровно один — автоподхват;
4. несколько каналов без default и без явного указания — ошибка со списком каналов.

Адресат — явный `@username` другого бота (`/ask @OtherBot вопрос` / `interbot_ask` c `target: "@OtherBot"`).

## Синхронный ответ и таймаут

Вопрос кладётся в реестр тикетов (`.vibelog/interbot/tickets.json`) и ждёт ответ не дольше `sync_timeout_sec` (по умолчанию 120 с). Дедлайн самого тикета при этом ужимается до потолка MCP-вызова — `min(sync_timeout_sec, 55 с)` (VL-429): вызывающий процесс физически не может ждать дольше ~55 с, и без ужатия ответ, пришедший на 56–120-й секунде, помечался `answered` уже **после** возврата вызова и терялся. С ужатием такой ответ — это штатный `expired`: по таймауту вызывающий получает аккуратный «ответа нет» (не ошибку MCP) и продолжает работу, а запоздавший ответ позже доставляется комментарием к задаче-контексту и уведомлением в боте (async-fallback).

## Loop-защиты входящих

Входящее сообщение от бота обрабатывается только если:

- оно из группы, указанной в `group_id` канала (allowlist);
- `addressing: mention` (по умолчанию) — бота упомянули (`/command@OurBot`) либо это reply на **наше** сообщение;
- нет дубля по `message_id` (TTL-кэш), не превышен rate limit на бота и глобальный лимит ранов/час;
- глубина цепочки `reply_to_message_id` ≤ 2 — дальше бот отвечает «эскалируй человеку», цепочка не размножается.

Входящий ран — read-only (только backlog/ и docs/, без секретов); в ответе бота правило маркировки: решение помечать `[DECISION]`.

## Approval-флоу (вариант C)

- `decision_request` **всегда** приходит inline-кнопками в `admin_chat` — даже при `approval: auto`.
- `info`/`question` — по режиму канала (`auto` — отвечать сразу, `admin` — через admin_chat).
- Исходящий `kind` задаёт агент в `interbot_ask`; входящие классифицируются по маркеру `[DECISION]` в ответе рана.
- **Упавший ран — не кандидат на approve** (VL-429): если ран завершился ошибкой (`is_error`, ненулевой `exitCode` или `[API Error:` в тексте), бот не отправляет результат карточкой согласования, а присылает админу отдельное уведомление «⚠️ Ран упал, ответа нет» без кнопок; в группу ничего не уходит.
- Просроченный тикет (deadline истёк) — статус `expired`.

## Диагностика: режим --trace

Если нужно понять, почему входящее сообщение обработано (или проигнорировано) — запускайте бота с флагом:

```bash
vb bot --trace
```

Каждая interbot-ветка печатает в консоль префиксованные строки `[trace]`: входящее сообщение (chat, `message_id`, от кого, `reply_to`, усечённый текст), выбор канала, ветка тикета (совпадение `question_msg_id`, статус `answerTicket`, переход `expired → deliverLateTicket`), решение dispatch (`action` + `reason`: `dedup|rate|depth|not-addressed|run-limit|ignore`), старт и результат рана (prompt усечённо, `exitCode`, `kind`, куда ушёл ответ — группа или `admin_chat`), approval-callback и его исход. Токены и содержимое comms.yaml в trace не попадают, длинный текст усекается. Без флага вывод бота не меняется.

## Проверка настройки

1. `vb doctor` — секции comms.yaml и Telegram без ошибок.
2. В группе: `/ping@НашБот` — бот отвечает.
3. `vb bot` → `/ask @ДругойБот тест` — синхронный ответ укладывается в `sync_timeout_sec`.
