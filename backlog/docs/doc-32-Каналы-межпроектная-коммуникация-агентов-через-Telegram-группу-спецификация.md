# Каналы: межпроектная коммуникация агентов через Telegram-группу

**Статус:** Draft · **Дата:** 2026-11-18 · **Scope:** v1 + отложенные шаги

## 1. Контекст и мотивация

В работе одновременно несколько проектов Vibelog (Vibelog.md, Vibelog UI, LB), у каждого — свой Telegram-бот (`vibelog bot`, grammy, long-polling). Агентам постоянно нужно перекидывать друг другу вопросы и решения. Существующий механизм upstream-репортов (VL-363/375/391, git-инбокс) — не подходит: он не realtime, однобок (только баги) и требует ручного приёма.

**Решение:** общая Telegram-группа как шина между ботами проектов. Пользователь создаёт группу, добавляет туда ботов проектов; боты пишут и читают в группе, отвечая на вопросы друг друга. Механика опирается на Bot-to-Bot Communication Mode Telegram (упоминания `/cmd@Bot`, replies, режим Privacy Mode / админ группы) и loop-рекомендации Telegram (dedup, rate limit, depth/timeout).

## 2. Сущность «Канал»

Единый контейнер настроек коммуникации — по аналогии с персонами (`chat_personas`). Название — «Канал». Рассмотренные альтернативы отклонены: «Шина» — технократно, «Мост» — конфликтует с существующим chat-bridge («Мост Telegram ↔ веб-чат»).

### Поля канала (v1)

| Поле | Тип | Назначение |
|---|---|---|
| `id` | string | уникальный id канала (латиница, slug) |
| `label` | string | человекочитаемое имя |
| `transport` | enum | `telegram` (v1); будущее — другие мессенджеры |
| `group_id` | number/string | id группы, в которой бот пишет и слушает |
| `addressing` | enum | `mention` (дефолт: только `/cmd@Bot` и reply на наше сообщение) \| `all` (слушать всю группу) |
| `approval` | enum | `auto` (бот отвечает сам) \| `admin` (отправка через подтверждение) |
| `admin_chat` | number | chat_id администратора, куда уходят approval-запросы; выбирается из привязанных чатов (`TELEGRAM_CHAT_IDS` → секция `chats` нового файла) |
| `limits` | object | опционально: переопределение rate limit / depth / timeout для канала |

### Поведение

- **addressing=mention**: входящее обрабатывается только при упоминании бота (`/command@OurBot`) или reply на сообщение нашего бота. Дефолт для v1.
- **addressing=all**: бот обрабатывает все сообщения группы, кроме собственных и отфильтрованных (dedup/rate limit). Переключение настройкой канала.
- **approval=auto**: ответ агента уходит в группу автоматически.
- **approval=admin**: перед отправкой в группу (исходящий ответ или исходящий вопрос) — inline-кнопки подтверждения в `admin_chat` (паттерн `chat-pause.ts`: APPROVAL_PREFIX + callback-кнопки). Просрочка = отказ, тикет закрывается как `expired`.

## 3. Конфигурация: новый файл `.vibelog/comms.yaml`

### Зачем отдельный файл

Пользователь хочет убрать конфиденциальное из корня `.env` и собрать все id и секреты коммуникации в одном месте. Имя файла — `comms.yaml` (communications): покрывает каналы, ботов и секреты, не привязан к телеграму (будущий мессенджер = новая секция). Чистое `channels.yaml` отклонено: внутри лежал бы токен бота, что семантически криво.

### Структура (v1)

```yaml
# .vibelog/comms.yaml — СЕКРЕТЫ + коммуникации. НЕ коммитить!
secrets:
  telegram:
    bot_token: "..."        # бывший TELEGRAM_BOT_TOKEN (.env)
    proxy: "..."            # бывший TELEGRAM_PROXY (.env)

chats:                      # бывший TELEGRAM_CHAT_IDS (.env)
  - 123456789               # привязанные чаты = кандидаты в admin_chat

default_channel: lb-link    # канал по умолчанию для /ask и interbot_ask
sync_timeout_sec: 120       # таймаут синхронного ожидания ответа (глобальный)

channels:
  - id: lb-link
    label: "Связь с LB"
    transport: telegram
    group_id: -1001234567890
    addressing: mention
    approval: admin
    admin_chat: 123456789
```

### Инварианты и миграция

1. **В gitignore ничего добавлять не нужно**: `.vibelog/.gitignore` по умолчанию запрещает всё — `comms.yaml` не попадает в git без дополнительных действий (решение, 2026-11-18).
2. **Пересмотр инварианта VL-329 «.env — единственный источник секретов»** — по сути требуется ADR: секреты переезжают в `comms.yaml`, `.env` остаётся для прочих переменных (LLM-ключи и т.п.).
3. **Приоритет чтения:** shell env → `comms.yaml` → legacy `.env` (fallback для уже настроенных проектов, с предупреждением о переносе). Миграцию выполняет wizard (`init-wizard.ts`, где сейчас спрашиваются token/proxy/chats) и/или одноразовое авто-перенесение при старте бота (`upsertDotEnv`-паттерн, VL-329).
4. **Затронутые читатели:** `resolveToken`/`resolveProxy` (`src/bot/settings.ts`), `readBotChats`/`saveBotChats` (`src/bot/env.ts`), auto-binding `/start` → `saveBotChats`, `checkTelegramToken` (`src/core/setup-check.ts`), CLI-флаги `--bot-token/--bot-chats/--bot-proxy` (`src/cli/router.ts`), тексты `instructions.ts`.
5. **Секция `env` в settings.json не возрождается** — это отдельный legacy-канал, остаётся мёртвым.

### Почему не settings.json (как персоны)

settings.json коммитится в git — секреты туда нельзя ни в каком виде. Каналы v1 тоже живут в `comms.yaml`, чтобы вся коммуникация была в одном файле; если позже понадобится коммитьить конфиг каналов без секретов — секция `channels` выносится в settings.json (задача будущего шага).

## 4. Механика v1

### Входящее (чужой бот спрашивает нас)

Сообщение в `group_id` одного из каналов → фильтры (`from.is_bot`, allowlist групп, dedup по `message_id`, rate limit на бота, depth по цепочке `reply_to`) → выбор режима `addressing` канала → при `approval=admin` — согласование с админом → короткий LLM-ран через `startPrompt` (read-only контекст: backlog/ и docs/, без секретов) → ответ реплаем (`reply_to_message_id`, GFM через `sendChatAnswer`, лимит `TELEGRAM_TEXT_LIMIT`).

### Исходящее: гибрид sync / async-fallback

1. MCP-инструмент `interbot_ask` / команда `/ask @Bot вопрос` постит вопрос в канал и создаёт **тикет** (`pending`, deadline = now + min(`sync_timeout_sec`, 55 с) — потолок MCP-вызова, VL-429: без него ответ на 56–120-й секунде терялся после возврата вызова).
2. MCP-вызов блокируется и ждёт: ответ бота-получателя дописывается в тикет процессом бота, MCP-сервер видит это через общий файл тикетов (процессная граница: бот ≠ MCP-сервер, только общий файл, паттерн `.vibelog/settings.json`).
3. Ответ пришёл → возвращается агенту, тот продолжает с ним в руках (**синхрон**).
4. Таймаут → возвращается «ответа нет, езжай без него», агент продолжает работу; тикет переходит в async-режим: запоздавший ответ доставляется комментарием к задаче-контексту тикета + уведомлением в боте (**async-fallback**).

### Тикеты

Файл-реестр (`.vibelog/interbot/tickets.json`, атомарная запись temp+rename — lesson-214). Поля: `id`, `channel_id`, `question_msg_id`, `asked_at`, `deadline`, `status`, `context { task, session }`, `reply`. Статусы: `pending → answered | expired → delivered`. На старте бота — разбор протухших (паттерн `recoverStalePhaseStatuses`, VL-196).

## 5. Loop-защита (с первого дня)

- **Dedup:** кэш `message_id` (+ hash текста), TTL-окно.
- **Rate limit:** на каждого чужого бота (сообщений/мин) и глобальный лимит входящих LLM-ранов/час (стоимость).
- **Depth:** счёт цепочки `reply_to_message_id`, лимит 2 хопа; дальше бот отвечает «эскалируй человеку» и не пускает ран.
- **Timeout:** тикеты (TTL) + таймаут синхронного ожидания 120 с.
- **Второй рубеж:** существующий loop detection агента (`resolveLoopDetectionRepeat`).

## 6. Безопасность

- Секреты — только в `comms.yaml` (в gitignore) и shell env; `.env` — legacy-fallback.
- Входящий ран отвечает ВСЕЙ группе: в промпте жёсткое правило — только backlog/ и docs/, никогда `.env`, секреты, чужие задачи; инструменты рана read-only.
- `approval=admin` как страховка для чувствительных действий; дефолт для `decision_request` — `admin`.
- Лог «ответ без тикета» — детект потерянных сообщений при офлайне бота.

## 7. Этапы реализации v1

1. **`comms.yaml` + миграция**: `src/core/comms.ts` (новый: чтение/запись/валидация, gitignore-гард), правки `bot/settings.ts`, `bot/env.ts`, wizard, fallback из `.env`; ADR на пересмотр VL-329.
2. **Сущность канала**: хранение, CRUD-секция настроек, валидация `group_id`/`addressing`/`approval`/`admin_chat`.
3. **Тикеты**: `src/core/interbot/tickets.ts` + юнит-тесты (статусы, TTL, конкурентная запись).
4. **Входящий путь**: `src/bot/interbot.ts` (новый) + хук в `handlers.ts` + режим approval; тесты dedup/depth/rate-limit отдельно от grammy.
5. **Исходящий синхрон**: `/ask` (`commands.ts`) + MCP `interbot_ask` (`mcp/server.ts`, паттерн `INTERBOT_TOOLS` по образцу `UPSTREAM_TOOLS`; зеркально в инструменты веб-чата — имена должны совпадать).
6. **Async-fallback**: доставка в комментарий задачи + уведомление; разбор pending на старте.
7. **Approval-флоу**: inline-кнопки в `admin_chat` (паттерн `chat-pause.ts`).
8. **Документация**: гайд настройки (BotFather → Bot-to-Bot Mode, Privacy Mode off/админ, allowlist), CHANGELOG.

**Проверка:** `npm test` / lint; сценар на тест-группе с двумя ботами: синхронный ответ (~5 с), таймаут-фолбэк (ответ на 10-й минуте → комментарий задачи), обрыв зацикливания на depth 2, approval-кнопка в admin-чате.

## 8. Вне v1 (будущие шаги)

- **Несколько Telegram-ботов у проекта** — секция `bots:` в comms.yaml, маппинг «бот → каналы».
- **Другой мессенджер** — абстракция `transport` (send/listen/update-callbacks), новая секция секретов.
- **addressing=all как дефолт** и автообнаружение ботов в группе.
- **Fan-out:** один вопрос нескольким проектам, сбор ответов по мере прихода.
- **История тредов:** сквозной диалог (не только вопрос→ответ), лог переписки в backlog.
- **UI управления каналами** (доска каналов, кнопки approval в веб-чате).
- **Вынос `channels` в settings.json** для коммитинга конфига без секретов.
- **Команды бота для управления каналом** (`/channel list|on|off`).

## 9. Решения по открытым вопросам (закрыты 2026-11-18)

1. **Approval — гибрид по типу сообщения (вариант C):** `decision_request` всегда уходит через approval-кнопку в `admin_chat`, даже в режиме `auto`; `info`/`question` — по режиму канала (`auto` → сам, `admin` → через кнопку). Классификация: исходящие — `kind` передаёт агент в `interbot_ask`; входящие — агент-ответчик в ране помечает решение маркером `[DECISION]` в ответе, бот парсит маркер и уводит сообщение в approval вместо автоматической отправки. Approval v1 действует только на отправку в группу; «запрос на действие» (чужой просит нас что-то сделать) — в будущие шаги.
2. **Таймаут — глобальная настройка (вариант B):** `sync_timeout_sec` в `comms.yaml`, дефолт 120 с. TTL тикета (async-доставка) от него не зависит и больше (15–30 мин). ~~При реализации проверить лимит MCP-клиента на вызов: `sync_timeout_sec` не должен его превышать~~ — проверено в VL-429: лимит MCP-клиента (~60 с) превышался, дедлайн тикета ужат до `min(sync_timeout_sec, MCP_CALL_CAP_SEC=55)` в `askTicketDeadlineSec` (`src/core/interbot/ask.ts`), ответ позле потолка уходит в async-fallback штатно. Per-channel таймаут — в будущие шаги.
3. **Выбор канала — default + явный override (вариант B):** `default_channel` в настройках (по аналогии с выбором персон сабагентом) + явный `channel` как переопределение; при одном канале — автоподхват; при нескольких, без default и без явного канала — ошибка с подсказкой списка каналов. Адресат внутри канала — явный `@username` получателя (`question@OtherBot`); broadcast «кто хочет, тот ответит» — в будущие шаги.
