# Развернуть репозиторий инфраструктуры как проект Vibelog.md

Чеклист для репозиториев `Vibelog-md/ui` и `Vibelog-md/templates` (doc-25 §11). Каждый из них — самостоятельный проект Vibelog.md со своим `backlog/`, потому что инструменты агента ограничены корнем проекта: `resolveInProject`, `ensureTaskWorktree` (worktree только внутри проекта) и `git_commit` (отклоняет `cwd` вне проекта) не позволяют агенту работать с файлами другого репозитория.

Разворачивается один раз на репозиторий, ~10 минут.

---

## 0. Предусловия

- `vibelog` доступен глобально (`which vibelog`), версия ≥ 1.12.
- Репозиторий склонирован локально, `git status` чистый.
- Есть ключ LLM-провайдера (тот же, что в основном проекте).

---

## 1. Инициализация проекта

```bash
cd <путь к репозиторию>
vibelog init
```

Wizard спросит:

| Вопрос | Значение для `ui` | Значение для `templates` |
|---|---|---|
| Имя проекта | `Vibelog UI` | `Vibelog Templates` |
| Префикс задач | `UI` | `TPL` |
| Агенты | `vb` | `vb` |
| Локация секретов | `env` (`.env`) | `env` (`.env`) |

**Префикс обязателен и должен отличаться от `VL`** — иначе задачи двух проектов неразличимы в переписке и коммитах.

Создаётся: `backlog/` (config.yml, tasks/, docs/, lessons/, references/, decisions/, milestones/), `AGENTS.md`, `.env`, `.vibelog/settings.json`.

---

## 2. Модели и провайдеры

`.vibelog/settings.json` нового проекта пуст — без секции `models` агент не запустится. Скопировать из основного проекта секции `providers` и `models` (не `chats`, не `mcpServers` — они машинно-специфичны).

Проверка:

```bash
vibelog model list
vibelog model current
```

Секреты — в `.env` (файл в `.gitignore`):

```
ROUTERAI_API_KEY=<ключ>
```

Проверка, что ключ виден:

```bash
vibelog doctor
```

---

## 3. Порт веб-интерфейса

`default_port` в `backlog/config.yml` по умолчанию `6420`. Если несколько проектов запускаются одновременно — развести порты:

```yaml
# backlog/config.yml
default_port: 6421   # ui
# default_port: 6422 # templates
```

Иначе второй `vibelog browser` упадёт на занятом порту.

---

## 4. Ссылка на контракт (doc-25)

Спецификация живёт **только** в `bobarev/Vibelog.md` — копировать её нельзя, иначе схемы разъедутся. Вместо копии — reference с кэшем:

```bash
vibelog reference add "doc-25: контракт реестра компонентов (v1.3)" \
  --type url \
  --url "https://gitverse.ru/api/repos/bobarev/Vibelog.md/raw/branch/master/backlog/docs/doc-25-vb-CLI-реестр-UI-компонентов-и-шаблоны-проектов-спецификация-v1.md" \
  --tags "contract,doc-25,registry" \
  --cache
```

`--cache` скачивает markdown локально (`backlog/references/cache/`, в `.gitignore`) — агент читает контракт без сети.

**Версия в заголовке обязательна.** Если контракт изменится, в задаче будет видно, от какой версии отталкивались.

## 5. `AGENTS.md` — дополнить под специфику репозитория

`vibelog init` создаёт общий файл. Дописать раздел:

```markdown
## Специфика этого репозитория

Контракт: doc-25 (reference, версия v1.3). Схемы — §3.3 (элемент реестра),
§3.4 (registry.json и структура), §5.1 (HTTP), §5.2 (коды выхода).

Правила:
- Версия элемента — РУЧНАЯ в `registry.json`, формат X.Y.Z. Из git-тега не выводится.
- `public/r/` — сгенерированный артефакт, но КОММИТИТСЯ: GitVerse раздаёт файлы
  из репозитория, а не собирает на лету. После правки `registry.json` или
  исходников — обязательно `npm run build`.
- `target` в элементе — путь относительно `aliases.ui`, без префикса `ui/`.
  Один файл — плоско (`button.svelte`), несколько — каталог (`card/card.svelte`).
- `target: "../utils.ts"` допустим ТОЛЬКО для `registry:lib` (элемент `base`).
- Компоненты — Svelte 5 Runes, только Tailwind, без `<style>`-блоков.
- Изменение контракта вносится в doc-25 в репозитории Vibelog.md, а не здесь.
```

## 6. Первые задачи

Создать задачи по doc-25 §7 (для `ui` — шаги 3, 5, 6, 7; для `templates` — шаг 1). В описании каждой — ссылка на версию контракта.

Порядок для `ui`:

| ID | Задача | Зависит от |
|---|---|---|
| UI-1 | `registry.json` + сборщик `public/r/*.json` + валидация | — |
| UI-2 | элемент `base`: `utils.ts`, `cn`, CSS-переменные | UI-1 |
| UI-3 | `Button` (порт с React-эталона на Runes) | UI-2 |
| UI-4 | `Input` + `Label` | UI-2 |
| UI-5 | `Card` (мультифайловый) | UI-2 |

---

## 7. Проверка, что проект живой

```bash
vibelog task list                 # задачи читаются
vibelog browser --port 6421        # доска открывается
vibelog agent                     # агент стартует, видит модели
```

Затем — одна пробная задача через полный цикл фаз (spec → plan → code → close), чтобы убедиться, что worktree, коммиты и MCP работают в этом репозитории.

---

## 8. Чего НЕ делать

- **Не копировать doc-25** в репозиторий — только reference со ссылкой на версию.
- **Не запускать бота с тем же токеном** в двух проектах одновременно: `vibelog bot` привязан к `cwd`, один токен — один процесс. Для второго проекта либо отдельный токен, либо только браузер.
- **Не переносить задачи** между проектами: ID и префиксы разные, ссылки вида `VL-337` в `ui` не разрешатся.
- **Не менять контракт локально** в `ui`: правка схемы — только в doc-25 основного репозитория, затем обновление reference.

---

## 9. Связь задач между репозиториями

Задачи не могут ссылаться друг на друга напрямую (разные backlog). Вместо этого:

- в описании задачи `ui` — «контракт: doc-25 v1.3, §3.3»;
- в задаче основного репозитория (например, приёмочной) — «требует опубликованного `public/r/base.json` из `Vibelog-md/ui`»;
- при изменении контракта — синхронная задача в затронутом репозитории со ссылкой на новую версию doc-25.
