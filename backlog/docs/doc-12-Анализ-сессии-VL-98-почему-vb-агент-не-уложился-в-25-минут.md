Подробный разбор сессии `agent-1791372983413` (Фаза 3 задачи VL-98, 2026-10-07): хронология, корневые причины неудачи, рекомендации по изменению промптов и кода Vibelog.md.

## 1. Исходные данные

- Задача: **VL-98** «bot: В отчёте Фазы X нужно добавить идентификатор задачи (VL-N) и поправить форматирование ответов ботов» (Priority: Medium). План в задаче — сверхдетальный: номера строк, готовый код, порядок действий, 7 файлов.
- Агент-исполнитель: **встроенный vb** (bot.yml: `default_agent: vb`). Системный промпт сессии — «Ты — Vibelog-agent…» из `src/agent/system-prompt.ts` (VL-96).
- Лимиты (bot.yml): `max_wall_time: 1500` секунд (25 минут); `max_requests` **не задан** — лимита ходов нет; `branch_mode: true`.
- Сессия: `.vibelog/agent-sessions/agent-1791372983413.jsonl`, 92 записи. Старт run 1 — 2026-10-07 14:36:23 (вычислено из ID сессии + время создания worktree), последняя запись файла — 15:36.

## 2. Хронология

### Run 1: 14:36:23 → ~15:01 — убит лимитом wall-time

- ~44 хода модели, ~70 вызовов инструментов, **НОЛЬ правок целевых файлов**.
- Последняя запись (84): частичный текст накопил пять почти одинаковых фраз «Приступаю к реализации…» + ошибка:

```
Превышен лимит --max-wall-time (1500 секунд) — фаза прервана.
```

- Формат ошибки — из `loop.ts` (`runLoop` → `fail` при превышении `maxWallTimeMs`). Механизм `partialText` в loop.ts склеивает промежуточные тексты всех ходов, поэтому в записи видны все пять повторов.

### Run 2: ~15:02 → 15:36 — resume по «Продолжи»

- Запись 85: user-сообщение «Продолжи» (reply бота → `startResume`, `runKey='resume'`).
- 3 хода:
  1. Записал патч-скрипт `.vibelog/tmp/vl98-patch-src.mjs` (10 KB) + запросил документ doc-6 через MCP.
  2. Запустил патч-скрипт — «OK» по 3 файлам: `src/web/orchestrator.ts`, `src/bot/rich.ts`, `src/bot/formatting.ts`.
  3. Запись 91 (последняя): **пустой финальный ответ модели** (content: пустая строка, без tool_calls) → loop.ts: `is_error=false`, exit 0.

### Фактический итог инцидента

- Шаги 4–7 шаблона phase-3 **НЕ выполнены**: отчёт-комментарий не оставлен, статус остался Planned (не Review), modifiedFiles не записаны, сборка/тесты/docs не выполнены.
- Патчи (3 из 7 файлов по плану) лежат в **главном** репозитории нетестируемыми, вперемешку с другим незакоммиченным кодом.
- Worktree vl-98 (ветка `vb/vl-98`) остался чистым на коммите `12297d5` — брошен.
- Общий расход: **~1 час; задача не сдвинулась**.

## 3. Куда ушли 25 минут run 1

| Блок | Ходы | Что происходило |

| Археология | ~12 | Полное чтение задачи VL-97 (19 KB) и close-шаблона (зап. 53–54) — только из-за упоминания «инцидент VL-94, расследование VL-97» в шаге 5 phase-3.md; git log/ветки (33, 65–67) |

Дополнительно контекст залили необрезанные tool-выводы: 34 KB (зап. 47), 25 KB (зап. 39), 31 KB doc-6, 19 KB VL-97, задача 8 KB ×2. В `llm.ts` **нет truncation истории** — каждый ход оценивал ~200+ KB. Ходы модели на растущем контексте идут по 5–15 минут — лимит сработал в точке, где модель стояла на «уточню якоря».

## 4. Побочные инциденты run 2

### 4.1. Resume в главном cwd — бага класса VL-107 для кода

В `src/web/orchestrator.ts` (`spawnQwenRun`): worktree создаётся только при регулярке `^VL-\d+$` на `runKey`; у resume `runKey='resume'` — комментарий в коде прямо говорит «остаются в главном cwd». Write-инструмент агента резолвит пути от cwd → патч-скрипт применил 3 файла **главного** репозитория, а worktree задачи остался нетронут. VL-107 чинил только директорию сессий; для кода дыра воспроизвелась.

### 4.2. Пустой финальный ответ маскируется под успех

В `src/agent/loop.ts` (завершение цикла): `toolCalls.length === 0` → результат = `response.text` → `is_error=false`, exit 0. Пустая строка — валидный результат. Оркестратор получил пустой result и «завершил» фазу молча: уведомление с пустым телом, шаги протокола не выполнены, никакого сигнала об ошибке.

### 4.3. Wall-time не суммируется по цепочке resume

Run 2 получил свежие 1500 с поверх уже потраченных 1500 с. Ограничение на цепочку отсутствует.

## 5. Корневые причины

1. **Промпт не запрещает расточительное исследование.** Ни в `templates/qwen-commands/phase-3.md`, ни в system-prompt vb нет правила «план уже содержит файлы/строки/код — применяй напрямую», бюджета ходов до первой правки, запрета читать задачи-инциденты по упоминаниям.
2. **Контекст не ограничивается.** Ни обрезки tool-выводов, ни truncation истории в `llm.ts`. Каждый лишний мегабайт замедляет ходы и приближает деградацию ответа модели.
3. **Resume — слабое звено цепочки**: неверный cwd (п. 4.1), промпт «Продолжи» без инструкции переориентации («проверь git status/diff, не повторяй исследование»), полная раздутая история, свежий лимит времени.
4. **Пустой результат не считается ошибкой** (п. 4.2) — обрыв фазы маскируется под успех.
5. **Устаревший путь в плане** (`docs/user-guide.md`, переименован VL-106): Фаза 2 не проверяет существование файлов; Фаза 3 не имеет правила «не более 2 ходов на поиск недостающего файла».
6. **Loop detection не ловит verify-loop**: `loop.ts` сравнивает только одинаковые сигнатуры tool-вызовов подряд; пять ходов с РАЗНЫМИ grep, но одинаковым намерением («начать патчить») прошли мимо.

## 6. Рекомендации

### 6.1. Промпты (быстрые, низкорисковые)

**P1. `templates/qwen-commands/phase-*.md` — блок «Экономия ходов»** (касается и qwen-фаз):

```
## Экономия ходов
- Если Implementation Plan содержит файлы, строки и готовый код — применяй
  напрямую; файлы, которые план уже описывает, повторно не читай.
- Упоминания инцидентов в шагах — контекст, а не задание: задачи-инциденты не читай.
- Файл из плана не найден — не более 2 ходов на поиск (grep по заголовку/разделу),
  затем продолжай с найденного.
- Первая правка целевого файла — в первых 5–8 вызовах инструментов.
```

**P2. System-prompt vb (`src/agent/system-prompt.ts`):**

- «Проверка якоря перед патчем — одна команда grep; после — сразу патч. Не перепроверяй якоря на всякий случай». **(правило удалено из `templates/agent-prompt.md` в VL-124: нативные `edit`/`write_file` — основной путь правки, патч-скрипт — только для массовых/многоякорных правок)**
- «При сообщении "Продолжи" после прерывания **НЕ повторяй исследование**: `git status` и `git diff` рабочего каталога показывают, что уже сделано; продолжай со следующего шага».
- Предупреждение про BSD: «`sed` на macOS — BSD-версия: GNU-диапазоны вида `N,+Mp` не работают; используй `node -e` или `grep -A/-B`».

**P3. Шаблон Фазы 2 (plan):** «перед записью плана проверь существование каждого файла одной командой `ls`».

### 6.2. Код (по убыванию выгоды)

| # | Файл | Суть |
|---|---|---|
| C1 | `src/agent/tools.ts` | **Truncation tool-выводов** до ~8 KB с маркером «обрезано» (`run_shell_command`, `grep_search`, `read_file`). Главный рычаг: 34/25/31 KB-выводы — прямая причина замедления и деградации |
| C2 | `src/agent/loop.ts` | **Guard пустого результата**: финальный текст пуст/whitespace → `fail("Пустой ответ модели")` → `is_error=true` — оркестратор сообщит о провале |

| C4 | `src/web/orchestrator.ts` | **Wall-time по цепочке resume**: бюджет `max_wall_time × (N resume + 1)` с потолком (напр. 2×) |
| C5 | `src/agent/loop.ts` | **Loop detection по намерению**: N ходов подряд с почти идентичным промежуточным текстом (паттерн зап. 70–84) → fail с понятным сообщением |
| C6 | `.vibelog/bot.yml` | Задать `max_requests` (напр. 60) — сейчас у vb он не ограничен, срезает ранние лупы дешевле wall-time |
| C7 | `src/web/orchestrator.ts` | Уборка брошенных worktrees после завершения/прерывания фазы (vl-98, vl-108 висят) |

### 6.3. Политика (решение владельца)

У vb **есть** нативные `read_file` / `write_file` / `edit` (`src/agent/tools.ts`), но политика патч-скриптов (документ `backlog/docs/doc-2` — **устарел, см. VL-124**; решение 2026-11-02: нативные `edit`/`write_file` — основной путь) заставляла идти путь «grep якорей → 10 KB .mjs-скрипт → запуск» = 3+ хода на файл против 1 вызова `edit`. Варианты: разрешить vb нативный `edit` для точечных правок (патч-скрипты оставить для массовых), либо явно зафиксировать политику — тогда C1 и P2 становятся ещё важнее. Решение принято в VL-124: вариант (а) — нативный `edit` для точечных правок, патч-скрипты только для массовых/многоякорных/многофайловых правок.

### 6.4. Текущее состояние VL-98 (требует решения)

В main repo лежат нетестируемые частичные патчи (3 файла, без тестов/docs), worktree `vb/vl-98` чист. Предлагаемый порядок: откатить патчи в main (`git checkout --` по трём файлам), затем либо довести Фазу 3 вручную по плану, либо перезапустить после применения P1/P2/C2.
