# GitVerse Issues как транспорт баг-репортов: итоги расследования и условия возврата

Дополняет doc-28 (описание реализованного API-клиента) — здесь именно **история и состояние**.

## 3. Почему GitVerse Issues не заработал

### 3.1. Симптомы, собранные вручную

Проверялось на `bobarev/Vibelog.md` с токеном, у которого выданы права: Пакеты — Чтение, Репозитории — Запись, Пользователи — Чтение, Организации — Чтение, Задачи — Запись.

| Запрос | Результат |
|---|---|
| `GET /repos/bobarev/Vibelog.md` | `200`, `permissions: {pull: true, push: true, admin: true}`, `role_name: "admin"` |
| `GET /repos/bobarev/Vibelog.md/labels?limit=100` | `200` — метки читаются |
| `GET /repos/bobarev/Vibelog.md/issues` **без токена** | `401 UNAUTHORIZED: Authorization is required` |
| `GET /repos/bobarev/Vibelog.md/issues` с токеном | **`403`** |
| `POST /repos/bobarev/Vibelog.md/issues` (тело `{"title":"Тест"}`) | **`403`** |
| `POST .../issues` с `{"title":"Тест","type":"bug"}` | **`403`** |
| `GET /issues` с `Accept: ...version=latest` | **`403`** |

### 3.2. Что это доказывает

- `401` без токена → эндпоинт **существует** и требует авторизации (не 404).
- `403` с токеном → токен **принят** (иначе снова был бы `401`), но доступ закрыт гейтом.
- `GET /labels` из **того же раздела документации** (`pull-and-issues_2`) работает → дело не в правах репозитория и не в токене.
- Права `admin` + `permissions.push: true` → дело не в ролевой модели репозитория.
- Смена `Accept` на `latest` не помогает → версия заголовка ни при чём.

**Вывод: доступ к системе «Задачи 2.0» не выдан аккаунту.** Это внешняя блокировка, со стороны кода исправить нечего.

### 3.3. Что пробовали безрезультатно

- Другие версии `Accept` (`version=1`, `version=latest`).
- `POST /issues` с `type` и без `type` — оба `403` (гипотеза «тип `bug` недоступен в организации» отвергнута).
- Поиск в текущей документации старого (до 2.0) набора путей — раздел `pull-and-issues_2` единственный, старых путей в справочнике нет.

### 3.4. Побочная находка: баг в нашем коде

Первый ручной прогон упал раньше API-гейта — с `400 VALIDATION_ERROR` на `/labels?per_page=100`. Причина: `GET /labels` принимает **`limit`**, а `GET /issues` — **`per_page`**. Исправлено в VL-367, там же фикстура научена отвергать неизвестные query-параметры (раньше принимала любые, поэтому расхождение с реальным API не ловилось тестами).

**Урок:** фикстура, принимающая любой запрос, проверяет только наш код, но не контракт API.

## 4. Условия возврата к GitVerse

Вернуться имеет смысл, когда выполнено **любое** из условий:

1. **GitVerse выдал доступ к «Задачи 2.0»** (главное). Проверка одной командой — см. 4.1.
2. GitVerse открыл старый (до 2.0) набор issues-эндпоинтов.
3. Появилась возможность создавать задачи через другой API (например, публичный REST без гейта).

### 4.1. Как проверить одной командой

```bash
TOKEN=$(grep -E '^GITVERSE_TOKEN=' .env | cut -d= -f2- | tr -d '\r')

curl -s -w "\nstatus: %{http_code}\n" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Accept: application/vnd.gitverse.object+json;version=1" \
  "https://api.gitverse.ru/repos/bobarev/Vibelog.md/issues?per_page=10"
```

| Результат | Значит |
|---|---|
| `200` + массив | **Доступ появился** — возвращаемся к VL-363, переключаем `upstream.mode` на `api` |
| `403` | Доступа всё ещё нет — остаёмся на git-транспорте |
| `401` | Токен протух/удалён — пересоздать на https://gitverse.ru/settings/tokens |

### 4.2. Что сделать при возврате

1. Прогнать проверку из 4.1 (все три варианта: `GET /issues`, `POST /issues` с минимальным телом).
2. Если `200`/`201` — выставить в `.vibelog/settings.json` `upstream.mode: "api"`, оставив `inbox` как запасной путь.
3. Ручной прогон `vibelog upstream report --title "..." --body "..."` — должен создать issue.
4. Проверить две вещи, которые нельзя было проверить без доступа:
   - **закрытие issue** — `PATCH /issues/{n}` с `{project_id, project_status_id}` колонки «Done» (поле `state` для задач игнорируется, см. ref-28); требует `project_id`/`done_column` в конфиге;
   - **ack** — `POST /issues/{n}/comments` с номером задачи Vibelog.
5. Дописать вторую половину (импорт + ack + закрытие) — она ещё не сделана.

## 5. Что осталось доделать по GitVerse-пути

Даже при появлении доступа остаются незакрытые пункты:

- [ ] **Импорт** — чтение входящих issues (`GET /issues?labels=upstream&state=open`) → дедуп по номеру в локальном журнале → создание задачи Vibelog.
- [ ] **Ack** — `POST /issues/{n}/comments` «принято как VL-N» + сохранение соответствия issue↔задача.
- [ ] **Закрытие** — `PATCH /issues/{n}` с `project_id` + `project_status_id` колонки «Done». Требует резолвера id колонки: `GET /projects` → `GET /projects/{id}` → поиск по имени (`upstream.done_column`, дефолт `"Done"`), с кэшем в настройках.
- [ ] **Тест на реальном API** — все текущие тесты идут на локальной `node:http`-фикстуре; против настоящего GitVerse клиент проверялся только вручную и упал на гейте.
- [ ] **`project_id`/`done_column`** — поля в конфиге читаются и валидируются, но нигде не используются (нечем было проверить).

## 6. Нерешённые вопросы (не забыть)

1. **Формат имени задачи.** `buildIssueBody` собирает секции «Что произошло / Воспроизведение / Окружение / Источник». При импорте нужно разобрать их обратно — парсер не написан.
2. **Дедуп между двумя транспортами.** Если отчёт ушёл в git-инбокс, а потом тот же баг попадёт в issues — как не создать две задачи? Сейчас `report_id` (sha1) есть только в git-схеме; для issues аналога нет.
3. **Токен в дочерних проектах.** Если репортить напрямую в чужой репозиторий, токен с правом записи лежит в каждом дочернем проекте. Безопаснее репортить в свой — это решается полем `upstream.repo`.
4. **Права внешних репортеров.** Для внешних людей путь остаётся ручным (fork + PR): PR-API GitVerse — тот же закрытый раздел «Задачи 2.0», автоматизировать создание PR нельзя.
