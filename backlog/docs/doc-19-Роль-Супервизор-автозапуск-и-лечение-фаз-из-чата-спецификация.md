# Роль «Супервизор»: автозапуск и лечение фаз из чата

Спецификация. Код по этому документу написан (VL-268, VL-269, VL-270); расхождения реализации с текстом ниже сведены в §22.

- **VL-268** — MCP-инструменты и grant-механизм;
- **VL-269** — лимиты чата в конфиг (общий механизм, от которого зависит супервизор);
- **VL-270** — тик, healing, планировщик параллельности, промпт роли;
- **VL-274** — idle-watchdog фаз (§8).

---

## 1. Назначение и терминология

**Супервизор** — роль веб-чата, которая заменяет человека на заранее заданном массиве задач: сама решает, что запустить сейчас, что параллельно, а что последовательно; распознаёт зацикливание и падения фаз, лечит их и, если не получается, заводит баг-задачу.

Терминология (важно, чтобы не путаться):

| Термин | Значение | Где |
|---|---|---|
| **Супервизор** | роль чата, тик-цикл наблюдения и лечения | подпись в UI, персона `supervisor` в `chat_personas` |
| `supervisor` | идентификатор роли, каталог данных, имена модулей | код и конфиги |
| **оркестратор** | существующий модуль запуска одной фазы | `src/web/orchestrator.ts` — **не переименовывается**, к роли не относится |
| **фаза** | run агента (`spec`, `plan`, `code`, `close`, `comment`, `analyze`, …) | `startPhase` |
| **прогон** | один ночной запуск супервизора по набору задач | grant, `state.json` |

Существующий `src/web/orchestrator.ts` — это исполнитель **одной** фазы (спавн процесса, ожидание, `PhaseRun`). Супервизор над ним надстраивается: решает, какие фазы и в каком порядке запускать, и что делать, когда фаза упала.

## 2. Зачем и чем отличается от auto-runner

Философия, сформулированная пользователем:

> «Allow All подразумевается. Он очень похож на auto-runner, запускает точно так же фазы, но в отличие от него должен сделать анализ, например при остановке на луп — написать комментарий фазе, чтобы она продолжила выполнение, выйдя из лупа, как это я сейчас делаю вручную. В общем замена человека на заранее определённом массиве задач.»

Отличие по существу:

| | `auto-runner` (есть) | Супервизор (новое) |
|---|---|---|
| Выбор задач | только из `.vibelog/auto-queue.json` | набор согласуется в чате, фиксируется в grant |
| Повтор при падении | слепой счётчик `attempts > max_retries` | сначала **диагностика** (`fail_reason`, `repeat_stats`, `logTail`), потом решение |
| Лечение зацикливания | нет | директива-комментарий фазе + рестарт |
| Параллельность | строго последовательно | группы параллельных фаз до лимита |
| Итог | `failed_permanent` + уведомление | повтор / лечение / авто-баг / стоп с отчётом |

Супервизор **не заменяет** `auto-runner` и не трогает `.vibelog/auto-queue.json` — это разные сущности: очередь отвечает «что прогонять», супервизор — «что происходит и почему».

## 4. Чего нет (разрыв)

1. **Нет MCP-инструментов запуска фаз.** `trigger` существует только как HTTP-роут; в чате модель физически не может запустить фазу.
2. Нет управления очередью из чата (в боте — команды `/auto add|start|stop|status`).
3. Нет лимита одновременно работающих фаз.
4. Нет механизма доверия на прогон (сейчас любая write-операция требует Allow/Deny).
5. Нет тик-механизма: кто-то должен периодически «будить» супервизора.
6. `activeRuns` живёт в памяти процесса: рестарт теряет знание о том, что фаза идёт.
7. Нет собственных лимитов у чат-роли — жёстко зашиты константы.

## 5. Архитектура: тик-модель (по референсу ref-10, hermes-agent)

Изучен клон `backlog/references/data/hermes-agent/`. Там многоагентная оркестрация сделана не долгоживущим процессом, а **cron-задачей**, которая периодически будит агента с промптом. Заимствуем схему:

| Механизм hermes | Где | Что берём |
|---|---|---|
| `script` — pre-run сборщик данных, stdout инжектится в промпт | `cron/scheduler.py`, `scheduler_script.py` | `heartbeat.md`: срез состояния фаз, инжектится в промпт тика |
| `context_from` — вывод предыдущего job'а в промпт следующего | `cron/scheduler_prompt.py` | «что я решил в прошлом тике и почему» |
| `notepad` — durable KV, 16 КБ на значение / 64 КБ на job | `cron/notepad.py` | курсоры и watermark'и в `state.json` |
| `_parse_wake_gate` — `{"wakeAgent": false}` → модель не вызывается | `cron/scheduler_prompt.py` | пустой тик бесплатен: ничего не изменилось — модель не зовём |
| `workdir` — загрузка `AGENTS.md` из каталога | `cron/jobs.py` | контекст проекта в промпте тика |
| inactivity watchdog — таймаут по простою, не по wall-clock | `cron/AGENTS.md` | см. §8 (реализовано в VL-274) |

**Итоговая схема работы:**

```
каждые tick_seconds (60) в процессе vibelog browser:
  1. собрать состояние   ← фазы, статусы, exitCode, fail_reason, repeat_stats
  2. записать heartbeat.md + state.json
  3. wake gate: изменилось ли что-то?  — нет → тик закончен без вызова модели
  4. вызвать модель с промптом (heartbeat + правила + grant)
  5. применить решение: запустить фазы / полечить / создать баг / ждать
```

Тик **не хранит состояния в памяти** — всё на диске. Поэтому рестарт процесса не ломает прогон: следующий тик читает файлы и продолжает.

**Кто крутит тик:** процесс `vibelog browser` (как `auto-runner` живёт в процессе бота). Отдельный демон и клиентский таймер отвергнуты. Таймер (`setInterval(...).unref()`, guard-флаг против наложения тиков) заводится **только при действующем grant'е** — без прогона наблюдать нечего; дополнительно глушится `VIBELOG_SUPERVISOR_TICK=off`. Снимается на `server.close`/`server.on('error')`.

**Момент подъёма и гашения таймера (уточнено в VL-272).** Таймер поднимается в двух точках: при старте `vibelog browser`, если grant уже лежит на диске (`src/web/server.ts`), и **в момент выдачи grant'а** — `startSupervisorRun` (`src/web/supervisor.ts`) вызывает `startSupervisorTimer` сразу после записи grant'а и запуска первой волны фаз. Вторая точка обязательна: сервер обычно уже работает, когда пользователь подтверждает состав, и без неё прогон оставался без планирования следующих волн, лечения и авто-багов до перезапуска процесса. Повторный вызов идемпотентен (второй интервал не создаётся), а ошибка подъёма таймера не отменяет уже запущенный прогон — пишется в лог.

Гасится таймер на `stop` прогона (`stopSupervisorRun`), при авто-отзыве grant'а (все задачи прогона в терминальном статусе — `supervisorRunStatus`), при неуспешном старте (grant отозван с причиной «ни одна фаза не запустилась») и на `server.close`/`server.on('error')`; в этих точках хелпер сначала проверяет, что активных прогонов не осталось, — таймер соседнего прогона не снимается. Истечение `expiresAt` замечает сам тик: получив `skipped='no-grant'`, интервал останавливается (иначе он молотил бы до конца процесса), а новый grant поднимает таймер заново через `startSupervisorRun`.

### Контракт решения модели (уточнено в VL-270)

Тик **не запускает LLM-tool-loop**: модель не вызывает инструменты сама. Код собирает состояние, отдаёт модели heartbeat-промпт и ждёт **один JSON-объект решения**:

```json
{
  "action": "run" | "heal" | "bug" | "stop" | "wait",
  "tasks": ["VL-263", "VL-264"],
  "groups": [["VL-263"], ["VL-264"]],
  "rationale": "обоснование групп (обязательно в conservative)",
  "diagnosis": "разбор содержательной ошибки (уровень 2)",
  "comment": "комментарий-директива фазе при heal",
  "tuning": { "heal_rules": [...] }
}
```

Применяет решение — код (`startTaskPhase`, создание баг-задачи, патч правил), а не модель. Причины: (а) детерминизм и тестируемость без реальной модели; (б) фазы выбирает workflow, значит у модели нет «ручки» фазы; (в) лимиты VL-269 относятся к ходу чата, а не к тику.

Парсинг **терпимый**: сначала fenced ```json-блок, затем первый balanced-объект. Не распарсили или схема невалидна → детерминированный фолбэк «последовательный запуск готовых задач по приоритету», в heartbeat пишется причина (`decision: fallback`). Тик никогда не падает из-за ответа модели. Фаза `analyze` в решении отбрасывается: для лечения не используется (см. §12).

## 6. Исправление фактов о лимитах

В ходе обсуждения я допустил ошибку, которую важно зафиксировать, чтобы она не переехала в реализацию:

- **Все фазы агента ограничены одинаково:** `MAX_WALL_TIME_MS_DEFAULT = 900_000` (`src/agent/loop.ts:213`), а также `--max-wall-time` и `--max-requests` из `.vibelog/settings.json`, которые оркестратор прокидывает для `vb` (в этом проекте `2400` с и `80` запросов). Утверждение «фаза close может длиться сколько угодно» **неверно** — у close те же лимиты, что у code.
- Поэтому архитектурное обоснование строится не на «долгом close», а на **несопоставимости масштабов**: запрос чата жёстко ограничен `MAX_LLM_ITERATIONS = 8` и `MAX_WALL_TIME_MS = 120_000` (`src/web/chat.ts:66`), тогда как одна фаза идёт до 40 минут. Держать цикл наблюдения внутри диалога нельзя.

## 7. Лимиты роли

Сейчас все лимиты чата — константы в `src/web/chat.ts:66`. Для супервизора нужны свои значения и возможность менять их без пересборки.

Секция `supervisor` в `.vibelog/settings.json` (пользовательская, модель не пишет):

```json
{
  "supervisor": {
    "tick_seconds": 60,
    "max_parallel_phases": 3,
    "heal_attempts": 2,
    "allow_self_tuning": false,
    "parallel_mode": "conservative",
    "limits": {
      "chat_max_iterations": 30,
      "chat_max_wall_time": 600
    }
  }
}
```

| Параметр | Дефолт | Смысл |
|---|---|---|
| `tick_seconds` | 60 | период пробуждения |
| `max_parallel_phases` | 3 | сколько фаз одновременно |
| `heal_attempts` | 2 | лечебных попыток на фазу (итого максимум 3 запуска) |
| `allow_self_tuning` | `false` | разрешено ли модели править правила лечения |
| `parallel_mode` | `conservative` | режим группировки (§14) |
| `chat_max_iterations` | 30 (у прочих ролей 8) | итераций инструментов за ход |
| `chat_max_wall_time` | 600 с (у прочих 120) | потолок времени на ход |

Остальные роли наследуют текущее поведение (8 / 120) — их значения не меняются. Общий механизм лимитов в конфиге даёт задача **VL-269**, значения для роли — **VL-270**.

Чтение и валидация секции — `resolveSupervisorRuntime` (`src/core/supervisor-config.ts`): диапазоны `tick_seconds` 5…3600, `max_parallel_phases` 1…8, `heal_attempts` 0…10, `chat_max_iterations` 1…200, `chat_max_wall_time` 1…86400. Битое значение откатывается к дефолту с текстом в `errors`, секция не роняет тик.

## 8. Idle-watchdog для фаз (заимствование из hermes)

Проблема, известная по VL-254: фаза сгорает на `--max-wall-time`, хотя работала — её обрывает общий таймер, а не признак зависания.

Решение из hermes: таймаут считается по **простою** — если N секунд не было активности (нет новых токенов, нет tool-вызовов), сессия считается зависшей и прерывается; длинная-но-активная не обрывается никогда.

Требование к реализации: для фаз агента ввести `idle_timeout_seconds` (дефолт 600, `0` — выключено) наряду с существующим wall-time. Wall-time остаётся жёстким потолком безопасности, но перестаёт быть первым, что срабатывает.

### Реализация (VL-274)

Реализовано отдельной задачей **VL-274** (в VL-270 было вне скоупа). Ключевые решения:

| Решение | Где |
|---|---|
| Модуль `createIdleGuard({ timeoutMs, now?, externalSignal? })` — чистый, без fs/LLM: `signal`, `noteActivity()`, `pause()`, `resume()`, `timedOut()`, `idleMs()`, `dispose()` | `src/agent/idle-guard.ts` |
| **Комбинированный сигнал** (внешний `options.signal` ИЛИ idle-abort) — свой `AbortController` + `addEventListener('abort')`, без `AbortSignal.any` (требует Node 20.3+, в `engines` заявлен `>=20`) | там же |
| Активность: каждый токен стрима (обёртка `onToken` → `noteActivity()`) и каждый завершённый tool-вызов (`resume()` после хендлера) | `src/agent/loop.ts` |
| **Таймер снимается на время tool-вызова** (`pause()` перед `spec.handler`, `resume()` после) — осознанное отклонение от «голого» hermes-watchdog: он сторожит тишину LLM-стрима, а не длительность инструмента (`pnpm test` на Catalina идёт 20+ минут молча). Зависший инструмент ловят его собственные таймауты (`bashTimeoutMs` + `remainingWallTimeMs` у `run_shell_command`, таймаут запроса у MCP-клиента) и жёсткий wall-time | `src/agent/loop.ts` |
| Две точки детекта: реальный таймер (абортит `streamChat` и не оставляет висящий HTTP-запрос) и проверка в начале итерации рядом с wall-time (`timedOut() \|\| idleMs() > timeout`) — вторая делает тесты детерминированными через инъекцию `now` | `src/agent/loop.ts` |
| Отдельный `reason: 'idle'` в `RunProgressReason` (не путается с `wall-time`/`max-requests`), подпись «по idle-таймауту (простой без активности)» | `src/agent/run-progress.ts` |
| Флаг `--idle-timeout <сек>` (неотрицательное целое, `0` допустим); оркестратор прокидывает его только агенту `vb` рядом с `--max-wall-time`/`--max-requests` | `src/agent/cli.ts`, `src/web/orchestrator.ts` |
| CLI-флаг, `/set idle-timeout <сек>`, секция `idle_timeout_seconds` в `.vibelog/settings.json` (отсутствие ключа → дефолт агента 600; явный `0` → выключено; битое значение → предупреждение `[vibelog-settings]` и откат к дефолту) | `src/bot/settings.ts`, `src/bot/commands.ts`, `src/web/api.ts` |
| Fail-текст: `Превышен idle-таймаут (N секунд без активности) — фаза прервана.` | `idleTimeoutText` (`src/agent/loop.ts`) |

**Семантика `0` отличается от прочих числовых настроек:** у `max-wall-time`/`max-requests` значение `0` в `/set` — сброс к дефолту, у `idle-timeout` `0` = **выключить watchdog** (как `HERMES_CRON_TIMEOUT=0` в референсе); сброс к дефолту — удалением ключа (в веб-API `null`). Задокументировано в README и в подсказке `/set`.

**Тесты:** `src/agent/idle-guard.test.mjs` (перевзвод на `noteActivity`, срабатывание по тишине, `pause()`/`resume()`, `timeoutMs=0`, внешний сигнал, `dispose()`), `src/agent/loop.test.mjs` (обрыв по простою с `reason='idle'`, реальный abort стрима через `signal`, выключение при `idleTimeoutMs: 0`, приоритет idle над wall-time, AC7-сценарий VL-254: 35 виртуальных минут с активностью каждые 5 минут завершаются нормально, долгий tool на паузе не ловится), `src/web/orchestrator.test.mjs` (флаг только для `vb`), `src/agent/cli.test.mjs`, `src/bot/settings.test.mjs`, `src/bot/commands.test.mjs`, `src/agent/run-progress.test.mjs`.

## 9. Раскладка файлов

Каталог данных:

```
.vibelog/supervisor/
├── settings.json     — правила лечения (heal_rules, comment_template) — модель может править
├── tuning.log        — история самонастроек: когда, что, почему
├── state.json        — машинное состояние прогона (после каждого тика)
├── heartbeat.md      — человекочитаемый срез, инжектится в промпт тика
└── grants/
    └── <runId>.json  — доверие на конкретный прогон
```

Незыблемые настройки — в основном `.vibelog/settings.json` (секция `supervisor` из §7). Причина разделения: модели можно доверить правку правил лечения, но не лимитов.

Модули кода:

| Файл | Ответственность |
|---|---|
| `src/core/supervisor-config.ts` | чтение и валидация конфига (`resolveSupervisorRuntime`), `heal_rules`, самонастройка (`applySelfTuning`, `tuning.log`) |
| `src/core/supervisor-state.ts` | `state.json`, `heartbeat.md`, живость фазы по `pid`+`phaseRunId`, `snapshotKey`, сбор наблюдений (`collectTaskObservation`) |
| `src/web/supervisor-tick.ts` | тик, wake gate, промпт и парсинг решения, healing L1/L2, планировщик параллельности (`planParallel`), авто-баг, таймер |

Дополнительные поля реализации (уточнено в VL-270):

| Поле | Смысл |
|---|---|
| `snapshotHash` | FNV-1a-хеш «изменилось ли» — основа wake gate; сравнение с ключом текущего тика |
| `tuning` | число применённых самонастроек и последняя из них (строкой) |
| `tasks[].statusAtStart` | статус задачи на момент старта фазы: по нему тик отличает «фаза упала» от «статус сменился, фаза успешна» |
| `tasks[].ruleChain` | цепочка сработавших правил лечения — уходит в описание авто-бага |
| `tasks[].frozen` | задача снята с прогона (действие `stop`) |
| `wakeAt` | время следующего пробуждения (для часовых тиков «прогон жив») |

Живость фазы определяется по `pid` + `phaseRunId`: при тике проверяется `process.kill(pid, 0)` (ESRCH → мёртв, EPERM → жив). Это компенсирует то, что `activeRuns` живёт в памяти и теряется при рестарте (`src/web/orchestrator.ts` — известное ограничение). Если state говорит `running`, а pid мёртв, сверяется статус задачи: сменился на ожидаемый `getStatusAfterPhase(...)` → фаза успешна (`done`), иначе `failed` + `lastError` и в лечение. Запись `state.json` **атомарна** (temp-файл в том же каталоге + `renameSync`).

### `heartbeat.md`

Человекочитаемый срез; он же инжектится в промпт тика (с усечением по бюджету промпта). Содержит:

- состояние прогона: идёт/остановлен, сколько тиков, grant до какого времени;
- таблицу задач: id, фаза, статус, попытки, группа;
- что решено в прошлом тике и почему;
- при `conservative` — **обоснование каждой параллельной группы** (§14);
- последние ошибки с фрагментом `logTail`;
- предупреждения невалидных `heal_rules` и записи самонастройки.

Heartbeat перезаписывается **каждый тик**, в том числе тогда, когда модель не вызывалась (wake gate закрыт): «прогон жив» видно утром.

## 11. Новые MCP-инструменты

Все четыре — «write» по природе (меняют состояние), но в рамках grant выполняются без Allow/Deny (§15).

### `backlog_trigger_phase`

Запускает фазу задачи. Аналог `POST /api/tasks/:id/trigger`, но из чата.

| Параметр | Обяз. | Смысл |
|---|---|---|
| `id` | да | ID задачи |
| `phase` | нет | имя фазы; если не указана — первая доступная по workflow из текущего статуса |
| `comment` | нет | комментарий к запуску (как `/plan VL-1 текст`) |
| `sameSession` | нет | продолжить plan-сессию (VL-147) |

Ошибки: задача не найдена; фаза не разрешена из текущего статуса (`isPhaseAllowed`); фаза уже идёт у этой задачи; превышен `max_parallel_phases`; задача вне grant.

### `backlog_phase_status`

Читает состояние запуска. Аналог `GET /api/tasks/:id/trigger` плюс диагностика.

| Параметр | Обяз. | Смысл |
|---|---|---|
| `id` | да | ID задачи |

Возвращает: `running`, `phase`, `pid`, `exitCode`, `logTail`, `result`, `repeat_stats`, `last_run.is_error`.

### `backlog_auto_queue`

Управление очередью (аналог `/auto`). Операции: `add` (ids), `start`, `stop`, `status`.

| Параметр | Обяз. | Смысл |
|---|---|---|
| `action` | да | `add` \| `start` \| `stop` \| `status` |
| `ids` | для `add` | список ID задач |

### `backlog_supervisor`

Управление прогоном супервизора.

| Параметр | Обяз. | Смысл |
|---|---|---|
| `action` | да | `plan` \| `start` \| `stop` \| `status` |
| `ids` | для `plan`/`start` | набор задач прогона |
| `expiresInHours` | нет | TTL grant (дефолт 8) |
| `expiresAt` | нет | явное время окончания grant |

`plan` — сухой прогон: показать, что запустится, в каком порядке, с обоснованием групп, без запуска. `start` — требует grant.

**`backlog_finish_phase` остаётся запрещённым** в чате (список `CHAT_DISALLOWED_TOOLS`, `src/web/tool-policy.ts`). Причина: иначе супервизор сможет подделывать прогресс — объявлять фазу завершённой, не выполнив работу. Завершение фазы остаётся прерогативой самой фазы.

## 12. Healing loop

Два уровня. Первый — правила без вызова модели, второй — решение модели внутри тика.

### Уровень 1: декларативные правила (без LLM)

Правила лежат в `.vibelog/supervisor/settings.json`:

```json
{
  "heal_rules": [
    {
      "id": "repeat-loop",
      "when": { "repeat_share_min": 0.25, "repeat_calls_min": 8 },
      "action": "comment_and_retry",
      "comment_template": "Ты повторно обращался к тем же путям: {top_repeats}. Используй ранее полученный результат; следующий шаг — правка, а не чтение."
    },
    {
      "id": "payload-limit",
      "when": { "fail_reason_contains": ["payload", "max-payload"] },
      "action": "retry"
    },
    {
      "id": "wall-timeout",
      "when": { "fail_reason_contains": ["max-wall-time", "таймаут", "timeout"] },
      "action": "retry"
    },
    {
      "id": "no-progress",
      "when": { "status_unchanged": true },
      "action": "retry_once_then_bug"
    }
  ],
  "default_action": "bug"
}
```

Свойства:

- правила **упорядочены**, выигрывает первое совпавшее; `id` сработавшего правила попадает в `state.json` и в отчёт;
- `action` — закрытый набор: `retry`, `comment_and_retry`, `retry_once_then_bug`, `bug`, `stop`;
- `when` — хотя бы один известный ключ; `repeat_share_min` (0…1) и `repeat_calls_min` (целое ≥1) должны выполниться **оба** (AND), `fail_reason_contains` — любое из значений (OR) по `lastError` в нижнем регистре, `status_unchanged` — фаза завершилась успешно, но статус задачи не сменился;
- `comment_template` поддерживает подстановки `{top_repeats}`, `{fail_reason}`, `{task_id}`, `{attempt}` (как в шаблонах фаз); для `comment_and_retry` обязателен;
- битое правило не роняет тик — выпадает с предупреждением (паттерн `loadWorkflows` в `src/core/workflow.ts`), валидные продолжают работать; файла нет — действуют дефолтные правила из кода;
- при отсутствии совпавшего правила применяется `default_action`.

Дерево решения:

```
фаза упала
├─ сработало правило heal_rules → действие правила
├─ повторяемый инструмент (repeat_share высокий) →
│     директива «что перечитывал» → фаза comment → рестарт
├─ транзиентная ошибка (payload / таймаут / лимит провайдера) → рестарт
├─ содержательная (тесты падают, статус не сменился) → один повтор, затем баг
└─ healAttempts исчерпан → стоп и отчёт в чат
```

Директива уходит фазе через `startTaskPhase(cwd, id, 'comment', { comment })` — так текст попадает и в задачу, и в промпт следующего рана.

### Уровень 2: модель в тике

Содержательные разборы (упавшие тесты, ошибочный план) делает сама модель тика — у неё уже есть `logTail`, `repeat_stats`, `fail_reason`. Отдельная фаза `analyze` для лечения **не используется**: по шаблону `templates/phases/phase-analyze.md` она read-only и только рекомендует. Если модель вернула `analyze` в решении, ход отбрасывается с записью в heartbeat.

## 13. Авто-создание баг-задачи

Когда лечение исчерпано (`healAttempts >= heal_attempts`) или правило дало `bug`, супервизор создаёт задачу **автоматически, в статусе Spec**, без подтверждения.

Содержимое формируется детерминированно:

- `title`: `[авто] <фаза> <taskId>: <краткая причина>`;
- `description`: `fail_reason` + фрагмент `logTail` (последние строки, ≤20) + ID сессии агента (со ссылкой на `.vibelog/agent-sessions/<id>.jsonl`) + цепочка попыток (какие правила срабатывали, в каком порядке);
- связь с исходной задачей: `dependencies` или явное упоминание в описании; реализация выбрала **упоминание** — зависимость от незавершённой задачи сделала бы баг-заблокированным и `isReady` не пустил бы его в работу;
- метки: `auto-bug`, имя фазы;
- дедуп: если по этой же цепочке правил для задачи уже открыт авто-баг, новый не создаётся.

## 14. Параллельность

### Фазы выбирает workflow, а не супервизор

Супервизор **не назначает фазы сам** и не строит свою последовательность. Источник истины — workflow задачи (`src/core/workflow.ts`):

```
getWorkflowForTask(cwd, task)  → воркфлоу по типу задачи (task_workflows)
getAvailablePhases(wf, status) → список допустимых фаз из текущего статуса
isPhaseAllowed(...)            → проверка перед запуском
```

Из этого следуют важные свойства, которые супервизор обязан уважать:

- **Порядок фаз задан переходами** `status → phase → produces_status`. Супервизор только выбирает, когда запустить следующую допустимую фазу, но не может переставить или пропустить шаг.
- **Создание worktree — свойство workflow, а не решение супервизора.** Изоляция (ветка `vb/vl-N`, каталог worktree) появляется на первой «кодовой» фазе воркфлоу: `plan` в дефолтном, `do` в simple (`src/web/orchestrator.ts:818`). Если в воркфлоу такой фазы нет (`epic`, воркфлоу без plan/do) — задача идёт в главном дереве, и это нормальное поведение воркфлоу, а не ошибка.
- **Ветвление (reject, fix-цикл `Review → code`)** — часть воркфлоу. Супервизор берёт первую НЕ-reject фазу как основную (как `auto-runner`, см. `pickAutoPhase`), reject — только вручную.
- **Разные типы задач идут по разным воркфлоу** (`investigation`, `bugfix`, `simple`, …), поэтому «одна и та же» по счёту фаза у двух задач может быть разной. Планировать прогон «по фазам» нельзя — только «по задачам, у каждой своя следующая фаза».
- **Невалидный или отсутствующий воркфлоу** → `DEFAULT_WORKFLOW` (fallback в `loadWorkflows`), супервизор не падает.

Практическое следствие для параллельности: две задачи в одной группе могут находиться на **разных** фазах и даже иметь разное число шагов до `close`. Лимит `max_parallel_phases` считается по числу одновременно работающих фаз, а не по числу задач.

### Почему не по `modified_files`

`modified_files` заполняется только фазой `code`, а worktree создаётся на `plan`/`do` (`src/web/orchestrator.ts:818`). Значит на момент принятия решения «можно ли запустить две задачи одновременно» этого поля ещё нет. Критерий строится по **метаданным задачи**: `title`, `description`, `labels`, `type`, `dependencies`.

### Режимы

**`conservative`** (дефолт) — модель обязана обосновать каждую параллельную группу: «эти задачи не пересекаются, потому что одна про бота (`labels: bot`), другая про веб (`labels: web`), общих модулей в описаниях нет». Не может обосновать — запускает последовательно. **Обоснование пишется в `heartbeat.md`**, чтобы утром было видно, почему сгруппировано именно так.

**`aggressive`** — параллель до `max_parallel_phases` без обоснования; конфликты разбираются после (git покажет, `closeQueue` не даст сломать merge).

### Жёсткие правила

- **`dependencies` / `blocks` — запрет параллели** в любом режиме: если задача A зависима от задачи B, они никогда не пойдут одновременно.
- `parallel_mode` — в основном `.vibelog/settings.json`, меняет только пользователь; модель может **предложить** смену в `heartbeat.md`, но не менять.
- git-конфликт слияния уже исключён сериализацией close (`closeQueue`, VL-146). Супервизор решает другую задачу — **смысловое пересечение работ** (один агент перепишет работу другого), а не merge.

### Рекомендация по дисциплине

Если нужна предсказуемая параллель — проставлять компонентные метки (`bot`, `web`, `cli`, `mcp`). При их отсутствии conservative вырождается в последовательный запуск, и это правильное поведение.

## 15. Доверие: grant на прогон

### Проблема

Пользователь запускает прогон на ночь и уходит спать. За ночь супервизор делает десятки write-операций, каждая из которых сегодня требует Allow/Deny — он встанет на первой же и будет ждать до утра.

### Решение

Доверие выдаётся **на конкретный прогон по конкретному набору задач**, а не на тред (тред живёт месяцами, доверие на тред забывается и превращается в дыру).

Сценарий:

1. В чате обсуждаем, какие задачи включить; добавляем их.
2. Говорим «стартуй» (или `backlog_supervisor(action: "start", ids: [...])`).
3. Супервизор показывает карточку подтверждения:

```
⏱ Ночной прогон
Задачи: VL-263, VL-264, VL-268
Развязываю без спроса:
 ☑ Запуск фаз           backlog_trigger_phase
 ☑ Статус фаз           backlog_phase_status
 ☑ Очередь              backlog_auto_queue
 ☑ Управление прогоном  backlog_supervisor
 ☑ Создание баг-задач   backlog_create_task
 ☐ Правка правил лечения (allow_self_tuning)
Действует до: утро, 08:00            [Отмена] [Разрешить]
```

4. После разрешения пишется `.vibelog/supervisor/grants/<runId>.json`:

```json
{
  "runId": "run-2026-10-31T22-00-00",
  "taskIds": ["VL-263", "VL-264", "VL-268"],
  "allowedTools": ["backlog_trigger_phase", "backlog_phase_status", "backlog_auto_queue", "backlog_supervisor", "backlog_create_task"],
  "grantedAt": "2026-10-31T21:58:00Z",
  "expiresAt": "2026-11-01T06:00:00Z"
}
```

### Правила

- **Задача вне `taskIds`** не запускается. Нужна — новое подтверждение «расширить прогон на VL-N».
- **Инструмент вне `allowedTools`** — обычный Allow/Deny, как раньше.
- **`expiresAt` истёк** — текущая фаза доводится до конца, новые не стартуют, в `heartbeat.md` запись «grant истёк, ждём продления».
- **Завершение прогона** (`stop` или все задачи в терминальном статусе) — grant отзывается.
- `expiresAt` задаётся TTL (дефолт 8 часов) либо явным временем; поле редактируется в карточке.
- **`write_file` и прочие write-операции модели вне grant — всегда с подтверждением.** Доверие не распространяется на правку файлов проекта.

## 16. Самонастройка

`allow_self_tuning` (по умолчанию **`false`**) разрешает модели править `.vibelog/supervisor/settings.json` — то есть `heal_rules` и `comment_template`.

Ограничения:

- изменения пишутся в `.vibelog/supervisor/tuning.log`: время, что было, что стало, формулировка причины от модели (формат строки: `<ISO> было=<hash|json> стало=<...> причина=<...>`);
- **защищённые поля** — `max_parallel_phases`, `heal_attempts`, `allow_self_tuning`, `parallel_mode` — вынесены в основной `.vibelog/settings.json`, модель туда не пишет; патч, упоминающий любое из них, отклоняется целиком с причиной;
- `comment_template` правится только внутри `heal_rules[i]` — отдельный ключ верхнего уровня отклоняется;
- лимит самонастроек за прогон (чтобы модель не «крутила ручки» каждый тик);
- смена `parallel_mode` — только пользователем; модель может предложить её в `heartbeat.md`.

Причина такого разделения: правила лечения — знание о проекте, они меняются чаще кода, и модель видит их результат. Лимиты — страховка, их правка моделью означала бы, что она сама себе разрешает больше.

## 17. Взаимодействие с чатом

1. **Согласование.** Пользователь обсуждает состав работ; супервизор предлагает набор и порядок.
2. **Карточка grant.** Явное подтверждение на прогон (§15).
3. **Статус шагов.** В треде видно: что запущено, что ждёт, что лечится, по какому правилу.
4. **`stop`.** Останавливает прогон: текущие фазы доводятся (или прерываются — отдельный флаг), новые не стартуют.
5. **Итоговый отчёт.** По завершении: какие задачи дошли до Done, какие получили баг-задачу, какие упали окончательно и почему, сколько сработало правило и какое.
6. **Закрытый чат.** Падения и решения фиксируются в `state.json` / `heartbeat.md`; при следующем открытии треда супервизор отдаёт сводку.

Лимиты хода роли: при активной персоне `supervisor` ход чата берёт `supervisor.limits.chat_max_iterations` и `chat_max_wall_time` через механизм VL-269 — остальные роли работают на прежних значениях.

| Нужны ли уведомления в Telegram по завершении прогона? | Да, по образцу `auto-runner` — но отдельной задачей |
| Поведение при пустом состоянии | wake gate: ничего не изменилось — модель не вызывается (экономия) |
| Что делать, если grant истёк, а фазы ещё идут? | Довести текущие, новые не стартовать, ждать продления |
| Нужен ли режим полного автопилота без карточки grant? | Нет: grant и есть автопилот, но выданный осознанно и с ограничением по времени и составу |

## 21. Критерии готовности реализации

Реализация считается готовой, когда:

1. Супервизор запускает ночной прогон по набору задач и доводит его до конца без участия человека (при выданном grant).
2. Тик переживает рестарт процесса: после перезапуска `vibelog browser` прогон продолжается с того же места.
3. Зацикливание распознаётся по `repeat_stats`, фаза получает комментарий-директиву и продолжает работу без ручного вмешательства.
4. Транзиентные ошибки (payload, таймаут) приводят к повтору, содержательные — к баг-задаче в статусе Spec с заполненным описанием.
5. Параллельный запуск не превышает `max_parallel_phases`; при `conservative` каждая группа имеет записанное обоснование в `heartbeat.md`.
6. Задача с зависимостью (`blocks`) никогда не идёт параллельно с блокируемой.
7. Инструмент вне `allowedTools` требует подтверждения; задача вне `taskIds` не запускается; `write_file` всегда с подтверждением.
8. По истечении `expiresAt` новые фазы не стартуют, а текущие доводятся.
9. Утром пользователь читает `heartbeat.md` и понимает, что делалось ночью, что упало и почему, без чтения логов.
10. Пустой тик не вызывает модель (wake gate работает).
11. Супервизор не назначает фазы сам: следующая фаза всегда берётся из workflow задачи (`getWorkflowForTask` → `getAvailablePhases` → `isPhaseAllowed`); перестановка или пропуск шага воркфлоу невозможны, ветвление (reject, fix-цикл) соблюдается.
12. Задачи с разными воркфлоу корректно идут в одном прогоне: у каждой своя следующая фаза, число шагов до close может различаться.

## 22. Расхождения реализации с документом (VL-270)

Зафиксировано при реализации; часть §3–§19 уточнена выше по тексту, здесь — сводка решений, принятых в коде:

1. **Модель в тике не вызывает инструменты.** В §5 изначально не был описан контракт ответа; реализация: код собирает состояние сам и ждёт один JSON-объект решения (см. «Контракт решения модели» в §5). Промпт роли описывает именно этот контракт.
2. **Живость фазы** — собственный `phaseRunId` (оркестратор своего не отдаёт) + `pid`, плюс `statusAtStart` для различения «упала» / «статус сменился, значит успех».
3. **`state.json` расширен** полями `snapshotHash`, `tuning`, `tasks[].statusAtStart`, `tasks[].ruleChain`, `tasks[].frozen`, `wakeAt` (§10).
4. **Модуль тика** — `src/web/supervisor-tick.ts` (§9): `src/web/supervisor.ts` остаётся модулем планирования/старта прогона из VL-268. `loadSupervisorSettings` в `supervisor.ts` стал тонкой обёрткой над `resolveSupervisorRuntime` из `src/core/supervisor-config.ts` (единый источник дефолтов).
5. **Авто-баг без `dependencies`** — связь с исходной задачей явным упоминанием в описании (§13), чтобы баг не оказался заблокирован незавершённой задачей.
6. **Дефолт `max_parallel_phases` = 3** (§7) — в VL-268 в коде стояло 2, приведено к документу.
7. **Таймер тика включается только при активном grant'е** и глушится `VIBELOG_SUPERVISOR_TICK=off` — и продовая логика (нет прогона — нечего наблюдать), и защита тестов от лишних LLM-вызовов.
8. **Парсинг решения терпимый**, при неудаче — детерминированный фолбэк «последовательный запуск готовых задач по приоритету» с записью `decision: fallback` в heartbeat; тик не падает из-за ответа модели.
9. **`quick`/лимит промпта** — бюджет `MAX_TICK_PROMPT_CHARS` (~24 КБ) с приоритетом «heartbeat без сырых логов», фрагменты `logTail` ≤40 строк суммарно, repeat-топ-3 вместо полной метрики.
10. **Idle-watchdog фаз** (§8) — был вне скоупа VL-270, реализован в **VL-274**: `idle_timeout_seconds` (дефолт 600, `0` — выключено), флаг `--idle-timeout`, отдельный `reason: 'idle'`; таймер снимается на время tool-вызова. По-прежнему не реализованы уведомления в мессенджеры.
