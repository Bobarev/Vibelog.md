### Корневая причина №1 (уверенность ~85%): отказ провайдера пришёл как валидный 200-ответ, а не как HTTP-ошибка → обе защиты VL-178 не сработали

Ключевой факт: JSONL сессии-1 **не содержит ни одного маркера ошибки** — нет `Ошибка LLM-запроса`, `Ошибка API Cloud.ru`, `Превышен лимит` (проверено grep по файлу). Цитата финала (`.vibelog/agent-sessions/agent-1793026414766.jsonl`, строка 65):

> `"role":"assistant","content":"The request was rejected because it was considered high risk"`

Это **финальный текст модели без `tool_calls`**. В `src/agent/loop.ts` (строки 311–330) такой ответ считается УСПЕХОМ: `is_error: false`, exit code 0. Следствия:

1. **LLM-клиентский shrink-повтор VL-178 не срабатывает** — он детектит отказ только в теле НЕ-ok HTTP-ответа (`src/agent/llm.ts:400-422`, `isHighRiskBody(e.message)` в catch). Получили `streamChat → attemptWithFallback → parseSse` с HTTP 200 и текстом-отказом → исключения нет → повторов нет.
2. **Авто-resume оркестратора VL-178 не срабатывает** — его guard требует `record.result?.is_error === true` (`src/web/orchestrator.ts:996-1005`): «`const isHighRisk = record.result?.is_error === true && /high\s*risk.../`». Раз `is_error=false` → ни `--resume`, ни лога «авто-resume после high-risk».

Отдельная деталь: сессия-1 неожиданно мала для «high risk by size» — весь JSONL 138 КБ, tool-выводы усечены ingestion-cap'ом (максимум 8323 байт — cap VL-178 работал), MCP-скриншотов не было. Вероятен **content-based** отказ Cloud.ru либо иной порог; точная причина отказа провайдера из имеющихся данных не восстановима (дампов `.vibelog/qwen-debug/` за 26 окт нет — они пишутся только когда `parseQwenResult` не распознал stdout, а result распознавался всегда).

### Корневая причина №2: retry авто-очереди перезапускает фазу с НОВОЙ сессией (не возобновляет)

Цепочка: сессия-1 → `is_error=false` → exit 0, но `finish_phase` не вызван → статус задачи не изменился → в `src/bot/auto-runner.ts` (`finishCurrentPhase`, строки 260–289): «Успех фазы = exitCode 0 И смена статуса задачи (нет смены → нет прогресса → retry)» → `handlePhaseFailure` → retry → `autoTick → startTaskPhase` **без `--resume`**. `startTaskPhase` вообще не передаёт `--resume` для фаз (только code получает `--resume` plan-сессии через `code_same_session`, `src/web/orchestrator.ts:229-256`). Результат — сессия-2 с полным исходным промптом (`agent-1793028420789.jsonl`, строка 1: «Ты — автоматический исполнитель Vibelog (Фаза 2: Plan) для задачи VL-193»), хотя «Продолжи с текущего места — автоматический повтор после отказа провайдера (VL-178)» в сессиях **не встречается** (проверено grep'ом по всем `.vibelog/agent-sessions/`).

Цена: сессия-1 (36 tool-вызовов, 34 минуты исследования README/doc-*) выброшена целиком, всё повторено в сессии-2.

### Проблема №3: «Команда отклонена» — ложные срабатывания guard'а на слэш-командах (3 случая)

- Сессия-1, строка 12–13: `grep -n "/auto" backlog/docs/doc-6*.md` → `Команда отклонена: обращение к путям вне проекта (/auto)`.
- Сессия-2, строки 29 и 39: аналогично `/web start` и `/web`.

Причина — `src/agent/tools.ts:315-340` (`checkShellCommandInProject`): паттерн grep без regex-метасимволов (`/auto`, `/web`) после снятия кавычек не проходит `isRegexPatternToken` (там проверяются только метасимволы `*?+{}[]^$|` и экранирования), далее `isAbsolute('/auto')` → `relative(cwd, '/auto')` наружу → reject. Слэш-команды — документированный объект поиска в docs (VL-151/161), это **паттерн, а не путь**. Каждый случай — потерянный ход: агент переформулирует команду.

### Проблема №4 (побочная): code-фаза упала по wall-time на середине

`max_wall_time: 2400` (`.vibelog/settings.json`). Code-попытка-1 потратила 40 минут на полную замену doc-6 (700 строк) через чтение чанками (≈12 вызовов `read_file`/`run_shell` по файлу, строки 110–136 сессии-2) и не уложилась. Retry продолжил сессию (`code_same_session`) — здесь механизм отработал, но часть работы повторена.

Найденные точки роста:

1. **Потеря целой сессии при high-risk** — доминирующий фактор (~100 КБ / 36 ходов впустую). Лечится задачами №1 и №2 ниже.
2. **Дублирование чтений**: в сессии-2 README прочитан/просканирован **более чем в 20 shell-вызовах** (`grep -n`, `sed -n`, `wc`, `node -e`-парсеры ссылок) + 15 `read_file`, хотя файл после правки — 78 строк. Мелкие выборки вместо одного пакетного чтения.
3. **Чанковое чтение doc-6** (≈12 вызовов «прочитал чанк → граница обрезалась → дочитываю») — прямой путь к исчерпанию wall-time.
4. **3 ложных reject'а команд** — по одному лишнему ходу на случай.
5. Что уже работает и не надо трогать: ingestion-cap 8 КБ (подтверждён: макс. tool-результат 8323 б), компакшн VL-122 (по умолчанию включён, `spawnLimitFlags` не добавляет `--no-compact`), `code_same_session` (code-ретрай продолжил сессию, а не создал новую).

### Повторяемость

Высокая: любой финальный ответ модели, совпадающий с маркером отказа провайдера (или любой отказ, придущий HTTP 200), повторит потери 1:1. Ложные reject'а слэш-команд повторяются на каждой docs-фазе, где агент ищет `/auto`, `/web` и т.п.

## Предложение задач

> Создание задач — работа фазы materialize. Поля ниже готовы к материализации.

### №1 — Детект «high risk» в финальном тексте ответа как ошибка фазы

- **title**: `bug: high-risk-отказ при HTTP 200 не детектится — авто-resume VL-178 и shrink-повтор не срабатывают`
- **type**: bug
- **priority**: High
- **описание**: Отказ провайдера «The request was rejected because it was considered high risk» пришёл валидным финальным assistant-текстом без tool_calls (инцидент VL-197, сессия `agent-1793026414766.jsonl`, строка 65). `loop.ts` трактует такой ответ как успех (`is_error=false`, exit 0) → guard авто-resume в `orchestrator.ts:996-1005` (требует `is_error===true`) не срабатывает, LLM-клиентский shrink-цикл (`llm.ts:411-422`) детектит отказ только в не-ok теле. Нужно: в `loop.ts` перед финализацией ответа сверять текст с `isHighRiskBody` и уходить в `fail()` (is_error=true), либо расширить guard авто-resume на `is_error===false` при совпадении маркера в `result`. Плюс: диагностический лог размера payload/usage при отказе (причина content-based отказа при payload ~140 КБ неизвестна — нужна наблюдаемость).
- **AC**:
  1. Финальный текст ответа, матчащий `isHighRiskBody`, завершает фазу как ошибка (`is_error=true`, exit 1) с русским пояснением.
  2. Авто-resume VL-178 (`--resume <sid>`, лог «авто-resume после high-risk») срабатывает в этом сценарии; есть регресс-тест в `orchestrator.test.mjs`/`loop.test.mjs`.

### №2 — Retry авто-очереди продолжает сессию фазы, а не создаёт новую

- **title**: `enhancement: retry фазы в авто-очереди должен возобновлять сессию (--resume), а не запускать с нуля`
- **type**: enhancement
- **priority**: High
- **описание**: При ошибке фазы `auto-runner.ts` (`handlePhaseFailure → autoTick → startTaskPhase`) перезапускает фазу с полным промптом в НОВОЙ сессии — инцидент VL-197: после обрыва plan VL-193 создана `agent-1793028420789.jsonl` вместо продолжения `agent-1793026414766.jsonl`, 36 tool-вызовов и 34 минуты исследования потеряны. `startTaskPhase` умеет принимать extraArgs с `--resume`, но auto-runner их не передаёт; при этом механизм `findTaskPhaseSessionSync` уже существует (им пользуется `code_same_session`). Передавать при retry `--resume <последняя сессия задачи/фазы>`; учесть, что resume возможен не в worktree, если сессия создавалась вне его (комментарий `session.ts:121`, инцидент VL-98).
- **AC**:
  1. Retry фазы после ошибки дописывает новые сообщения в существующий JSONL сессии этой фазы (не создаёт `agent-*.jsonl`), при этом промпт retry-рана — штатный фазовый.
  2. Тест `auto-runner.test.mjs`: после `exitCode!=0` следующий `startTaskPhase` вызван с `--resume` корректного sessionId; счётчик attempts и max_retries не ломаются.

### №3 — Ложный reject grep-паттернов слэш-команд в checkShellCommandInProject

- **title**: `bug: guard shell-команд отклоняет паттерны вида "/auto", "/web" (слэш-команды) как абсолютные пути`
- **type**: bug
- **priority**: Medium
- **описание**: `tools.ts:315-340`: паттерн grep без regex-метасимволов (например `grep -n "/auto" backlog/docs/...`, `"/web"`) после снятия кавычек не распознаётся `isRegexPatternToken` (проверяет только метасимволы) и отклоняется как абсолютный путь вне проекта. 3 случая в сессиях VL-193 (VL-197). Слэш-команды — штатный объект поиска в документации. Нужен контекстный анализ: токен в позиции аргумента-паттерна (`grep/rg/sed -e/-n/…`, следующий за командой-фильтром), либо правило «токен начинается с `/`, но не резолвится в существующий путь-каталог и сопровождается файловыми аргументами внутри проекта». Существующие отказы (`~`, `$HOME`, `..`, реальные абсолютные пути) должны остаться.
- **AC**:
  1. `grep -n "/auto" backlog/docs/doc-6*.md` и `grep -n "/web start" …` выполняются без `Команда отклонена`.
  2. `ls /etc`, `cat ~/x`, `cat ../outside`, `grep x /etc/passwd` по-прежнему отклоняются; есть unit-тесты в `tools.test.mjs` на оба класса.

### №4 — Пакетное чтение файлов вместо десятков точечных выборок (промпты фаз)

- **title**: `docs: правило пакетного чтения файлов в промптах фаз (один read_file вместо 20 grep-выборок)`
- **type**: docs
- **priority**: Medium
- **описание**: В сессии-2 VL-193 README затронут в 20+ shell-вызовах, doc-6 читан ≈12 чанками с промежуточными проверками границ — прямой вклад в исчерпание `max_wall_time` (code-1 упала на 40-й минуте, VL-197). В промпты фаз (templates/phases и/или system-prompt) добавить: «анализируй файл одним `read_file` (offset/limit при файле >200 строк — последовательно, а не через grep-подстроки); точечные правки — после полного чтения; объединяй связанные проверочные команды в один вызов через `&&`». Согласовать с правилом «не читать файлы целиком >200 строк» (читать чанками offset/limit, но без промежуточного grep-поиска границ).
- **AC**:
  1. В шаблонах промптов фаз есть правило пакетного чтения/команд; CHANGELOG/документация обновлены.
  2. На тестовом docs-прогоне число shell-вызовов на файл снижается (метрика из jsonl: README ≤5 обращений вместо 20+).

### №5 — Наблюдаемость «high risk»: причина отказа при малом payload

- **title**: `task: логировать размер wire-payload и usage на каждый LLM-запрос фазы (диагностика high-risk)`
- **type**: task
- **priority**: Low
- **описание**: Отказ «high risk» в VL-197 случился при payload ~140 КБ (все tool-выводы усечены до 8 КБ) — аномально мало для размерного отказа (VL-178 ловил 1.25 МБ). Чтобы отличать content-based отказ от размерного, фазовый лог/JSONL-мета должны содержать размер тела запроса, `usage` по ходам и уровень компакшна. Данные нужны для решения №1 (какую защиту усиливать).
- **AC**:
  1. В diagnostics-выводе фазы (logTail/лог оркестратора) есть байты payload и usage последнего запроса.
  2. Отказ провайдера сопровождается этими числами в логе (проверить на мок-fetch тесте).
