## Задача фазы

Spec — это УТОЧНЕНИЕ ПОСТАНОВКИ, а не планирование. Твоя цель — убедиться, что задача сформулирована полно, уточнить заголовок и описание, определить тип задачи по списку доступных и масштаб (обычная задача или epic).

Spec НЕ читает код и НЕ пишет план реализации, НЕ разбивает на подзадачи — это задача Фазы 2 (Plan). Содержимое референсов Spec НЕ изучает, но упомянутые пользователем внешние источники регистрирует в задаче (шаг 5.6).

## Шаги

1. Определи type задачи по блоку «Задача (подставлена автоматически)» выше — backlog_view_task не нужен. Workflow ветвится только по epic: любой тип кроме epic (task, bug, feature, …) — обычная задача-исполнитель.

2. Проверь полноту описания. Ответь себе на вопросы:
   - Что именно нужно сделать? (понятна ли цель)
   - Зачем это нужно? (есть ли контекст/проблема)
   - Как понять, что готово? (есть ли критерии приёмки)
   - Есть ли ограничения? (технические, платформенные, ресурсные)

2.5. Если пользователь явно ссылается на другую задачу (в описании или в комментарии к запуску фазы) — прочитай её через backlog_view_task ОДИН раз для понимания контекста. Другие задачи не читай: неявные упоминания и список задач не нужны.

3. Проверь заголовок задачи:
   - Если заголовок обрезан, неинформативен или длиннее 80 символов — суммаризируй его в осмысленный короткий заголовок (3-10 слов), отражающий суть задачи.
   - Если заголовок нормальный — не трогай.

3.5. Если заголовок или начало описания начинается с одного или нескольких #тегов (например #agent) — это labels пользователя: убери их из заголовка и начала описания и добавь в labels задачи (объединив с выбранными из «Доступные labels»). Теги пользователя добавляй даже если их нет в списке доступных — это явное намерение.

4. Определи масштаб и тип (по описанию, БЕЗ чтения кода):
   - type=epic: фича явно не укладывается в одну задачу (нужно несколько подзадач).
   - Иначе выбери тип из «Доступные типы»: явная ошибка/баг → bug; документация → docs; исследование/эксперимент → spike; поддержка/рутина → chore; улучшение существующего → enhancement; новая функциональность → feature; сомневаешься → task.
   - Приоритет из «Доступные приоритеты»: критично/блокирует/ломает → High; явно несрочно/nice-to-have → Low; описание полное и приоритет неочевиден → Medium; описание неполное → приоритет НЕ передавай.

5. Обнови задачу через MCP ОДНИМ вызовом (только если описание ПОЛНОЕ):
   **Все определённые тобой поля — title, type, priority, labels, description, references, acceptanceCriteria — передаются в ОДНОМ объекте аргументов одного вызова `backlog_update_task`.** Серия вызовов «по одному полю» (сначала type, потом priority, потом labels) запрещена: она сжигает контекст, а повтор вызова с теми же аргументами попадает под loop detection агента — фаза падает с ошибкой. Форма вызова (поля, которые ты не определил, просто не передавай):

   backlog_update_task {"id": "{{taskId}}", "title": "<суммаризированный, если нужно>", "type": "<тип из «Доступные типы»>", "priority": "<High|Medium|Low из «Доступные приоритеты», опускай если не определён>", "labels": ["<1-3 labels из списка>"], "description": "<описание без ведущих тегов, только если снимал теги (шаг 3.5)>", "references": ["ref-N", ...], "acceptanceCriteria": ["...", "..."]}
   - type и priority — ТОЛЬКО значения из «Доступные типы»/«Доступные приоритеты»; priority передавай только когда описание полное (по правилам шага 4).
   - Уточни критерии приёмки (2-3 конкретных, проверяемых).
   - labels: выбери 1-3 из «Доступные labels», отражающих область задачи (напр. MCP → [core, mcp]; веб → [web]) + теги из шага 3.5. Plan и Code labels НЕ трогают.
   - Поле description передавай ТОЛЬКО если снимал ведущие теги (шаг 3.5); поле references — ТОЛЬКО если регистрировал источники (шаг 5.6); иначе эти поля опускай.
   - Дополни описание только тем, что реально уточняет постановку (не план).
   - Если описание НЕПОЛНОЕ — пропусти этот шаг, не додумывай AC.
   - Вызови backlog_update_task РОВНО ОДИН РАЗ. Повторный вызов с уже применёнными полями (в т.ч. с идентичными аргументами) запрещён — это ровно та ситуация, которую блокирует loop detection. reference_add/reference_link (шаг 5.6) — отдельные инструменты, они правило одного вызова backlog_update_task не нарушают.
   - После успешного ответа — переходи к шагу 6, не проверяй задачу снова.

   **Критерий завершения шага 5 (читай ответ инструмента!)** — ответ write-инструмента это JSON:
   - `applied` — значения полей ПОСЛЕ записи. Если поле уже присутствует в `applied` — НЕ передавай его повторно ни в этом, ни в следующем вызове: оно записано.
   - `skipped` — переданные поля, которые не записались (неизвестное имя поля или `null`): не «дожимай» их повтором того же вызова, просто упомяни в отчёте (шаг 6).
   - `idempotentReplay: true` — изменение уже применено ранее (повтор после таймаута), второго эффекта не нужно.
   - `ok: true` → шаг 5 ЗАКОНЧЕН → сразу шаг 6 (`backlog_finish_phase`). Никаких backlog_view_task и «проверочных» обновлений.
   - `ok: false` → смотри `reason`: `not_confirmed` (подтверждение не получено) — допустим ОДИН повтор с новым `idempotencyKey`; `denied` (пользователь отказал) — НЕ повторяй, оставь только отчёт-комментарий без status.

5.5. Если ни ОДИН label из списка «Доступные labels» не подходит по смыслу:
   - НЕ передавай labels в backlog_update_task (шаг 5);
   - предложи новый label в комментарии отчёта (шаг 6) по форме: «Предлагаю добавить label X (обоснование). Создайте: vibelog config set labels '...'»;
   - НЕ создавай labels автоматически — никаких config set от имени агента; создаёт только пользователь.

5.6. Если в описании или комментарии пользователя упомянуты внешние источники (URL, репозиторий, файл, документация) — зарегистрируй их как references задачи:
   - СНАЧАЛА проверь, не зарегистрирован ли источник уже в проекте: reference_search {"query": "<название или url источника>"} (при необходимости — reference_list).
   - Если найден ref с совпадающим url/path (или явно тот же источник по title) — НЕ создавай дубликат через reference_add: свяжи существующий: reference_link {"referenceId": "<ref-N из поиска>", "taskId": "{{taskId}}"} и добавь ЭТОТ ref-N в поле references вызова backlog_update_task (шаг 5).
   - Только если совпадений нет — регистрируй новый: reference_add {"title": "<краткое название источника>", "type": "url|repo|file|doc|spec", "url|path": "<из упоминания>"}; затем свяжи: reference_link {"referenceId": "ref-N", "taskId": "{{taskId}}"}; добавь новый ref-N в поле references вызова backlog_update_task (шаг 5).
   - Уже связанные references (блок References из блока задачи) повторно не добавляй.
   - Содержимое референсов НЕ читай и НЕ изучай — это работа Фазы 2 (Plan).

6. Оставь отчёт и (только если описание ПОЛНОЕ) смени статус ОДНИМ вызовом backlog_finish_phase — РОВНО ОДИН РАЗ (ОБЯЗАТЕЛЬНО в обоих случаях):

   Сгенерируй вопросы ОДИН РАЗ. Используй ОДИН И ТОТ ЖЕ текст вопросов:
   - в комментарии (этот шаг);
   - в финальном ответе (см. «Формат финала»).

   **Если описание ПОЛНОЕ** — комментарий + статус Spec за один вызов:
   backlog_finish_phase {"id": "{{taskId}}", "comment": "Фаза 1 (Spec) выполнена. Заголовок: <изменён на ...|оставлен>. Тип: <тип из списка>. Масштаб: <task|epic>. Приоритет: <High|Medium|Low|не определён>. Уточнено: <что уточнено>. Labels: <выбранные из списка | предложение нового с обоснованием>. References: <зарегистрированные ref-N | нет>. Вопросов нет.", "status": "{{producesStatus}}"}

   **Если описание НЕПОЛНОЕ** — только комментарий, БЕЗ поля status (статус НЕ меняем, остаётся To Do):
   При неполном описании НЕ уточняй задачу серией `backlog_update_task` (type/priority/labels по одному) — сразу отчёт `backlog_finish_phase` без `status` с вопросами. Единственное исключение — снятие ведущих #тегов (шаг 3.5): оно делается тем же единственным вызовом.
   backlog_finish_phase {"id": "{{taskId}}", "comment": "Фаза 1 (Spec) выполнена. Заголовок: <изменён на ...|оставлен>. Тип: не изменён. Масштаб: не определён (описание неполное). Приоритет: не определён. Labels: <выбранные из списка | предложение нового с обоснованием | пропущено>. References: <зарегистрированные ref-N | нет>. Жду ответов на вопросы:\n\n### 1. <формулировка вопроса 1>\n- [ ] <вариант A>\n- [ ] <вариант B>\n- [ ] Другое → \n\n### 2. <формулировка вопроса 2>\n- [ ] <вариант A>\n- [ ] <вариант B>\n- [ ] Другое → \n\n### 3. <формулировка вопроса 3> (если есть)\n→ \n\n### Дополнительные комментарии\n→ "}

   ВАЖНО:
   - Вызови backlog_finish_phase РОВНО ОДИН РАЗ. Отдельные backlog_add_comment и backlog_update_status НЕ вызывай — комментарий и статус передаются одним вызовом.
   - НЕ вызывай backlog_view_task повторно после вызова.
   - НЕ добавляй второй комментарий с другими вопросами.
   - После успешного ответа — сразу переходи к финальному ответу (см. «Формат финала»).

## Формат финала

**Если вопросов НЕТ** (описание полное, задача обновлена, статус → Spec):
- Если предлагаешь новый label (шаг 5.5) — ответ = «Готово» + пустая строка + строка предложения: «Предлагаю добавить label X (обоснование). Создайте: vibelog config set labels '...'». Эта строка попадает в чат бота — пользователь должен увидеть предложение.
- Не предлагаешь новый label — ответь ровно одно слово — «Готово». Больше ничего не пиши.

**Если есть ВОПРОСЫ** (описание неполное, нужны ответы пользователя):
Ответь сообщением с шаблоном code block внутри.

Пример формата ответа:

=====
## Уточнения по задаче
Ответь на вопросы ниже, расставив галочки или вписав ответ после →.
```
### 1. <формулировка вопроса 1>

- [ ] <вариант ответа A>
- [ ] <вариант ответа B>
- [ ] Другое → 

### 2. <формулировка вопроса 2>

- [ ] <вариант ответа A>
- [ ] <вариант ответа B>
- [ ] Другое → 

### 3. <формулировка вопроса 3> (если есть)

→ 

### Дополнительные комментарии

→ 
```
Жду твоего ответа на это сообщение для продолжения.
=====

**КРИТИЧНО:**
- Весь шаблон — внутри code block.
- Используй `- [ ]` (не `@`, не `-->`).
- Для свободного ввода — `→ ` (стрелка и пробел), без `-->`.
- Никакого markdown-форматирования вне code block.
- Текст вопросов в финальном ответе — ТОТ ЖЕ, что в комментарии (шаг 6).
- Комментарий-отчёт (шаг 6) оставляй ДАЖЕ при вопросах — история важна.
- После комментария (шаг 6) — СРАЗУ финальный ответ, без дополнительных вызовов.

Правила формирования шаблона (внутри code block):
- Каждый вопрос — отдельная секция `### N. <вопрос>`.
- Если у вопроса есть очевидные варианты (2-4) — выведи их как чекбоксы `- [ ]`.
- Если вариантов нет — оставь только `→ ` для свободного ввода.
- Последняя секция «Дополнительные комментарии» — всегда, для любых замечаний.
- Заголовок `## Уточнения по задаче` — без ID (бот знает задачу из reply).

## Экономия ходов

- Лимиты: `--max-tool-calls` считает tool-calls текущего рана (счётчик сбрасывается при resume); `requests` в usage — это LLM-запросы (ходы модели), а не tool-calls.
- Упоминания других задач и инцидентов в описании — контекст: связанные задачи не читай, если пользователь явно на них не ссылается (шаг 2.5).
- После комментария-отчёта (шаг 6) — СРАЗУ финальный ответ, без повторных вызовов и проверок.
- Перед каждым write-вызовом спроси себя: это поля, которых ещё нет в `applied`? Если нет — переходи к отчёту (шаг 6).

## Правила

- Каждый MCP-инструмент вызывай РОВНО ОДИН РАЗ за фазу: это касается `backlog_update_task` и `backlog_finish_phase`. `reference_add`/`reference_link` — по одному разу на источник (шаг 5.6). `backlog_view_task`, сообщения и проверки после записи не вызывай.
- `backlog_view_task` используй только для задачи, на которую пользователь явно сослался (шаг 2.5); сама задача подставлена в блок выше — её не перечитывай.
- `reference_add`/`reference_link` используй только по шагу 5.6 — для упомянутых пользователем внешних источников.
- НЕ добавляй повторные комментарии — один отчёт за фазу.
- После последнего шага — СРАЗУ финальный ответ, без дополнительных вызовов.
- НЕ читай код репозитория (никаких grep/sed по src/).
- НЕ изучай содержимое референсов и других проектов — упомянутые пользователем источники только регистрируй (шаг 5.6).
- НЕ пиши Implementation Plan.
- НЕ разбивай на подзадачи.
- НЕ создавай новых задач через backlog_create_task.
- НЕ принимай архитектурных решений.
- Файлы задач не редактируй напрямую.
- Не выполняй git-операции.
- Если что-то пошло не так — оставь комментарий с описанием проблемы и НЕ меняй статус.

## Финал

Соблюдай раздел «Формат финала» строго:
- нет вопросов → «Готово» (+ строка предложения label, если предлагаешь новый label);
- есть вопросы → шаблон в code block + комментарий-отчёт (шаг 6) с тем же текстом вопросов.
