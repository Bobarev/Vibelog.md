## Шаги

1. Определи type задачи и modified_files по блоку «Задача (подставлена автоматически)» выше — backlog_view_task не нужен. Ветвление ниже — только epic/не-epic: любой тип кроме epic ведёт себя как обычная задача.

2. Проверь worktree ветки:
   git -C {{worktreeDir}} status --porcelain
   - Грязный worktree (есть незакоммиченные файлы) — закоммичи их в ветку {{branch}} ИЗ worktree (это единственные git-команды с -C):
     git -C {{worktreeDir}} add <явные пути затронутых файлов>
     git -C {{worktreeDir}} commit -m "feat: {{taskId}} — <кратко>"
     Только явные пути файлов задачи; никогда git add -A.
   - Worktree отсутствует (директории нет) — пропусти шаги 3–5 и продолжай с шага 6: код либо уже слит в master, либо фазы не меняли файлы.

3. Покажи состав ветки относительно master:
   git log --oneline master..{{branch}}
   Если коммитов нет — переходи к шагу 6, сливать нечего.

4. Слей ветку в master (merge выполняется ТОЛЬКО из главного cwd: master checked-out здесь, git-worktree запрещает merge главной ветки из других worktree):
   git merge --no-ff {{branch}} -m "merge: {{taskId}} — <заголовок задачи>"
   - ЕСЛИ merge УПАЛ НА КОНФЛИКТЕ:
     - НЕ резолвь конфликты сам и НЕ делай git merge --abort — конфликтные файлы оставь как есть для ручного разбора.
     - Шаги 6–10 НЕ выполняй: DoD, статус и документацию не трогай (задача остаётся в своём текущем статусе).
     - Отчёт (шаг 9) сделай сразу с `"aborted": true` (БЕЗ status и dodChecks): «Фаза Close прервана: конфликт слияния {{branch}} → master (файлы: <git status --porcelain>). Разреши конфликт вручную и повтори Фазу Close.» — и завершай. Это аварийный итог: не завершай цикл как успех и оформляй его по единой формуле (см. «Правила», буллет «Аварийный итог»).

5. После успешного merge проверь главный репо — merge может дать сломанную комбинацию даже без конфликта строк. Порядок обязателен:
   - Сборка (команда — по правилам AGENTS.md проекта): сломанную сборку отсекаем до тестов.
   - Ранний точечный фильтр (НЕ замена полному прогону): возьми `git diff --name-only HEAD^1..HEAD` (файлы, принесённые merge) и прогони тесты, затронутые diff'ом: модуль → соседний `*.test.mjs` (`src/core/foo.ts` → `src/core/foo.test.mjs`); соответствующего теста нет — весь каталог модуля (`src/<каталог>/`). Цель — быстро отсечь «слитый код нерабочий».
   - Полный прогон тестов обязателен (команда — по правилам AGENTS.md проекта): единственная проверка merge-интерференции, интеграционных наборов и инвариант-тестов, взаимовлияния кода соседних задач.
   - Оговорка про «затронутые»: интеграционные наборы на чужие модули (`src/cli/*.test.mjs` проверяют `core/`) и инвариант-тесты, читающие файлы репозитория (`src/web/phase-prompt.test.mjs` следит за `templates/` и `AGENTS.md`), по имени модуля НЕ выводятся — для них действует только полный прогон.
   - Повторные полные прогоны запрещены: полный прогон в фазе — один. Упал → сначала классификация: (а) тот же набор на родительском коммите (`HEAD^1`) и сравнение РАЗНИЦЫ падений (пре-существующий красный — не твоя регрессия); (б) проверка, не идёт ли параллельный `vitest` в другом worktree (`ps aux | grep -E 'vitest'`). Только затем — максимум один повторный полный прогон, причина повтора фиксируется в отчётном комментарии.
   - Единственное исключение из полного прогона: diff не затрагивает `src/`, `templates/`, `package.json`, `tsconfig.json`, `vitest.config.mts` (чистые правки docs/backlog) — полный прогон допустимо пропустить, пропуск фиксируется в отчётном комментарии с причиной.
   Сборка или тесты падают и после классификации — НЕ выполняй шаги 6–10: вызови `backlog_finish_phase` с `"aborted": true` и отчётом-причиной (без status/dodChecks): «Фаза Close прервана: merge {{branch}} слит в master, но сборка/тесты падают: <детали>». Флаг `aborted` обязателен: без него завершение ран с кодом 0 применит `produces_status`. Это аварийный итог: не завершай цикл как успех — оформляй по единой формуле (см. «Правила», буллет «Аварийный итог»).

6. Удали worktree и ветку (команды выполняются ИЗ главного cwd — не переходи в worktree: удаление собственного рабочего каталога отклоняется guard'ом):
   git worktree remove {{worktreeDir}}
   - remove отказался «contains modified or untracked files» — посмотри git status {{worktreeDir}} --short:
     в worktree ТОЛЬКО untracked-симлинки node_modules/refs (их кладёт туда оркестратор; это ссылки на главный репозиторий, данные не теряются) — удали с force: git worktree remove --force {{worktreeDir}};
     есть modified-файлы или иной мусор — НЕ удаляй силой, упомяни в отчёте.
   git branch -d {{branch}}
   - branch -d отказался (ветка не считается слитой) — перепроверь шаг 4, упомяни в отчёте.

7. Получи список DoD и запомни индексы реально выполненных пунктов:

## Правила

- Рабочий каталог — главный репозиторий. Git-команды с -C {{worktreeDir}} — единственное разрешённое исключение; сам ты в worktree не переносишься и код напрямую не правишь.
- Пакетируй последовательные git/shell-команды в ОДИН вызов через && (например: git -C {{worktreeDir}} status --porcelain && git log --oneline master..{{branch}}).
- git-коммиты — только файлы этой задачи и её подзадач по явным путям + слияние её ветки: никогда git add -A, не push, не чужие ветки.
- Конфликты слияния не резолви и не откатывай — только отчёт (шаг 4).
- **Close не правит код:** любые `edit`/`write_file` по `src/`, `web/src/`, `templates/`, `scripts/` в этой фазе запрещены. Упавшая сборка или упавшие тесты — это аварийный итог (`aborted: true` с причиной), а исправление делается новой фазой Code. Причина правила — инцидент авто-задачи про close: close лечил `src/mcp/tools.ts` в цикле со сборкой, payload вырос до 508 КБ и фаза сгорела за 5 попыток без результата.
- **Сборка проекта — не более одного раза за фазу** (и только если diff затронул `src/`/`web/src/`): повторная сборка без правок кода даёт тот же результат и жжёт контекст. Сборка упала — фиксируй аварийный итог, не собирай снова.
- **Аварийный итог фазы** (конфликт merge, падение сборки/тестов — любая причина, по которой Close не выполнена) оформляется ТОЛЬКО вызовом `backlog_finish_phase {"id": "{{taskId}}", "comment": "Фаза Close прервана: <причина>", "aborted": true}` — без `status` и `dodChecks`. Не завершай цикл как успех: обычный текст без флага фреймворк считает успехом (код выхода 0) и выставит `produces_status` незавершённой задаче. Прерванную фазу не продолжай по пользовательскому сообщению без нового рана (случай уже прерванной close и сообщения «Заверши фазу.» в той же сессии): работа возобновляется только новым раном фазы, а в ответ на сообщение сообщи, что фаза прервана и требует нового запуска, и не меняй статус.
- Если type=epic — не реализуй код; закрытие детей выполняет их собственная Фаза Close. Эпик со слитой веткой закрывай по шагам выше; ветки нет — по шагам 6–10.
- **README — витрина, не справочник.** `README.md` в этой фазе НЕ расширяй и не переписывай: лимит 150 строк и белый список H2 закреплены тестом `src/web/readme-standard.test.mjs`, падение которого — регрессия. Новая техническая деталь идёт в `backlog/docs/doc-*`; в README допустима только правка существующей строки/ссылки.
- Полный прогон тестов — один раз за фазу: ранний точечный прогон затронутого diff'ом — только фильтр перед полным; повторный полный прогон — лишь после классификации падений (родительский коммит, параллельный vitest в другом worktree) и с причиной в отчёте.

## Финал

После последнего шага (docs(task)-коммит) ответь ровно одно слово — «Готово». Не повторяй отчёт, не добавляй анализ и выводы, не выполняй дополнительных действий — терминальный вывод не нужен.

Если фаза прервана (merge/сборка/тесты) — финальный ответ не означает успех: работа возобновляется только новым раном фазы, и по пользовательскому сообщению без нового рана прерванную фазу не продолжай.
