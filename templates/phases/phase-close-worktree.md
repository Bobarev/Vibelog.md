## Что делает Close

Слить ветку задачи в master, проверить сборку и тесты после merge, удалить worktree и ветку, закоммитить refs, lessons и документацию, отметить DoD, поставить терминальный статус. Код Close не правит.

## Порядок

1. **Тип и ветвление.** Тип и modified_files возьми из блока выше — backlog_view_task не нужен. Ветвление только epic/не-epic: любой тип кроме epic ведёт себя как обычная задача.

2. **Worktree.** git -C {{worktreeDir}} status --porcelain. Грязный worktree (незакоммиченные файлы) — закоммить их в ветку {{branch}} ИЗ worktree (единственная git-команда с -C — чтение статуса): git_commit {"paths": [<явные пути затронутых файлов>], "message": "feat: {{taskId}} — <кратко>", "cwd": "{{worktreeDir}}"}. Только явные пути файлов задачи; git -C для коммита не нужен — путь worktree передаётся полем cwd. Worktree отсутствует (директории нет) — пропусти шаги 3–5 и продолжай с шага 6: код либо уже слит в master, либо фазы не меняли файлы.

3. **Состав ветки.** git log --oneline master..{{branch}}. Коммитов нет — переходи к шагу 6, сливать нечего.

4. **Слияние в master** (merge выполняется ТОЛЬКО из главного cwd: master checked-out здесь, git-worktree запрещает merge главной ветки из других worktree): git merge --no-ff {{branch}} -m "merge: {{taskId}} — <заголовок задачи>".
   - **Merge упал на конфликте:** НЕ резолвь конфликты сам и НЕ делай git merge --abort — конфликтные файлы оставь как есть для ручного разбора. Шаги 6–10 НЕ выполняй: DoD, статус и документацию не трогай (задача остаётся в текущем статусе). Сразу отчёт с `"aborted": true` (БЕЗ status и dodChecks): «Фаза Close прервана: конфликт слияния {{branch}} → master (файлы: <git status --porcelain>). Разреши конфликт вручную и повтори Фазу Close.» — и завершай. Это аварийный итог: не завершай цикл как успех и оформляй его по единой формуле («Запреты», буллет «Аварийный итог»).

5. **Проверка после merge** (merge мог дать сломанную комбинацию даже без конфликта строк). Порядок обязателен:
   - **Сборка** (команда — по правилам AGENTS.md проекта): сломанную сборку отсекаем до тестов.
   - **Ранний точечный фильтр** — НЕ замена полному прогону: возьми `git diff --name-only HEAD^1..HEAD` (файлы, принесённые merge) и прогони тесты, затронутые diff'ом: модуль → соседний `*.test.mjs` (`src/core/foo.ts` → `src/core/foo.test.mjs`); соответствующего теста нет — весь каталог модуля (`src/<каталог>/`). Цель — быстро отсечь «слитый код нерабочий».
   - **Полный прогон тестов обязателен** (команда — по правилам AGENTS.md проекта): единственная проверка merge-интерференции, интеграционных наборов и инвариант-тестов, взаимовлияния кода соседних задач.
   - **Оговорка про «затронутые»**: интеграционные наборы на чужие модули (`src/cli/*.test.mjs` проверяют `core/`) и инвариант-тесты, читающие файлы репозитория (`src/web/phase-prompt.test.mjs` следит за `templates/` и `AGENTS.md`), по имени модуля НЕ выводятся — для них действует только полный прогон.
   - **Повторные полные прогоны запрещены**: полный прогон в фазе — один. Упал — сначала классификация: (а) тот же набор на родительском коммите (`HEAD^1`) и сравнение РАЗНИЦЫ падений (пре-существующий красный — не твоя регрессия); (б) проверка, не идёт ли параллельный `vitest` в другом worktree (`ps aux | grep -E 'vitest'`). Только затем — максимум один повторный полный прогон, причина повтора фиксируется в отчётном комментарии.
   - **Единственное исключение из полного прогона**: diff не затрагивает `src/`, `templates/`, `package.json`, `tsconfig.json`, `vitest.config.mts` (чистые правки docs/backlog) — полный прогон допустимо пропустить, пропуск фиксируется в отчётном комментарии с причиной.
   - Сборка или тесты падают и после классификации — НЕ выполняй шаги 6–10: вызови `backlog_finish_phase` с `"aborted": true` и отчётом-причиной (без status и dodChecks): «Фаза Close прервана: merge {{branch}} слит в master, но сборка/тесты падают: <детали>». Флаг `aborted` обязателен: без него завершение рана с кодом 0 применит `produces_status`. Это аварийный итог — оформляй его по единой формуле («Запреты», буллет «Аварийный итог»).

6. **Уборка worktree и ветки** (команды выполняются ИЗ главного cwd — не переходи в worktree: удаление собственного рабочего каталога отклоняется guard'ом):
   git worktree remove {{worktreeDir}}
   - remove отказался «contains modified or untracked files» — посмотри git status {{worktreeDir}} --short: в worktree ТОЛЬКО untracked-симлинки node_modules/refs (их кладёт туда оркестратор; это ссылки на главный репозиторий, данные не теряются) — удали с force: git worktree remove --force {{worktreeDir}}; есть modified-файлы или иной мусор — НЕ удаляй силой, упомяни в отчёте.
   git branch -d {{branch}}
   - branch -d отказался (ветка не считается слитой) — перепроверь шаг 4, упомяни в отчёте.

7. **DoD.** Список — backlog_manage_dod с action "list". Отдельными вызовами action "check" НЕ помечай: индексы реально выполненных пунктов передай в dodChecks вызова backlog_finish_phase (шаг 9). Неотмеченные пункты оставь честно и упомяни в отчёте.

7.5. **Lessons learned** (была в Code: modified_files непусты или в комментариях есть отчёт Фазы 3; иначе пропусти шаг):
   - Сформулируй 1–3 урока: императив, конкретика, одно предложение.
   - Похожие проверь: lesson_search_lessons {"query": "<ключевые слова>"} и/или listLessons с tags задачи, status=active.
   - Похожий активный есть → обнови: lesson_update {"id": "lesson-N", "linkedTasks": ["{{taskId}}", ...]} (linked_tasks += {{taskId}}).
   - Нет → создай: lesson_create {"title": "...", "tags": [...], "sourceTasks": ["{{taskId}}"], "content": "## Проблема\n\n<что было не так>\n\n## Решение\n\n<что сделали>\n\n## Пример\n\n<конкретный пример>"} + lesson_link {"lessonId": "lesson-N", "taskId": "{{taskId}}"}. Аргумент `content` ОБЯЗАТЕЛЕН: урок без тела — пустышка, которую потом нельзя дополнить..
   - Свяжи задачу: backlog_update_task {"id": "{{taskId}}", "lessons": ["lesson-N", ...]} (полная замена списка).
   - Фиксировать нечего — пропусти шаг.

7.6. **Refs и lessons** этой задачи закоммить в ГЛАВНОМ репо (файл задачи коммитит шаг 10 — сюда его НЕ включай):
   - Получи ID: backlog_view_task {"id": "{{taskId}}", "fields": ["references", "lessons"]} + refs и lessons, созданные или обновлённые в этой фазе (references ставили Spec/Plan/Code через MCP в главный репо; lessons — шаг 7.5).

   - Сверь git status --porcelain -- <пути>; backlog/references/data/ НЕ коммить (в .gitignore).
   - Незакоммиченное — явные пути, один коммит: git_commit {"paths": [<явные пути>], "message": "docs(task): {{taskId}} — refs и lessons", "allowForeign": true}. Нечего коммитить — пропусти (пустой коммит запрещён).

Менялось поведение, форматы, CLI или промпты — обнови соответствующие документы backlog/docs. git_commit {"paths": ["CHANGELOG.md", <путь к обновлённому документу>], "message": "docs: {{taskId}} — документация и CHANGELOG", "allowForeign": true}. Флаг allowForeign обязателен: CHANGELOG.md и backlog/docs/* не входят в modified_files задачи, без него git_commit отклоняет коммит.

## Экономия ходов

- Рабочий каталог — главный репозиторий. Git-команды с -C {{worktreeDir}} — единственное разрешённое исключение; сам ты в worktree не переносишься и код напрямую не правишь.
- Пакетируй последовательные git/shell-команды в ОДИН вызов через && (например: git -C {{worktreeDir}} status --porcelain && git log --oneline master..{{branch}}).
- Файлы кода не читай — фаза работает с git-статусом, modified_files и файлами задач.
- Полный прогон тестов — один раз за фазу: ранний точечный прогон затронутого diff'ом — только фильтр перед полным; повторный полный прогон — лишь после классификации падений (родительский коммит, параллельный vitest в другом worktree) и с причиной в отчёте.

## Запреты

- git-коммиты — только файлы этой задачи и её подзадач по явным путям + слияние её ветки: массовый add запрещён (правило в общем промпте агента), не push, не чужие ветки.
- Конфликты слияния не резолви и не откатывай — только отчёт (шаг 4).
- **Close не правит код:** любые edit/write_file по src/, web/src/, templates/, scripts/ в этой фазе запрещены. Упавшая сборка или упавшие тесты — аварийный итог (aborted: true с причиной), а исправление делается новой фазой Code. Причина правила — инцидент авто-задачи про close: close лечил src/mcp/tools.ts в цикле со сборкой, payload вырос до 508 КБ и фаза сгорела за 5 попыток без результата.
- **Сборка проекта — не более одного раза за фазу** (и только если diff затронул src/ или web/src/): повторная сборка без правок кода даёт тот же результат и жжёт контекст. Сборка упала — фиксируй аварийный итог, не собирай снова.
- Если type=epic — не реализуй код; закрытие детей выполняет их собственная Фаза Close. Эпик со слитой веткой закрывай по шагам выше; ветки нет — по шагам 6–10.
- **README — витрина, не справочник** (полное правило и адреса doc-* — в общем промпте агента): в этой фазе `README.md` не расширяй и не переписывай — лимит строк и белый список H2 закреплены тестом.
- **Аварийный итог фазы** (конфликт merge, падение сборки или тестов — любая причина, по которой Close не выполнена) оформляется ТОЛЬКО вызовом `backlog_finish_phase {"id": "{{taskId}}", "comment": "Фаза Close прервана: <причина>", "aborted": true}` — без `status` и `dodChecks`. В `comment` при `aborted: true` укажи, ЧТО и КЕМ должно быть сделано, чтобы фазу можно было повторить (например: «разреши конфликт UU README.md в главном репозитории и повтори Close»): по этому тексту супервизор заводит баг вместо слепого перезапуска. Не завершай цикл как успех: обычный текст без флага фреймворк считает успехом (код выхода 0) и выставит `produces_status` незавершённой задаче. Прерванную фазу не продолжай по пользовательскому сообщению без нового рана (случай уже прерванной close и сообщения «Заверши фазу.» в той же сессии): работа возобновляется только новым раном фазы, а в ответ на сообщение сообщи, что фаза прервана и требует нового запуска, и не меняй статус.

## Финал

После последнего шага (docs(task)-коммит) ответь ровно одно слово — «Готово». Не повторяй отчёт, не добавляй анализ и выводы, не выполняй дополнительных действий — терминальный вывод не нужен.

Если фаза прервана (merge/сборка/тесты) — финальный ответ не означает успех: работа возобновляется только новым раном фазы, и по пользовательскому сообщению без нового рана прерванную фазу не продолжай.
