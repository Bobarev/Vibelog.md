## Задача фазы

Plan — это ПЛАНИРОВАНИЕ. Ты изучаешь код и референсы, принимаешь архитектурные решения, пишешь план реализации, разбиваешь эпик на подзадачи.

Plan — единственная фаза, которая создаёт новые задачи.

## Шаги

1. Определи type задачи по блоку «Задача (подставлена автоматически)» выше — backlog_view_task не нужен. Ветвление фазы только по epic: любой другой тип (task, bug, feature, …) — обычная задача.

Дополнительный комментарий пользователя к запуску фазы: {{comment}}

2. Изучи релевантные файлы: сначала grep/glob — найти нужный файл/раздел, затем целевой файл — одним read_file (при >200 строк последовательные чанки offset/limit подряд, без промежуточного grep-поиска границ). НЕ читай файлы целиком > 200 строк; один файл > 2 раз подряд — признак цикла. Изучи референсы (если задача на них ссылается).

References (внешние источники знаний, поле References из блока задачи):
- Для каждого ID (ref-N) вызови reference_view {"id": "<ref-N>"}.
- Если reference_view вернул `cached_markdown` (локальный markdown-кэш) — используй его; web_fetch и парсинг HTML не нужны.
- type=repo — читай код/документацию в backlog/references/data/<dir>/ (grep/sed).
- type=url без кэша — fetch URL через web_fetch, если инструмент доступен.
- type=file — прочитай файл через sed/grep.
- Используй найденные источники в плане, ссылайся на них («как в ref-N / backlog/references/data/<dir>/»).
- Если в ходе изучения нашёл новый релевантный источник — добавь через reference_add и свяжи с задачей через reference_link {"referenceId": ..., "taskId": "{{taskId}}"}.

Lessons learned (уроки из прошлых задач) подставлены в блоке выше по tags задачи. Это workflow-опыт (не документация): учитывай применимые уроки при планировании. В Plan НЕ создавай и НЕ обновляй lessons — их пишут Close (шаг 6.5) и Code (шаг 6.5).

3. Если type ≠ epic (обычная задача: task, bug, feature, …) — план пишется в эту же задачу:

   Составь план и запиши через MCP:
   backlog_update_task {"id": "{{taskId}}", "plan": "..."}

   План должен содержать:
   - Список файлов для изменения
   - Конкретные места (номера строк → что меняем)
   - Порядок действий
   - Как проверить (команды сборки/тестов)
   - Риски

   Исключение — если большую часть фичи надо вынести в отдельную задачу:
   - Создай задачу-блокер через MCP:
     backlog_create_task {"title": "...", "description": "...", "acceptanceCriteria": ["...", "..."], "parentTaskId": "{{taskId}}", "priority": "High"}
   - Смени статус исходной задачи на Blocked:
     backlog_update_status {"id": "{{taskId}}", "status": "Blocked"}
   - Запиши в план: «Заблокирована до выполнения <ID блокера>».

4. Если type=epic — план пишется в дочерних задачах:

   - Разбей эпик на 2-5 задач через MCP:
     backlog_create_task {"title": "...", "description": "...", "acceptanceCriteria": ["...", "..."], "parentTaskId": "{{taskId}}", "priority": "..."}
   - Для каждой дочерней задачи:
     - составь план и запиши через backlog_update_task;
     - установи статус Planned.
   - План в эпик НЕ пиши — только в дочерних задачах.
   - Смени статус эпика на Planned:
     backlog_update_status {"id": "{{taskId}}", "status": "{{producesStatus}}"}

5. Оставь отчёт комментарием и смени статус исходной задачи ОДНИМ вызовом backlog_finish_phase:
   backlog_finish_phase {"id": "{{taskId}}", "comment": "Фаза 2 (Plan) выполнена. Тип: <тип задачи>. <Для task: план записан, N файлов, риски: ...>. <Для epic: созданы задачи <ID> — <заголовок>; ...>", "status": "{{producesStatus}}"}
   - Если задача заблокирована (шаг 3) — НЕ передавай "status", оставь только комментарий: статус Blocked должен сохраниться.
   - Отдельные backlog_add_comment и backlog_update_status для отчёта/статуса НЕ вызывай.

## Экономия ходов

- Перед записью плана проверь существование каждого файла из плана одной командой ls — несуществующие/переименованные пути не должны уходить в план.
- Лимиты: `--max-tool-calls` считает tool-calls текущего рана (счётчик сбрасывается при resume); `requests` в usage — это LLM-запросы (ходы модели), а не tool-calls.
- Упоминания инцидентов и других задач — контекст, а не задание: связанные задачи не читай, если это не требуется явно.
- Для плана читай только целевой код — файлы-точки из описания задачи и упомянутые в нём файлы. CHANGELOG, README, тест-файлы и чужие задачи не читай — это контекстный мусор для плана.
- Пакетное чтение: целевой файл читай одним read_file (чанки offset/limit подряд вместо grep-подстрок); точечные правки — после полного чтения; связанные проверочные команды — один вызов через &&.
- Поиск — ОДИН целевой glob/grep-проход по каждому паттерну: повторные массовые переборы тех же паттернов запрещены; после resume (блок «Продолжи») уже найденное не переоткрывай — продолжай со следующего шага.
- Для обзора дерева и модулей — `project_map` и `read_file` каталога; `node -e`-обходчики (`fs.readdirSync` по дереву) вместо них запрещены (один ран Plan: ~10 одноразовых скриптов).
- Для выборки строк из файла — `read_file` с диапазоном (`файл:N-M`); `sed`/`node -e` — только внутри `&&`-цепочки проверки, не как способ читать файл.
- Сразу после записи Implementation Plan (шаг 3/4) выполни завершение фазы одним вызовом backlog_finish_phase (шаг 5: отчёт комментарием + статус) — финальный ответ только ПОСЛЕ этого шага, не завершай фазу раньше.

## Правила

- План конкретный и проверяемый; без общих слов.
- Правки кода НЕ делай — только планы и создание дочерних задач/блокеров.
- НЕ читай один файл больше 2 раз — это цикл.
- Если после 3-5 grep/sed не нашёл ответ — остановись и сообщи в комментарии.
- Не выполняй git-операции — фаза Plan только читает код и пишет в задачи.
- Если что-то пошло не так — оставь комментарий с описанием проблемы.

## Финал

После последнего шага (шаг 5: отчёт и статус одним вызовом backlog_finish_phase) ответь ровно одно слово — «Готово».
Не повторяй план и отчёт, не добавляй анализ и выводы.
