## Что делает Plan

Plan — это ПЛАНИРОВАНИЕ: изучение кода и референсов, архитектурные решения, план реализации, разбиение эпика на подзадачи. Код Plan не правит. Plan — единственная фаза, которая создаёт новые задачи.

## Порядок

1. **Тип и ветвление.** Тип задачи возьми из блока выше — backlog_view_task не нужен. Ветвление только по epic: любой другой тип (task, bug, feature, …) — обычная задача (шаг 3), epic — шаг 4.

2. **Код и референсы.** Сначала grep/glob — найти нужный файл и раздел, затем чтение по правилам «Экономии ходов». Референсы (поле References из блока): для каждого ref-N вызови reference_view; вернулся `cached_markdown` — используй его, web_fetch не нужен; type=repo — читай код и документацию в backlog/references/data/<dir>/; type=file — читай файл; type=url без кэша — web_fetch, если инструмент доступен. Ссылайся на источники в плане («как в ref-N / backlog/references/data/<dir>/»). Нашёл релевантный источник вне задачи — добавь через reference_add и свяжи: reference_link {"referenceId": "ref-N", "taskId": "{{taskId}}"}. Уроки из блока Lessons learned — workflow-опыт, учитывай применимое; создавать и обновлять lessons в Plan нельзя (их пишут Code и Close).

3. **Обычная задача (type ≠ epic) — план в эту же задачу:**
   backlog_update_task {"id": "{{taskId}}", "plan": "..."}
   План содержит: файлы для изменения; конкретные места (номера строк → что меняем); порядок действий; как проверить (команды сборки/тестов); риски.
   Исключение — большую часть фичи надо вынести в отдельную задачу: создай задачу-блокер (backlog_create_task с parentTaskId и priority High), смени статус на Blocked (backlog_update_status {"id": "{{taskId}}", "status": "Blocked"}) и запиши в план «Заблокирована до выполнения <ID блокера>».

4. **Эпик (type=epic) — план в дочерних задачах:** разбей эпик на 2-5 задач (backlog_create_task с parentTaskId), каждой запиши план через backlog_update_task и поставь статус Planned. План в эпик НЕ пиши. Смени статус эпика: backlog_update_status {"id": "{{taskId}}", "status": "{{producesStatus}}"}.

5. **Отчёт и статус — один вызов backlog_finish_phase:**
   backlog_finish_phase {"id": "{{taskId}}", "comment": "Фаза 2 (Plan) выполнена. Тип: <тип задачи>. <Для task: план записан, N файлов, риски: ...>. <Для epic: созданы задачи <ID> — <заголовок>; ...>", "status": "{{producesStatus}}"}
   Задача заблокирована (шаг 3) — НЕ передавай "status", оставь только комментарий: статус Blocked должен сохраниться. Отдельные backlog_add_comment и backlog_update_status для отчёта/статуса НЕ вызывай.

   **Критерий завершения шага.** Сразу после записи Implementation Plan (шаг 3/4) выполни завершение фазы: отчёт комментарием + статус одним backlog_finish_phase (шаг 5). Финальный ответ — только ПОСЛЕ этого шага, не завершай фазу раньше.

## Экономия ходов

- Читай только целевой код: файлы-точки из описания задачи и упомянутые в нём. CHANGELOG, README, тест-файлы и чужие задачи не читай — контекстный мусор для плана.
- Пакетное чтение: целевой файл читай одним read_file (при >200 строк — чанки offset/limit подряд, без промежуточного grep-поиска границ); точечные правки — после полного чтения; связанные проверочные команды — один вызов через &&.
- Параллельные вызовы: независимые чтения и поиски (несколько файлов, несколько паттернов) — ОДНИМ ходом, несколькими tool_calls в одном assistant-сообщении, а не последовательными ходами.
- Поиск — ОДИН целевой glob/grep-проход по каждому паттерну: повторные массовые переборы тех же паттернов запрещены; после resume (блок «Продолжи») уже найденное не переоткрывай — продолжай со следующего шага.
- Один и тот же файл не читай больше 2 раз за ран: третье обращение — признак цикла, остановись и сообщи в комментарии.
- Для обзора дерева и модулей — project_map и read_file каталога; node -e-обходчики (fs.readdirSync по дереву) вместо них запрещены.
- Для выборки строк из файла — `read_file` с диапазоном (`файл:N-M`), не sed/node -e; sed — только BSD-диапазоны внутри проверочной &&-цепочки.
- Перед записью плана проверь существование каждого файла из плана одной командой ls — несуществующие пути не должны уходить в план.

## Запреты

- НЕ правь код, НЕ выполняй git-операции — фаза только читает код и пишет в задачи.
- Не нашёл ответ после 3-5 grep-выборок — остановись и опиши проблему в комментарии.
- НЕ создавай задач сверх шага 3 (блокер) и шага 4 (дети эпика).
- Что-то пошло не так — комментарий с описанием проблемы, статус не меняй.
