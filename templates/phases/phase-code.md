## Шаги

1. Определи type задачи по блоку «Задача (подставлена автоматически)» выше — backlog_view_task не нужен. Для type ≠ epic (task, bug, feature, …) реализуй План из блока (раздел «План»).

Дополнительный комментарий пользователя к запуску фазы: {{comment}}

2. Если type ≠ epic (task, bug, feature, …) — реализуй план. Проверки проекта (сборка, тесты) выполняй по правилам AGENTS.md проекта; если AGENTS.md нет — сделай минимальную самопроверку и зафиксируй в отчёте.
   - Полный прогон тестов обязателен: если прогон шёл с `--exclude`/`--skip` или только по отдельным файлам — в отчётном комментарии фазы **обязательно перечисли имена исключённых/пропущенных тест-файлов** и причину; DoD «Тесты проходят» не отмечается без полного прогона тестов проекта (команда прогона — по правилам AGENTS.md проекта) либо без явной оговорки «прогон частичный: <файлы>» в комментарии.

3. Если type=epic — код НЕ реализуй, оркестрируй дочерних задач:
   - Получи список детей: backlog_list_tasks {"parentTaskId": "{{taskId}}"}
   - Проверь их статусы.
   - Если не все дети Done — НЕ реализуй сам. Вместо этого запусти Фазу 3 на каждом ребёнке (отдельными сессиями qwen) или сообщи пользователю: «Запусти Code на детях: <список ID>».
   - Когда все дети Done — смени статус эпика на Done:
     backlog_update_status {"id": "{{taskId}}", "status": "Done"}

4. Отметь реально выполненные AC/DoD:
   списки: backlog_manage_ac / backlog_manage_dod c action "list"; проверяй пункты.
   Отдельными вызовами action "check" НЕ помечай — индексы реально выполненных пунктов передай в acChecks/dodChecks вызова backlog_finish_phase (шаг 7); списки по-прежнему читай через manage_ac/manage_dod (action "list").
   Не отмечай «задним числом» — невыполненные пункты оставь незакрытыми и упомяни в отчёте.

5. References (внешние источники знаний):
   - Использовал новые внешние источники (URL, репозитории, файлы, документацию)? Добавь их: reference_add {"title": "...", "type": "url|repo|file|doc|spec", "url": "..."} и свяжи: reference_link {"referenceId": "ref-N", "taskId": "{{taskId}}"}.
   - Использовал уже существующие references (блок References из задачи)? Просто свяжи их через reference_link {"referenceId": "ref-N", "taskId": "{{taskId}}"} (если ещё не связаны).
   - Обнови поле references задачи: backlog_update_task {"id": "{{taskId}}", "references": ["ref-N", ..."]} (полная замена списка).
   - Если источники не использовались — шаг пропусти.

6. Если type ≠ epic и менялся код — закоммичи изменения в текущую ветку, чтобы владелец увидел диффы сразу (в режиме worktree это ветка задачи; без worktree — текущая ветка репозитория):
   git status --porcelain
   git add <явные пути изменённых файлов кода>
   git commit -m "feat: {{taskId}} — <краткое описание сути>"
   Только файлы этой задачи (код, тесты, шаблоны); файлы backlog/ НЕ коммит; никогда git add -A; не push. Если изменений нет — пропусти шаг.
   Трейлер Co-authored-by: если `{{commitTrailer}}` не пусто — передай его ВТОРЫМ `-m` (git сделает из него отдельный абзац после пустой строки): `git commit -m "feat: {{taskId}} — <суть>" -m "{{commitTrailer}}"`. Если `{{commitTrailer}}` пусто — второй `-m` НЕ передавай (иначе пустой абзац).

6.5. Lessons learned (если в задаче есть lessons или в процессе работы вспомнил урок):

   - Создал новый полезный урок? lesson_create {"title": "Императив, конкретика, 1 предложение", "tags": [...], "sourceTasks": ["{{taskId}}"]} и свяжи: lesson_link {"lessonId": "lesson-N", "taskId": "{{taskId}}"}.
   - Обнови задачу при добавлении: backlog_update_task {"id": "{{taskId}}", "lessons": ["lesson-N", ...]} (полная замена списка).
   - Если lessons не применялись и не создавались — пропусти шаг.

7. Заверши фазу ОДНИМ вызовом backlog_finish_phase — отчёт комментарием + modifiedFiles + статус + батч-отметки AC/DoD (упомяни хэш feat-коммита из шага 6):
   backlog_finish_phase {"id": "{{taskId}}", "comment": "Фаза 3 (Code) выполнена. Изменено: <файлы>, коммит <хэш>. Проверки: <список выполненных>. Что осталось: ...", "modifiedFiles": ["src/foo.ts", "docs/bar.md"], "acChecks": [<индексы выполненных AC из шага 4>], "dodChecks": [<индексы выполненного DoD из шага 4>], "status": "{{producesStatus}}"}
   - type ≠ epic: передавай modifiedFiles (только явные пути ВНЕ backlog/ — код, тесты, шаблоны, docs; файлы задач в backlog/ не включай; если ничего не менял — поле опусти) и status "Review".
   - type=epic: передавай только comment (и acChecks/dodChecks, если отмечал); status эпик НЕ получает — Done ставится в шаге 3, когда все дети Done.
   - acChecks/dodChecks — только если есть реально выполненные пункты; пустой список — поле опусти. DoD «Тесты проходят» передавай в dodChecks только при полном прогоне; частичный прогон — не отмечай и укажи исключённые тест-файлы в комментарии.
   - Отдельные backlog_update_task (modifiedFiles), backlog_add_comment и backlog_update_status для завершения фазы НЕ вызывай.
   - НЕ вызывай backlog_view_task повторно после вызова.

## Экономия ходов

- Если в задаче есть Implementation Plan с указанием файлов и строк — применяй его напрямую: не перечитывай файлы, которые план уже описывает.
- Пакетируй последовательные git/shell-команды в ОДИН вызов через && (например: git status --porcelain && git log -1 --stat). Сборку и тесты проекта тоже пакетируй одной командой через &&.
- Пакетное чтение: целевой файл читай одним read_file (чанки offset/limit подряд вместо grep-подстрок); точечные правки — после полного чтения; связанные проверочные команды — один вызов через &&.
- Лимиты: `--max-tool-calls` считает tool-calls текущего рана (счётчик сбрасывается при resume); `requests` в usage — это LLM-запросы (ходы модели), а не tool-calls.
- **Бюджет времени фазы:** агент получает предупреждения об остатке бюджета на 70% и 90% wall-time (в сообщении — остаток секунд и текущий payload). Если осталось **меньше 5 минут** — НЕ запускай полный прогон тестов и сборку: проверь только затронутые файлы (`npx vitest run <файл>`), зафиксируй прогресс и остаток работ комментарием в задаче. Команда с `timeout_ms` больше остатка бюджета будет усечена инструментом — иначе фаза сгорит на wall-time без отчёта.
- Поиск — один целевой glob/grep-проход: повторные mass-glob/grep с теми же паттернами запрещены; результаты уже сделанных поисков не перепроверяй.
- Упоминания инцидентов и других задач — контекст, а не задание: связанные задачи не читай, если это не требуется явно.
- Файл из плана не найден — не более 2 ходов на поиск (grep по разделу/заголовку), затем продолжай с найденного.
- Первая правка целевого файла — в первых 5–8 вызовах инструментов.

## Правила

- Code на эпике НЕ реализует код — он проверяет детей и запускает Фазу 3 на них.
- Реализуй по плану из задачи; если план отсутствует — сделай минимально достаточную реализацию и честно зафиксируй это в комментарии.
- git push не выполняй; git commit — только по шагу 5 (изменения этой задачи по явным путям).
- CHANGELOG.md и документы backlog/docs в Фазе 3 НЕ обновляй — итоговую документацию пишет Фаза Close после слияния.
- **README — витрина, не справочник.** `README.md` НЕ расширяй: лимит 150 строк и белый список H2 закреплены тестом `src/web/readme-standard.test.mjs` — превышение роняет тесты проекта. Новая техническая деталь (раздел, подраздел, абзац-объяснение, таблица параметров) идёт в `backlog/docs/doc-*` (пользовательское — doc-6, CLI — doc-7, MCP — doc-8, агент/лимиты/модели — doc-10, супервизор — doc-19); в README допустима только правка уже существующей строки или ссылки в таблице «Документация». Нужен новый раздел в README — сначала перенос в doc-*, потом (если реально нужно) одна строка-ссылка.
- Если тесты падают и не чинятся — исправь или честно зафиксируй в комментарии, статус всё равно смени на Review.
- Аварийный итог: если фазу завершить нельзя (запуск/сборка/тесты не идут, нужны внешние действия), вызывай `backlog_finish_phase` с `"aborted": true` и отчётом-причиной без `status`. В `comment` при `aborted: true` укажи, ЧТО и КЕМ должно быть сделано, чтобы фазу можно было повторить (например: «останови лок оркестратора и перезапусти Code»): по этому тексту супервизор заводит баг вместо слепого перезапуска.
