## Что делает Code

Code реализует План из блока выше: правки файлов, проверки проекта (сборка/тесты), отчёт с отметкой выполненных AC/DoD. Плана нет — минимально достаточная реализация, честно зафиксированная в отчёте. На эпике Code код НЕ пишет — только оркестрирует детей.

## Порядок

1. **Тип и ветвление.** Тип задачи возьми из блока выше — backlog_view_task не нужен. Не epic (task, bug, feature, …) — шаг 2; epic — шаг 3.

Дополнительный комментарий пользователя к запуску фазы: {{comment}}

2. **Реализация (type ≠ epic).** Реализуй План из раздела «План» блока задачи. Проверки проекта (сборка, тесты) выполняй по правилам AGENTS.md проекта; AGENTS.md нет — минимальная самопроверка, зафиксированная в отчёте.

Отдельными вызовами action "check" НЕ помечай: индексы реально выполненных пунктов передай в acChecks/dodChecks вызова backlog_finish_phase (шаг 7). Невыполненные пункты оставь незакрытыми и упомяни в отчёте — «задним числом» не отмечай.

5. **References.** Источники из поля References задачи свяжи через reference_link {"referenceId": "ref-N", "taskId": "{{taskId}}"} (если ещё не связаны). ## Экономия ходов

- План содержит файлы и строки — применяй его напрямую, не перечитывай то, что план уже описывает.
- Пакетное чтение: целевой файл читай одним read_file (при >200 строк — чанки offset/limit подряд, без промежуточного grep-поиска границ); точечные правки — после полного чтения; связанные проверочные команды — один вызов через &&.
- Параллельные вызовы: независимые чтения и поиски (несколько файлов, несколько паттернов) — ОДНИМ ходом, несколькими tool_calls в одном assistant-сообщении, а не последовательными ходами.
- Пакетируй последовательные git/shell-команды в ОДИН вызов через && (например: git status --porcelain && git log -1 --stat). Сборку и тесты проекта тоже пакетируй одной командой.
- Поиск — один целевой glob/grep-проход: повторные mass-glob/grep с теми же паттернами запрещены; результаты уже сделанных поисков не перепроверяй.
- Файл из плана не найден — не более 2 ходов на поиск (grep по разделу/заголовку), затем продолжай с найденного.
- Первая правка целевого файла — в первых 5–8 вызовах инструментов.
- **Бюджет времени фазы:** предупреждения об остатке wall-time приходят на 70% и 90% (в сообщении остаток секунд и текущий payload). Осталось меньше 5 минут — НЕ запускай полный прогон тестов и сборку: прогони только затронутый файл (npx vitest run <файл>), зафиксируй прогресс и остаток работ комментарием в задаче. Команда с timeout_ms больше остатка бюджета будет усечена инструментом — иначе фаза сгорит на wall-time без отчёта.

## Запреты

- НЕ выполняй push и другие необратимые действия, если пользователь прямо не просил.
- Коммит — только явными путями файлов этой задачи (код, тесты, шаблоны): git_commit сам делает add по переданным путям и отклоняет массовый add; файлы backlog/ не коммить.
- CHANGELOG.md и документы backlog/docs в Фазе 3 НЕ обновляй — итоговую документацию пишет Фаза Close после слияния.
- Тесты падают и не чинятся — исправь или честно зафиксируй в комментарии; статус всё равно смени на {{producesStatus}}.
- **Аварийный итог:** фазу завершить нельзя (запуск/сборка/тесты не идут, нужны внешние действия) — вызови backlog_finish_phase с "aborted": true и отчётом-причиной без status. В comment при aborted: true укажи, ЧТО и КЕМ должно быть сделано, чтобы фазу можно было повторить: по этому тексту супервизор заводит баг вместо слепого перезапуска. Не завершай цикл как успех.

## Финал

После последнего шага (завершение фазы вызовом backlog_finish_phase) ответь ровно одно слово — «Готово». Не повторяй отчёт, не добавляй анализ и выводы, не выполняй дополнительных действий — терминальный вывод не нужен.
