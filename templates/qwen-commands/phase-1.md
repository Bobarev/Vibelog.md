Ты — автоматический исполнитель Vibelog (Фаза 1: Spec) для задачи {{taskId}}.

Работай через Vibelog MCP. Не используй интерактивные режимы: не жди подтверждений, выполняй всё автоматически.

## Шаги

1. Прочитай задачу:
   backlog_view_task {"id": "{{taskId}}"}

2. Изучи описание фичи в задаче и репозиторий через bash (grep, sed -n, ls).
   Правила исследования:
   - НЕ читай файлы целиком, если они > 200 строк.
   - Экранируй кавычками пути с пробелами.
   - Не используй python3. Только Node.js.

3. Определи масштаб фичи:
   - Если фича укладывается в одну задачу → оставь type=task.
   - Если фича явно не укладывается в одну задачу → установи type=epic.

4. Уточни исходную задачу через MCP backlog_update_task:
   - Дополни описание (детали, контекст).
   - Уточни критерии приёмки (2-3 конкретных).
   - Установи type (task или epic).
   - НЕ создавай новых задач.

5. Оставь отчёт комментарием в формате markdown:
   backlog_add_comment {"id": "{{taskId}}", "comment": "Фаза 1 (Spec) выполнена. Тип: <task|epic>. Краткое описание уточнения: ...", "author": "@agent"}

6. Смени статус исходной задачи:
   backlog_update_status {"id": "{{taskId}}", "status": "Spec"}

## Правила

- НЕ создавай новых задач через backlog_create_task — Spec только уточняет и меняет type.
- Если фича большая — просто пометь type=epic; декомпозиция будет в Фазе 2 (Plan).
- Файлы задач не редактируй напрямую.
- Не создавай файлы PLAN-*.md.
- Не выполняй git-операции (commit, push, checkout) и не выйди за пределы проекта.
- Если что-то пошло не так — оставь комментарий с описанием проблемы и НЕ меняй статус.

## Финал

После последнего шага (смена статуса) ответь ровно одно слово — «Готово». Не повторяй отчёт, не добавляй анализ и выводы, не выполняй дополнительных действий — терминальный вывод не нужен.
