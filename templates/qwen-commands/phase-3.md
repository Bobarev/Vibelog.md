## Шаги

1. Определи type задачи (task или epic) по блоку «Задача (подставлена автоматически)» выше — backlog_view_task не нужен. Для type=task реализуй План из блока (раздел «План»).

Дополнительный комментарий пользователя к запуску фазы: {{comment}}
Если вместо комментария остался неподставленный {{comment}} (запуск без комментария) — просто продолжай по шагам.

2. Если type=task — реализуй план. Проверки проекта (сборка, тесты) выполняй по правилам AGENTS.md проекта; если AGENTS.md нет — сделай минимальную самопроверку и зафиксируй в отчёте.

3. Если type=epic — код НЕ реализуй, оркестрируй дочерних задач:
   - Получи список детей: backlog_list_tasks {"parentTaskId": "{{taskId}}"}
   - Проверь их статусы.
   - Если не все дети Done — НЕ реализуй сам. Вместо этого запусти Фазу 3 на каждом ребёнке (отдельными сессиями qwen) или сообщи пользователю: «Запусти Code на детях: <список ID>».
   - Когда все дети Done — смени статус эпика на Done:
     backlog_update_status {"id": "{{taskId}}", "status": "Done"}

4. Отметь реально выполненные AC/DoD:
   списки: backlog_manage_ac / backlog_manage_dod c action "list"; отметка: action "check", index N.
   Не отмечай «задним числом» — невыполненные пункты оставь незакрытыми и упомяни в отчёте.

5. Если type=task и менялся код — закоммичи изменения в текущую ветку, чтобы владелец увидел диффы сразу (в режиме worktree это ветка задачи; без worktree — текущая ветка репозитория):
   git status --porcelain
   git add <явные пути изменённых файлов кода>
   git commit -m "feat: {{taskId}} — <краткое описание сути>"
   Только файлы этой задачи (код, тесты, шаблоны); файлы backlog/ НЕ коммит; никогда git add -A; не push. Если изменений нет — пропусти шаг.

6. Если type=task и в Фазе менялись файлы вне backlog/ — запиши затронутые файлы в задачу через backlog_update_task (поле modifiedFiles) — для отчёта и проверок Фазы Close:
   backlog_update_task {"id": "{{taskId}}", "modifiedFiles": ["src/foo.ts", "docs/bar.md"]}
   Включай только явные пути к файлам ВНЕ backlog/ (код, тесты, шаблоны, docs); файлы задач в backlog/ не включай. Если ничего не менял — пропусти шаг.

7. Оставь отчёт комментарием в формате markdown (упомяни хэш feat-коммита из шага 5):
   backlog_add_comment {"id": "{{taskId}}", "comment": "Фаза 3 (Code) выполнена. Изменено: <файлы>, коммит <хэш>. Проверки: <список выполненных>. Что осталось: ...", "author": "@agent"}

8. Смени статус (только для type=task):
   backlog_update_status {"id": "{{taskId}}", "status": "Review"}

## Экономия ходов

- Если в задаче есть Implementation Plan с указанием файлов и строк — применяй его напрямую: не перечитывай файлы, которые план уже описывает.
- Пакетируй последовательные git/shell-команды в ОДИН вызов через && (например: git status --porcelain && git log -1 --stat). Сборку и тесты проекта тоже пакетируй одной командой через &&.
- Упоминания инцидентов и других задач — контекст, а не задание: связанные задачи (VL-N) не читай, если это не требуется явно.
- Файл из плана не найден — не более 2 ходов на поиск (grep по разделу/заголовку), затем продолжай с найденного.
- Первая правка целевого файла — в первых 5–8 вызовах инструментов.

## Правила

- Code на эпике НЕ реализует код — он проверяет детей и запускает Фазу 3 на них.
- Реализуй по плану из задачи; если план отсутствует — сделай минимально достаточную реализацию и честно зафиксируй это в комментарии.
- git push не выполняй; git commit — только по шагу 5 (изменения этой задачи по явным путям).
- CHANGELOG.md и документы backlog/docs в Фазе 3 НЕ обновляй — итоговую документацию пишет Фаза Close после слияния (VL-126).
- Если тесты падают и не чинятся — исправь или честно зафиксируй в комментарии, статус всё равно смени на Review.
