# Best practices и производительность Vibelog.md

Практики из реальной разработки этого проекта (Vibelog.md ведёт свои же задачи
через Vibelog — dogfooding: VL-1…VL-21, эпики, релизы) и сценарии, где Vibelog
сокращает количество шагов по сравнению с «ручным» подходом.

Смотрите также: [Руководство пользователя](user-guide.md) · [CLI-справочник](cli-reference.md)

---

## 1. Workflow с Qwen Code: spec → plan → code

Флаг `--skills` при `init` создаёт три команды, разбивающие работу на фазы с
подтверждением пользователя на каждой:

```bash
vibelog init "Мой проект" --skills
```

| Команда | Фаза | Что делает агент |
|---|---|---|
| `/vibelog:spec <описание фичи>` | 1 | Исследует репозиторий, разбивает фичу на 2-3 задачи с проверяемыми AC, создаёт их через MCP, ждёт подтверждения |
| `/vibelog:plan <ID>` | 2 | Составляет план (файлы, строки, порядок, проверки, риски), записывает в задачу, ждёт «да» |
| `/vibelog:code <ID>` | 3 | Реализует план, запускает проверки, отмечает AC, меняет статус на Done |

### Как ставить задачи агенту

- **AC формулируйте проверяемыми**: «`pnpm test` проходит», «флаг X виден в help», «round-trip сохраняет поле» — агент отмечает их фактами, а не на словах.
- **Одна фича = 2-3 задачи.** Если больше — фича слишком крупная, разбейте epic-задачу (как VL-2 → VL-3 + VL-4).
- **Явные подтверждения.** Фазы ждут «да» — так вы ловите ошибки спеки до кода.
- **Не коммитить без подтверждения** — правило этого проекта: агент показывает diff, вы решаете.

Реальный пример: фича «Milestones + Types» из ресёрча была разбита на VL-3
(CLI+MCP вех) и VL-4 (типы), каждая прошла spec → plan → code с тестами 212/212
и 230/230 соответственно.

## 2. Dogfooding: как этот проект ведёт свои задачи

- **Эпики**: родительская задача (VL-2) ссылается на подзадачи; закрытие подзадач двигает релиз.
- **AC в задаче** = чек-лист: агент отмечает `backlog_manage_ac` по мере выполнения, вы видите прогресс в `task view`.
- **Комментарии как лог**: каждая Фаза 3 оставляет в задаче, что сделано, какие отклонения от плана и результаты проверок.
- **Коммиты**: `feat(scope): VL-N — ...` для кода, `docs(task): ...` для файлов задач, отдельный `fix` для багфиксов (пример: гонка MCP-сервера в `3952ed8` — вынесена из фичи).
- **CHANGELOG + теги**: перед релизом — сводка закрытых задач (см. `CHANGELOG.md` v1.4.0: 16 задач за релиз).

## 3. Организация работ

```bash
# Метки и приоритеты — сразу при создании
vibelog task create "Чинить парсер" --labels bug,parser --priority High

# Зависимости: что можно делать прямо сейчас
vibelog task create "Тесты парсера" --deps api-1
vibelog task list --ready                     # только разблокированные

# Веха = релиз; задачи привязываются флагом
vibelog milestone add v1.5 --due-date 2026-12-01
vibelog task create "Фича X" --milestone v1.5

# Типы — для разрезов «баги vs фичи»
vibelog task list --type bug
```

Практика: метка версии (`v1.5`) + веха с тем же именем — фильтр по релизу
работает и по метке, и по вехе.

## 4. Batch-операции и сокращение вызовов

```bash
# 3 критерия за один вызов вместо трёх
vibelog task edit api-1 --check-ac 1,2,3

# Обрезка выдачи после фильтрации — вместо просмотра всех задач
vibelog task list --type bug --ready --limit 5

# JSON-вывод для скриптов и агентов
vibelog task list --json --limit 3
vibelog search --status "To Do" --json
```

MCP-аналог: `backlog_manage_ac` с `index: [1,2,3]` — агент отмечает пачку
критериев одним вызовом.

## 5. Производительность: сценарии «было / стало»

Честный подсчёт по реальным командам (без маркетинга; «шаг» = одна команда или
одно действие в редакторе).

### 5.1 Захват идеи → задача

| | Действия |
|---|---|
| **Было** | открыть редактор → создать файл заметки → придумать формат → позже вручную оформить задачу (3-4 шага + контекст-свитч) |
| **Стало** | `vibelog draft create "Идея"` → позже `vibelog draft promote draft-1` (**2 команды**, задача уже в системе со всеми полями) |

### 5.2 Отметка критериев приёмки

| | Действия |
|---|---|
| **Было** | `task edit --check-ac 1` → `task edit --check-ac 2` → `task edit --check-ac 3` (3 вызова CLI или MCP) |
| **Стало** | `task edit --check-ac 1,2,3` (**1 вызов**) |

### 5.3 «Что готово к работе сейчас»

| | Действия |
|---|---|
| **Было** | открыть несколько задач, вручную сверить `dependencies` со статусами blocker-задач |
| **Стало** | `vibelog task list --ready` (**1 команда**; MCP: `backlog_ready`) |

### 5.4 Поиск по backlog

| | Действия |
|---|---|
| **Было** | `grep -rn "авторизация" backlog/` + чтение сырых markdown-файлов, фильтры вручную |
| **Стало** | `vibelog search "авторизация" --status "To Do" --type bug` (**1 команда** с типизированными фильтрами) |

### 5.5 Релиз-чек-лист

| | Действия |
|---|---|
| **Было** | открыть трекер/файлы, собирать список задач релиза вручную |
| **Стало** | задачи с `--milestone v1.5` + `task list` по вехе (через JSON/search) — список собирается сам; веха архивируется одной командой `milestone archive` |

### 5.6 Работа агента без вашего участия

| | Действия |
|---|---|
| **Было** | диктовать агенту контекст задачи каждый раз |
| **Стало** | задача с AC/планом/заметками в markdown — агент читает её через MCP (`backlog_view_task`) и пишет прогресс обратно (`backlog_add_comment`, `backlog_manage_ac`) — контекст персистентен в репозитории |

## 6. Интеграция с git

- **backlog/ живёт в репозитории** — задачи версионируются вместе с кодом, доступны в code review.
- **Что коммитить**:
  - код + тесты — `feat(scope): VL-N — ...`;
  - файлы задач (планы, AC, комментарии) — `docs(task): ...`;
  - багфиксы — отдельным `fix(...)`, не смешивая с фичей.
- **Не пушить без подтверждения** — правило проекта: сначала diff, потом push.
- **Теги релизов**: `vX.Y.Z` на коммит с CHANGELOG (пример: `v1.4.0`).

---

## 7. Чего избегать

- **Не дублируйте трекер**: Vibelog.md совместим с Backlog.md — при апгрейде macOS данные просто переходят на оригинал, поэтому держайте всё в `backlog/`, а не в стороннем TODO-файле.
- **Не редактируйте `config.yml` руками** без нужды — `config set` типизирует значения (массивы/boolean/числа) и не затирает соседние ключи.
- **Не создавайте задачу раньше, чем идея сформулирована** — сначала черновик, потом `promote`.
- **Не помечайте AC невыполнимыми формулировками** — «сделать хорошо» нельзя проверить; агент не сможет честно отметить такой критерий.
